# P06: 统一内容平台的分发网络与播放 QoE

## 业务场景

承接 P00 的域 7（分发与播放）。域 7 是**全平台的可用性底线**——即使投稿、转码、审核、推荐全部挂掉，已发布内容的播放**必须**还能工作。同时它也是**成本中心中的成本中心**：带宽占平台总成本 73%，优化后仍是 ¥9,220 万/月，远超第二名存储。

**已知数据：**
- DAU 2 亿，日播放量（VV）160 亿，人均 80 次/天
- 均播时长 32s，平均码率 1.5 Mbps
- 平均 / 峰值出口带宽：8.9 Tbps / 26.7 Tbps；日出流量 96 PB
- 播放请求峰值：64.8 万 QPS
- 播放体验红线：首帧（P95）< 800ms，卡顿率 < 1%，播放成功率 > 99.5%
- 云 CDN ¥0.05/GB，自建边缘节点约 ¥0.018/GB
- 播放端形态：移动端 70%、Web 15%、OTT/大屏 10%、桌面 5%

**为什么分发网络是"体验 × 成本"双目标优化，而不是单纯追求快？**

播放链路是唯一一个**体验指标和成本指标直接对撞**的系统。起播要快，就要预连接、预加载、多缓冲——每一项都在多花带宽；带宽要省，就要精确计算预加载量、压低码率、开 P2P——每一项都在伤害体验。这个矛盾在 P00 的带宽成本熔断里已经出现：档位 2 省 58% 带宽，代价是 QoE 降 4.2%。

更麻烦的是**播放链路横跨多家外部厂商**（CDN、P2P 网络），调度权、议价权、切换能力必须在平台自己手里，否则厂商故障或涨价都是不可控的。

**核心矛盾**：**播放体验每提升 1%，都要在带宽成本上付出超额代价；而带宽成本占 73% 意味着这个代价直接决定平台生死。** 本篇解决的是"如何让 99.5% 的播放成功、800ms 内起播、卡顿率 < 1%，同时把带宽成本压到 ¥9,220 万/月以内"。

## 核心挑战

### 挑战 1：QoE 与带宽的成本对撞——每个体验优化都在烧钱

用 P00 的数据量化这个对撞：

| 体验优化手段 | 效果 | 带宽代价 |
|------------|------|---------|
| 预加载 3 片 | 起播/切换更顺滑 | +15% 带宽（P00 标称 ¥3,456 万/月，修正后 ¥1,752 万，见"性能与成本分析"） |
| 全档位可选 | 用户选更高清 | 非会员乱选高清 = 带宽失控 |
| 无脑 1080P 起播 | 首帧画质好 | 码率 ×2，弱网下反而更卡 |
| 全片预热 | 零等待 | 72GB×N 推到边缘，纯烧钱 |

反过来，省带宽的手段也都在伤体验：P2P 强制开启伤弱网用户、默认档位压低伤画质、预加载减片伤起播成功率。

**这张表本身就演示了这个挑战为什么难：左边是形容词，右边是金额。** "更顺滑"和"¥1,752 万/月"无法比较大小，于是**评审会上永远是拿钱说话的一方赢**——因为只有一方有数字。所有"体验 vs 成本"的争论最终都会退化成成本单方面胜出，不是因为成本更重要，而是因为体验没被量化。

**破解方式是强制把体验侧也换算成同一单位**。本篇后文对"预加载减 1 片省 8%、起播成功率降 0.3%"这笔交易做了完整换算（`0.3% → 每人每 4 天一次起播失败` vs `¥934 万 → 每人每月 4.7 分钱`），换算完之后原文"远小于"的结论直接翻转。**这个换算不难，难的是它默认不会被做**——因为不做的时候，结论对提议方有利。

**难点不在"选哪边"，而在"有一个可量化、可一键切换的权衡标尺"**——本篇的核心设计之一就是带宽成本熔断三档（承接 P00），把"体验 vs 成本"的权衡变成运营可执行的分档开关，而不是工程师每次临场拍脑袋。**注意熔断三档解决的是"临时权衡"，上面那种换算解决的是"常态权衡"，两者都需要，不能互相替代。**

### 挑战 2：多 CDN 的调度权与议价权——CNAME 是把命根子交给别人

单 CDN 的风险 P00 已充分论证（成本 + 可用性 + 质量三重暴露）。多 CDN 的真正难点是**调度权落在谁手里**：

- 若用 CNAME 方式（域名解析交给 CDN 厂商），调度权在厂商手里，平台只能看到聚合后的流量，无法按区域、按质量、按成本精细分配，切流也慢
- 若自建调度（自建 DNS/HTTPDNS + 客户端多地址下发），平台拿到全部调度权，但要承担调度系统本身的复杂度与稳定性

议价也一样：**没有切换能力就没有议价能力**。只能接受单一厂商时，续约涨 20% 只能认；有分钟级全量切换能力时，单价谈判的筹码完全不同。

**这里有一个反直觉的量化结论：切换能力的价值不来自切换，而来自"能切但不切"。** 后文算过：厂商 B 的质量确实更好，但按它的报价全量迁移要多付 ¥1,613 万/月；而拿着"我能在 15 分钟内切走"这个能力去和厂商 A 续约，拿到的折扣约 ¥1,420 万/月。**两个数字几乎相等，而后者不需要真的切。** 切换能力是一个期权——**它的价值在持有期，不在行权时。** 这解释了为什么"我们从来没真的切过厂商"不是多 CDN 投资失败的证据，恰恰可能是它一直在生效的证据。

**为什么是三家，不是两家也不是五家**——这个数字有硬约束，不是折中：

```
两家：任一家故障 → 50% 流量要压到剩下那一家
      → 每家都必须常备 100% 冗余（等于买两倍容量）
      → 容灾成本吃掉多厂商省下的钱

三家：任一家故障 → 33% 流量分摊到剩下两家（各 +17%）
      → 每家备 50% 冗余即可，这个量级的 headroom 是常态运营水位
      → 【三家是"故障冗余可负担"的最小家数】

五家：每家分到 20%，任一家的年度量都拿不到规模折扣档位
      → 单价上升，且五套接入/监控/对账的运维成本线性增长
```

**难点：** 调度权、切换能力、议价机制要一起设计，缺一个，多 CDN 就只是"多花了钱却没拿到多厂商的收益"。**特别地：切换能力必须定期演练，否则它会静默腐化**——而一个腐化的切换能力在谈判桌上照样能用（对方不知道），直到真的故障那一天。**这是唯一一种"自欺"比"欺人"后果更严重的架构能力。**

### 挑战 3：起播优化的边界——预连接省的是时间，预加载烧的是钱

首帧 800ms 预算里，起播相关的环节是：换地址 35ms + QUIC 建连 15ms（冷连接则 +90ms）+ 首片下载 180ms（边缘未命中再 +120ms）+ 硬解 85ms。

```
这四项合计：315ms（理想）/ 525ms（冷连接 + 边缘未命中）
而 P00 的完整账本是：485ms / 695ms

差值恒为 170ms —— 那是本篇不负责的环节
（推荐返回、播放器初始化、首帧渲染上屏等）

把这 170ms 写出来是必要的：否则读者会以为上面四项就是全部，
而在优化时把 315ms 当成基数去算收益比例，得到偏大 54% 的结论
```

- 预连接（DNS 预解析 + QUIC 0-RTT）**不花带宽**，纯粹省时间——必须做
- 预加载（把还没播的分片先拉到本地）**花带宽**——必须算清楚加载几片
- 预热（把内容推到边缘）**花存储和推送带宽**——必须算清楚预热什么档位、前几个分片

**"免费"这个词需要限定：预连接不花带宽，但不是不花任何东西。** 维持连接池要保活包（移动端耗电）、要抗系统后台回收（iOS 尤其激进）、0-RTT 还有重放攻击面。**准确的说法是"不花带宽这项占成本 73% 的资源"**——所以它在本篇的语境下可以当免费用，但换到"客户端电量预算"这个语境下它不免费。**分类为"免费"的手段，要写清是相对哪个预算免费。**

**难点：** 起播优化里"免费的省时间手段"和"烧钱的省时间手段"混杂在一起，团队很容易全做，带宽账单随之失控。设计上必须**先做所有免费的，再给烧钱的手段配预算上限**。

**"先免费后付费"这条规矩有一个必然的后续问题：免费手段做完了，收益不够，怎么办？** 此时团队面对的是一堆都要花钱的选项，而且没有任何标尺告诉他们该花多少。**这正是成本熔断三档和上面那种"换算成同一单位"的方法必须存在的原因**——它们不是锦上添花的治理工具，而是免费手段耗尽之后唯一还能做决策的依据。

### 挑战 4：P2P 分担的收益与风险

P2P/PCDN 等效省 22% 带宽，是带宽优化手段里单笔最大的（P00 标称 ¥5,069 万/月，**这个金额的分母是错的，修正后约 ¥2,700 万/月，见"性能与成本分析"**）。但它的风险也最直接：

- **端侧上行占用**：从用户设备上传分片，消耗用户流量与电量，长期使用会导致卸载
- **弱网体验风险**：P2P 源不可靠时，下载分片比 CDN 慢，直接表现为卡顿
- **合规风险**：用户设备作为"内容分发节点"，涉及用户协议与运营商政策
- **首发/冷门内容**：没有其他用户缓存，P2P 拉不起来，等于白做

**P2P 有一个别的手段都没有的性质，以及一个与之互为镜像的缺陷：**

```
性质：供给与需求同向 —— 看的人越多，能提供分片的人也越多
      峰值时【每个 peer 的负担反而更低】
      这是唯一一种"越到高峰越有效"的带宽手段
      （CDN 是越到高峰越贵，自建是越到高峰越挤）

镜像：失效是全局且同时的 —— 协议 bug、tracker 故障、版本灰度
      不存在"部分区域 P2P 挂了"，只存在"P2P 挂了"
      → 容量规划必须假设 P2P = 0
```

**这个镜像关系直接改写 P2P 的收益公式：**

```
P2P 净收益 = 省下的带宽费 − 为它全局失效准备的兜底成本

后文验证：兜底靠成本熔断档位 1（降 32%），刚好覆盖 P2P 失效的 20% 缺口
所以兜底成本不是"再买 5.3 Tbps 容量"，而是"保持熔断能力可用"

→ 净收益接近毛收益，但【前提是熔断能被 P2P 健康度事件直接触发】
  如果只能靠成本超支触发（分钟级聚合），中间会留一段裸奔窗口
```

**难点：** P2P 不是"开还是不开"的二元决策，而是"什么内容、什么网络、什么时间开"的精细策略。**而且它的"开"有一个容易做反的方向：后文推导过，鼓励用户多做中继在超过某个配额后会反向亏损（上行带宽的机会成本超过节省的下行费用），"贡献越多越好"这个直觉有明确的翻转点，必须把它算出来。**

### 挑战 5：QoE 的可观测与归因——卡顿率突增时，到底怪谁

卡顿率是结果指标，但它的成因可能是：CDN 某区域抖动、某运营商链路劣化、编码档位码率虚高、播放器缓冲策略 bug、P2P 源质量差、用户设备弱网。**没有归因体系，卡顿率一波动，五个团队互相甩锅，而问题还在线上持续烧带宽、烧用户。**

**但"建立归因体系"这个答案本身有一个陷阱，而且是本篇最重要的发现之一：按维度下钻是不完备的。**

```
最自然的归因做法：按 (CDN, 区域, ISP, 档位, 版本) 五维下钻，
                找出卡顿率最高的格子，处理它

这个做法在一类情况下会给出【方向正确但原因完全错误】的答案：
  当卡顿率上升的原因是【流量分配变了】而不是【某个格子变差了】

  Δ整体 = Σ wᵢ_new(rᵢ_new − rᵢ_old)   ← 组内效应：格子自己变差了
        + Σ (wᵢ_new − wᵢ_old)rᵢ_old   ← 结构效应：流量搬到了差格子上

下钻只能看到第二项的【结果】，看不到它是第二项
→ 于是每次都得到"某厂商变差了"，每次降它权重都有效
→ 根因（调度器为什么把流量搬过去）永不暴露
```

**这就是 Simpson 悖论在 QoE 归因里的具体形态。** 后文给出了完整的 `attribute()` 实现与一个数值算例（整体卡顿率 1.023% → 2.294%，而**组内效应为 0，全部由结构效应贡献**——即没有任何一个 CDN 变差）。**归因的第一步必须是组内/结构分解，第二步才是下钻**，顺序颠倒会系统性地把排查方向从调度器引向厂商。

**更进一步：归因的产出不是"怪谁"，而是"改什么"。** 这两者的区别在场景 4 里非常具体——"怪厂商 C"每次都成立，降它的权重每次都有效，但"改什么"永远没有答案，因为真正要改的是那个把流量搬过去的调度器。**一个能稳定给出"怪谁"却从不给出"改什么"的归因体系，是在制造一种问题正在被解决的错觉。**

**难点：** QoE 必须从埋点到归因形成闭环——采集什么、怎么分维度聚合、异常怎么自动定位到"某个 CDN × 某个区域 × 某个档位"。**而闭环的最后一环是"归因结果反哺调度"：质量分必须是调度决策的直接输入，否则 QoE 只是一张没人看的报表。** 本篇的 `QoeRegistry` 就在这个闭环里，也正因如此，它里面两个看似只影响统计精度的 bug，实际后果是**闭环静默断开**——质量分恒为 0.5，调度退化成纯成本排序，而所有监控面板都显示正常。

## 设计约束

- 播放首帧（P95）< 800ms；卡顿率 < 1%；播放成功率 > 99.5%（红线）
- 带宽月成本 ≤ ¥9,220 万（成本熔断三档可一键切换）
- 任一 CDN 厂商故障，15 分钟内切走 80% 流量
- 调度权必须在自己手里（自建 HTTPDNS + 客户端多地址），禁止 CNAME 交出调度权
- 播放是最后底线：即使全平台其他域故障，已发布内容的播放必须可用
- 非会员清晰度上限可一键收窄（预算紧张时最高 720P）
- 所有播放变更（新档位、新协议、新 CDN 接入）必须可灰度、可回滚

## 设计解析

### 播放链路全景：一次播放的完整旅程

```
用户点击视频
  │
  ├─ ①② 播放请求 + 地址签发（64.8 万 QPS 峰值）        服务内预算 35ms
  │    · 鉴权：域1 身份 + 域11 权益结论（是否会员/付费）
  │    · 可播校验：查 guard（P02 的强一致 key）—— 已下架内容在此被物理阻断
  │    · 选档：网络类型 + 会员等级 + 设备解码能力 → 档位
  │    · 选 CDN：质量分 × 成本权重 → 厂商 + 节点
  │    · 签名：防盗链 token（短时效 30-60min）
  │    ↓ 返回 {play_url, backup_urls, quality_list}
  │
  ├─ ③ 传输建连（QUIC 0-RTT 复用预连接）                    预算 15ms（冷连接 +90ms）
  │    · 首片请求：GOP 对齐的 2s 分片（约 250KB）
  │    · 边缘命中 → 30ms；未命中回源 → +120ms
  │    ↓
  ├─ ④ 缓冲 + 解码 + 渲染首帧                               预算 85ms
  │    · 硬解初始化 60ms 与首片下载并行（已重叠，不单独计入）
  │
  └─ ⑤ 播放中：ABR 自适应 + 卡顿治理 + QoE 上报
       · 缓冲水位管理、吞吐估计、降码率切线
       · 首帧/卡顿/失败事件上报 → QoE 归因
```

**35ms 是"服务内"预算，不是"端到端"预算——这个区分必须写清楚，否则会与 P00 的账本重复计算。** P00 场景② 的账本里，「换取播放地址（域7）≈ 35ms」这一项已经包含了客户端到播放服务的网络往返；本篇的 35ms 指的是**播放服务收到请求到返回响应之间的处理时间**。两者的关系：

```
P00 的 35ms（端到端）= 客户端→接入层 RTT 15ms + 服务内处理 20ms
本篇的 35ms（服务内）= 一个更宽松的内部预算，留 15ms 余量给抖动
  → 两者不矛盾，但【不能相加】
  → 若把①和②各算 35ms 得到 70ms，会让整条账本凭空多出 35ms
```

**这类"同一个数字在两篇文档里指不同范围"的问题，是跨文档预算账本最常见的错误来源。** 规避方式是每个预算数字都标注口径（服务内 / 端到端 / 含客户端渲染），而不是只写数字。

**播放地址签发是全链路的决策核心**，它的输入输出在 P00 域 7 契约里定义好了：输入 content_id + 用户上下文，输出签名播放地址 + 档位列表。**签发必须快（服务内 < 35ms）且几乎无状态**——决策要素里"网络类型、会员等级、设备能力"是客户端上报 + 本地缓存的，不查库。

**唯一的例外是可播校验：它必须查强一致存储。** 这是 P02 「场景 4」推导出的结论——在一个有 5 层独立缓存的系统里，下架的硬保证只能落在"所有播放请求都必经的那个单点"上，而这个单点就是签发。所以签发服务的延迟构成是：

```
签发服务内的 35ms 预算分解：
  ┌────────────────────────────────────────────────┐
  │ 权益结论（本地缓存，60s TTL）        ≈  1ms    │
  │ guard 查询（强一致 Redis，无 TTL）    ≈  2ms    │ ← 唯一的强一致依赖
  │ 档位决策（纯计算 + 本地档位表）        ≈  1ms    │
  │ CDN 调度（本地质量分快照 + 打分）      ≈  2ms    │
  │ 签名计算（HMAC-SHA256）               ≈  1ms    │
  │ 序列化 + 框架开销                     ≈  3ms    │
  ├────────────────────────────────────────────────┤
  │ P50 合计                             ≈ 10ms    │
  │ P99（含 GC、guard 抖动）              ≈ 28ms    │
  └────────────────────────────────────────────────┘
```

**P50 只用掉预算的 29%，这个余量不是浪费——它是给 64.8 万 QPS 留的。** 在这个量级下，P99 与 P50 的差距主要来自 GC 与排队，而排队延迟对负载是超线性的：负载从 70% 涨到 90%，排队延迟涨 3 倍以上（M/M/1 排队论下 `E[W] ∝ ρ/(1-ρ)`）。**35ms 的预算配 10ms 的 P50，等价于把服务的目标负载压在 70% 以下——预算余量就是容量余量。**

#### 首帧 800ms 的预算分解与推导

P00 给出了 485ms（理想路径）与 695ms（边缘未命中 + 冷连接）两个数字。**这两个数字都是"路径求和"，不是分位数——和 P02 「分位数不可加」是同一个问题。** 必须说清楚它们各自是什么：

```
485ms = 各环节 P50 之和 ≈ 端到端 P50（因为各环节的慢是独立事件）
695ms = 各环节 P50 之和 + 两个【结构性】的额外开销
        （冷连接 +90ms、边缘未命中 +120ms）
      = "遭遇两个特定不利条件时的典型耗时"
      ≠ P95

真正的 P95 要看这两个不利条件各自的发生概率：
  冷连接概率      ≈ 12%（App 冷启动、切网、后台被杀）
  边缘未命中概率  ≈ 8%（长尾内容首次播放、边缘刚扩容）
  两者独立 → 四种组合：
    都命中（都好）      80.9% → ≈485ms
    仅冷连接            10.5% → ≈575ms
    仅边缘未命中         7.0% → ≈605ms
    两者皆遇             1.0% → ≈695ms

  累积到 95% 分位：80.9% + 10.5% = 91.4%（不够）
                  再加 7.0% = 98.4%（够了）
  → P95 落在"仅边缘未命中"这一档 ≈ 605ms
  → 再叠加各环节自身的尾延迟（约 +80ms）→ 端到端 P95 ≈ 685ms
```

**结论：685ms < 800ms 红线，余量 115ms（14%）。** 而这个推导给出了两条比"总数达标"更有用的信息：

1. **改善 P95 的杠杆是"降低边缘未命中率"，不是"优化各环节耗时"。** 未命中率从 8% 降到 3%，P95 直接从 605ms 掉到"仅冷连接"档的 575ms；而把首片下载从 180ms 优化到 150ms，只让每一档各降 30ms——两者收益相近，但前者顺带省了回源带宽（钱），后者要么烧带宽（更多预热）要么降画质。
2. **800ms 的红线其实是被"两者皆遇"的 1% 用户定义的。** 他们的体验是 695ms，仍在红线内——**这说明 800ms 这个红线定得恰到好处：它让最差的 1% 也刚好达标，而不是让平均用户达标。** 红线应当按最差的可接受比例定，不是按平均定。

**冷连接的 +90ms 为什么值得单列：** 它是唯一一个**完全可以靠预连接消除**的项，且成本为零（预连接不传输媒体数据）。12% 的冷连接率里，大部分来自"App 启动后还没建连就点了播放"——把预连接触发点从"进入播放页"提前到"App 启动 + Feed 请求并行"，冷连接率可以压到 4% 以下。**零成本消除 8% 的用户的 90ms，这是本篇性价比最高的单项优化，也是"免费的先做"这条原则的最佳例证。**

### 多 CDN 调度与议价：质量分 × 成本权重

**调度目标函数**（每个播放请求的 CDN 选择）。先给出一个**错误的**版本，因为这个错误在真实系统里极其常见且完全静默：

```
score(cdn) = quality_score(cdn, region) × w_quality + cost(cdn) × w_cost
```

**这个公式是错的——量纲不统一。** 代入实际数值就能看到：

```
quality_score ∈ [0, 1]        （归一化的质量分）
cost          ∈ [0.012, 0.028] 元/GB（各家单价）

若按"成本越低越好"取倒数：1/cost ∈ [35.7, 83.3]

score = 0.95 × 0.7 + 83.3 × 0.3 = 0.665 + 24.99 = 25.66
                     ↑ 质量项              ↑ 成本项
        质量项占总分的 2.6%，成本项占 97.4%
```

**文档上写的是 0.7/0.3，实际生效的是 0.026/0.974——调度器永远选最便宜的那家，无论它的质量分是 0.95 还是 0.15。** 而这个 bug 不会以任何形式报错：

- 单测会过（`score` 计算正确、返回了一个 CDN）
- 灰度会过（便宜的那家平时质量也不差）
- 只在**便宜那家出故障时**暴露——而那正是调度器最该切走流量的时刻
- 现象是"配了 0.7 的质量权重却完全不起作用"，排查者会去怀疑权重下发、配置热更新、灰度开关，**很少有人第一时间怀疑公式本身的量纲**

**这就是量纲错误的危险性：它在正常时期完全无害，只在故障时期失效。** 它属于那种"平时不跑、故障时必须对"的逻辑，与 P02 的降级路径同类。

**正确的目标函数——所有项先归一化到 [0,1]，再加权：**

```
cost_score(cdn) = (cost_max - cost(cdn)) / (cost_max - cost_min)
    其中 cost_max / cost_min 取【当前候选集】内的极值，不是全局常量
    → 便宜的那家得 1.0，最贵的得 0.0，中间线性插值

score(cdn) = quality_score(cdn, region) × w_quality
           + cost_score(cdn)            × w_cost
           其中 w_quality + w_cost = 1，score ∈ [0, 1]

代入同样的数据（三家：A 质量 0.95/单价 0.028，B 质量 0.90/单价 0.018，
                    C 质量 0.60/单价 0.012）：
  cost_score:  A = 0, B = 0.625, C = 1.0
  score(A) = 0.95×0.7 + 0    ×0.3 = 0.665
  score(B) = 0.90×0.7 + 0.625×0.3 = 0.818   ← 胜出
  score(C) = 0.60×0.7 + 1.0  ×0.3 = 0.720
  → 选 B：质量与成本的平衡点，符合 0.7/0.3 的设计意图 ✓

再看故障场景（B 的质量分掉到 0.40）：
  score(A) = 0.665   ← 胜出，流量自动切给 A
  score(B) = 0.40×0.7 + 0.625×0.3 = 0.468
  score(C) = 0.720   ← 实际上 C 胜出
  → 权重真的在起作用了
```

**用候选集内极值归一化（而非全局常量）有一个额外好处：它让成本项自动适应议价结果。** 如果全网单价整体下降 20%，`cost_score` 的相对关系不变，调度行为也不变——**成本项衡量的应当是"这家相对于其他家便宜多少"，而不是"这家的绝对单价是多少"。** 绝对单价的高低是议价问题，不是调度问题。

**`quality_score` 的构成——五个指标如何合成一个分：**

| 指标 | 权重 | 归一化方式 | 为什么是这个权重 |
|------|------|-----------|----------------|
| 首帧成功率 | 0.30 | 直接用比率 | 起播失败是用户直接感知的最严重故障 |
| 卡顿率 | 0.30 | `1 - min(stall_rate/0.05, 1)` | 5% 卡顿率视为完全不可用（红线的 5 倍） |
| 播放成功率 | 0.20 | `(rate - 0.95) / 0.05`，裁剪到 [0,1] | 95% 以下视为不可用；99.5% 是红线 |
| 边缘命中率 | 0.15 | 直接用比率 | 影响回源带宽（成本）而非体验，权重低于体验项 |
| 建连 RTT | 0.05 | `1 - min(rtt/200ms, 1)` | 15ms 的 RTT 差异在 800ms 预算里几乎不可见 |

**权重的推导依据是"该指标劣化 1 个单位，损失多少播放时长"**，而不是"该指标看起来多重要"：

```
以卡顿率为例的量化：
  行业经验：卡顿率每上升 1 个百分点，人均播放时长下降约 2.5%
  首帧成功率：每下降 1 个百分点，该次播放直接损失（100% 时长损失）
  → 首帧成功率的边际影响是卡顿率的 40 倍

  但卡顿率的【取值范围】比首帧成功率宽得多：
    首帧成功率在 [0.98, 0.999] 之间波动（极差 0.019）
    卡顿率在 [0.002, 0.03] 之间波动（极差 0.028）
  → 归一化后两者对分数的实际影响量级接近
  → 权重取相同的 0.30

边缘命中率为什么只有 0.15：它不影响体验（回源只是慢一点，已计入 RTT 与卡顿），
  只影响成本。而成本已经在 cost_score 里单独计权了 ——
  【同一个因素不应在目标函数里被计两次】。
  留 0.15 是因为回源率异常往往是 CDN 侧配置故障的先行指标（见异常场景）。
```

**最后一句是这张表里最容易做错的地方：把命中率的权重设得很高，等于让成本因素在目标函数里出现两次（一次通过 cost_score，一次通过命中率），实际权重变成 0.3 + 0.15 = 0.45，又一次偏离了设计意图。**

- `quality_score`：该 CDN 在该区域的近 5 分钟实时质量，按上表五项加权合成
- `cost_score`：候选集内归一化的成本优势
- 权重 `w_quality / w_cost`：平时 0.7/0.3；**成本熔断档位切换时权重随之调整**——档位 2 下 w_cost 升到 0.8，自动把更多流量导给便宜 CDN 和 P2P

**调度权在自己手里的三件套：**

| 组件 | 职责 | 为什么不能交给厂商 |
|------|------|------------------|
| 自建 HTTPDNS | 客户端本地解析，返回按区域/运营商调度的多地址 | CNAME 的解析权在厂商，切流只能等厂商 |
| 客户端多地址下发 | 首地址失败秒切备用地址（backup_urls） | 单地址失败要重新解析，慢且重 |
| 调度决策服务 | 实时计算各 CDN 质量分与权重 | 质量数据来自自家 QoE 归因，厂商给不了 |

**议价机制**：议价不是一年谈一次，而是**月度循环**——用上月各区域的流量分布 + 质量表现作为谈判筹码：

```
月初：用上月的流量分配数据（含"如果切走会损失多少"）与各家谈单价
月中：调度权重根据新单价与质量表现动态调整
月末：评估议价收益 → 决定下月分配比例
```

关键点：**议价能力 = 切换能力 × 流量规模**。分钟级全量切换能力 + 每月切换演练，让平台对任何一家厂商都有"今天就切走"的底气，单价自然谈得下来。

#### "15 分钟切走 80%"是怎么算出来的

这个约束不是目标，是**推导结果**——它由播放地址的时效与用户的换址频率共同决定：

```
存量流量的衰减机制：
  已在播放的会话持有旧地址，不受调度权重变化影响
  只有【下一次换址】才会拿到新厂商的地址
  换址发生在：新起播、切档位、地址过期续签

单用户的换址间隔：
  人均单次播放时长 32s，即平均每 32 秒起播一次 → 换址间隔 ≈ 32s

于是流量迁移是一个指数衰减过程：
  旧厂商剩余流量占比 R(t) = e^(-t/τ)，τ = 平均换址间隔 = 32s
  要 R(t) ≤ 20%：
      e^(-t/32) ≤ 0.2
      t ≥ 32 × ln(5) = 32 × 1.609 = 51.5 秒
  → 理论上【52 秒】就能切走 80%
```

**理论 52 秒，实际承诺 15 分钟——27 倍的余量从哪来？** 三处：

```
1. 长视频会话（占播放次数 3%，占带宽 35%）
   长视频单次会话可达 40 分钟，中途不换址
   → 按带宽加权的 τ 不是 32s，而是 32×0.65 + 2400×0.35 = 861s
   → 要切走 80% 的【带宽】：t ≥ 861 × 1.609 = 1,385 秒 ≈ 23 分钟
   → 这才是真正的约束，比 52 秒差 27 倍

2. HTTPDNS 缓存
   客户端本地缓存解析结果 60s，权重变化要等缓存过期
   → +60s

3. 灰度节奏
   全量切换有风险（新厂商可能扛不住突增），实操是 10% → 30% → 100% 三档
   每档观察 2 分钟 → +4 分钟
```

**所以 15 分钟这个承诺其实是"切走 80% 的播放请求"，而不是"切走 80% 的带宽"。** 按带宽算需要 23 分钟以上，且必须**主动打断长视频会话**（下发新地址强制换址）才能压进 15 分钟。

**这个区分在故障切换时至关重要：** CDN 区域故障时，SRE 关心的是"多久能把用户救出来"（按请求数算，52 秒足够）；成本熔断时，财务关心的是"多久能把账单压下来"（按带宽算，23 分钟）。**同一个"切换能力"指标，在两个场景下的正确口径差 27 倍——只报一个数字必然误导其中一方。**

**分钟级全量切换的实现**：所有播放地址由签发服务统一签名，切换时只需把调度权重目标改成"某厂商 0%"，HTTPDNS 下发自然不再返回该厂商地址，存量播放地址短时效（30-60min）自动过期。**注意 30-60min 的地址时效是切换速度的硬上限**——它决定了"最坏情况下多久能把一个厂商彻底清零"。想把这个上限压到 15 分钟，就得把地址时效缩短到 15 分钟，代价是续签请求量翻倍（长视频会话每 15 分钟要重签一次地址）：

```
地址时效 60min：长视频会话（40min）平均续签 0.67 次
地址时效 15min：长视频会话平均续签 2.67 次
  → 长视频的签发 QPS ×4
  → 长视频占播放次数 3%，即 64.8万 × 3% = 1.94 万 QPS
  → 增量 = 1.94 万 × 3 = 5.8 万 QPS（总签发 QPS +9%）
  → 换来"最坏切换时间"从 60 分钟降到 15 分钟

判断：值得。9% 的签发容量成本，换的是【一个 CDN 厂商整体不可用时】
      的止损速度 —— 这是低概率高损失事件，值得为它常态化付费。
```

### QUIC/HTTP3 传输优化

QUIC 是点播场景收益最直接的传输协议升级：

| 优化点 | 效果 | 落地 |
|--------|------|------|
| 0-RTT 建连 | 复用上次连接，省 1 个 RTT | 冷启动首帧省 ~90ms |
| 连接迁移 | 网络切换（WiFi→4G）不断流 | 减少"切网即卡顿" |
| 多路复用 | 消除 HTTP/2 的队头阻塞 | 弱网下多分片并发下载更稳 |
| 可插拔拥塞控制 | 按网络类型调拥塞算法 | 移动网/弱网专项优化 |

**但 QUIC 不是银弹**：边缘节点要支持 QUIC、客户端要升级、部分旧设备不支持。落地策略是**灰度升级**——先覆盖起播最敏感的移动端头部版本，再逐步扩散，老设备回退 TCP。

**关键设计：预连接与首片下载重叠。** QUIC 0-RTT 复用上次会话的连接，首片请求在连接建立的同时就发出，把"建连 + 首片下载"重叠成一段。这是 P00 场景② 中 485ms 理想路径的重要来源——**预连接不花带宽，是纯赚的优化，必须全量做。**

### 起播优化：免费的先做，烧钱的配预算

**免费层（不花带宽，全量做）：**
- DNS 预解析 + QUIC 预连接（App 启动即触发，与 Feed 并行）
- 首片请求 GOP 对齐（分片边界对齐关键帧，拿到即可解出首帧）
- 硬解初始化与首片下载并行
- 播放地址与 Feed 结果并行换取（不等播放页跳转）

**烧钱层（配预算上限）：**

| 手段 | 预算 | 收益 | 副作用 |
|------|------|------|--------|
| 预加载 1 片 | 每个起播多拉 1 片 | 播放中切换更顺滑 | +8% 带宽（P00 标称 ¥1,843 万，修正后 ¥934 万） |
| 预热首 3 分片 + 单一档位 | 仅新发布/热点内容 | 冷启动零等待 | 推送带宽 + 边缘存储 |
| 全片预热 | **禁止**（除非顶级预约内容） | — | 72GB×6 档纯烧钱 |

**预热策略（承接 P00 场景① 的结论）：** 只预热"首 3 分片 + 单一档位"（720P 主力档），覆盖 95% 观众的起播需求；后续分片靠边缘回源 + JIT。**预热不是把整条视频推到边缘，是把"起播那一下"推到边缘。**

#### 预加载的账本：8% 是怎么来的，以及它为什么不等于"多拉一片"

文档里写"从预加载 2 片降到 1 片，省 8% 带宽 = ¥1,843 万/月，起播成功率只降 0.3%"。这两个数字都需要推导，否则无法迁移到别的分片时长 / 别的均播时长上。

**先算一阶账（纯字节）：**

```
分片时长 2s（GOP 对齐，约 250KB）
均播时长 32s → 平均播放 16 片
预加载深度 d：会话结束时缓冲区里有 d 片已下载未播放

浪费的前提是"这片还没被播到，会话就结束了"：
  · 完播的会话：片尾之后没有内容可预加载 → 浪费 0
  · 中途退出的会话：浪费 d 片
设中途退出比例 q ∈ [0,1]

d 从 2 降到 1，每次会话少拉 q 片：
  按"总下载量"口径：q / (16 + 2q)，q=1 时 = 1/18 = 5.6%
  按"内容消费量"口径：2s / 32s = 6.25%
```

**一阶账给出 5.6%~6.25%，而且这已经是上界**（q=1 意味着没有任何会话完播）。可是账上记的是 8%。**差的 1.75~2.4 个百分点不是估算误差，是一阶模型漏掉了一整条因果链。**

**二阶效应一：预加载把 ABR 推高了一档。** 这是主要来源。

```
ABR 规则 2：buffer_level > 15s（缓冲充足）→ 可升一档码率
预加载深度 2 片比 1 片多 2s 水位 → 更频繁越过升档阈值
一旦升档，不是"多拉 1 片"，而是【后续所有片都按更高码率拉】

720P (1.5 Mbps) → 1080P (3.5 Mbps)：单位时间字节 ×2.33
只要 3% 的会话因水位充足而多升一档并保持到结束：
  3% × 133% = +4.0 个百分点
```

**预加载真正烧的钱不在预加载的那一片上，而在它把 ABR 推高了一档。** 一阶模型只盯着"多拉的那 1 片"，于是低估了一半。

**二阶效应二：预加载请求的边缘命中率更低。** 预加载跑在播放波前**之前**，更可能是该分片在该区域的首次请求，回源率高于普通播放请求。回源字节在 P00 的成本模型里同样计费（中心出口 + 商业 CDN 回源费），所以同样的一片，预加载拉的比正常播放拉的贵。

| 口径 | 数值 | 说明 |
|------|------|------|
| 一阶（纯字节，上界） | 6.25% | 2s / 32s |
| + ABR 升档连带 | ≈ +1.5~4.0 pt | 取决于升档触发率 |
| + 回源率差异 | ≈ +0.3 pt | 预加载片回源率高于均值 |
| **实测（AB 实验带宽差）** | **8%** | 账上记的就是这个 |

**这个差值本身是要记住的教训：** 带宽账要用 AB 实验的实测差，不能用一阶估算。如果只信一阶模型，结论会是"预加载没那么贵，那就多加一片"，然后在下个月的账单上看到说不清来源的增长——因为**多出来的钱花在 ABR 上，而不是花在预加载上，归因会指向错误的地方**。

#### 0.3% 起播成功率：这笔交易真的划算吗

文档的原话是"0.3% 的起播成功率损失远小于 1843 万/月的带宽收益"。**这个比较的两边量纲不同，不能直接比大小。** 把两边都换算成同一单位：

```
0.3% × 160 亿 VV/日 = 4,800 万次/日 起播失败增量
                     = 14.4 亿次/月
摊到 2 亿 DAU：每人每 4 天多遇到一次起播失败 ← 已进入可感知区间

¥1,843 万/月 ÷ 总成本 ¥1.17 亿/月 = 1.6%
             ÷ 2 亿 DAU = ¥0.09/人/月

等价于：用"每人每 4 天一次起播失败"换"每人每月 ¥0.09"
```

写成这样，"远小于"就不成立了。**而且 ¥1,843 万这个数本身还是高估的。** "性能与成本分析"一节会证明它用错了分母——8% 应当作用在编码升级与 P2P 之后的剩余流量（¥1.168 亿）上，而不是原始基线（¥2.304 亿）上：

```
修正后：¥1.168 亿 × 8% = ¥934 万/月
        ÷ 2 亿 DAU = ¥0.047/人/月

真实的交易是：用"每人每 4 天一次起播失败"换"每人每月 4.7 分钱"
```

**收益腰斩，代价不变——这笔交易比原文描述的差一倍。** 值得注意的是修正方向：**分母错误总是让降本手段看起来更划算**，因为它只放大收益一侧，代价一侧（起播成功率）是实测的、没有分母可选。这种单向偏差会让一个组织系统性地过度优化成本。

**但结论也不是"不该做"，而是"不该这样做"** ——关键问题被漏掉了：**这 0.3% 集中在谁身上？**

| 分布假设 | 实际含义 | 判断 |
|---------|---------|------|
| 均匀分布在全体用户 | 每人每 4 天一次 | 勉强可接受 |
| 集中在弱网用户（约 5%） | 弱网用户每天多次失败 | **流失级伤害，不能做** |

现实是后者：起播失败的成因是首片没能在超时内下载完，这在弱网上的发生率比强网高一个数量级。**而带宽账的大头恰恰在强网**——弱网用户本来就跑低码率档，是带宽消耗的少数。

```
省钱的大头  → 强网高码率用户（1080P/4K，3.5~15 Mbps）
风险的大头  → 弱网低码率用户（480P，0.8 Mbps）
两拨人几乎不重叠
```

于是正确的做法不是全局把预加载从 2 片降到 1 片，而是**按网络类型分档**（这是本仓库设计原则 3「把二元决策变成连续谱系」的又一次应用）：

| 网络类型 | 预加载深度 | 理由 |
|---------|-----------|------|
| WiFi / 5G | 1 片 | 带宽消耗大户，且重试成本低，省钱主战场 |
| 4G 正常 | 2 片 | 折中 |
| 弱网（高 RTT / 高丢包） | 3 片 | 起播失败的主要承受者，多缓冲是保命的 |

**同时把 ABR 升档阈值与预加载深度解耦**——弱网加深缓冲是为了防卡顿，不是为了让它升档。弱网的升档阈值单独提高到 25s 水位，避免"为保成功率加的缓冲"反过来变成"升档多烧的带宽"。这一条不做，分档预加载省下的钱会被 ABR 吃回去（就是上面二阶效应一的机制）。

**分档后的账：** 省钱从 8% 降到约 6.5%（弱网那部分不省了），但 0.3% 的起播成功率损失降到 0.05% 以下，且不集中在弱网。**用 1.5 个百分点的带宽收益，换掉了这笔交易里最危险的部分。**

### ABR 自适应与卡顿治理

卡顿治理的核心不是"网不好就暂停缓冲"，而是**在卡顿发生前提前降码率**。

**ABR 决策模型**（播放器内）：

```
每 2s 评估一次：
  throughput = 最近 5 个分片下载吞吐（滑动窗口）
  buffer_level = 当前缓冲水位（秒）

  决策规则（按优先级）：
  1. buffer_level < 2s 且 throughput 持续走低 → 立即降一档码率（切线）
  2. buffer_level > 15s（缓冲充足）→ 可升一档码率
  3. throughput < 当前码率 × 1.2 持续 10s → 降档
  4. buffer_level < 0.5s → 才允许短暂暂停（最后的兜底）
```

关键设计判断：
1. **降码率切线优先于暂停**——卡顿的定义是"播放中断"，降码率只是画质变化，用户无感的概率远大于暂停
2. **用缓冲水位做主判据，不用吞吐做唯一判据**——吞吐估计有噪声，缓冲水位是实际存量，混合判断更稳
3. **降档是渐进的**（一步降一档），避免 1080P→360P 的画质悬崖
4. **切线时机由播放器本地决定，不走网络**——64.8 万 QPS 下任何集中决策都是死路，ABR 必须完全本地化

#### 2s 降档阈值是怎么定出来的

规则 1 的 `buffer_level < 2s` 不是拍的。**降档不是瞬时的**——它要等一个新档位的分片下载完才能生效，这段时间必须由现存水位掩盖。2s 是这段时间的预算和：

```
触发降档 → 新档位第一片可播，中间发生什么：
  ① 请求新档位分片（QUIC 连接已复用，0-RTT）        ≈  30ms
  ② 新档位在边缘未命中，回源（最坏情况）             ≈ 150ms
  ③ 下载 2s 分片：1.6 Mb @ 当时实测吞吐 ~1.0 Mbps   ≈ 1600ms
  ④ 解码器重配置（分辨率变化需要 reinit，硬解更慢）   ≈ 100ms
  ⑤ GOP 对齐等待：2s 分片起点即关键帧               =    0ms
  ─────────────────────────────────────────────────────────
  合计                                            ≈ 1880ms → 取 2s
```

**这个预算被 ③ 主导（1.6s / 1.88s = 85%），而 ③ 正比于分片时长。** 于是得到一个非显然的结论：**分片时长直接决定了降档阈值，也就决定了 ABR 的反应速度。** 4s 分片需要 4s 水位才能无卡顿降档，2s 分片只需 2s。这是选 2s 分片的第二个理由（第一个是首帧），也解释了为什么"分片时长"这个看起来只影响起播的参数，其实是卡顿治理的核心参数。

反过来说，如果水位阈值定成 1s，降档过程本身就会引发一次卡顿——**为了防卡顿而降档，却在降档过程中卡顿**，这是 ABR 最尴尬也最常见的失效模式。

规则 4 的 `0.5s` 同理：0.5s 是解码器缓冲 + 渲染队列的物理下限，再低就是画面冻结。**主动暂停要比被动冻结早一点触发**——主动暂停能显示 loading 指示，用户知道在等；被动冻结用户以为 App 崩了。同样的等待时长，两种归因，QoE 上报里前者是 `rebuffer`，后者常被用户投诉成"闪退"。

#### 升档阈值与目标水位必须协同：一个静默失效

上面 ABR 规则 2 写的是"`buffer_level > 15s` → 可升一档"，而本节末尾的成本熔断写的是"档位 0 目标水位 10s"。**这两个数字放在一起，规则 2 永远不会触发。**

```
目标水位 10s  →  下载调度器在水位到 10s 时停止预取
升档阈值 15s  →  需要水位 > 15s 才允许升档
        10s < 15s  →  升档分支是死代码
```

后果是 **ABR 变成单向的**：只会降档，不会恢复。用户在一次地铁隧道里降到 480P，出隧道后网络恢复了，画质也不会回来——直到下一个视频重新起播。这个 bug 在 QoE 报表上**完全看不见**：卡顿率漂亮（因为一直跑低码率），首帧漂亮，成功率漂亮。唯一的信号是"平均码率缓慢下滑"和"1080P 播放占比逐日走低"，而这两个指标通常没人看。

这类 bug 的成因是**两个数字由两个团队各自拥有**：升档阈值在播放器团队的 ABR 逻辑里，目标水位在成本团队的熔断配置里。各自都合理，组合起来是死的。

正确做法是把它变成一条**显式不变式**，在配置下发时校验：

```
不变式：升档阈值 < 目标水位 − 一个分片时长
即      upshift_threshold < target_buffer − segment_duration

档位0：目标 10s → 升档阈值 ≤ 8s   ✓
档位1：目标  6s → 升档阈值 ≤ 4s   ✓
档位2：目标  3s → 升档阈值 ≤ 1s   ✗ 与降档阈值 2s 冲突
                 → 档位 2 下明确【关闭升档】，而不是留一个恒不触发的阈值
```

**档位 2 那一行是关键**：约束解不出来，说明这个档位下升档在物理上不成立。正确的处理是**在配置里显式写"关闭升档"**，而不是留一个永远不触发的阈值假装功能还在。前者是设计决策，后者是隐藏的 bug——而它们的运行时行为一模一样，只有代码可读性区分得出来。

**这一条直接关系到上一节的成本账**：二阶效应一（预加载把 ABR 推高一档）的前提是升档路径活着。如果因为配置不协同而事实上关闭了升档，那么预加载的成本就只有一阶的 6.25%，而 AB 实验测出 8% 反过来证明了升档确实在发生——**实测值与一阶模型的差，本身就是"升档路径是活的"的证据**。带宽账单在这里成了配置正确性的探针。

#### 快启阶梯：起播用低档，稳定后再升

首帧优化和画质是对立的：首片越小起播越快，但画质越差。折中是**不用同一个档位跑完全程**：

| 分片序号 | 档位 | 理由 |
|---------|------|------|
| 第 1 片 | 目标档位下移一档（如 720P→480P） | 250KB → 130KB，首帧提前约 120ms |
| 第 2-3 片 | 目标档位 | 水位建立起来了，切回正常画质 |
| 第 4 片起 | 交给 ABR | 进入常规自适应 |

代价是**开头 2 秒画质较低**。这个代价的可接受性取决于内容形态：短视频前 2s 通常是转场/片头，用户注意力还没建立，损失很小；长视频的前 2s 同理。**但直播不适用**——直播用户往往是为了"这一刻"进来的，开头降档会正好落在关键时刻上。这也是 P07 直播链路必须单独设计起播策略的原因之一。

**缓冲区水位与带宽的联动：** 缓冲水位上限是"预加载 1 片"的物理约束——水位越高，拉的数据越多，带宽越大。ABR 的目标缓冲水位随成本熔断档位调整（档位 0 目标 10s，档位 2 目标 3s）。

### P2P/PCDN 分担：省 22% 带宽的大头

**为什么是 22% 等效带宽：** 热门内容（占播放 80%）被大量用户同时观看，同一分片反复从 CDN 拉取。P2P 让用户从其他用户设备获取分片，等效减少了 CDN 出口流量。

#### 22% 的推导，以及一个口径陷阱

**先说陷阱：不能用"热门内容占播放 80%"这个 VV 口径的数字直接算带宽分担。** P2P 省的是**字节**，而字节的分布和 VV 的分布不一样：

```
VV 口径   ：短视频占绝对多数（均播 32s，但次数极多）
字节口径  ：长视频权重被时长放大（一次播放 = 几十倍短视频的字节）

长尾长视频贡献的【字节】远多于它贡献的【VV】
→ 按字节算，"热门内容"的占比从 80% 降到约 65%
```

用错口径会把 P2P 收益高估约 23%（80/65），而这笔账直接挂在容量规划上。

**P2P 的物理条件**是：同一分片在同一 swarm（同区域 + 同 ISP）内有足够多的持有者。持有者数量可以估：

```
播放器缓存最近约 30s 内容（15 片 × 2s）
某内容峰值并发观看数 C，观众进度均匀分布在时长 T 内
→ 某个特定 2s 分片的持有者数 ≈ C × min(1, 30s / T)

短视频 T = 32s ：30/32 ≈ 0.94  → 几乎所有并发观众都持有几乎所有分片
长视频 T = 2h  ：30/7200 = 0.4% → C 要大于 250 才有 1 个 peer 持有该片
```

**这解释了 P2P 策略表里"冷门内容关闭 P2P"的真正原因：不是"缓存源少"这么含糊，而是 `C × 30/T` 算出来小于 1。** 也解释了一个反直觉的事实：**短视频的 P2P 条件比长视频好得多**——因为内容只有 32s，所有观众的进度天然对齐，swarm 密度极高。长视频只有在"热门 + 高并发"时才凑得出 swarm。直播是最好的情况（进度完全对齐），但归 P07 管。

**分担率的分层折算：**

| 层 | 系数 | 依据 |
|----|------|------|
| 可分担的内容（字节口径） | 65% | 见上文口径修正 |
| 可分担的用户 | 78% | 排除弱网 8%、未授权 P2P 约 12%、iOS 后台限制等 |
| swarm 内实际命中 | 55% | peer 持有该片 × 上行有余量 × NAT 打洞成功 |
| **小计** | **27.9%** | 65% × 78% × 55% |
| 协议开销 + 回退重复传输 | ×0.80 | 200ms 超时转 CDN 时，已传的部分白费 |
| **等效分担** | **22.3% ≈ 22%** | |

**NAT 打洞成功率是 55% 里最脆弱的一项。** 对称型 NAT（运营商级 NAT，CGNAT 尤其）之间无法直连，需要中继（TURN），而中继流量走的还是自家带宽——**中继过多会让 P2P 从省钱变成花钱**。所以必须给中继流量单独设配额（如不超过 P2P 总量的 5%），超了就直接判定该 peer 对不可用，回退 CDN。这一条是 P2P 系统里最容易被忽略的成本反转。

#### 上行带宽的可行性校验

22% 不能只是纸面算出来，还要验证 peer 的上行**供得起**：

```
22% × 96 PB/日 = 21 PB/日 需由 peer 上行提供
21 PB/日 ÷ 86400s = 243 GB/s = 1.94 Tbps 平均 peer 上行

平均并发观看数 = 160 亿 VV × 32s ÷ 86400s = 592.6 万
可分担用户 = 592.6 万 × 78% = 462 万 peers
→ 每 peer 平均上行占用 = 1.94 Tbps / 462 万 = 0.42 Mbps
```

家宽上行典型 30~50 Mbps（千兆下行的 1/20~1/10），**0.42 Mbps 只占约 1%**，可行性没问题。移动网络上行 5~20 Mbps，占 2~8%，也在可接受范围——但移动网络要考虑流量计费，所以蜂窝网络下必须默认关闭 P2P 上传（这是合规问题，不是技术问题）。

**再看峰值，会发现 P2P 最重要的性质：**

```
峰值带宽 26.7 Tbps × 22% = 5.87 Tbps 需由 peer 提供
峰值并发 = 592.6 万 × 3.5 = 2,075 万 → 可分担 1,619 万 peers
→ 每 peer 峰值上行 = 5.87 Tbps / 1,619 万 = 0.36 Mbps

峰值时的单 peer 负担【比平均时更低】
```

因为需求涨 3.5 倍的同时，供给（在线 peer 数）也涨了 3.5 倍。**P2P 是全套带宽手段里唯一"越热越省"的一项**——CDN 容量是固定的、必须按峰值预留（P00 的"为峰值付全价"就是这笔钱），而 P2P 的容量**本身就是峰值的函数**。这是它值得承担全部复杂度的根本理由，也是它在爆款场景（场景 2）里作用最大的原因。

**但这个性质有个致命的反面**：既然供给随需求增长，那么**P2P 失效时缺口也随需求成比例增大**。峰值时 P2P 挂掉，CDN 要瞬间多承接 5.87 Tbps（相当于总容量的 22%）。所以：

> **容量预留必须按 P2P = 0 计算。** P2P 省的钱可以进成本账，但不能进容量账。

这不是保守，是因为 P2P 的失效模式是**全局同时**的（调度服务故障、协议 bug 灰度、某个 ISP 封禁 P2P 端口），不像 CDN 故障那样按区域隔离。见场景 3。

**P2P 的精细策略（不是二元开关）：**

| 场景 | 策略 | 量化依据 |
|------|------|---------|
| 热门内容 + 强网用户 | 开启 P2P，尽力分担 | `C × 30/T ≫ 1`，swarm 密度足够 |
| 弱网用户（4G 弱覆盖/高延迟） | 强制关闭 P2P，走 CDN，保体验 | P2P 首字节比 CDN 慢，弱网上放大 |
| 首发视频（发布 < 24h） | 关闭 P2P（没有缓存源，拉了也白拉） | 首发时 C 还没起来，且没人持有分片 |
| 冷门内容（观看 < 阈值） | 关闭 P2P | `C × 30/T < 1`，算出来就没有 peer |
| 蜂窝网络上传 | 强制关闭（合规） | 消耗用户计费流量 |
| 对称 NAT 需中继 | 超配额即关闭 | 中继流量走自家带宽，成本反转 |
| 成本熔断档位 2 | 强制开启 P2P（档位 2 的省钱手段之一） | 此时体验已让位于成本 |

**P2P 网络结构：**

```
┌───────────┐     ┌───────────┐
│ 用户设备 A │◄────►│ 用户设备 B │    P2P 网络（端侧互传分片）
└─────┬─────┘     └─────┬─────┘
      │                  │
      │  CDN 边缘（兜底）  │
      └─────────┬────────┘
                ▼
           商业 CDN 回源
```

**P2P 的可靠性设计：** P2P 源失败时自动回退 CDN——分片请求先问 P2P，P2P 源在 200ms 内无响应则转 CDN。**P2P 永远是"尽力而为"，CDN 永远是"兜底承诺"，这个主从关系不能反。**

#### 200ms 超时与"不能对冲"的约束

200ms 这个数字被两个约束夹住：

**上界来自降档预算。** 上一节算过，2s 水位里下载占 1.6s，只剩约 280ms 余量给请求与解码器重配置。P2P 探测的时间必须落在这个余量里，否则一次 P2P 失败就会把降档过程本身拖成卡顿。取 200ms，留 80ms 冗余。

**下界来自打洞与首包时间。** NAT 打洞 + peer 首包在正常家宽上是 80~150ms（比 CDN 的 30ms 慢一个量级，因为多了信令交换）。低于 150ms 会把大量本来能成功的 peer 判死，命中率从 55% 掉到 30% 以下。

**更关键的是一条不能违反的约束：绝对不能对同一分片同时发 P2P 和 CDN 请求。**

```
对冲请求（hedged request）在别处是好手段：
  发两个请求取先到的，用少量额外资源换尾延迟

但在 P2P 上，"额外资源"就是【要省的那个资源】
  同时发 → CDN 流量一分不少 → P2P 的 22% 全部作废
  P2P 成功率 55% 时，对冲让带宽变成 100% CDN + 55% P2P 上行
  = 比不开 P2P 更糟（多烧了用户上行，还得付中继费）
```

所以必须**串行**：先试 P2P，超时才转 CDN。但串行的代价是 200ms 的确定性延迟惩罚。于是引出第三条策略：

> **P2P 的准入条件里必须包含缓冲水位。** 水位 > 6s（≥ 2s 降档阈值 + 200ms 探测 + 安全余量）才允许试 P2P；水位紧张时直接走 CDN，不试。

这条规则让 P2P 的分担率在**用户体验紧张时自动归零**——正是它该归零的时候。也就是说 P2P 的实际分担率不是一个常数，而是随全网水位分布浮动的，这是成本预测里必须留出的方差来源。

**用户激励与合规：** 开启 P2P 需要用户协议授权；可考虑"贡献上行换权益"（如换会员积分）平衡用户卸载。这是产品决策，架构上只需支持"按用户开关 P2P"的粒度。**授权率直接决定 22% 能不能达到**——上面的 78% 可分担用户里，未授权占 12%，如果授权引导做得差（比如藏在二级设置里默认关闭），这一项会掉到 40%，等效分担率从 22% 跌到 11%，一年少省 ¥2 亿。**一个产品文案的位置，值 2 亿。**

### 防盗链与带宽盗用治理

带宽占总成本 73%，而**盗链盗走的是纯成本，一分收益都没有**。这一节在成本占比最高的那一项上直接止损，优先级不比 QoE 低。

**盗用的三种形态，成本量级差三个数量级：**

| 形态 | 手法 | 典型量级 | 危害 |
|------|------|---------|------|
| 网页嵌链 | 第三方站直接 `<video src>` 引用播放地址 | 单站日耗 GB~TB | 白送带宽，无收益 |
| 聚合 App 盗刷 | 抓包拿签名接口，批量签发地址后转发 | 日耗 100TB+ | 相当于免费给对手做 CDN |
| 内容爬取转载 | 全量下载后二次分发到别的平台 | 一次性，但带走内容资产 | 带宽 + 版权双重损失 |

**防线是分层的，每层拦住不同的攻击者：**

```
① URL 签名（HMAC + 40min 有效期）
   拦住：静态嵌链、搜索引擎索引到的裸地址
   拦不住：实时抓包转发（40min 内地址是有效的）

② 签名绑定 uid + IP 段（不绑精确 IP）
   拦住：地址被转发给其他用户
   为什么不绑精确 IP：移动网络切换基站/WiFi↔4G 会换 IP，
   绑死会让正常用户播放中断。绑 /24 或运营商 AS 号是折中

③ Referer / Origin 白名单（仅 Web 端）
   拦住：网页嵌链
   拦不住：Referer 可伪造，且 App 端根本没有 Referer
   → 这一层只对"懒惰的盗链者"有效，但成本极低，值得开

④ 签发接口的风控（真正的主防线）
   拦住：批量签发。这是唯一能拦住聚合 App 的一层
   判据：单 uid 签发频次、单 IP 段签发的 uid 数、
        签发后是否有对应的 QoE 上报（签了不播 = 高度可疑）

⑤ 播放 token 与设备指纹绑定（客户端加固）
   拦住：模拟客户端。需要客户端安全能力配合，成本最高
```

**第 ④ 层里"签了不播"是最有效的信号，也最容易被忽略。** 正常用户签发一次地址就播一次，签发数和 QoE 上报数应当近似 1:1。盗刷方拿地址去转发，转发出去的播放不会回传 QoE 上报到本平台：

```
签发/上报比 = 签发次数 / 收到 QoE 上报次数

正常：1.0 ~ 1.15（少量起播失败、进程被杀不上报）
异常：> 2.0  → 一半以上的签发没有对应播放，强烈的转发嫌疑

按 (IP 段, 客户端版本, uid) 三个维度分别算这个比值，
偏离最大的维度就是盗刷来源
```

这个指标的妙处是**它不依赖识别攻击手法**——不管盗刷方怎么伪装签名请求，只要它转发出去的播放不回传埋点，比值就会暴露。而如果它为了掩护而伪造 QoE 上报，那些伪造数据会污染质量分并被 `drill_down` 的异常检测捕获（伪造的埋点很难在五维分布上与真实流量一致）。**两条路都堵住了。**

**处置必须分级，不能一刀切封禁：**

| 判定强度 | 处置 | 理由 |
|---------|------|------|
| 疑似 | 缩短签名有效期（40min → 5min） | 转发地址的价值随有效期线性下降，且对正常用户几乎无影响 |
| 较确定 | 降档位上限至 480P | 盗刷方拿到的内容价值降低，带宽损失降 78%；误判时正常用户只是画质下降 |
| 确定 | 拒绝签发 + 加入黑名单 | 需要人工复核，因为误封的代价是用户彻底无法播放 |

**"缩短有效期"是这里最被低估的手段**——它不需要确定性判断，因此可以在疑似阶段就用，而且它的成本几乎是零（多一次签发请求，签发服务是无状态的，扛得住）。**对抗类系统里，能在"疑似"阶段就动手的低成本手段，价值远高于需要"确定"才敢用的强手段。**

### 自建边缘与商业 CDN 的分工

`¥0.018/GB` 这个综合单价不是任何一家 CDN 的报价，它是一个**加权平均结果**。拆开看才能知道优化空间在哪：

| 承载方 | 流量占比 | 单价 (¥/GB) | 加权贡献 | 说明 |
|--------|---------|------------|---------|------|
| P2P 分担 | 22% | ~0.001 | 0.0002 | 只有信令与中继成本 |
| 自建边缘节点 | 31% | 0.008 | 0.0025 | 摊销后的边际成本，见下 |
| 商业 CDN A（主力） | 28% | 0.022 | 0.0062 | 量大价优，质量最好 |
| 商业 CDN B（次主力） | 14% | 0.026 | 0.0036 | 议价筹码，必须留量 |
| 商业 CDN C（长尾/溢出） | 5% | 0.038 | 0.0019 | 覆盖偏远区域与突发溢出 |
| **合计** | 100% | — | **≈0.0144** | 加上回源与协议开销后约 0.018 |

**自建边缘的 ¥0.008/GB 是怎么来的，以及它为什么不能覆盖 100%：**

```
自建节点成本 = 机架托管 + 服务器摊销 + IP 带宽（按 95 计费）+ 运维人力
关键：IP 带宽按【95 峰值】计费，而不是按流量计费

→ 自建节点的成本几乎与"跑了多少流量"无关，只与"峰值多高"有关
→ 单价 = 固定成本 / 实际流量，【流量越满，单价越低】
→ 利用率 70% 时约 ¥0.008/GB，利用率 30% 时涨到 ¥0.019/GB，
  就没有优势了
```

这直接给出了分工原则：

> **自建承载"可预测的基线"，商业 CDN 承载"不可预测的波峰"。**

自建节点必须跑在高利用率上才划算，所以它只能接**稳定可预测**的那部分流量。爆款、突发、地域性热点全部交给商业 CDN——不是因为自建扛不住，而是因为**为突发预留的自建容量在平时是空的，空着的容量把单价推高到比商业 CDN 还贵**。

这正是本仓库设计原则 3「把二元决策变成连续谱系」：不是"自建 vs 上云"，而是"基线自建 + 溢出上云"，比例由利用率经济学决定，而不由技术能力决定。

**留量给 CDN B 是议价而非技术决策。** 14% 给次主力看起来是浪费（B 比 A 贵 ¥0.004/GB，14% × 96PB × 30 天 × 0.004 ≈ ¥1,613 万/月的溢价）。但这笔钱买的是两件事：

1. **可切换性**：A 出故障时 B 已有热流量、已完成预热、配置已验证。从 0 起量的备份是不可信的备份——**没跑过流量的容灾等于没有容灾**
2. **议价权**：A 知道随时有 14% 的量可以立刻扩到 40%，续约时的报价会不一样。这部分收益不体现在带宽账单上，体现在下一份合同上

**议价权的量化：** 假设留量让 A 的续约报价低 8%（这是行业常见幅度），A 承载 28% × 96PB × 30 天 × ¥0.022 × 8% = ¥1,420 万/月。**几乎正好抵掉给 B 的溢价，而可切换性是白得的。** 这就是"多 CDN 不是为了性能，是为了议价"这句话的账。

**但比例不能无限拆分。** 每多一家 CDN 就多一套接入、监控、对账、故障演练成本，而且量分散后每家都拿不到最优阶梯价：

| CDN 家数 | 议价效果 | 边际管理成本 | 净收益 |
|---------|---------|------------|--------|
| 1 家 | 无议价权，完全被动 | 最低 | 差 |
| 2 家 | 有替代威胁，但切换风险集中 | 低 | 中 |
| **3 家** | **议价 + 双备份，量仍够拿阶梯价** | **中** | **最优** |
| 5 家以上 | 议价边际收益趋零 | 高（对账与演练成本非线性增长） | 差 |

**3 家是甜点，且第 3 家的角色和前两家不同**——它不是"第三个主力"，而是"溢出与长尾承载者"，只需要 5% 的量。它存在的意义是让前两家都知道自己不是唯一的替代方案。

### QoE 埋点与归因体系

**采集（播放器每会话上报）：**

```
play_session {
  content_id, uid, region, isp, device, app_version, quality_level,
  first_frame_ms,   // 首帧延迟
  stall_count,      // 卡顿次数
  stall_duration_ms,// 卡顿总时长
  rebuffer_events,  // 缓冲暂停次数
  avg_bitrate,      // 平均码率
  play_success,     // 是否成功起播
  cdn, p2p_ratio,   // 用的哪家 CDN、P2P 占比
}
```

**归因：** QoE 指标（首帧、卡顿率、成功率）按 `(CDN, 区域, ISP, 档位, 版本)` 五维聚合。卡顿率突增时，先看哪个维度偏移：

```
卡顿率 1.0% → 2.3%：
  1. 按 CDN 拆：厂商 B 卡顿率 4.8% vs 厂商 A 1.1% → 定位到厂商 B
  2. 按区域拆：华东 6.2% vs 华南 0.9% → 定位到厂商 B × 华东
  3. 按档位拆：1080P 5.9% vs 720P 1.2% → 该厂商华东 1080P 节点劣化
  4. 结论：厂商 B 华东 1080P 边缘节点回源异常 → 调度降低该节点权重
```

**归因闭环：** 归因结果反哺调度——某个 (CDN, 区域, 档位) 组合质量分跌破阈值，调度服务自动降低该组合权重，流量自动转移。**QoE 归因不是报表，是调度决策的输入。**

#### 上面那套下钻是错的（至少是不完备的）

那个流程是**贪心下钻**：每层挑最差的那个值往下走。它有一个致命前提——**假设指标恶化来自某个格子自身变差**。但整体指标恶化还有另一条完全不同的成因：**每个格子都没变，只是流量在格子之间重新分配了。**

这是辛普森悖论在 QoE 归因里的直接形态。看一个精确对上 1.0% → 2.3% 的例子：

| CDN | 卡顿率（前） | 流量占比（前） | 卡顿率（后） | 流量占比（后） |
|-----|------------|--------------|------------|--------------|
| A（主力，贵） | 0.9% | 97% | 0.9%（**没变**） | 66% |
| C（长尾，便宜） | 5.0% | 3% | 5.0%（**没变**） | 34% |
| **整体** | **1.02%** | 100% | **2.29%** | 100% |

```
前：0.97 × 0.9% + 0.03 × 5.0% = 1.02%
后：0.66 × 0.9% + 0.34 × 5.0% = 2.29%

没有任何一家 CDN 的质量下降了一丝。
```

贪心下钻的输出会是"CDN C 卡顿率 5%，远高于 A 的 0.9% → 降低 C 的权重"。这个结论**方向恰好正确，理由完全错误**——C 一直是 5%，它不是变差了，它是**被灌进来了更多流量**。真正要问的是：谁把 C 的占比从 3% 抬到了 34%？

答案很可能是本篇前面拆过的那个 **调度目标函数量纲 bug**：`quality_score × 0.7 + (1/cost) × 0.3` 里成本项实际占 97% 权重，于是调度器持续把量往最便宜的 C 上倒。也可能是熔断档位从 0 切到 1（成本权重升到 0.5），或者某次配置下发改了候选集。

**如果只按贪心下钻的结论"降 C 权重"处置，会发生什么：** C 的权重被压下去，量回到 A，卡顿率回落，事件关闭。**而那个量纲 bug 还在**，它会在下一次熔断、下一次候选集变更、下一次 C 降价时再次把量倒过去。归因系统每次都会指向 C，每次处置都有效，**根因永不暴露**。这是"症状级归因"最危险的地方——它足够有效，以至于没人去找根因。

#### 正确的做法：先做组内/结构分解，再决定下钻

在下钻之前，先把整体变化量拆成两部分：

```
Δ整体 = Σᵢ wᵢ_new × (rᵢ_new − rᵢ_old)      ← 组内效应（格子自己变差了）
      + Σᵢ (wᵢ_new − wᵢ_old) × rᵢ_old      ← 结构效应（流量搬家了）

代入上例：
  组内效应 = 0.66×0 + 0.34×0 = 0.00 pt        （0%）
  结构效应 = (0.66−0.97)×0.9 + (0.34−0.03)×5.0
           = −0.279 + 1.550 = +1.27 pt        （100%）
```

**结构效应占 100% → 结论是"没有任何 CDN 变差，是调度改变了流量分配"，排查方向从 CDN 厂商转向调度器与配置变更。** 这和贪心下钻给出的方向完全不同。

```python
def attribute(old: dict, new: dict) -> dict:
    """把整体指标变化分解为组内效应与结构效应。
    old/new: {维度组合: (指标值, 流量权重)}，权重各自归一化到 1。

    这一步必须在下钻【之前】做。顺序反了就会把结构问题
    误判成质量问题 —— 两者的处置完全不同：
      组内效应大 → 找那个格子的技术故障
      结构效应大 → 找是谁改了流量分配（调度/熔断/发版/候选集）
    """
    keys = set(old) | set(new)
    within = between = 0.0
    contrib = {}
    for k in keys:
        r_old, w_old = old.get(k, (0.0, 0.0))
        r_new, w_new = new.get(k, (0.0, 0.0))
        # 新出现的格子（w_old=0）全部计入结构效应：
        # 它没有"变差"可言，它的存在本身就是结构变化
        within_k = w_new * (r_new - r_old)
        between_k = (w_new - w_old) * r_old
        within += within_k
        between += between_k
        contrib[k] = (round(within_k, 4), round(between_k, 4))

    total = within + between
    return {
        'delta_total': round(total, 4),
        'within_effect': round(within, 4),
        'between_effect': round(between, 4),
        # 占比是给人看的判据：谁占主导决定排查方向
        'within_share': round(within / total, 3) if total else 0.0,
        # 按【绝对贡献】排序，而不是按指标值排序 ——
        # 贪心下钻的错误就在于按指标值排序
        'top_contributors': sorted(
            contrib.items(),
            key=lambda kv: -abs(kv[1][0] + kv[1][1]))[:10],
    }
```

**关键是 `top_contributors` 按【贡献量】排序而不是按【指标值】排序。** 一个卡顿率 40% 但只占 0.01% 流量的格子，对整体的贡献是 0.004 pt，不值得半夜叫人起来；一个卡顿率 2.5% 占 30% 流量的格子贡献 0.75 pt，才是主因。**贪心下钻按指标值排序，系统性地把注意力引向小流量的极端格子**——那些格子往往是偏远区域的少量弱网用户，指标常年很差，年年被归因，年年无法处置。

#### 自动下钻：把五维笛卡尔积交给机器

五个维度（CDN 5 × 区域 8 × ISP 4 × 档位 5 × 版本 ~20）的组合数是 16,000 量级，人工下钻只能看前两三层。而故障常常发生在**深层组合**上——`(厂商B, 华东, 移动, 1080P, v8.2.1)` 这一格坏了，前三层的边际聚合可能都被健康流量稀释到看不出来。

```
自动下钻（每分钟一轮）：
  1. 对全部有效格子（样本量 ≥ 30）算质量分 → QoeRegistry.drill_down()
  2. 对上一个窗口做 attribute() 分解，取 top_contributors
  3. 对每个候选格子，检查它的"兄弟格子"是否正常：
       固定其余四维，只变一维 → 该维的其他值是否也差？
       · 只有这一个值差   → 根因在这一维（如某厂商某节点）
       · 该维所有值都差   → 根因在其余四维的组合上，继续上钻
  4. 输出最小充分描述：能解释 top contributor 的最短维度组合
```

**第 3 步的"兄弟检查"是把下钻从"贪心"变成"可证伪"的关键。** 贪心下钻只往下走，从不回头验证；兄弟检查在每一步都问"如果根因真在这一维，那这一维的其他取值应该是好的吗？"，答案不符就说明这一步走错了。

**最小充分描述是给值班人的核心产出。** 不是"这 47 个格子有问题"，而是"`厂商B × 华东` 可以解释 89% 的恶化，其中 1080P 档贡献最大"——前者需要人再花 20 分钟判断，后者可以直接处置。

### 带宽成本熔断与容量预留

承接 P00 的带宽成本熔断三档，这是域 7 的**成本治理开关**：

```
档位0 正常     : 全档位可选，默认 1080P，预加载 3 片
档位1 温和降级 : 默认档位降至 720P，预加载 2 片，关闭 4K
                → 省 32% 带宽，用户几乎无感（QoE 降 0.4%）
档位2 强力降级 : 默认 480P，预加载 1 片，非会员禁 1080P+，P2P 强制开启
                → 省 58% 带宽，用户可感知（QoE 降 4.2%，投诉率 +0.8%）
```

**关键设计：熔断必须是一键、分档、可量化影响的运营开关**，不是工程师临时改配置。三个档位在架构上的体现：

- 档位由**下发配置**（客户端从 HTTPDNS 同步）传播，秒级生效，不需要发版
- ABR 目标缓冲水位、P2P 策略、非会员清晰度上限都随档位联动
- 每个档位的影响（省多少带宽、QoE 降多少）提前算好，值班总监一键切换

**容量预留：** 峰值 26.7 Tbps 需要各 CDN 合约保障（包量 + 弹性）。合约策略：商业 CDN 合约只签"均值 + 50% 弹性"，突发部分走自建边缘与 P2P——**不为峰值付全价，是议价的核心技巧**。

### 数据库设计

域 7 的表设计有一个必须先讲清的前提：**64.8 万 QPS 的播放地址签发链路，一次也不碰数据库。**

```
数据面（64.8 万 QPS）：
  PlaybackService.grant() 的三个输入
    variants           ← 本地缓存（媒资域推送，秒级更新）
    endpoints          ← 本地缓存（质量分来自 Redis，10s 拉一次）
    manifest_templates ← 配置下发（分钟级）
  → 纯计算 + HMAC 签名，无 IO

控制面（QPS < 千级）：
  质量分聚合、权重调整、熔断档位切换、预热任务、合约对账
  → 这些才是本节要建的表
```

**如果本节任何一张表出现在了签发路径上，说明设计错了。** 这不是性能洁癖：签发服务是播放的**唯一必经点**，它的可用性上限就是播放的可用性上限。让它依赖数据库，就是把 MySQL 的可用性变成播放的可用性——而带宽账单不会因为数据库挂了就停止计费，用户流失也不会。

还有一个反直觉的划分：**实时质量分不入 MySQL。** `CdnEndpoint.quality_score` 每 10 秒更新，写 MySQL 是纯粹的浪费；它活在 Redis 里，MySQL 只存**分钟级快照**（供事后归因与合约举证）。区分标准是"这个数据是决策依据还是审计证据"——决策依据要快，审计证据要持久，两者的存储选型天然不同。

```
160 亿行/日 × 约 200 字节 = 3.2 TB/日 原始数据
MySQL 存这个量级需要数百张分表，且分析型查询（五维聚合下钻）
是全表扫描模式，InnoDB 的行存布局完全不适合

→ ClickHouse，按 (bucket_minute, cdn, region, isp) 排序键
→ 明细保留 14 天，分钟级聚合结果回写 MySQL 的
  cdn_endpoint_quality 保留 13 个月
→ 五维聚合查询在秒级返回
```

**为什么明细只留 14 天而聚合留 13 个月：** 明细的用途是**故障排查**——排查窗口从来不超过两周，两周前的单会话明细没有人会看。聚合的用途是**合约举证与趋势对比**，需要跨年同比，且必须覆盖完整合约周期。**两种用途的保留期差 28 倍，混在一起存会让成本按最长的那个算，而数据量按最大的那个算。**

这个划分还有一层：**明细数据的采样。** 160 亿会话全量上报，埋点上行本身就是 3.2 TB/日的成本。做**分层采样**：

| 会话类型 | 占比 | 采样率 | 理由 |
|---------|------|-------|------|
| 起播失败（1 − 99.7%） | 0.3% | 100% | 异常样本是排查的全部价值所在，一条都不能丢 |
| 卡顿 ≥ 1 次 | ~1.0% | 100% | 同上 |
| 新版本客户端（灰度期） | ~0.7% | 100% | 灰度期需要高灵敏度，且量本来就小 |
| 正常会话 | ~98% | 1% | 只用于算分母（成功率、占比），1% 的统计精度足够 |

```
上报量 = 3.2 TB × (2% × 100% + 98% × 1%) ≈ 96 GB/日   （降到 1/33）
ClickHouse 列存 + ZSTD 压缩后 ≈ 10 GB/日
14 天明细存量 ≈ 140 GB —— 完全可以放在单集群里全内存化查询
```

**异常样本一条不少，而存储与上行都降到 3%。** 这个不对称是可能的，正是因为 QoE 分析里 98% 的样本只用来当分母，而分母不需要精确到每一条。

**但采样率必须随会话一起上报。** 这是采样系统最常见的错误：采了样但没记采样率，事后所有比率型指标都算错——而且错得看不出来。假设正常会话按 1% 采、异常会话全采，不还原权重直接算卡顿率：

```
错误算法：卡顿会话数 / 总会话数
        = 1.0% × 100%  /  (1.0% × 100% + 98% × 1% + ...)
        = 0.010 / 0.0298 = 33.6%     ← 真实值是 1.0%
```

**算出来的 33.6% 仍然是一个"看着像卡顿率"的数字**，只是错了 33 倍。如果这个数进了告警阈值或者质量分，它会稳定地错，没有任何异常可以被察觉。所以每条上报必须自带 `sample_rate`，聚合时按 `1/sample_rate` 加权还原。

## 常见陷阱（深度分析）

### 陷阱 1：用 CNAME 把调度权交给 CDN 厂商

**后果：** 域名解析权在厂商手里，切流只能等厂商配合（分钟级变小时级）；无法按区域/质量/成本精细分配；厂商故障时"切走"要等厂商自己恢复或电话协调。**多 CDN 的唯一收益被 CNAME 交回给了单厂商。**

**为什么这个陷阱如此普遍：** 因为 CNAME 接入是**厂商推荐的、文档写得最全的、上线最快的**方式。改一条 DNS 记录，半小时接入完成，看起来完美。自建 HTTPDNS 要写客户端 SDK、建解析集群、处理首次启动没有缓存的冷启动问题、还要自己扛 DDoS——三个月的活。**在项目早期，谁都会选 CNAME，而选择的代价要到第一次厂商故障时才付。**

**代价的量化：**

| 能力 | CNAME 接入 | 自建 HTTPDNS |
|------|-----------|-------------|
| 切流生效时间 | DNS TTL（60~300s）+ 递归缓存不遵守 TTL 的长尾（最坏数小时） | 秒级（下次播放请求即生效） |
| 切流粒度 | 域名级（全国一起切） | (区域, ISP, 版本, 用户分组) 任意组合 |
| 灰度能力 | 无 | 按 uid 哈希做 1% 灰度 |
| 故障时的自主性 | 需厂商配合改解析 | 完全自主 |
| 单用户多地址 | 不可能（DNS 一次只返回一组） | 主 + 2 备一次下发 |

**"递归缓存不遵守 TTL"是最容易被低估的一项。** 把 TTL 设成 60s 不代表 60s 后全网都切走了——运营商递归 DNS 普遍会拉长 TTL（有的强制最小 600s），部分家用路由器缓存到重启为止。**故障时你会看到"90% 的流量切走了，剩下 10% 怎么都切不走"，而那 10% 正在持续失败。** 这 10% 里往往集中在某几个 ISP 的某几个地市，投诉会集中爆发。

**解决方案：** 自建 HTTPDNS + 客户端多地址下发 + 调度决策服务三件套，调度权 100% 在自己手里。

**但自建 HTTPDNS 本身引入了一个新的单点**——它挂了就全局无法解析（见后文异常场景）。所以三件套必须是四件套：

```
① 自建 HTTPDNS（主路径）
② 客户端本地缓存上次结果（HTTPDNS 短暂不可用时兜底）
③ 兜底静态 CNAME 域名（HTTPDNS 长时间不可用时降级，牺牲调度能力保可用）
④ 客户端内置的 IP 直连列表（连 DNS 都不可用时的最后一层，随发版更新）
```

**④ 这一层是最容易被砍掉的，也是最关键的。** 它的代价是"IP 变更要等发版"，收益是"在 DNS 体系整体失效时仍能播放"。判断要不要做，看的不是概率而是后果：DNS 整体失效的概率极低，但后果是**播放成功率归零**，没有任何其他手段可以补救。

**判据：任何 CDN 厂商明天涨价 30%，你能不能今天切走 80%？不能，就是调度权不在自己手里。** 更严格的版本：**你能不能只切华东移动的 1080P 用户？** 能做到这个粒度，调度权才算真正在手。

### 陷阱 2：只看 QoE 不看带宽，预加载无脑做

**后果：** 预加载从 1 片做到 3 片、全片预热、起播拉满缓冲。QoE 从 98% 提到 98.3%，带宽账单 +30%。**对一个 73% 成本在带宽的平台，用 3000 万/月换 0.3% 的体验提升是负收益决策。**

**这个陷阱的成因是组织性的，不是技术性的。** 播放器团队的 OKR 是 QoE 指标，带宽账单不在他们的考核里；成本团队看得到账单，但看不到是哪个功能造成的。**两边都在正确地优化自己的目标，合起来是负收益。**

```
播放器团队视角：
  预加载 1 片 → 3 片，起播成功率 +0.4%，卡顿率 −0.2%
  → 这是一次成功的优化，写进季度总结

成本团队视角：
  本月带宽超预算 12%，环比 +30%
  → 排查方向：是不是 DAU 涨了？是不是 CDN 涨价了？
  → 很难想到是"播放器改了一个缓冲参数"
```

**归因困难是核心问题**：带宽账单是一个总数，看不出增量来自哪个功能。所以必须有**带宽的功能级归因**：

```
在播放请求上打功能标记（不是打在埋点上，要打在【请求】上）：
  X-Fetch-Reason: playback | preload | prefetch_next | prewarm | abr_switch

CDN 日志按此维度聚合 → 每个功能的带宽账单单独可见
→ "预加载"这一项从 8% 涨到 24%，一眼就能看到

代价：CDN 日志字段增加，需要厂商配合（大部分厂商支持自定义日志字段）
```

**这个标记必须打在请求上而不是埋点上**，因为埋点是采样的、可能丢失的、且只覆盖有播放器的场景；而 CDN 日志是全量的、与计费同源的。**唯一能和账单对上的归因，必须来自和账单同源的数据。**

**解决方案：** 烧钱的手段一律配预算上限（预加载 ≤ 1 片、预热仅首 3 分片），并且**每个手段的带宽占比进月度评审**。

**判据：每个带宽烧钱项都要能回答"每多花 1 万元带宽，换来多少 QoE 提升"，答不上来的不做了。** 更实操的判据：**打开 CDN 账单，能不能按功能拆出每一项的金额？** 不能，就没有能力发现这个陷阱，只能等超预算。

### 陷阱 3：ABR 只看吞吐不看缓冲水位

**后果：** 吞吐估计受网络抖动影响大（一个慢分片就让估计暴跌），播放器频繁降码率，画质上下跳，用户感知明显。或反过来，吞吐虚高导致缓冲水位见底才降档，卡顿已经发生。

**为什么纯吞吐判据必然抖动：** 吞吐估计是**除法**，分母是下载耗时。一个 250KB 的分片正常 300ms 下完（6.7 Mbps），偶发 TCP 重传变成 900ms（2.2 Mbps）——估计值瞬间掉 3 倍，而实际网络容量没变。

```
纯吞吐判据的行为：
  分片1 6.7 Mbps → 保持 1080P
  分片2 2.2 Mbps → 降到 720P（误判）
  分片3 6.5 Mbps → 升回 1080P
  分片4 2.4 Mbps → 又降 720P
  → 每 2s 一次画质切换，比卡顿更让人烦躁

而缓冲水位在这四个分片里始终 > 8s，从未有过卡顿风险
```

**水位是积分，吞吐是微分。** 水位天然平滑了单分片的噪声——一个慢分片只让水位从 10s 掉到 8s，触发不了任何决策。这是"用状态量而非速率量做控制判据"的一般原则：**状态量自带积分平滑，速率量自带微分放大。**

**但纯水位判据也不行**，因为它是**滞后**的：水位下降说明问题已经发生了。正确的组合是：

| 判据 | 角色 | 类比 |
|------|------|------|
| 缓冲水位 | 主判据，决定**是否**动作 | 位置反馈（P 项） |
| 吞吐趋势 | 辅判据，决定**动作幅度**与提前量 | 速度反馈（D 项） |

也就是一个 PD 控制器：水位低了要降档（P），水位还够但下降很快也要提前降（D）。**规则 3（`throughput < 当前码率 × 1.2 持续 10s → 降档`）就是 D 项**，它的"持续 10s"就是对吞吐噪声的低通滤波——单次抖动进不来，趋势性下降才进来。

**升档必须比降档保守得多（非对称阈值）：** 降档阈值 2s 水位，升档阈值 8s 水位，中间 6s 是**死区**。没有死区就会在阈值附近反复振荡（降档→水位回升→升档→水位下降→降档），这是控制系统里最经典的抖动来源。

**解决方案：** 吞吐 + 缓冲水位双判据，降档以缓冲水位为主要触发（水位 < 2s 即降），吞吐只作为趋势参考，升降档阈值之间留足死区。**判据：卡顿治理的目标是"在卡顿发生前降码率"，不是"卡顿发生后补救"。** 补充判据：**同一会话内的档位切换次数应当有上限（如 5 次/分钟）**——超了说明 ABR 在振荡，此时应当锁档而不是继续切。

### 陷阱 4：P2P 全量强制开启

**后果：** 弱网用户从 P2P 拉分片比 CDN 还慢，卡顿率上升；首发内容没有缓存源，P2P 命中率接近 0，白白增加复杂度；用户上行被大量占用，卸载率上升。

**"P2P 命中率接近 0"这件事的代价比想象的大**，因为它不是"没省到钱"，而是"倒赔"：

```
每次 P2P 尝试失败的成本：
  ① 200ms 的额外延迟（串行探测，不能对冲）
  ② 已传的部分字节白费（峰值上行 0.36 Mbps × 0.2s ≈ 9 KB）
  ③ 信令交换的流量与服务端 tracker 的 QPS
  ④ 客户端电量与后台唤醒（iOS 上会被系统限制，进一步降低成功率）

首发内容全量开 P2P：
  命中率 ≈ 2%（几乎没人持有分片）
  → 98% 的请求都付了上面四项成本，一点收益没有
  → 起播延迟系统性 +196ms（0.98 × 200ms）
  → 首发内容恰恰是最需要好体验的内容（创作者在看数据、推荐在评估冷启动）
```

**最讽刺的地方在于：P2P 在最需要它省钱的场景（爆款）里效果最好，在最需要好体验的场景（首发）里效果最差，而这两个场景在时间上是紧挨着的**——首发 24 小时后如果爆了，就变成 P2P 的最佳场景。所以开关必须是**动态的、按内容生命周期驱动的**，不能是内容级的静态配置。

**弱网上的放大效应：** 弱网用户的 RTT 本来就高（200~500ms），P2P 打洞需要 2~3 个 RTT，探测超时的 200ms 预算根本不够，命中率趋近 0；同时弱网用户的水位本来就紧张，多 200ms 就可能直接触发卡顿。**弱网用户承担了 P2P 的全部成本，拿到零收益，还额外多了卡顿。**

**解决方案：** P2P 按"内容热度 × 网络质量 × 内容新鲜度 × 缓冲水位"四维精细开关，弱网/首发/冷门/低水位一律关，CDN 永远是兜底。**判据：P2P 的每一次使用都要比"直接走 CDN"更快、更省，否则关掉。** 可执行的版本：**监控 P2P 的"尝试成功率"而不是"分担率"**——分担率高可能只是因为尝试次数多，尝试成功率才反映每次尝试是否值得。低于 40% 就该收紧准入条件。

### 陷阱 5：播放失败没有分档重试

**后果：** 播放失败直接弹错误页，用户流失。边缘节点故障、CDN 区域抖动、P2P 源失效这些"可恢复"的失败都被当成"真失败"处理。

**解决方案：** 播放失败分档处理——① 备用地址秒切（backup_urls）；② 备用地址也失败则切厂商（换 CDN）；③ 换厂商失败则降档重试（换码率）；④ 全部失败才弹错误页并上报。**每层重试都在毫秒级，用户感知的只是"好像顿了一下"。**

**但分档重试有一个必须先解决的前提：重试放大。** 这一层做错会让局部故障升级成全局故障：

```
CDN 厂商 A 华东故障，占该区域 40% 流量
该区域峰值播放 QPS 假设 8 万

无节制重试：
  8万 × 40% = 3.2万 QPS 失败
  每个失败按 ① → ② → ③ 重试 3 次
  → 厂商 B/C + 自建边缘要瞬间承接 3.2万 × 3 = 9.6万 QPS
  → 而它们的常态容量只按 60% 流量（4.8万 QPS）+ 余量配置
  → B/C 也被打挂 → 全区域失败 → 重试再翻倍
  → 亚稳态失效（metastable failure）：故障源已恢复，系统仍然起不来
```

**关键认识：重试是在故障时才启用的功能，而故障时恰恰是容量最紧张的时刻。** "平时不用、故障才用"的逻辑天然缺少压力验证，且它的负载模式与常态完全不同。

三条必须的约束：

| 约束 | 具体做法 | 为什么 |
|------|---------|--------|
| 重试预算 | 全局重试 QPS ≤ 正常 QPS 的 10%，超了直接放弃重试 | 把重试的最坏影响限制成 +10% 而不是 +200% |
| 逐层退避 | ① 立即，② +50ms 抖动，③ +200ms 抖动 | 避免所有失败客户端同时打到备用节点（惊群） |
| 熔断 | 某目标连续失败率 > 50% 时，直接跳过该层不重试 | 已知会失败的重试是纯粹的伤害 |

**"超了直接放弃重试"这条最反直觉但最重要。** 直觉是"故障时更应该努力重试"，但事实相反：**故障时的重试是零和的**——你重试挤占的容量正是别人成功所需的容量。全局重试预算把"每个客户端各自尽力"变成"整体上有多少容量可以用于重试"，这是从局部最优转向全局最优。

**判据：模拟一家 CDN 全挂，重试放大后的总 QPS 是常态的多少倍？** 超过 1.2 倍就是危险的。

### 陷阱 6：QoE 埋点无归因

**后果：** 卡顿率突增，五个团队（CDN 对接、编码、播放器、网络、P2P）互相甩锅，问题在线持续烧带宽烧用户。归因靠人工查日志，定位以小时计。

**但"有了五维聚合"不等于"有了归因"。** 这是本篇 QoE 一节展开讲的：贪心下钻会在流量结构变化时给出**方向可能正确但根因完全错误**的结论，而且因为处置有效，根因永远不会暴露。一个只做贪心下钻的归因系统，会稳定地把所有问题归到"某个 CDN 质量差"，因为**流量总会流向便宜且质量稍差的那家**，它永远是那个"最差的格子"。

**三个层次的归因能力，只有第三层算达标：**

| 层次 | 能回答 | 不能回答 |
|------|-------|---------|
| 一维聚合 | "整体卡顿率涨了" | 涨在哪 |
| 贪心下钻 | "厂商 B 华东 1080P 最差" | 是它变差了，还是流量搬过去了 |
| **分解 + 兄弟检查** | **"结构效应占 100%，是调度改变了分配"** | — |

**解决方案：** QoE 埋点按 (CDN, 区域, ISP, 档位, 版本) 五维聚合 + **组内/结构效应分解** + 自动下钻 + 归因结果反哺调度。

**判据：卡顿率突增时，能否 5 分钟内定位到"哪个 CDN × 哪个区域 × 哪个档位"？不能，归因体系不达标。** 更强的判据：**能否区分"某节点劣化"与"流量搬家"？** 区分不了，就会把配置问题反复误判成厂商问题。

### 陷阱 7：预热全片全档位

**后果：** 一条长视频 12GB × 6 档 = 72GB 推到所有边缘，而 95% 观众只看前 3 分钟。冷门内容全片预热等于为不会发生的播放预付带宽与边缘存储。

**放大效应：预热的成本是三个维度的乘积。**

```
预热成本 = 内容体积 × 档位数 × 目标区域数

全片全档位全区域：12GB × 6 档 × 8 区域 = 576 GB / 条
首 3 片单档位全区域：0.75MB × 1 × 8 = 6 MB / 条
                    （3 片 × 2s × 1.5Mbps ÷ 8 = 1.1MB，取 720P 约 0.75MB）

比例 ≈ 96,000 : 1
```

**九万六千倍。** 这不是"优化了一点"，这是两个完全不同量级的方案。而它们在功能上的差别只是"第 4 分钟之后的分片要不要回源一次"。

**更隐蔽的成本是边缘存储的挤出效应。** 边缘节点的磁盘是固定的，预热进去的字节会**驱逐别的内容**：

```
边缘节点 SSD 假设 20 TB
全片预热 100 条长视频 = 57.6 TB > 20 TB
→ 塞不进去，LRU 开始驱逐【正在被播放的热门内容】
→ 热门内容命中率下降 → 回源率上升 → 带宽成本上升
→ 预热的初衷是降低回源，结果是提高了回源
```

**这是本篇里第二次出现"手段与目标反转"**（第一次是 P2P 中继超配额）。共同结构是：一个手段在小剂量下有效，在大剂量下符号翻转。**凡是"越多越好"的直觉，都要找一下它的翻转点在哪。**

**解决方案：** 预热只做"首 3 分片 + 单一档位 + 预测热区"，后续靠边缘回源。并且**必须有效果反馈**——`edge_prewarm_task.hit_rate_after` 这一列的作用就是让"预热了但命中率没提升"的任务可见。

**判据：预热的字节数必须正比于"该内容前 3 分钟的实际播放量"，而不是内容总时长。** 补充判据：**预热任务有没有失败/无效的统计？** 没有，说明预热是"发射后不管"，无法收敛。

### 陷阱 8：为峰值带宽付全价

**后果：** 按峰值 26.7 Tbps 跟 CDN 签包量合约，一年大部分时间流量在均值 8.9 Tbps 附近，包量利用率只有 33%，多付的钱全变成 CDN 厂商的利润。

**先看这笔钱有多大：**

```
按峰值签：26.7 Tbps 全年 ≈ 96 PB/日 × 3（峰均比）的容量
按均值+50% 签：8.9 × 1.5 = 13.35 Tbps

差额 = 26.7 − 13.35 = 13.35 Tbps 的冗余容量
若按 ¥0.022/GB 折算相应流量成本，年化差额在【十亿量级】
```

**但"不为峰值付全价"不是无代价的**，它把峰值风险转移给了自建边缘与 P2P。所以这个决策的前提是那两者真的接得住：

| 承接方 | 峰值时的可用容量 | 风险 |
|--------|---------------|------|
| P2P | 随并发线性增长，峰值时供给最足 | 全局同时失效（见场景 3） |
| 自建边缘 | 固定容量，按 95 计费，峰值可短时超卖 | 超卖时间受 95 计费规则约束 |
| 商业 CDN 弹性 | 合约弹性 50% | 超出后按惩罚价，比包量贵 2~3 倍 |

**"95 计费下可以短时超卖"是自建边缘最重要的经济性质，也最容易用错。** 95 计费的含义是"去掉 5% 的最高采样点后取峰值"，一个月约 8,640 个 5 分钟采样点，5% = 432 个点 = **36 小时**。也就是说每月有 36 小时可以任意超卖而不影响账单。

```
用对了：把 36 小时的免费额度用在【真正的突发】上
        （爆款、赛事、节假日晚高峰）

用错了：日常晚高峰每天超 2 小时 → 30 天 × 2 = 60 小时 > 36 小时
        → 超出的 24 小时进入 95 计费统计
        → 峰值带宽被抬高，账单按抬高后的峰值算
        → 而"日常晚高峰"是【可预测的】，本该用容量覆盖而不是用超卖额度覆盖
```

**结论：95 的免费额度是给不可预测的突发准备的战略储备，不是日常运营的常规手段。** 必须监控"本月已使用的超卖小时数"，超过 24 小时（2/3 额度）就该告警——因为剩下的 12 小时要留给真正的意外。

**解决方案：** 合约只签"均值 + 50% 弹性"，突发部分走自建边缘与 P2P，并把 95 超卖额度当作有限资源管理。**判据：包量合约的上限应接近"均值 × 1.5"，超过的部分由自建/P2P 消化，不为 3 倍峰值付费。** 补充判据：**本月 95 超卖额度用了多少？** 答不上来，说明自建边缘的经济性没有被真正管理。

### 陷阱 9：调度目标函数的量纲不统一

**后果：** `quality_score × 0.7 + (1/cost_per_gb) × 0.3` 这一行看起来是"质量七成、成本三成"，实际是"成本九成七"。因为 `quality_score ∈ [0,1]` 而 `1/cost ≈ 35~83`，两项差两个数量级，**权重系数完全不生效**。

```
CDN A：quality 0.95, cost 0.022 → 0.95×0.7 + 45.5×0.3 = 14.3
CDN C：quality 0.60, cost 0.012 → 0.60×0.7 + 83.3×0.3 = 25.4
                                        ↑ 质量项贡献 2.4%

→ 调度器【永远】选最便宜的那家，与质量分无关
```

**这个 bug 最恶劣的性质是它的失效时机：** 平时最便宜的那家质量通常也还行（否则早被淘汰了），调度看起来正常工作。**只有当便宜的那家出故障时——也就是最需要调度躲开它的时刻——bug 才显现，而且显现为"调度器把全部流量灌进故障节点"。** 系统在最需要它的那一刻，行为与预期完全相反。

**它还会伪装成别的问题：** 因为流量持续偏向便宜且质量稍差的一家，整体卡顿率会缓慢上升，而归因系统（如果只做贪心下钻）会稳定报告"CDN C 质量差"。**运维每次都降 C 的权重，每次都有效，根因永不暴露**——这就是陷阱 6 里说的症状级归因。**两个 bug 互相掩护。**

**解决方案：** 归一化后再加权。归一化基准取**候选集内**极值：

```python
span = cost_max - cost_min
cost_score = 0.5 if span < 1e-9 else (cost_max - e.cost_per_gb) / span
score = e.quality_score * w_quality + cost_score * w_cost
```

**为什么取候选集内极值而不是全局固定基准：** 成本项应当衡量"在可选范围内相对便宜多少"，而不是"绝对单价多少"。全网单价整体下降 20% 时，调度行为不应该改变——用固定基准会让所有节点的成本分一起上升，相当于悄悄提高了成本权重。

**同价时给 0.5 而不是 0 或 1**：全部同价意味着成本项不提供任何区分度，此时应当让质量项独自决定排序。给 0 或 1 都会给所有候选加上一个相同的常数，不影响排序但会让分数的绝对值失去意义（进而让"分数跌破阈值"这类判据失效）。

**判据：把目标函数里每一项的取值范围写出来，是不是都在同一量纲？** 更实操的：**给一组极端输入（最贵但完美 vs 最便宜但很差），手算一遍，结果符合预期吗？** 这个 bug 只需要两组输入就能测出来，但需要有人想到去测。

### 陷阱 10：忽略 OTT/大屏端的带宽权重

**后果：** OTT（电视盒子、智能电视）只占播放次数的约 10%，于是被当成边缘场景处理——用手机端的默认策略、共用手机端的调度权重、QoE 归因里不单独拆维度。**而它的带宽占比远高于 10%。**

```
手机端：均码率 1.5 Mbps，均播 32s
OTT：  均码率 8 Mbps（4K/1080P 为主），均播 25 分钟

单次播放字节数比 = (8/1.5) × (1500/32) = 5.3 × 46.9 = 250 倍

带宽占比 = 10% × 250 / (10% × 250 + 90% × 1) = 25 / 25.9 ≈ 96.5%
```

**这个算法夸大了**（真实平台的 OTT 长视频与手机短视频并非同一内容池，且手机端也有长视频），但方向是对的：**按次数占 10% 的端，按字节可能占一半以上。** 一个针对手机端优化的带宽策略，可能对总账单的影响不到一半。

**具体的错误后果：**

| 错误做法 | 为什么在 OTT 上更糟 |
|---------|-------------------|
| 预加载深度用手机端配置 | OTT 单片是手机的 5.3 倍大，同样"预加载 1 片"的字节代价高 5.3 倍 |
| 熔断降档策略照搬 | 大屏上 480P 是不可接受的（观看距离近似，屏幕大 20 倍），熔断在 OTT 上必须用不同的档位阶梯 |
| P2P 策略照搬 | OTT 设备常年在线、有线网络、上行稳定——**它是最好的 P2P 种子**，当成手机处理浪费了最优质的供给 |
| QoE 归因不拆端 | OTT 的首帧预算完全不同（遥控器操作，用户预期更宽容），混在一起算 P95 会同时误判两端 |

**"OTT 是最好的 P2P 种子"这一点是纯收益，且经常被漏掉。** 电视盒子插电常开、接有线网、存储空间大、没有电量顾虑、没有 iOS 后台限制——把它作为区域内的半永久缓存节点，实际上是**免费的边缘节点**。这需要把 P2P 策略从"对等互传"扩展为"分层：OTT 做超级节点，手机做叶子"，收益远超把它当普通 peer。

**解决方案：** 端类型（mobile / OTT / PC / Web）必须是调度与 QoE 归因的**第六个维度**，且每个维度值有独立的策略配置（预加载深度、档位阶梯、熔断映射、P2P 角色）。

**判据：把带宽账单按端类型拆开，各占多少？** 如果拆不出来，就无法知道优化到底作用在哪一半上。补充判据：**熔断档位 2 在 OTT 上的具体档位是什么？** 如果答案和手机一样，说明端维度没有真正落地。

## 异常场景完整演练

### 场景 1：CDN 厂商区域故障

**场景描述：** 傍晚高峰，CDN 厂商 A 的华东节点突发故障，华东卡顿率从 1.0% 飙升到 12%，播放成功率从 99.6% 跌到 82%。厂商 A 占华东流量的 40%。

**错误做法：** 等厂商 A 自己恢复（"他们正在处理"）。恢复时间不可控（历史故障 20-90 分钟），期间华东用户持续流失。

**第二种错误做法（更常见，也更危险）：把厂商 A 华东权重一把降到 0。**

```
华东峰值播放 QPS 假设 8 万，厂商 A 占 40% = 3.2 万 QPS
厂商 B/C + 自建边缘常态承接 4.8 万 QPS

权重一把降到 0：
  3.2 万 QPS 瞬间转移 → B/C/自建 要承接 8 万 QPS（+67%）
  而它们的边缘缓存里【没有这部分内容】
  → 回源率从 8% 飙到 60%+（本来在 A 上的热内容，B/C 没缓存）
  → 回源带宽 × 7.5，中心出口被打满
  → B/C 也开始超时 → 全区域失败

叠加陷阱 5 的重试放大，这就是一次典型的亚稳态失效：
厂商 A 20 分钟后恢复了，系统仍然起不来
```

**"切走"这个动作本身会制造第二次故障，而且这次故障是自己造成的。** 关键原因是**缓存亲和性**：流量切到新厂商时，新厂商的边缘是冷的，回源放大数倍。这一点在"多 CDN 容灾"的设计文档里几乎从不被提及，因为它只在真实切流时出现。

**正确做法：**

```
1. 检测：QoE 归因发现 (厂商A, 华东) 组合质量分跌破阈值 → 自动告警
   · 判据用【组内效应】而非绝对值（见 attribute()）：
     确认是 A 自己变差，而不是流量搬到 A 导致的统计偏移
   · 同时检查 A 在其他区域是否正常 → 区分"区域故障"与"厂商级故障"

2. 分档切流（不是一把切走）：
   40% → 25% → 12% → 0%，每档间隔 90s
   每档切换前检查承接方的容量水位与回源率：
     · 承接方 CPU / 带宽利用率 < 75%
     · 承接方回源率 < 25%
     · 承接方 P95 首帧未劣化超过 20%
   任一条不满足 → 暂停降档，等待边缘预热
   （分档的意义就是给新厂商的边缘缓存留出预热时间）

3. 并行预热：切流的同时向 B/C 推送华东 TOP 1000 内容的首 3 片
   —— 这是"边缘预热"能力在容灾场景下的第二个用途，
   平时用来降首帧，故障时用来降回源

4. 兜底：播放失败的存量会话走 backup_urls 秒切备用地址
   （backup_urls 已经是跨厂商的，见 grant() 的去重逻辑）

5. 验证：15 分钟后华东流量 90% 已切走，卡顿率回到 1.2%

6. 事后：要求厂商 A 提交故障报告；复盘每档切换的容量判断是否准确
```

**检测与切流控制的实现：**

```python
class CdnFailoverController:
    """CDN 故障切流控制器。
    核心职责不是"切走"，而是"切走而不打挂承接方"。

    这个类存在的全部理由是：切流的瞬时冲击本身就是一次故障源。
    """

    # 分档序列：当前权重 → 下一档。间隔 90s 给边缘预热留时间
    LADDER = [0.40, 0.25, 0.12, 0.0]
    STEP_INTERVAL_SEC = 90

    # 承接方准入门槛。任一项不满足就暂停降档 ——
    # 宁可让故障厂商多承载一会儿（部分用户继续差），
    # 也不能把承接方打挂（全部用户都差）
    MAX_UTILIZATION = 0.75
    MAX_ORIGIN_RATE = 0.25
    MAX_FF_DEGRADE = 0.20

    def __init__(self, registry: QoeRegistry, weights: dict):
        self.registry = registry
        self.weights = weights          # {(cdn, region): weight}
        self._step_at: dict[tuple, float] = {}
        self._baseline_ff: dict[tuple, float] = {}

    def evaluate(self, cdn: str, region: str,
                 old_snapshot: dict, new_snapshot: dict,
                 receivers: list[EndpointHealth],
                 now: float) -> FailoverDecision:
        """每 30s 调用一次。返回"降到哪一档"或"暂停"。"""
        # ── 1. 先确认这真的是 A 自己变差 ──────────────────────
        attr = attribute(old_snapshot, new_snapshot)
        if attr['within_share'] < 0.5:
            # 结构效应主导 → 是流量搬家，不是节点劣化。
            # 此时切流是错的：切走只会让流量继续搬家，根因在调度器
            return FailoverDecision(
                action='investigate_scheduler',
                reason=f"structural {1 - attr['within_share']:.0%}")

        score = self.registry.quality_score(cdn, region)
        if score >= 0.55:
            return self._maybe_recover(cdn, region, now)

        # ── 2. 区分区域故障与厂商级故障 ────────────────────────
        # 厂商级故障不能靠"切到该厂商其他区域"解决，
        # 而且意味着 backup_urls 里同厂商的地址也不可信
        other = [self.registry.quality_score(cdn, r)
                 for r in ALL_REGIONS if r != region]
        vendor_wide = other and (sum(1 for s in other if s < 0.55)
                                 >= len(other) * 0.6)
        if vendor_wide:
            return FailoverDecision(
                action='vendor_wide_drain', target_weight=0.0,
                reason='厂商级故障，全区域摘除，且需重算 backup_urls')

        # ── 3. 分档节流 ───────────────────────────────────────
        key = (cdn, region)
        last = self._step_at.get(key, 0.0)
        if now - last < self.STEP_INTERVAL_SEC:
            return FailoverDecision(action='hold', reason='等待本档稳定')

        blocked = self._blocked_receivers(receivers)
        if blocked:
            # 承接方顶不住 —— 这是必须暴露的状态，不能静默等待。
            # 值班人需要知道"切流卡住了"，因为这意味着
            # 故障厂商上还有流量在持续失败
            return FailoverDecision(
                action='hold', reason=f'承接方受限: {blocked}',
                alert=True)

        cur = self.weights.get(key, 1.0)
        nxt = next((w for w in self.LADDER if w < cur - 1e-9), 0.0)
        self._step_at[key] = now
        return FailoverDecision(
            action='step_down', target_weight=nxt,
            prewarm=True,              # 每一档都触发一次承接方预热
            reason=f'质量分 {score:.2f}，{cur:.0%} → {nxt:.0%}')

    def _blocked_receivers(self, receivers: list[EndpointHealth]) -> list[str]:
        out = []
        for r in receivers:
            base = self._baseline_ff.setdefault(
                (r.cdn, r.region), r.p95_first_frame_ms)
            if (r.utilization > self.MAX_UTILIZATION
                    or r.origin_rate > self.MAX_ORIGIN_RATE
                    or r.p95_first_frame_ms > base * (1 + self.MAX_FF_DEGRADE)):
                out.append(f'{r.cdn}/{r.region}')
        return out

    def _maybe_recover(self, cdn: str, region: str,
                       now: float) -> FailoverDecision:
        """恢复必须比切走更慢：切走是止损，恢复是冒险。
        先给 5% 试探流量，观察 5 分钟再逐档回升。
        且【恢复不能自动全量】—— 需要人确认厂商已提交根因，
        否则"抖动型故障"会导致流量来回搬，两边缓存都是冷的
        （反复切换比停在任一边都更糟）"""
        key = (cdn, region)
        cur = self.weights.get(key, 0.0)
        if cur >= 0.40:
            return FailoverDecision(action='hold', reason='已恢复')
        if now - self._step_at.get(key, 0.0) < 300:
            return FailoverDecision(action='hold', reason='观察期')
        self._step_at[key] = now
        nxt = 0.05 if cur == 0.0 else min(0.40, cur * 2)
        return FailoverDecision(
            action='step_up', target_weight=nxt,
            reason=f'试探恢复 {cur:.0%} → {nxt:.0%}',
            require_human=(nxt >= 0.25))
```

**`_maybe_recover` 里"恢复比切走更慢"是不对称设计的关键。** 切走是止损，宁可切多了；恢复是冒险，切错了要再切一遍，而**反复切换比停在任何一边都更糟**——两边的边缘缓存都是冷的，回源率持续偏高。这也是为什么恢复到 25% 以上需要人工确认：机器无法判断"厂商是真的修好了"还是"刚好在故障的间歇期"。

**结果：** 15 分钟切走 80%+ 流量，用户感知为"短暂变慢"，无大规模流失。**这验证了"分钟级全量切换能力"不是纸面设计，是真实故障时的救命能力。** 但要注意上文推导过的口径：15 分钟切走的是 **80% 的请求**，按带宽算只有约 35%（长视频会话的存量地址仍在用旧 CDN 拉流），**带宽账单和故障影响面的收敛速度差 27 倍**。汇报时说清是哪个口径，否则会得出"已经切完了，为什么账单没降"的困惑。

### 场景 2：爆款视频打穿单点 + 带宽成本飙升

**场景描述：** 一条爆款视频 2 小时内播放冲到 5 万 QPS，且恰好撞上未预期的头部直播，单日出口流量从 96 PB 冲到 290 PB。按 ¥0.05/GB 计，单日带宽成本从 ¥4,800 万冲到 ¥1.45 亿。

**错误做法：** 技术团队自行决定"再加边缘、再多拉点 CDN"，没有成本熔断意识——**技术系统不会告诉你钱花超了，CDN 会自动承接所有流量而不会拒绝。**

**这是本篇最重要的一条认识，值得单独强调：CDN 没有"容量拒绝"这个行为。** 数据库过载会拒连、Redis 内存满会 OOM、线程池满会抛异常——所有这些都是**技术系统自带的刹车**。而 CDN 会尽职尽责地承接你给它的一切流量，账单在月底才到。

```
常规容量故障：系统先坏 → 你被迫处理
带宽成本故障：系统一切正常 → 账单月底到 → 已经无法挽回

前者的反馈延迟是秒级，后者是【30 天】
30 天的反馈延迟意味着：没有任何自动控制系统能靠反馈工作
→ 必须做【前馈】：按当前速率预测月末总额，而不是等月末结算
```

**成本必须被建成一个可观测、可熔断的技术指标**，与 CPU、内存、QPS 并列。这不是财务的事，是架构的事。

**正确做法：**

```
1. 检测：分钟级成本预测（流量 × 各厂商单价）超预算 15% → 告警
   · 关键是"预测"而不是"实际"：按当前速率外推到月末
   · 分子要用【边际成本】而不是合约单价：
     承诺量以下的流量边际成本为 0（committed_gb 那一列的用途）
   · 直播与点播分开预测：直播的突发性完全不同

2. 值班总监一键切换到档位 1（温和降级）：
   默认 720P、预加载 2 片、关闭 4K → 省 32% 带宽

3. 爆款视频单条触发"成本守卫"：强制开启 P2P + 默认档位下调
   · 单条内容的成本守卫优先于全局熔断 —— 先动一条内容，
     不要为一条爆款让全站降档

4. 直播侧开启独立容量池限流

5. 流量回落后切回档位 0（带自动恢复时间，见 cost_fuse_state）
```

**成本预测与熔断决策：**

```python
class CostGuard:
    """带宽成本前馈控制。
    与所有其他容量保护的区别：它保护的资源【没有物理上限】，
    所以没有任何技术信号会提示越界，必须靠预测。
    """

    # 触发档位的月度预算消耗阈值。注意不是"当前消耗"，
    # 是"按当前速率外推到月末的预计消耗"
    THRESHOLDS = {1: 1.15, 2: 1.35}

    def __init__(self, monthly_budget: float, contracts: dict):
        self.budget = monthly_budget
        self.contracts = contracts       # {(cdn, region): ContractTerms}

    def marginal_cost(self, cdn: str, region: str,
                      month_to_date_gb: float, extra_gb: float) -> float:
        """边际成本，不是平均成本。
        承诺量以内为 0 —— 这一点如果算错，调度会在
        "已付费但未用完"的厂商上省流量，把量切到按量计费的厂商，
        钱花得更多而账面上"优化了"
        """
        c = self.contracts[(cdn, region)]
        if c.billing_mode == BillingMode.BY_95_PEAK:
            # 95 计费下，不打破当前 95 峰值的流量边际成本为 0。
            # 这是"削峰比省量更重要"的根源
            return 0.0 if not c.would_raise_p95(extra_gb) else \
                c.p95_marginal(extra_gb)
        used = month_to_date_gb
        remaining_committed = max(0.0, c.committed_gb - used)
        billable = max(0.0, extra_gb - remaining_committed)
        return billable * c.overage_price

    def project_month_end(self, mtd_cost: float, mtd_hours: float,
                          hours_in_month: float,
                          recent_hourly_rate: float) -> float:
        """月末预测。用【最近速率】外推剩余时间，而不是用
        月度均值 —— 爆款是突发的，均值会严重低估。

        这是一个刻意保守的估计：假设当前的高速率会持续到月末。
        对成本控制来说，高估的代价是提前熔断（可恢复），
        低估的代价是超支（不可恢复）。不对称，所以选保守。
        """
        remaining = max(0.0, hours_in_month - mtd_hours)
        return mtd_cost + recent_hourly_rate * remaining

    def decide(self, mtd_cost: float, mtd_hours: float,
               hours_in_month: float, recent_hourly_rate: float,
               hot_content: list[HotContent]) -> FuseDecision:
        projected = self.project_month_end(
            mtd_cost, mtd_hours, hours_in_month, recent_hourly_rate)
        ratio = projected / self.budget

        # 先看能不能靠"单条内容治理"解决 —— 如果超支主要由
        # 少数爆款贡献，动那几条比全站降档便宜得多
        concentrated = sum(h.share for h in hot_content[:10])
        if ratio >= self.THRESHOLDS[1] and concentrated > 0.35:
            return FuseDecision(
                scope='per_content', targets=[h.cid for h in hot_content[:10]],
                actions=['force_p2p', 'default_quality_down_1'],
                reason=f'TOP10 占 {concentrated:.0%}，先动内容不动全站',
                projected_ratio=round(ratio, 3))

        for level in (2, 1):
            if ratio >= self.THRESHOLDS[level]:
                return FuseDecision(
                    scope='global', fuse_level=level,
                    # 熔断必须自带恢复计划，否则会被永久遗忘
                    auto_recover_after_hours=6,
                    require_human=(level == 2),
                    reason=f'月末预测 {ratio:.0%} 预算',
                    projected_ratio=round(ratio, 3))
        return FuseDecision(scope='none', projected_ratio=round(ratio, 3))
```

**`decide` 里"先动内容不动全站"的优先级是核心。** 全局降档影响 2 亿用户，单条内容治理影响看那条视频的人。**当超支高度集中时（TOP10 占 35% 以上），全局熔断是用 2 亿人的体验去解决 10 条视频的问题。** 这个判断只需要一个"热点内容成本占比"指标，但很多成本熔断系统只有全局开关，于是每次都只能全局降档。

**结果：** 带宽成本从 1.45 亿压回 ~1.0 亿，QoE 只降 0.4%，用户几乎无感。**关键洞察：带宽成本熔断是"把财务约束变成技术约束"——不是靠自觉省钱，是系统强制守门。**

### 场景 3：P2P 失效导致带宽飙升

**场景描述：** 某版本客户端 P2P 协议升级后存在 bug，P2P 命中率从 60% 掉到 8%。等效带宽成本 22% 的省钱能力消失，CDN 出口流量 +28%，带宽成本一夜多花 ¥2,000 万。

**错误做法：** 认为是"P2P 网络问题"继续排查，而不回滚——P2P 是省钱手段，它的失效直接表现为成本暴涨。

**这个场景的诊断难点在于：所有 QoE 指标都是正常的，甚至是变好的。**

```
P2P 命中率 60% → 8% 之后：
  卡顿率      1.0% → 0.9%   （变好了！CDN 比 P2P 稳）
  首帧 P95    695ms → 660ms  （变好了！少了 200ms 探测）
  播放成功率  99.7% → 99.7%  （不变）
  带宽        +28%           （唯一的异常信号）

→ 播放器团队的所有指标都在改善，他们会认为这次发版很成功
→ 唯一的坏信号在成本，而成本不在播放器团队的看板上
```

**"故障让体验变好了"是最难被发现的一类故障。** 它的检测必须依赖一个与体验方向相反的指标（成本），而这个指标通常属于另一个团队。**组织边界与指标边界重合的地方，就是这类故障的藏身处。**

**正确做法：**

```
1. 检测：按版本聚合的 P2P 命中率监控，跌到 40% 以下告警
   · 更早的信号：P2P【尝试成功率】（每次尝试是否拿到数据）
     它比命中率提前，因为命中率还受准入条件影响
   · 更强的信号：CDN 出口流量的【版本维度归因】——
     用 attribute() 做结构效应分解，v6.2.0 的流量占比未变
     而它的人均字节数变了，直接指向版本

2. 定位：按 app_version 拆，v6.2.0 命中率 8%，其他版本正常

3. 应急：远程开关灰度关闭 v6.2.0 的 P2P（走 CDN 兜底）
   · 注意此时【不要】同时开熔断降档：
     两个变更同时下发，无法判断哪个起了作用，
     而且降档会掩盖 P2P 修复后的效果验证

4. 修复：v6.2.0 的协议 bug 修复后灰度放量

5. 预防：P2P 协议变更必须过"命中率 + 卡顿率 + 【单位播放字节数】"
   三项回归测试。第三项是这次漏掉的那一项
```

**监控实现的关键点：**

```python
class P2pHealthMonitor:
    """P2P 健康度监控。
    与常规监控的根本区别：它的核心指标是【成本】而不是【可用性】，
    所以所有阈值都要挂在"单位播放字节数"上，
    而不是挂在"错误率 / 延迟"上 —— 后两者在 P2P 失效时反而变好。
    """

    HIT_RATE_FLOOR = 0.40          # 命中率地板
    ATTEMPT_SUCCESS_FLOOR = 0.40   # 尝试成功率地板（更早的信号）
    BYTES_PER_PLAY_TOLERANCE = 0.12  # 单位播放字节数的允许偏移

    def __init__(self):
        self._baseline: dict[str, float] = {}   # {version: bytes_per_play}

    def check(self, by_version: dict[str, VersionStats]) -> list[Alert]:
        alerts = []
        # 用【同期其他版本】做基线，而不是用【本版本的历史】——
        # 本版本历史在灰度初期样本太少，而且如果 bug 从第一天就有，
        # 历史基线本身就是错的（这是自比较基线的通病）
        peers = [s for s in by_version.values() if s.sample_count > 10_000]
        if len(peers) < 2:
            return alerts
        peer_bpp = self._median([s.bytes_per_play for s in peers])

        for ver, s in by_version.items():
            if s.sample_count < 10_000:
                continue          # 灰度太早，样本不足，不判

            # ① 成本信号（主判据）：单位播放字节数偏高
            drift = (s.bytes_per_play - peer_bpp) / peer_bpp
            if drift > self.BYTES_PER_PLAY_TOLERANCE:
                alerts.append(Alert(
                    severity='P1',
                    # 明确写出钱，否则这条告警会被当成"性能波动"忽略
                    msg=(f'{ver} 单位播放字节数 +{drift:.1%}，'
                         f'折算月度带宽 +¥{drift * 14400:.0f} 万'),
                    hint='优先查 P2P 命中率与预加载深度'))

            # ② 尝试成功率（更早的信号，可能在 ① 之前触发）
            if s.p2p_attempt_success < self.ATTEMPT_SUCCESS_FLOOR:
                alerts.append(Alert(
                    severity='P1',
                    msg=f'{ver} P2P 尝试成功率 {s.p2p_attempt_success:.0%}',
                    hint='协议/打洞/tracker 三处之一'))

            # ③ 命中率（滞后信号，但直观）
            if s.p2p_hit_rate < self.HIT_RATE_FLOOR:
                alerts.append(Alert(
                    severity='P2',
                    msg=f'{ver} P2P 命中率 {s.p2p_hit_rate:.0%}'))

            # ④ 反向信号：QoE 变好但字节数变多 = 强烈的 P2P 失效特征
            #    这一条是本场景的"指纹"，单独列出来是因为
            #    它的组合比任何单项都更有诊断价值
            peer_stall = self._median([p.stall_ratio for p in peers])
            if drift > 0.08 and s.stall_ratio < peer_stall * 0.95:
                alerts.append(Alert(
                    severity='P0',
                    msg=(f'{ver} 字节数 +{drift:.1%} 而卡顿率反而更低 '
                         f'—— 典型的"省钱手段失效"特征'),
                    hint='几乎确定是 P2P 或预加载策略失效，不是网络问题'))
        return alerts

    @staticmethod
    def _median(xs: list[float]) -> float:
        s = sorted(xs)
        n = len(s)
        return s[n // 2] if n % 2 else (s[n // 2 - 1] + s[n // 2]) / 2
```

**告警 ④ 是这个类里唯一真正有诊断价值的一条。** 单看"字节数涨了"可能是内容变长、可能是画质提升、可能是 DAU 结构变化；单看"卡顿率降了"是好事。**但"字节数涨且卡顿率降"这个组合几乎只有一个原因：某个省钱手段停止工作了，CDN 在兜底。** 用两个方向相反的指标的组合做指纹，比给任何单一指标调阈值都更准。

**结果：** 2 小时识别、1 小时关闭，带宽成本回到正常区间。**P2P 是"省钱组件"，它出问题时的症状不是功能异常，而是成本异常——监控必须盯 P2P 命中率与单位播放字节数，而不是盯 P2P 功能本身。**

### 场景 4：卡顿率突增的归因排查

**场景描述：** 凌晨卡顿率从 1.0% 缓慢爬升到 2.8%，无明显告警（慢爬升不触发阈值）。持续 3 小时后团队才发现，用户投诉已堆积。

**错误做法：** 各团队自查——编码说码率没问题，CDN 说质量正常，网络说链路健康。三个小时过去了，问题还在。

**"各方自查都正常"这件事本身就是一条信息：** 它说明问题不在任何单个组件内部，而在**组件之间的组合上**，或者在**流量分配上**。每个团队查的都是"我的组件在我的流量上表现如何"，而没有人查"流量是怎么分配的"。这正是结构效应问题的典型表现。

**正确做法：**

```
1. 检测：卡顿率的"斜率"监控（单位时间增幅），慢爬升也告警
2. 分解：先做组内/结构效应分解，再决定排查方向
   · 结构效应主导 → 查调度器、熔断档位、配置下发、候选集变更
   · 组内效应主导 → 查具体格子的技术故障
3. 归因：按 (CDN, 区域, ISP, 档位, 版本, 端类型) 六维自动下钻
   + 兄弟检查（固定其余维度，看该维其他取值是否也差）
4. 定位：发现 (厂商C, 全国, 移动, 所有档位, 所有版本) 组合卡顿率 5.1%
   → 兄弟检查：厂商 C 的联通/电信正常，其他厂商的移动正常
   → 交叉确认：根因在 (厂商C × 移动) 这个组合上，不在任一单维
   → 该厂商对移动网络的链路全局劣化（可能是运营商互通故障）
5. 处理：调度把厂商 C 的移动流量切走 80%（分档，走 CdnFailoverController）
6. 复盘：与厂商 C 确认移动链路问题，修复后回放流量
```

**为什么斜率告警是必需的，以及它为什么难做：**

```
阈值告警：卡顿率 > 2.0% 报警
  1.0% → 2.8% 用了 3 小时，在 2.0% 时才报
  → 已经烧了 2 小时，且已过 2.0% 说明恶化已成规模

斜率告警：卡顿率 15 分钟内上升 > 30% 报警
  1.0% → 1.3% 就报（约 25 分钟）
  → 提前 2.5 小时

但斜率告警的误报率天然高：
  · 凌晨低谷期基数小，绝对值的小波动就是大比例
  · 早高峰/晚高峰的自然爬升本身斜率就大
  · 单次发版灰度会造成一次性台阶

→ 斜率告警必须配【三个抑制条件】才可用：
  ① 绝对值下限：卡顿率 < 0.8% 时不报（低基数噪声）
  ② 样本量下限：窗口内会话数 < 10 万不报
  ③ 同比对照：与上周同一时刻的斜率对比，只报异常斜率
     （这一条消掉了"高峰期自然爬升"的绝大部分误报）
```

**③ 是最关键也最常被省掉的一条。** 没有同比对照，斜率告警会在每天早晚高峰各报一次，两周之后就没人看了——**一个被静音的告警比没有告警更糟，因为它给了"我们有监控"的错觉。**

**斜率检测的实现：**

```python
class StallSlopeDetector:
    """卡顿率斜率告警。
    设计目标不是"最早发现"，而是"最早发现且不被静音" ——
    一个每天误报两次的告警，两周内一定会被关掉，
    此时它的实际检出率是 0。
    """

    WINDOW_MIN = 15
    SLOPE_THRESHOLD = 0.30         # 窗口内相对上升 30%
    ABS_FLOOR = 0.008              # 绝对值下限 0.8%
    MIN_SESSIONS = 100_000
    SEASONAL_RATIO = 2.0           # 相对上周同刻斜率的倍数

    def __init__(self):
        self._series: list[tuple[float, float, int]] = []   # (ts, rate, n)

    def ingest(self, ts: float, stall_ratio: float, sessions: int) -> None:
        self._series.append((ts, stall_ratio, sessions))
        cutoff = ts - 8 * 86400        # 留 8 天，供上周同刻对照
        self._series = [r for r in self._series if r[0] >= cutoff]

    def check(self, now: float, last_week_slope: float | None) -> Alert | None:
        win = [r for r in self._series if now - r[0] <= self.WINDOW_MIN * 60]
        if len(win) < 3:
            return None
        sessions = sum(r[2] for r in win)
        cur = win[-1][1]

        # 抑制条件 ①②：低基数与小样本一律不报
        if cur < self.ABS_FLOOR:
            return None
        if sessions < self.MIN_SESSIONS:
            return None

        base = win[0][1]
        if base <= 0:
            return None
        slope = (cur - base) / base
        if slope < self.SLOPE_THRESHOLD:
            return None

        # 抑制条件 ③：同比对照。没有上周数据时【降级为 P3】而不是不报 ——
        # 新上线的维度组合没有历史，但它也可能真的在恶化。
        # 静默丢弃是错的，降低优先级是对的
        if last_week_slope is None:
            return Alert(severity='P3',
                         msg=f'卡顿率斜率 +{slope:.0%}（无同比基线）')
        if last_week_slope > 0 and slope < last_week_slope * self.SEASONAL_RATIO:
            return None            # 与上周同刻的自然爬升相当，不是异常

        return Alert(
            severity='P1',
            msg=(f'卡顿率 {base:.2%} → {cur:.2%}（{self.WINDOW_MIN}min，'
                 f'+{slope:.0%}），上周同刻 +{last_week_slope:.0%}'),
            # 告警直接带上下一步动作，而不是让值班人从零开始
            hint='先跑 attribute() 看结构/组内占比，再决定查调度还是查厂商')
```

**告警里带 `hint` 不是锦上添花。** 凌晨三点被叫起来的人需要的不是"有问题"，而是"下一步做什么"。**把归因流程的第一步写进告警文本，能把平均处置时间压掉一半以上**——因为它消掉了"想起来该干什么"这个最耗时的环节。

**结果：** 从"发现"到"定位到厂商 × ISP"用 15 分钟，切流后恢复。**慢爬升故障比突发故障更危险——它不触发阈值、不引起警觉、持续烧用户。监控必须包含趋势（斜率）告警，且斜率告警必须配同比抑制，否则会被误报淹没并最终被关掉。**

### 降本手段的收益不可相加

原始表格把四项手段的节省额并列，读起来像是可以相加。**不能。** 每项手段作用在**前一项处理完之后的剩余流量**上，四项是**乘性**关系。

```
原始基线：153.6 PB/日 @ H.264 2.4 Mbps
  = 160 亿 VV × 32s × 2.4 Mbps
  → 月度 4,608 PB × ¥0.05/GB = ¥2.304 亿

注意：README 的 96 PB/日 @ 1.5 Mbps 已经【包含了编码升级】。
所以"编码升级省 ¥8,064 万"这一项的分母是 ¥2.304 亿，
而后续手段的分母只能是 ¥1.44 亿。混用分母就是下面这张表的病根。
```

**逐项作用（按实际生效顺序）：**

| 顺序 | 手段 | 降幅 | 作用于 | 本项节省 | 剩余 |
|------|------|------|--------|---------|------|
| — | 原始基线（2.4 Mbps） | — | — | — | ¥2.304 亿 |
| ① | 编码升级 H.265/AV1 | 35% | ¥2.304 亿 | ¥8,064 万 | ¥1.498 亿 |
| ② | P2P/PCDN 分担 | 22% | ¥1.498 亿 | **¥3,295 万** | ¥1.168 亿 |
| ③ | 精准预加载减 1 片 | 8% | ¥1.168 亿 | **¥934 万** | ¥1.075 亿 |
| ④ | 自建边缘价差 | 45% 流量 × ¥0.032/GB | ¥1.075 亿 | ¥3,264 万 | ¥7,483 万 |
| — | + 回源 ¥920 万 + 调度 ¥930 万 | — | — | — | **¥9,333 万** |

**对照原表：P2P 从 ¥5,069 万修正为 ¥3,295 万（原值高估 54%），精准预加载从 ¥1,843 万修正为 ¥934 万（原值高估 97%）。** 原表的三项都拿 ¥2.304 亿做分母，而只有第一项有资格用这个分母。四项修正后的总节省 ¥1.556 亿，落到 ¥7,483 万出口 + ¥1,850 万非出口 = **¥9,333 万**，与标称的 ¥9,220 万差 1.2%——**这说明 ¥9,220 万这个结果是对的，错的只是拆分。** 一个正确的总数配上一组错误的分项，比总数也错更难发现。

**这张表的原始版本来自 P00 的成本模型（P00:1213-1218），本文的修正应当回灌 P00。** 顺带记录一处 P00 内部的口径不一致：P00:1780 用"月 96 PB × 60%"折算优化后带宽，隐含残余系数 60%；而 P00 自己那四项手段（P2P 22% + 预加载 8%）的乘性残余是 `0.78 × 0.92 = 71.8%`。**两个数字差 20%，且 60% 无法从 P00 列出的任何手段组合推出。** 本文一律采用 71.8% 口径（对应 2,149 PB/月），因为它可追溯到具体手段。

**为什么这类错误特别顽固：** 每个手段由不同团队负责，每个团队都用"全站带宽成本"做分母算自己的收益——**因为那是唯一一个人人都知道、且看起来最权威的数字。** 用剩余流量做分母需要知道别人已经省了多少，而这个数字没人维护。于是每个团队的汇报都是对的（在自己的口径下），加起来超过 100%。

**更麻烦的是排序即分配：** 上表里 ① 拿了 ¥8,064 万是因为它排第一。如果把 P2P 排第一，P2P 就能拿 ¥5,069 万（这正是原表的数字！），而编码升级只剩 ¥6,290 万。**四项手段的总节省是确定的（¥1.556 亿），但每一项拿多少完全取决于排序。** 这是 Shapley 值问题，而组织里的实际做法是"谁先汇报谁用大分母"。

**可执行的规矩：** 收益归因表必须写明**分母**和**顺序**。要做到与顺序无关，就对每项手段用**边际贡献**（关掉它，账单涨多少）而不是**独立贡献**（只开它，能省多少）。边际口径下四项之和会**小于**总节省（因为手段间有重叠），这个缺口应当明确列成"协同项"，而不是分摊掉。

**P2P 的 22% 本身也要打折。** 上文推导过：这个 22% 若用**播放次数**加权（"热门内容占 80% 播放"）会高估约 23%，按**字节**加权后 P2P 的真实等效降幅约 17-18%。用 18% 重算 ②：¥1.498 亿 × 18% = ¥2,696 万。**所以 ¥5,069 万 → ¥3,295 万 → ¥2,696 万，两次修正累计砍掉 47%。** 汇报口径的两处小问题，复合出一个近乎腰斩的误差。

### ¥930 万那一行：一个不该被默认接受的数字

按自下而上估算，调度 + HTTPDNS + QoE 的真实资源需求远低于 ¥930 万：

```
播放地址签发：峰值 64.8 万 QPS
  单核约 3,000 QPS（一次本地查表 + HMAC 签名 + 打分）
  → 216 核峰值，三地多活各按峰值备 → ~650 核
  → ¥300/核/月 × 650 ≈ ¥20 万/月

HTTPDNS 解析：峰值约 10 万 QPS（有客户端缓存，远低于播放 QPS）
  → ~¥30 万/月（含全国接入点）

QoE 数据链路：3.2 TB/日 原始上报
  → 采样后 96 GB/日 → ZSTD 后约 10 GB/日 → 14 天约 140 GB 在线
  → Kafka + Flink 聚合 + ClickHouse 集群 ≈ ¥100 万/月（计算为主，存储可忽略）

自建边缘管控面 + 配置下发 + 演练平台：~¥50 万/月

合计 ≈ ¥200 万/月，与表中 ¥930 万差 4.6 倍
```

**这个差额不是笔误，是"其他"桶的典型症状。** 成本表里总有一行是把所有算不清的东西装进去的，它的特征是：**没有折算流量、没有折算单价、名字里带斜杠（"调度/HTTPDNS/QoE"）。** 三个斜杠分隔的东西属于三个团队、三种计价方式，被合成一行，就再也没人能质疑它。

**处理方式不是把它改成 ¥200 万**（真实值可能包含本文没考虑的项，比如跨域专线、CDN 厂商的接口调用费、日志归档），**而是把它拆开，每一项各自给出流量或核数口径。** 拆不出来的部分单独列成"未归因"，并把它的绝对值和占比写在表里——**¥930 万占播放链路总成本 10%，一个占 10% 的黑盒不该存在。**

**这条规矩对读者的意义大于对本文的意义：** 拿到任何成本表，先找那一行没有单价的。

### 播放体验指标达成（P95）

| 指标 | 目标 | 达成 | 口径备注 |
|------|------|------|---------|
| 首帧 | 800ms | 485ms（理想路径）/ 695ms（边缘未命中 + 冷连接） | 与 P00 首帧预算账本一致；800ms 是预算上限而非目标值 |
| 卡顿率 | < 1% | 0.7%（档位 0） | 分母是播放时长而非会话数；换分母会得到完全不同的数 |
| 播放成功率 | > 99.5% | 99.7% | 口径是"可播"而非"可见"，见 P02 的同名区分 |
| 切流能力 | 15min 切 80% | 15min 切 90%（**按请求数**） | **按带宽只有约 35%**，两个口径差 27 倍，见上文 τ 推导 |

**切流那一行的双口径必须同时写出来。** 只写"15min 切 90%"会导致故障复盘时的一个固定困惑：影响面已经收敛了，为什么账单和回源率还在高位？答案是长视频的存量会话仍在用旧地址拉流，**请求数的切换是秒级的，字节的切换是会话生命周期级的**。

### 一个必须声明的口径：96 PB/日 是短视频模型

README 的 96 PB/日来自 `160 亿 VV × 32s × 1.5 Mbps ≈ 6 MB/次`。**这是一个纯短视频模型**——它隐含假设每一次播放都是 32 秒。本文所有成本数字都建立在这个基线上，而它对长视频/大屏的敏感度极高：

```
一次 OTT 长视频播放：25 分钟 × 8 Mbps ≈ 1,500 MB = 短视频的 250 倍

让 OTT 长视频字节数追平全部短视频字节数（96 PB）需要多少次播放？
  x × 160 亿 × 1,500 MB = 96 PB
  → x = 0.4%，即每日 6,400 万次 OTT 长视频播放

对 2 亿 DAU 的平台，6,400 万次大屏播放完全在合理范围内
```

**0.4% 的播放次数决定 50% 的字节。** 这不是"OTT 也很重要"这种程度的结论，而是：**字节总量几乎完全由时长分布的尾部决定，与 DAU、VV 这两个所有人都在看的数字关系不大。** 一个平台可以 VV 增长 30% 而带宽账单不动（新增全是短视频），也可以 VV 零增长而账单翻倍（用户从刷短视频转向看剧）。

**这直接推翻了一个常见的容量规划做法：用 VV 增速预测带宽增速。** 正确的预测量是**总播放时长 × 平均码率**，且必须按端类型与内容形态分开算。VV 是产品指标，字节是成本指标，两者之间没有稳定的换算系数。

**本文的处理：** 保留 96 PB 作为统一基线以便与 README/P00 对齐，但所有涉及 OTT 的策略（陷阱 10）按独立口径论证，不并入主账本。**真实平台必须做的是把带宽账单按端类型 × 内容形态拆成矩阵**——否则无法知道任何一项优化作用在哪一格上。

### 容量账本与 P2P = 0 的校验

峰值 26.7 Tbps 的承担结构：

| 来源 | 峰值供给 | 性质 | P2P 全失效时 |
|------|---------|------|-------------|
| 商业 CDN 合约 | ~13.4 Tbps（均值 ×1.5） | 刚性，合约锁定 | 不变 |
| 自建边缘 | ~8.0 Tbps（头部区域） | 刚性，资产锁定 | 不变 |
| P2P | ~5.3 Tbps | **弹性，且供给与需求同向** | **0** |
| 合计 | 26.7 Tbps | | **21.4 Tbps** |

**"不为峰值付全价，峰值由弹性手段吸收"这句话成立，但它同时意味着一个必须显式回答的问题：弹性手段全失效时，缺口 5.3 Tbps（20%）怎么办？**

上文论证过 P2P 的失效模式是**全局且同时**的（协议 bug、tracker 故障、版本灰度），所以这个 20% 不能靠"不会同时失效"来消解。校验：

```
熔断档位 1 的降幅 32%
  26.7 Tbps × (1 − 0.32) = 18.2 Tbps < 21.4 Tbps 可用容量 ✓
  余量 3.2 Tbps（15%），可吸收切流瞬时冲击

→ 结论：熔断档位 1 就是 P2P 全失效的兜底容量，
  且必须能在【P2P 命中率跌破阈值时自动触发】，
  而不是等成本预测超预算才触发（后者要等分钟级聚合，太慢）
```

**这条联动是场景 3 的架构化表达：** `P2pHealthMonitor` 的 P0 告警不应只是通知人，它应当直接是熔断档位 1 的触发条件之一。**成本熔断的触发器有两个来源——预算超支（慢，前馈）和弹性容量失效（快，事件驱动）**，只做前者会在 P2P 崩溃时留下 20% 的裸奔窗口。

**反过来说：这也是为什么容量规划必须假设 P2P = 0。** 如果按 26.7 Tbps 全额规划刚性容量，P2P 的 ¥2,696 万/月就白省了；如果只按 21.4 Tbps 规划而不准备熔断，P2P 一挂就是全站事故。**弹性容量的正确用法是"省钱 + 预备降级方案"，而不是"省钱"或"不用"二选一。**

## 延伸思考

- **调度权在自己手里之后，HTTPDNS 本身成为单点**——HTTPDNS 挂了怎么办？调度决策服务的可用性预算该给多少？注意这个问题有一个反直觉的答案方向：**调度服务的可用性不需要很高，因为客户端可以缓存上一次的调度结果**——但这要求缓存的调度结果里带着"过期后降级到哪个固定地址"，而这个兜底地址的选择又是一次调度决策。
- **QUIC 在 OTT/大屏端的推进成本**——非移动端设备升级慢，双协议长期共存会不会让运维复杂度失控？延伸：既然 OTT 按字节可能占一半以上，而它恰恰是最难升级协议的一端，那么"QUIC 省了多少带宽"这个数字是不是也犯了上文那个分母错误？
- **P2P 的长期用户教育**——如何让用户理解并接受"贡献上行换权益"？产品上怎么设计才不引起反感？延伸：陷阱 10 指出 OTT 是最优质的种子，而 OTT 用户对上行占用的感知最弱（有线网、不计流量、不看电量）——**是否应该把 P2P 的供给侧重心从手机整体迁移到 OTT？** 这会让"用户教育"从一个全民问题变成一个小众问题。
- **边缘函数（C23）与自建边缘的协同**——播放地址签名能不能下沉到边缘函数，让签发更近用户、延迟更低？关键约束：签名下沉意味着密钥下沉，而边缘节点的物理安全性低于中心机房。是否可以用**短 TTL + 边缘专用密钥 + 中心可撤销**来换这个延迟？
- **多 CDN 的质量分是否会被厂商"刷"？** 本文已给出部分答案：质量分的数据源是**客户端上报**而非厂商上报，厂商没有直接的写入通道；要伪造必须让客户端发出假数据，而这会破坏五维分布并被自动下钻发现（见"防盗链"一节的同源论证）。**但仍有两个未解口子**：① 厂商可以针对**探测流量**优化（识别出质量探测请求并优先处理），使探测结果好于真实用户体验；② 厂商可以在**质量分统计窗口内**临时提升服务质量，窗口外回落——这需要把统计窗口本身随机化才能防。这两个都属于"被测方知道自己在被测"的经典问题，值得单独设计。
- **本篇所有成本数字的可信度分级**——上文修正了两处分母错误、指出了一行 10% 的黑盒、声明了一个短视频口径假设。**如果给本篇每个数字标注一个可信度（合约价 > 实测量 > 推导值 > 估算值），有多少比例是最低那一档？** 一份成本方案如果不做这个标注，读者无法知道哪些结论经得起追问。


## 播放地址签发与调度服务完整实现

播放链路的核心是**播放地址签发服务**：接收 content_id + 用户上下文，返回签名地址 + 档位列表 + 备用地址。实现要点：无状态、短时效签名、多 CDN 调度、ABR 档位决策、QoE 上报聚合。

```python
from __future__ import annotations

import hashlib
import hmac
import math
import time
from dataclasses import dataclass, field
from typing import Optional


# ── 显式异常：播放链路的每种"给不出地址"都要能被区分 ─────────────
# 统一抛 ValueError 会让上层无法决定回退策略：
# 无可播档位 → 提示升级客户端；无可用 CDN → 触发全局告警

class NoPlayableVariant(Exception):
    """设备解码能力不匹配任何档位。"""


class NoAvailableCdn(Exception):
    """候选 CDN 集为空。到这一步说明调度上游已经出了问题。"""


# ── 域7 播放地址签发的核心：选档 + 选CDN + 签名 ──────────────────

@dataclass
class PlaybackContext:
    """播放请求的用户上下文（客户端上报 + 本地缓存，不查库）。"""
    uid: int
    content_id: int
    network_type: str              # 'wifi' / '4g' / '5g' / 'weak'
    region: str                    # 'cn-east' ...
    isp: str                       # 'cmcc' / 'cucc' / 'ctcc'
    device_hw: str                 # 'hw-vp9' / 'hw-av1' / 'hw-h264'
    membership_level: int          # 0-非会员, 1-普通会员, 2-旗舰
    client_version: str

    @property
    def device_codecs(self) -> set[str]:
        return set(self.device_hw.split('-'))


@dataclass
class Variant:
    quality: str                   # '360p' / '480p' / '720p' / '1080p' / '4k'
    codec: str                     # 'h264' / 'h265' / 'av1'
    bitrate_kbps: int
    manifest_key: str


@dataclass
class CdnEndpoint:
    cdn: str
    region: str
    cost_per_gb: float
    quality_score: float           # 近5分钟实时质量分，来自 QoE 归因


class CostFuseLevel:
    """成本熔断档位（P00 带宽成本熔断三档的代码化）。
    档位由下发配置传播，秒级生效，不需要发版。"""
    NORMAL = 0
    MILD = 1
    STRONG = 2

    DEFAULT_QUALITY = {NORMAL: '1080p', MILD: '720p', STRONG: '480p'}
    MAX_QUALITY_NON_MEMBER = {NORMAL: '4k', MILD: '720p', STRONG: '480p'}
    PREFETCH_SEGMENTS = {NORMAL: 3, MILD: 2, STRONG: 1}
    P2P_FORCE = {NORMAL: False, MILD: False, STRONG: True}


class QualitySelector:
    """ABR 档位决策：网络 + 设备能力 + 会员等级 + 成本熔断档位。"""

    def __init__(self, fuse_level: int):
        self.fuse = fuse_level

    def select(self, ctx: PlaybackContext, available: list[Variant]) -> Variant:
        # 0. 先按档位排序。后续所有"取最高可用"都依赖这个顺序 ——
        #    不能假设调用方传进来的 available 是有序的：
        #    媒资域返回的顺序取决于它的存储与查询实现，
        #    某次重构改了排序，这里的 usable[-1] 就会静默返回错误档位
        #    （比如给 4K 设备下发 360p，或给弱网下发 4K）
        usable = sorted(
            (v for v in available if v.codec in ctx.device_codecs),
            key=lambda v: self._rank(v.quality),
        )
        if not usable:
            # 设备解码能力不匹配任何档位 —— 必须显式失败，不能返回一个
            # 播不了的档位。上层据此回退到软解或提示升级客户端
            raise NoPlayableVariant(f"uid={ctx.uid} codecs={ctx.device_codecs}")
        fallback = usable

        # 1. 非会员清晰度上限（成本熔断联动）
        max_q = self._max_quality(ctx)
        usable = [v for v in usable if self._rank(v.quality) <= self._rank(max_q)]
        # 2. 弱网直接限制最高档位，避免虚高码率引发卡顿
        if ctx.network_type == 'weak':
            usable = [v for v in usable if self._rank(v.quality) <= self._rank('720p')]
        if not usable:
            # 上限过滤后为空：说明所有可解码档位都高于上限。
            # 取【最低】的那个，而不是回退到 fallback 的最高档 ——
            # 弱网下宁可给 1080p（唯一可用）也不该给 4K
            return fallback[0]

        # 3. 默认档位：优先 default_quality，兜底"不超过上限的最高可用"
        default = CostFuseLevel.DEFAULT_QUALITY[self.fuse]
        for v in usable:
            if v.quality == default:
                return v
        return usable[-1]          # usable 已排序，[-1] 确定是最高可用

    def _max_quality(self, ctx: PlaybackContext) -> str:
        if ctx.membership_level == 0:
            return CostFuseLevel.MAX_QUALITY_NON_MEMBER[self.fuse]
        # 会员也受熔断约束，只是上限更高。
        # 熔断档位 2 下会员仍给 4K，等于熔断对 35% 的带宽完全无效
        return {CostFuseLevel.NORMAL: '4k',
                CostFuseLevel.MILD: '1080p',
                CostFuseLevel.STRONG: '720p'}[self.fuse]

    @staticmethod
    def _rank(q: str) -> int:
        return {'360p': 1, '480p': 2, '720p': 3, '1080p': 4, '4k': 5}[q]


class CdnScheduler:
    """多 CDN 调度：质量分 × 成本权重。权重随成本熔断档位联动。

    这是【唯一】的打分实现。此前 PlaybackService 里有一份重复的 _score，
    两份实现会各自演化 —— 改了一处忘了另一处，调度行为取决于走到哪条代码路径。
    目标函数是核心业务规则，必须单一来源。
    """

    def __init__(self, w_quality: float = 0.7, w_cost: float = 0.3):
        self.w_quality = w_quality
        self.w_cost = w_cost

    def set_fuse(self, fuse_level: int) -> None:
        """档位 2 下成本权重升到 0.8，流量自动导向便宜 CDN + P2P。"""
        if fuse_level == CostFuseLevel.STRONG:
            self.w_quality, self.w_cost = 0.2, 0.8
        elif fuse_level == CostFuseLevel.MILD:
            self.w_quality, self.w_cost = 0.5, 0.5
        else:
            self.w_quality, self.w_cost = 0.7, 0.3

    def score(self, e: CdnEndpoint,
              cost_min: float, cost_max: float) -> float:
        """归一化后加权。两项都在 [0,1]，权重才有实际含义。

        错误的写法是 quality_score * w_q + (1/cost) * w_c：
          quality_score ∈ [0,1]，而 1/cost ≈ 35~83
          → 成本项占实际权重的 97%，文档写的 0.7/0.3 完全不生效
          → 只在"便宜的那家出故障时"暴露，而那正是最该切走流量的时刻
        """
        span = cost_max - cost_min
        # 全部同价时成本项不提供区分度，给中性值 0.5（不是 0 也不是 1）
        cost_score = 0.5 if span < 1e-9 else (cost_max - e.cost_per_gb) / span
        return e.quality_score * self.w_quality + cost_score * self.w_cost

    def rank(self, endpoints: list[CdnEndpoint]) -> list[CdnEndpoint]:
        """返回按分数降序的候选。归一化基准取【候选集内】极值，
        使成本项衡量"相对便宜多少"而非"绝对单价多少" ——
        全网单价整体下降时调度行为不应改变。
        """
        if not endpoints:
            raise NoAvailableCdn()
        costs = [e.cost_per_gb for e in endpoints]
        lo, hi = min(costs), max(costs)
        return sorted(endpoints, key=lambda e: self.score(e, lo, hi), reverse=True)

    def pick(self, endpoints: list[CdnEndpoint]) -> CdnEndpoint:
        return self.rank(endpoints)[0]


class PlaybackSigner:
    """播放地址签名：短时效防盗链 token。
    签名是唯一需要"知道密钥"的地方，密钥只存在域7内部。"""
    def __init__(self, secret: bytes, ttl_sec: int = 2400):  # 40min
        self.secret = secret
        self.ttl = ttl_sec

    def sign(self, url: str, uid: int, expires_ts: int) -> str:
        payload = f"{url}|{uid}|{expires_ts}".encode()
        sig = hmac.new(self.secret, payload, hashlib.sha256).hexdigest()[:16]
        sep = '&' if '?' in url else '?'
        return f"{url}{sep}sign={sig}&e={expires_ts}"


@dataclass
class PlaybackGrant:
    play_url: str
    backup_urls: list[str]
    quality_list: list[str]
    expires_at: int
    cdn: str


class PlaybackService:
    """域7 播放地址签发服务（无状态、纯函数、可水平扩展）。"""

    def __init__(self, signer: PlaybackSigner,
                 scheduler: CdnScheduler, fuse_level: int):
        self.signer = signer
        self.scheduler = scheduler
        self.fuse = fuse_level

    def grant(self, ctx: PlaybackContext, variants: list[Variant],
              endpoints: list[CdnEndpoint],
              manifest_templates: dict[str, str]) -> PlaybackGrant:
        """
        variants / endpoints / manifest_templates 由媒资与CDN域提供，
        本服务只做决策与签名，不查库（决策要素全在上下文与输入里）。
        """
        # 1. 档位决策
        qs = QualitySelector(self.fuse)
        chosen = qs.select(ctx, variants)

        # 2. CDN 调度（主 + 两个备用，按质量分 × 成本权重）
        #    打分与排序全部委托给 scheduler，本服务不再自己算分：
        #    目标函数只有一份实现
        ordered = self.scheduler.rank(endpoints)
        main = ordered[0]
        # 备用地址必须来自【不同厂商】。同一家的两个区域节点在
        # "厂商级故障"（证书过期、配置全网下发错误）下会一起挂，
        # 备用地址等于没有 —— 这正是场景 1 要防的失效模式。
        # 直接取 ordered[:3] 就可能三个都是同一家（该家在本区域
        # 有多个节点且质量分都高），静默丢掉容灾能力
        backs, seen = [], {main.cdn}
        for e in ordered[1:]:
            if e.cdn not in seen:
                seen.add(e.cdn)
                backs.append(e)
            if len(backs) == 2:
                break

        # 3. 签名：主地址 + 备用地址都签名，短时效
        expires = int(time.time()) + self.signer.ttl
        base = manifest_templates[chosen.quality].replace('{cdn}', main.cdn)
        play_url = self.signer.sign(base, ctx.uid, expires)
        backup_urls = [
            self.signer.sign(
                manifest_templates[chosen.quality].replace('{cdn}', b.cdn),
                ctx.uid, expires)
            for b in backs
        ]

        return PlaybackGrant(
            play_url=play_url, backup_urls=backup_urls,
            quality_list=[v.quality for v in variants],
            expires_at=expires, cdn=main.cdn)

    def _score(self, e: CdnEndpoint) -> float:
        """保留此方法仅为兼容旧调用方，实现委托给 scheduler。
        归一化基准需要候选集，单个 endpoint 无法独立打分 ——
        这本身就说明"给单个节点算绝对分"是错的抽象。"""
        raise NotImplementedError("use CdnScheduler.rank(endpoints) instead")


# ── QoE 埋点聚合（归因决策的输入）───────────────────────────────

@dataclass
class PlaySession:
    content_id: int
    region: str
    isp: str
    cdn: str
    quality: str
    version: str
    first_frame_ms: int
    stall_count: int
    stall_ms: int
    play_ms: int                   # 播放时长，卡顿率的分母
    success: bool
    reported_at: float             # 埋点【产生】时间（客户端时钟已校正）


class QoeRegistry:
    """QoE 五维聚合：(CDN, 区域, ISP, 档位, 版本)。
    归因结果反哺调度：某组合质量分跌破阈值 → 调度降权重。

    这个类的正确性直接决定调度闭环是否成立 —— 它算错不会报错，
    只会让 quality_score 永远返回默认值 0.5，于是"质量分×成本权重"
    退化成"纯成本排序"，而监控上一切正常。
    """

    # 样本量不足时不能相信统计量：3 个会话里 1 次卡顿 = 33% 卡顿率，
    # 会把一个健康节点直接踢出调度。低于此阈值一律返回中性分
    MIN_SAMPLES = 30

    def __init__(self, window_sec: int = 300):
        self.window = window_sec
        self._buckets: dict[tuple, list[PlaySession]] = {}

    def ingest(self, session: PlaySession, now: float | None = None) -> None:
        now = time.time() if now is None else now
        key = (session.cdn, session.region, session.isp,
               session.quality, session.version)
        bucket = self._buckets.setdefault(key, [])
        bucket.append(session)
        # 用埋点自带的 reported_at 做窗口裁剪。
        # 原实现的 _age() 恒返回 0.0，于是 now - 0.0 < 300 恒为 False
        # —— 每次 ingest 都把整个桶清空，quality_score 永远走
        # "无样本 → 返回 0.5"的分支。整条反哺链路静默空转
        self._buckets[key] = [
            s for s in bucket if now - s.reported_at < self.window
        ]

    def gc(self, now: float | None = None) -> int:
        """只有被 ingest 的组合才会裁剪。某个 (CDN,区域,ISP,档位,版本)
        组合彻底没流量后，它的桶会永久驻留 —— 版本维度尤其致命：
        客户端每周发版，版本号只增不减，桶数量单调增长。
        必须有独立 GC 定期清空组合本身，而不只是清桶内元素。"""
        now = time.time() if now is None else now
        stale = [k for k, v in self._buckets.items()
                 if not v or now - v[-1].reported_at >= self.window]
        for k in stale:
            del self._buckets[k]
        return len(stale)

    def quality_score(self, cdn: str, region: str) -> float:
        """调度用的质量分：首帧 + 卡顿 + 成功率的合成分，落在 [0,1]。"""
        # _buckets 的 value 是 list[PlaySession]，不是单个 PlaySession。
        # 原实现写成 `for (c, r, *_), s in items()` 后直接访问
        # s.stall_count —— s 是 list，AttributeError。
        # 必须展平后再统计
        samples = [
            s
            for (c, r, *_), bucket in self._buckets.items()
            if c == cdn and r == region
            for s in bucket
        ]
        if len(samples) < self.MIN_SAMPLES:
            return 0.5                       # 中性分：不奖励也不惩罚

        n = len(samples)
        success_rate = sum(1 for s in samples if s.success) / n
        # 卡顿率的分母是【播放时长】而不是【会话数】：
        # 一个 3 小时长视频卡 2 次和一个 15 秒短视频卡 2 次，
        # 体验差异巨大。按会话数平均会把长视频误判成劣质
        total_play_ms = sum(s.play_ms for s in samples) or 1
        stall_ratio = sum(s.stall_ms for s in samples) / total_play_ms
        # 首帧用 P95 而不是均值：均值被大量快速起播样本拉低，
        # 掩盖尾部用户的糟糕体验（这正是要调度躲开的）
        p95_ff = self._percentile([s.first_frame_ms for s in samples], 0.95)

        return max(0.0, min(1.0,
                            0.45 * success_rate
                            + 0.35 * (1 - min(stall_ratio / 0.02, 1.0))
                            + 0.20 * (1 - min(p95_ff / 2000.0, 1.0))))

    def drill_down(self, min_samples: int | None = None
                   ) -> list[tuple[tuple, float, int]]:
        """归因用：返回所有维度组合的质量分，按分数升序。
        最差的组合排在最前面，就是"卡顿率突增怪谁"的答案候选。"""
        floor = self.MIN_SAMPLES if min_samples is None else min_samples
        rows = []
        for key, bucket in self._buckets.items():
            if len(bucket) < floor:
                continue
            n = len(bucket)
            total = sum(s.play_ms for s in bucket) or 1
            score = (0.45 * (sum(1 for s in bucket if s.success) / n)
                     + 0.35 * (1 - min(sum(s.stall_ms for s in bucket)
                                       / total / 0.02, 1.0))
                     + 0.20 * (1 - min(self._percentile(
                         [s.first_frame_ms for s in bucket], 0.95)
                         / 2000.0, 1.0)))
            rows.append((key, round(score, 4), n))
        return sorted(rows, key=lambda r: r[1])

    @staticmethod
    def _percentile(values: list[int], q: float) -> float:
        if not values:
            return 0.0
        ordered = sorted(values)
        # 向上取整索引：P95 要落在"至少 95% 的样本不高于它"的位置
        idx = min(len(ordered) - 1, math.ceil(q * len(ordered)) - 1)
        return float(ordered[max(0, idx)])
```

**关键设计：**
1. `PlaybackService.grant` 是**无状态纯函数**——决策要素全部来自输入，天然可水平扩展扛 64.8 万 QPS。注意它**不查库**：64.8 万 QPS 的数据面碰任何数据库都是灾难，`variants` / `endpoints` / `manifest_templates` 全部来自本地缓存 + 配置下发（见后文「数据库设计」一节的说明）
2. `QualitySelector` 把"会员等级、网络类型、成本熔断档位"三个约束叠加在档位决策上，弱网直接限 720P 防虚高码率卡顿。**排序在第 0 步而不是靠调用方保证**——`usable[-1]` 这类"取最高可用"的写法一旦依赖入参顺序，就是一颗等着媒资域重构时引爆的雷
3. `CdnScheduler` 是**唯一**的打分实现。此前 `PlaybackService._score` 有一份重复的同名逻辑，两份实现会各自演化；目标函数是核心业务规则，必须单一来源。`score()` 里两项都归一化到 `[0,1]`——`quality_score × 0.7 + (1/cost) × 0.3` 这种写法量纲不统一，成本项实际占 97% 权重，而且**只在便宜的那家出故障时才暴露**
4. `set_fuse` 让成本熔断档位自动联动调度权重——档位 2 下流量自动流向便宜 CDN，**熔断不只降码率，还调路由**
5. `grant` 的备用地址强制**跨厂商去重**。`ordered[:3]` 看着没问题，但同一家在一个区域可能有多个高分节点，三个地址落到同一厂商，厂商级故障（证书过期、配置全网下发错误）下备用地址与主地址一起挂
6. `PlaybackSigner` 的短时效签名（40min）让下架/换流时存量地址自然过期，是"分钟级切换"能力的一部分
7. `QoeRegistry` 归因结果反哺调度——`quality_score` 直接是调度决策的输入，**QoE 体系不是报表，是调度闭环的一部分**。也正因为它在闭环里，它的两个 bug（`_age` 恒返回 0 导致每次 ingest 清空整桶；把 `bucket` 当 `PlaySession` 用）不是"统计不准"而是**闭环静默断开**：质量分永远是 0.5，"质量分 × 成本权重"退化成纯成本排序，监控面板上一切正常
8. 质量分的三项都有明确的分母选择理由：卡顿率除以**播放时长**而非会话数（否则长视频被系统性误判），首帧取 **P95** 而非均值（均值被快速起播样本拉低，掩盖的正是要躲开的尾部），样本量 < 30 返回中性分（3 个样本里 1 次卡顿 = 33%，足以把健康节点踢出调度）

## 异常场景补充

### 场景：HTTPDNS 故障导致全局无法解析

```
触发：自建 HTTPDNS 集群故障 → 客户端拿不到 CDN 地址
      → 播放请求大面积失败，播放成功率从 99.7% 跌到 30%
检测：
  1. HTTPDNS 服务可用性监控（QPS 下降 + 错误率上升）
  2. 播放成功率骤降 + 无 CDN 质量异常（定位到"解析层"而非 CDN 层）
  3. 客户端侧解析失败率埋点
处理：
  1. 客户端缓存兜底：HTTPDNS 故障时回退系统 DNS + 上次缓存的多地址
  2. 调度服务降级：直接下发各家 CDN 的静态 CNAME 地址（无区域调度，仅保可用）
  3. 修复后灰度放量
预防：HTTPDNS 多副本 + 客户端缓存兜底 + 系统 DNS 回退路径保留
```

**这个场景里藏着一个直接的架构对立：容灾能力与切流能力共用一个旋钮，且方向相反。**

```
客户端缓存 TTL 短（60s）
  → 切流快：权重一改，1 分钟内全网生效 ✓
  → HTTPDNS 故障时缓存 1 分钟就失效，全站不可用 ✗

客户端缓存 TTL 长（30min）
  → HTTPDNS 挂 30 分钟用户无感 ✓
  → 切流慢：故障厂商要摘 30 分钟 ✗

"提高 HTTPDNS 可用性"不能解决这个对立，只能降低它的触发概率
```

**解法是把一个旋钮拆成两个：soft TTL + hard TTL。**

```
soft_ttl = 60s    正常情况下过期即刷新 → 切流速度由它决定
hard_ttl = 30min  刷新失败时仍可继续使用旧结果 → 容灾能力由它决定

即 stale-while-revalidate：
  · now < soft          → 直接用
  · soft < now < hard   → 用旧值 + 异步刷新（失败则继续用旧值）
  · now > hard          → 必须刷新，失败则走系统 DNS 兜底
```

**两个能力就都拿到了，代价只是客户端多一个字段。** 这类"看起来必须二选一"的对立，很多时候是因为把两个语义压在了同一个参数上——**先问"这个参数在为几件事服务"，往往比在两难之间找平衡点更有价值。**

**第二个必须提前知道的事：容灾路径会让你暂时退回你花大力气摆脱的架构。**

回退系统 DNS = 回退到 CNAME 解析 = 陷阱 1 里说的"把调度权交给 CDN 厂商"。故障期间：

| 能力 | 状态 |
|------|------|
| 区域级质量调度 | 失效（厂商自己决定用户去哪个节点） |
| 成本权重调度 | 失效（可能全部打到最贵的厂商） |
| 故障厂商摘除 | 失效（如果同时有厂商故障，摘不掉） |
| 基本可播 | 保住 ✓ |

**这不是设计缺陷，是兜底路径的必然代价——但必须写进预案。** 否则 HTTPDNS 故障期间会同时出现"带宽成本异常告警"和"质量分全线中性"，值班人会把它当成第二起、第三起故障去排查。**兜底降级带来的次生异常，应当在预案里预先声明为"预期现象"，而不是让人在故障中现场推断。**

### 场景：CDN 回源率异常导致带宽翻倍

```
触发：边缘缓存 LRU 参数误调 → 边缘命中率从 90% 掉到 40%
      → 大量流量回源，内网带宽暴涨，同时边缘回源计入成本
检测：
  1. 按 CDN 分组的边缘命中率监控，跌破 80% 告警
  2. 回源带宽监控（对象存储出网 + CDN 回源），超预算告警
  3. 与 QoE 联动：命中率下降时卡顿率是否同步上升
处理：
  1. 回滚 LRU 配置（配置必须可秒级回滚）
  2. 热点内容重新预热，恢复边缘命中率
  3. 复盘：边缘配置变更为什么没有做成本影响预演
预防：边缘配置变更强制"命中率 + 回源成本"预演 + 分钟级成本告警
```

**命中率是一个乘性放大器，这一点决定了告警阈值该定在哪。**

```
命中率 90% → 回源率 10%
命中率 40% → 回源率 60%

命中率降了 56%（相对），回源量涨了 6 倍

常态回源 ≈ 172 PB/月（2,149 PB × 8%，对应成本表的 ~180 PB）
异常回源 ≈ 1,289 PB/月（× 7.5）
```

**回源侧的所有容量——中心出口带宽、对象存储 QPS、内网链路——都是按 8-10% 的回源率设计的。命中率的小幅下降会以 6-7 倍放大打到这些容量上。** 所以"跌破 80% 告警"这个阈值需要重新检查：90% → 80% 意味着回源率从 10% 翻到 20%，回源容量已经**翻倍**了。**告警应该定在 87% 左右（回源率 +30%），而不是 80%（回源率 +100%）。** 用命中率定阈值容易低估严重性，**正确做法是把阈值直接定在回源率上**——它才是被冲击的那个量。

**这个场景与场景 1（切流打挂承接方）是同一个机制的两种触发方式：**

| | 场景 1 | 本场景 |
|---|--------|--------|
| 触发 | 流量搬到冷边缘 | 边缘缓存被误配置清空 |
| 机制 | **缓存亲和性失效 → 回源放大** | 同 |
| 后果 | 承接方被打挂 | 中心出口被打满 |
| 共同结论 | **回源容量必须按"缓存大面积失效"预留，而不是按常态回源率** | 同 |

**检测里的第 3 条（与 QoE 联动）是滞后信号，不能作为主判据。** 回源虽然慢，但只要中心还扛得住，用户只是首帧多几十毫秒——**QoE 会在中心被打满的那一刻断崖式恶化，而不是随命中率线性恶化。** 靠 QoE 发现回源异常，等于等到雪崩才知道。**回源率必须有独立告警。**

**最后一条：为什么"配置变更做预演"这件事在 LRU 参数上特别难。**

```
缓存容量 → 命中率 的关系由内容访问的 Zipf 分布决定，是【凹函数且有相变】

容量 100% → 命中率 90%
容量  80% → 命中率 89%    ← 几乎不动，线性外推会以为很安全
容量  60% → 命中率 85%
容量  40% → 命中率 62%    ← 越过拐点
容量  30% → 命中率 40%    ← 断崖

拐点位置取决于当期的内容热度分布，会随热点事件移动
```

**所以 LRU 参数不能做线性外推的预演，也不能用历史数据算一次就固定下来。** 唯一可靠的做法是**真实小流量灰度**（单节点或单区域先改，观察实际命中率），并且**把命中率-容量曲线作为一个持续测量的量**——因为拐点会移动。这也解释了复盘里那个问题的答案：不是团队偷懒不做预演，而是**这个参数的预演在方法上就不可能靠计算完成**。

### 场景：播放器 ABR 升级引入画质抖动

```
触发：ABR 升级后降档策略过激进 → 网络轻微波动就降码率
      → 画质频繁上下跳（用户感知"画质抽风"），投诉率上升
检测：
  1. 按 app_version 聚合的"码率切换频率"监控，超阈值告警
  2. 同版本卡顿率对比（卡顿没降、切档狂涨 → 判定过激进）
  3. 用户反馈"画质跳"类问题的聚类
处理：
  1. 远程配置灰度关闭新 ABR 逻辑，回退旧策略
  2. 调整降档判据（缓冲水位阈值从 2s 放宽到 3s）
  3. 修复后小流量灰度，观察码率切换频率恢复后再放量
预防：ABR 变更必须过"码率切换频率 + 卡顿率"双指标回归 + 可远程回滚
```

**这是场景 3 的同构问题：故障让所有标准指标变好了。**

```
激进降档之后：
  卡顿率      1.0% → 0.6%   （变好！降得早，当然不卡）
  首帧        不变
  播放成功率  不变
  平均码率    1.5 → 1.1 Mbps（带宽还省了！）
  切换频率    0.8 → 6 次/次播放   ← 唯一的坏信号

→ 播放器团队看到"卡顿降 40%、带宽省 27%"，会认为这是一次成功发版
→ 而用户体验实际是变差的
```

**切档频率必须是一个一等指标，因为它不在任何标准 QoE 指标里，也不能从它们推出来。** 这与场景 3 是同一个教训的两个实例：**当一个手段的代价不在现有指标体系中时，这个手段一定会被过度使用。**

**量化用户感受，说明为什么"少卡顿"换不来"多切档"：**

```
32s 短视频里切 6 次档 = 每 5.3 秒一次画质变化
用户感知：整个观看过程都在"抽风"，且无法预期

而 1.0% 的卡顿率意味着：100 次播放里 1 次卡一下
用户感知：偶发，且有明确归因（"我这网不行"）

→ 卡顿是【偶发且可归因】的，抖动是【持续且不可理解】的
→ 用户对稳定低画质的容忍度远高于对画质抖动的容忍度
```

**这直接改写 ABR 的目标函数。** 不是"在不卡顿的前提下最大化平均码率"，而是：

```
maximize  E[码率] − λ · 切换次数 − μ · 卡顿时长

λ 的量级由 AB 实验定，但它一定不为 0 ——
目标函数里没有切换惩罚项，是"激进降档"能通过所有评审的根本原因
```

**处理步骤 2 里有一个可能让修复变成加剧的陷阱。**

"降档阈值从 2s 放宽到 3s"只动了一侧。回顾上文推导过的死区约束：

```
必须满足：downshift_threshold < upshift_threshold − hysteresis

若原配置 downshift=2s, upshift=3s  → 死区 1s，勉强可用
放宽 downshift 到 3s               → 死区 0s
                                   → 水位在 3s 附近时升降档条件同时成立
                                   → 每个决策周期都切一次，抖动【更严重】
```

**"放宽降档阈值"这个动作听起来是在减少切换，实际可能是在消灭死区。** 正确的修复是**同时抬升两侧并检查死区**：`downshift=3s, upshift=5s`，死区 2s。**任何只调一侧阈值的 ABR 变更都应当被拒绝**——阈值对是一个整体，单独改一个就是改死区。

**预防里的双指标回归不够，必须是三项。**

```
只看"切换频率 + 卡顿率"，一个【永远停在最低档】的 ABR 会完美通过：
  切换频率 = 0（从不切换）✓
  卡顿率   = 0（码率极低）✓
  平均码率 = 0.5 Mbps      ← 没人在看这一项

→ 回归必须是【平均码率 + 切换频率 + 卡顿率】三项同时不劣化
→ 三项之间互相制约，缺任何一项都能被一个退化策略骗过
```

**"三项互相制约"是 ABR 回归测试的完整性条件，不是保险起见多加一项。** 判据：能不能写出一个通过全部回归指标但明显更差的策略？如果能，指标集就是不完备的。

### 场景：自建边缘节点区域过载

```
触发：某区域自建边缘突发流量（本地爆款内容）超过节点容量
      → 该区域自建节点 P99 劣化，开始影响播放体验
检测：
  1. 自建节点 CPU/带宽/连接数监控，超 70% 预警、超 85% 告警
  2. 该区域播放成功率与卡顿率监控
  3. 节点容量水位与容量规划数据对比
处理：
  1. 调度把该区域 30% 流量切回商业 CDN（自建是弹性层，不是必选层）
  2. 爆款内容强制开启 P2P 分担
  3. 评估该区域是否扩容（流量增长是否趋势性）
预防：自建边缘容量按"均值 × 2"预留 + 溢出自动切商业 CDN + 趋势性扩容评估
```

**先验证"均值 × 2"这条规矩与成本表是否自洽——结论是完全吻合，而且它推出了一个必须说明的设计意图。**

```
自建边缘按字节占比 = 1,020 / 2,250 = 45%
全站均值带宽 8.9 Tbps → 自建均值需求 = 8.9 × 45% = 4.0 Tbps
"均值 × 2" 预留       → 自建供给 = 8.0 Tbps  ✓ 与容量账本的 8 Tbps 一致

但：全站峰值 26.7 Tbps → 自建峰值需求 = 26.7 × 45% = 12.0 Tbps
    供给只有 8.0 Tbps → 峰值必然溢出 4.0 Tbps 到商业 CDN
```

**所以自建边缘在每天的晚高峰都会溢出，这不是容量不足，是"基线自建 + 溢出上云"原则的具体数字。** 但如果预案里不写清楚，晚高峰的溢出告警会被当成故障处理——**每天一次的"故障"，两周后就没人看了**（和斜率告警被静音是同一个失效模式）。**告警必须区分"计划内溢出"与"计划外过载"：前者判据是全站带宽同步处于高位，后者是本区域独立冲高。**

**处理步骤 1 有一个成本副作用，方向和直觉相反。**

自建边缘的成本是**固定资产摊销**，不随流量变化。切走流量不省钱，只降低负载率，从而**推高单位成本**：

```
¥0.018/GB 是在某个负载率下摊出来的（满载理论值 ¥0.008/GB
→ 隐含负载率约 44%）

切走 30% 流量 → 负载率 44% × 0.7 = 31%
              → 单位成本 ¥0.008 / 0.31 = ¥0.026/GB

仍低于商业 CDN 的 ¥0.045/GB → 切是对的 ✓
但溢出的那 30% 要按 ¥0.045 付费，而自建的资产钱一分不省
→ 这 30% 流量的实际成本 = ¥0.045（商业） + 自建闲置摊销
```

**结论不变（切流保体验是对的），但要知道账是怎么算的：溢出切商业 CDN 是"花两份钱买一份流量"。** 这决定了它只能是应急手段——**如果它频繁触发，说明容量规划错了。**

**而这里有一个比过载更隐蔽的问题：过载会告警，闲置不会。**

```
自建节点负载率 85% → 技术告警 ✓ → 有人处理
自建节点负载率 20% → 【没有任何告警】→ 没人处理

而对固定资产，闲置是比过载更大的浪费：
  过载：体验受损，切流可缓解，损失有界
  闲置：钱已经花了，永久损失，且不断累积
```

**这是场景 2 的镜像。** 场景 2 说的是"带宽成本没有技术信号，因为 CDN 不会拒绝流量"；这里说的是"资产闲置没有技术信号，因为闲置的系统一切正常"。**两者是同一条原理的两面：技术监控只能发现"系统在受苦"，发现不了"钱在受苦"。**

**所以自建边缘必须有一个与利用率挂钩的成本告警：**

```
单位成本告警：自建边缘折算 ¥/GB 连续 7 天高于商业 CDN 的 80%
  → 触发"缩容或增加承载"评审

而不是等年度预算复盘时才发现某区域的节点一直在半空转
```

**判据：自建边缘的月度报表里，有"单位成本 ¥/GB"这一行吗？** 如果只有"承载流量"和"节点数"，那么闲置永远不会被发现——**因为这两个数字单独看都很正常。**
