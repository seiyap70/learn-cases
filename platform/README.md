# 统一内容平台架构蓝图

> 把「内容平台」与「视频平台」当作**一个统一平台**（图文 + 短视频 + 长视频 + 直播一体）来做全栈架构规划。
> 规模假设：亿级 DAU 终局。技术栈：多语言混合按域选型。

## 这套蓝图与 `cases/` 的关系

仓库根目录的 [31 个架构案例](../README.md) 是**单点纵深**——每篇聚焦一个孤立难题（秒杀、推荐、审核、弹幕……），自成一体。

本目录是**平台级横向视野**。真实内容平台是几十个业务域彼此咬合的整体，而最难的部分恰恰不在单个域内部，而在**域与域的边界上**：

- 投稿链路 30 分钟的 SLA，如何切分给上传 / 转码 / 审核 / 索引四个域？
- 转码档位决策同时受播放 QoE、CDN 成本、存储成本三方约束，该由谁拍板？
- 审核的"先审后发"与推荐的"抢冷启动窗口"直接冲突，怎么调和？

**两者是「面 × 点」的互补**：蓝图负责域划分、边界契约、选型总纲、跨域场景串讲；单域的纵深实现细节，能引用现有案例的就引用，不重写。

## 规模基线

全篇所有设计与选型均以此组数据为依据（DAU 2 亿、人均 80 次播放、均播 32s、均码率 1.5 Mbps）。

| 指标 | 数值 |
|------|------|
| DAU | 2 亿 |
| 日播放量（VV） | 160 亿 |
| 播放请求 QPS | 均值 18.5 万 / 峰值 64.8 万 |
| Feed 请求 QPS | 均值 1.85 万 / 峰值 6.5 万 |
| 日出流量 | 96 PB |
| 平均 / 峰值带宽 | 8.9 Tbps / 26.7 Tbps |
| 日新增内容 | 图文 800 万、短视频 500 万、长视频 5 万、直播 40 万场 |
| 稳态存储存量 | 534 PB（运营第 3 年，含生命周期策略） |
| 日转码素材量 | 3 亿秒 |
| 点赞 / 弹幕峰值 QPS | 23 万 / 9 万 |
| 工程团队规模 | 742 人 / 十四个业务域 |
| 月度技术成本 | ¥1.17 亿（单位 DAU ¥0.59） |

**贯穿全篇的第一结论**：**带宽与存储合计占总成本九成以上，其余全部加起来不到 7%。** 亿级 DAU 内容平台的第一约束是**成本**——具体说是**字节数**（传输的字节 + 留存的字节），不是延迟也不是并发。这颠覆了常规架构直觉，并驱动了窄带高清、AV1 分层编码、P2P 分担、多 CDN 议价、JIT 按需转码、EC 纠删码、转码副本回收等一整套决策。架构优化的优先级应当等于成本占比排序。

> **这个结论有两个口径，必须分开说**——混用它们是本仓库此前的一处错误（README 与 P00:55 都把"¥1.44 亿"与"占 73%"并列，而这两个数来自不同口径）：
>
> | 口径 | 带宽 | 存储 | 两者合计占比 | 总成本 |
> |------|------|------|------------|--------|
> | **朴素方案**（H.264 2.4 Mbps，全量商业 CDN，存储三副本） | ¥23,040 万（73.0%） | ¥6,409 万（20.3%） | **93.3%** | ¥31,559 万 |
> | **优化后**（编码升级 + P2P + 预加载 + 自建边缘；分层 + EC + 副本回收） | ¥9,220 万（80.0%） | ¥1,258 万（10.9%） | **90.9%** | ¥11,528 万 |
>
> 上表 73% / 20.3% 属于**朴素方案**；¥1,258 万属于**优化后**。而 **¥1.44 亿 = 96 PB/日 × 30 × ¥0.05/GB 是第三个数**——它是"编码升级已完成、但 P2P / 预加载 / 自建边缘都还没做"的中间态，因为规模基线里的 96 PB @ 1.5 Mbps **本身已经含了编码升级**。全篇把 ¥1.44 亿当作降本手段的**共同分母**使用（P02、P06、P09、P11 均如此），这是合理的；但它既不是 73% 对应的分子，也不是 ¥1.17 亿的组成部分。**三个数各有各的口径，谁也不能替谁。** 完整推导与四项手段"收益不可相加"的乘性修正见 [P06 §降本手段的收益不可相加](p06-delivery-qoe.md)。

## 贯穿全篇的六条设计原则

从 P00/P01 的具体决策中提炼出的可复用原则：

1. **统一在"内容"，差异下沉到"媒体"** —— "内容"是业务对象（所有形态同构），"媒体"是物理载体（完全异构）。混淆两者是内容平台架构腐化的起点。判据：如果推荐系统里出现 `if content_type == VIDEO`，说明抽象边界画错了。

2. **架构优化的优先级 = 成本占比排序** —— 带宽 73% > 存储 20% > 转码 3.5% > 其余。前两项合计 93%，工程资源应按此比例投放。注意存储容易被低估——因为人们习惯用年增量而非稳态存量估算，且容易忘记三副本冗余把物理占用放大 3 倍。

3. **把二元决策变成连续谱系** —— "发/不发"改成"发多少"（分级曝光池）、"自建/上云"改成"基线自建+溢出上云"。二元决策必然牺牲一方；连续谱系能让双方都拿到大部分收益。

4. **状态单写方** —— `content.status` 只有编排层能写，其他域一律发事件。多写方并发是状态机乱序的唯一根源。

5. **按可逆性分配论证精力** —— 内容 ID 方案（不可逆）值得两周论证，某内部服务用 Go 还是 Java（两周可重写）值得两小时。工程师习惯按"技术优劣"选型，却很少评估"选错了多久能改回来"。

6. **异构的复杂度必须被框架吸收** —— 5 种语言、9 种存储、3 套消息中间件的选择判断不能暴露给业务开发者。业务声明数据/事件的**特征**，框架决定落到哪个后端，并在声明与能力不匹配时**主动报错**。
