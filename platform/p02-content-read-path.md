# P02: 统一内容平台的内容读链路与缓存体系

## 业务场景

承接 P00 的十四域划分与 P01 的技术选型，本篇聚焦**读侧**：从用户发出一次请求到屏幕上渲染出内容的整条路径。写侧（投稿、转码、审核）在 P03/P04 展开，读侧是全平台**最高频、最容易在域边界上烂掉**的部分。

**已知数据：**
- Feed 请求：均值 1.85 万 QPS、峰值 6.5 万 QPS，每次返回 30 条内容
- 播放请求峰值：64.8 万 QPS
- 内容元数据：80 亿行（图文 60 亿 + 视频 20 亿），单条约 2 KB
- 互动状态读：点赞 / 收藏 / 关注关系，随 Feed 每次请求都要回填
- 冷启动到 Feed 可渲染预算：200ms（P95）
- 计数写入峰值 23 万 QPS，与读侧展示解耦

**为什么读链路是全平台最难做对的部分？**

写侧的问题可以在一个域内部消化（队列、限流、重试），读侧的问题**天然发生在域边界上**。一条 Feed 里的 30 条内容，元数据在内容中台、统计在计数服务、作者在账号域、点赞状态在互动域、关注状态在关系域——一次请求要穿过 5 个域。

而读侧最大的放大器是**扇出**：一次 Feed 请求 × 30 条内容 × 每条 5 类字段，朴素实现是 150 次子请求。6.5 万 QPS 峰值下就是 **975 万次/秒的 RPC**——这还没算进详情页、播放、搜索。扇出不治理，任何域的一丁点抖动都会被放大成全局事故。

**核心矛盾**：**用户的延迟预算只有 200ms，而一次请求需要聚合 5 个域的数据；缓存能挡住绝大部分读，但缓存的一致性要求（下架必须实时、统计可以最终一致）是分级且冲突的。** 本篇解决的是"如何让读链路在 200ms 内、5 个域的依赖下，既不慢、又不错、还不塌"。

## 核心挑战

### 挑战 1：跨域读扇出——一次请求穿过 5 个域

一次 Feed 请求返回 30 条内容，每条内容的完整视图需要：

| 字段 | 来源域 | 数据 |
|------|--------|------|
| 标题 / 封面 / 状态 / 类型 | 内容中台 | content + content_ext |
| 播放 / 点赞 / 评论数 | 计数服务 | content_stat |
| 作者昵称 / 头像 / 是否认证 | 账号域 | author |
| 当前用户是否已赞 / 已收藏 | 互动域 | 域 10 |
| 当前用户是否关注该作者 | 关系域 | 域 2 |

朴素方案是每条内容 5 次子调用 → 每请求 150 次 → 峰值 975 万 RPC/s。但 RPC 总量不是最致命的，**尾延迟放大**才是。

聚合请求的耗时由**最慢的那个子调用**决定，所以只要有一个子调用落进长尾，整个 Feed 就慢。设单次子调用超过 100ms 的概率为 p，扇出度为 N，则"这个 Feed 请求至少踩到一次慢调用"的概率是 `1 - (1-p)^N`：

| 扇出度 N | 单次慢调用概率 p | 该请求含慢调用的概率 | 含义 |
|---------|----------------|-------------------|------|
| 150 | 1%（P99=100ms，很常见的健康水位） | **77.8%** | 四分之三的 Feed 都慢 |
| 150 | 0.1%（P999=100ms，已是顶级水位） | 13.9% | 仍然一成多的 Feed 慢 |
| 30 | 1% | 26.0% | 依然不可接受 |
| **6** | **1%** | **5.9%** | 勉强压进 P95 预算 |
| 6 | 0.1% | 0.6% | 舒适 |

反过来解这个不等式更有说服力。要让聚合的 P95 达标（含慢调用的概率 ≤ 5%），单次子调用的慢概率必须满足 `p ≤ 1 - 0.95^(1/N)`：

```
N = 150  →  p ≤ 0.034%   即要求每个域做到 P9997 < 100ms
N = 30   →  p ≤ 0.171%   即要求每个域做到 P998  < 100ms
N = 6    →  p ≤ 0.854%   即要求每个域做到 P99   < 100ms
```

**这是本篇最重要的一个数字关系：把扇出从 150 压到 6，等价于把对每个下游域的稳定性要求从"P9997 达标"降到"P99 达标"——从一个只能靠运气维持的指标，变成一个可以靠工程运维守住的指标。** 扇出治理的本质不是省 RPC，是**把不可能的 SLA 要求变成可能的**。

难点不只是"快"，而是**扇出要有预算、要有合并、要有降级**——什么时候可以砍掉某个字段，砍掉之后用户看到什么。

### 挑战 2：缓存一致性是分级的，但常被当成一个问题处理

读侧的数据变更可以分成三类，失效的时效要求完全不同：

| 变更类型 | 例子 | 失效时效 | 若延迟的代价 |
|---------|------|---------|------------|
| 监管 / 版权强失效 | 下架、封禁、可见范围改为私密 | **< 1 秒** | 违规内容仍在传播 = 生存风险 |
| 用户可见元数据 | 作者改名、封面替换、标题修改 | < 5 秒 | 用户看到旧信息，观感差 |
| 统计类 | 播放数、点赞数 | 60 秒内即可 | 用户感知不到 60 秒内的统计差 |

难点在于**用一套机制统一处理三类失效必然失败**：按最强的（下架）设计，元数据每改一次就全网清缓存，编辑频繁的热门内容缓存形同虚设；按最弱的（统计）设计，下架后缓存还顶 60 秒，违规内容继续可看。缓存一致性的正确姿势是**给三类变更配三套失效通道**。

**但"分三级"这个答案会遇到一个必然的退化，必须提前设计对策：谁来判定一次变更属于哪一级？**

```
若由调用方在调失效接口时选级别：
  业务开发者面对"选强了浪费缓存 / 选弱了可能出事故"这个选择，
  且【浪费缓存的代价不由他承担，出事故的责任由他承担】
  → 理性选择永远是选最强的
  → 三个月后所有变更都走 F 级，三级退化成一级，且没人发现
```

**分级机制的崩塌不需要任何人犯错，只需要每个人各自做理性选择。** 这类退化的共同特征是：**代价的承担方与决策方分离。** 修法只有一个方向——把决策权从调用方手里拿走：

```
级别由【字段】决定，不由调用方决定：
  投影注册表（content_projection_field）里每个字段标注失效级别
    status / visibility / copyright_state → F 级（< 1s）
    title / cover / author_name           → M 级（< 5s）
    play_count / like_count               → S 级（60s）
  变更哪个字段，就走哪个通道，调用方【无法选择】

想让一个字段升级到 F 级，要改注册表，走评审 —— 有成本、有归属
```

**第二个必须知道的耦合：弱通道的回填是强失效的对手。**

```
T+0.0s  下架，F 级通道清掉 L1-L5 的 content:{id}   ✓
T+0.3s  统计通道的 60s 聚合任务恰好完成，用它手里的
        【聚合前读到的旧快照】回填 content:{id}     ✗
        → 下架的内容重新出现在缓存里，且 TTL 重新计时
T+60s   下一轮统计通道再次回填 …

→ 失效成功了，内容仍然可见。而失效通道的监控显示一切正常
  （它确实删掉了，是别人又写回来的）
```

**所以 F 级失效不能只是"删除"，必须留墓碑（tombstone）。** 删除是幂等的但不是排他的——它阻止不了后续写入。墓碑（一个带 TTL、标记为"此 key 已强失效至 T"的短记录）让任何回填在写入前先检查，从而把"删除"升级为"禁止重建"。**判据：问失效通道的实现者"删完之后，谁能把它写回来"**——答不出全部写入方就说明缺墓碑。

**第三点："< 1 秒"这个 SLA 的作用域必须写清楚，因为它对客户端不成立。**

```
服务端五级缓存：可推送、可清除 → 1 秒可达 ✓
客户端本地缓存：不可靠推送（离线、后台被杀、弱网）→ 1 秒不可达 ✗

→ "< 1 秒"只能承诺到服务端边界
→ 已经下发到客户端的内容，只能靠【播放前校验】这条独立通道拦住
```

**这正是后文"可见"与"可播"分离的根据**：可见性靠缓存失效（尽力而为，服务端 1 秒），可播性靠播放前的实时校验（强保证，不依赖任何缓存）。**违规内容治理的红线挂在后者上，不挂在前者上**——因为前者在客户端这一段物理上无法保证。**把 1 秒 SLA 当成端到端承诺，是这类合规设计里最常见的越界。**

### 挑战 3：热点内容的读放大——1% 的内容吃掉 80% 的播放

内容消费极度偏斜：1% 的内容占 80% 的播放，一条爆款能在数小时内被上亿人访问。**关键是这个偏斜是嵌套的**——在头部 1% 内部，分布同样陡峭，最终会收敛到"若干条内容各自吃掉全站个位数百分比的读"。

把这件事换算成单个 Redis 分片上的负载，问题的严重性才显出来：

```
单条头部内容的读 QPS = 播放侧 + Feed 曝光侧

  播放侧：峰值播放 64.8 万 QPS，头部单条占全站播放 5%（重大热点的实测量级）
          → 3.24 万 QPS
  曝光侧：峰值 Feed 6.5 万 QPS × 30 条 = 195 万条/秒的元数据读
          该内容出现在 20% 的 Feed 里 → 195 万 × 20% ÷ 30 ≈ 1.3 万 QPS
  ─────────────────────────────────────────────────────────────
  合计 ≈ 4.5 万 QPS，全部落在 content:{id} 这一个 key 上
```

而单个 Redis 分片的运维上限约 5 万 QPS——**不是带宽打满，是 CPU 打满**：Redis 单线程处理 2 KB value 的 GET，实测约 8-10 万 QPS 见顶，扣掉不能跑满的余量（尾延迟在 70% 负载后急剧恶化）与主从复制开销，运维上限就在 5 万 QPS 附近。带宽侧反而宽裕：2 KB × 5 万 = 100 MB/s = 0.8 Gbps，万兆网卡毫无压力。**这个"CPU 先于带宽见顶"的判断决定了解法方向：加大内存没用，必须分散请求。**

于是：

- 一条爆款就能吃掉一个分片 90% 的处理能力，**并把同一分片上其他几十万条无关内容一起拖慢**——缓存从"挡压力"变成"故障放大器"
- 热点 key 一过期，回源流量瞬间打穿 DB——这是"击穿"，和"雪崩""穿透"合称缓存三兄弟
- 热点内容的每次读都是相同的字节在网络上重复传输，是带宽成本（占 73%）的直接来源

热点治理不能靠"加大缓存"，要靠**把同一个 key 拆成多个副本 + 本地缓存兜底 + 请求合并**——三者分别解决"分片内 CPU 集中""跨实例流量集中""失效瞬间回源集中"三个不同的集中。

### 挑战 4：同一个 content 要喂 6 种消费场景，传输字节也是钱

同一个 content 模型，Feed 卡片只要 14 个字段，详情页要 40+ 个，分享卡片只要 6 个，创作者后台要 25 个，播放前校验只要 5 个，嵌入第三方只要 8 个。全字段约 15 KB。

**这个成本要算对，而算对的关键是别漏掉 Feed 的 ×30。**

```
每条内容的浪费 = 15 KB（全字段）− 4 KB（Feed 卡片 14 字段）= 11 KB

一次 Feed 请求返回 30 条 → 单请求浪费 30 × 11 KB = 330 KB
                            ← 漏掉这个 ×30，结果会偏小 30 倍

Feed 均值 1.85 万 QPS × 330 KB = 6.1 GB/s
月度 = 6.1 GB/s × 2.592e6 s ≈ 15.8 PB/月
成本 = 1.58e7 GB × ¥0.05/GB ≈ ¥79 万/月
```

（原文的 ¥92 万对应约 2.15 万 QPS 的 Feed 均值，或含详情页等其他场景的合计。本文取 ¥79 万这个只含 Feed、可逐步复现的口径。）

**但接下来这一步必须做，而且它会削弱这个挑战原本的论证：把 ¥79 万放回总账里看占比。**

```
Feed 元数据的浪费流量 = 15.8 PB/月
全平台视频流量        = 2,880 PB/月

占比 = 0.55%
¥79 万 / ¥1.44 亿 = 0.55%
```

**按 P00 的第二原则"架构优化的优先级 = 成本占比排序"，字段裁剪排在 0.55% 这一档，远低于编码升级、P2P、预加载这些百分之几十的手段。** 所以原文"字段裁剪不是代码洁癖，是成本治理"这句话需要修正：**它确实是成本治理，但金额在总账里很小，不足以作为它的主要理由。**

**字段裁剪真正的价值在别处，而且这些价值更硬：**

| 收益维度 | 量级 | 为什么比带宽更重要 |
|---------|------|------------------|
| 首帧延迟 | 330 KB → 120 KB，弱网（1 Mbps）下省约 1.7s | 直接吃进首帧预算，而首帧预算只有 800ms 总额 |
| 客户端解析 | JSON 解析量降 73%，低端机的主线程卡顿显著 | Feed 滑动流畅度，无法用带宽换 |
| 服务端序列化 CPU | 序列化开销与字节数近似线性 | 6.5 万 QPS 峰值下是实打实的机器数 |
| Redis 网络与 CPU | value 更小 → 单分片 QPS 上限更高 | 直接放宽挑战 3 里那个 5 万 QPS 的红线 |

**最后一行是最值钱的：** 挑战 3 算出单分片上限 5 万 QPS 是基于 2 KB value 的。**value 从 15 KB 裁到 4 KB，同一个分片能承受的 QPS 上限会上移**，等于凭空拿到热点容量。**这个收益不出现在带宽账单上，所以按成本占比排序会把它排低——这是"按成本占比排序"这条原则的一个已知盲区：它只能看见出现在账单上的收益。**

**正确的表述是：字段裁剪的理由是延迟与容量，成本是附带收益。** 用 ¥79 万去说服评审会得到"只有 0.5%，不着急"的答复；用"它把 Feed 弱网首帧减 1.7 秒、把热点分片上限抬高"去说服，才对得上它的真实价值。

### 挑战 5：缓存三兄弟——雪崩、击穿、穿透

读侧挂在缓存上，缓存崩溃方式多样且都致命：

| 现象 | 成因 | 后果 |
|------|------|------|
| 雪崩 | 大量 key 同一时刻过期 | 回源风暴打垮 DB |
| 击穿 | 单个热点 key 过期瞬间 | 单点回源放大，打垮 DB |
| 穿透 | 查询不存在的 content_id | 绕过缓存直击 DB，恶意遍历即可拖垮 |

**这三个还漏了一个同后果的第四种，它防不住上面任何一条防护：**

| 现象 | 成因 | 为什么现有防护都拦不住 |
|------|------|-------------------|
| **缓存污染 / 冷数据踩踏** | 爬虫、批量任务、运营导出扫过大量冷内容，把热内容从 LRU 里挤出去 | 那些 id **全是合法存在的**——布隆过滤器放行、singleflight 无从合并（每个 key 只请求一次）、TTL 抖动无关 |

**后果与雪崩相同（热内容集体 miss → 回源风暴），但成因完全不同，所以防护也必须不同：** 按调用来源分池（离线/批量流量用独立的缓存实例或只读不写缓存），或对扫描型访问模式识别后禁止其回填。**判据：一个批量导出任务能不能把线上 Feed 的缓存命中率打下来？** 如果能，就缺这一层。

三个问题都要在**缓存层**解决，而不是寄希望于"DB 很能扛"。**而"DB 扛不住"这个论证需要说得更准确，因为字面上它是可以扛的：**

```
195 万 QPS 回源，单 MySQL 实例读上限约 1 万 QPS
→ 需要约 200 个实例组

技术上做得到。所以真正的论证不是"扛不住"，而是：

  99.5% 命中率下，DB 承载 = 195 万 × 0.5% ≈ 9,750 QPS ≈ 1 个实例组
  无缓存                  = 195 万 QPS      ≈ 200 个实例组

→ 缓存把 DB 容量需求降低 200 倍
→ 若 DB 必须按"缓存失效"的容量准备，就等于【缓存不产生任何容量价值】
  它退化成一个纯延迟优化，而 200 倍的成本收益全部作废
```

**这才是三兄弟必须在缓存层解决的真正理由：不是 DB 扛不住，而是让 DB 扛得住就否定了缓存的存在意义。** 缓存的经济价值完全等于它替代掉的下游容量，**所以命中率红线不是性能指标，是一条容量红线**——后文会用它推出 99.5% 这个具体数字。这也解释了为什么缓存崩溃类故障的正确应对是"保护缓存 + 限流兜底"，而不是"给 DB 扩容"：后者是在为一个不该发生的状态永久付费。

## 设计约束

- Feed 请求端到端 P95 < 200ms；单条内容聚合的缓存命中路径 < 10ms
- 下架 / 封禁 / 可见范围变更的缓存失效延迟 < 1s（监管与版权红线）
- 用户可见元数据变更失效 < 5s；统计类数据允许 60s 内最终一致
- 内容元数据缓存命中率目标 > 99.5%（L4），本地缓存命中率 > 70%（L3）
- 播放是最后底线：任一非播放域故障不得导致播放不可用
- 缓存代理层必须消化"雪崩 / 击穿 / 穿透"，DB 只承担兜底流量
- 禁止为每个字段单独建缓存（缓存一致性爆炸的根源）

## 设计解析

### 读路径全景：一次 Feed 请求的旅程

先画全图。读侧分成四段，职责严格分离：

```
┌──────────┐    ┌──────────┐    ┌──────────────┐    ┌─────────────────────┐    ┌──────────────────┐
│  客户端   │    │ 边缘网关   │    │    BFF        │    │   内容中台（读侧）      │    │     各域数据源       │
│ L1 本地   │───▶│ Go 接入层  │───▶│ Java 聚合/裁剪 │───▶│ 缓存代理 + 批量聚合    │───▶│ content / stat /  │
│ 缓存兜底  │    │ 鉴权/路由  │    │  Protobuf/JSON│    │  L3 本地 + L4 分布式    │    │ author / 互动 / 关系│
└──────────┘    └──────────┘    └──────────────┘    └─────────────────────┘    └──────────────────┘
    ▲  本地渲染                    ▲ 只关心"这个端                                     ▲ 只关心"数据在哪"
    │  版本自校验                  │ 要哪几个字段"                                     │ 不关心"谁在消费"
```

各段职责与"不该做什么"：

| 层 | 职责 | 不该做什么 |
|----|------|-----------|
| 客户端 L1 | 上次会话内容兜底、版本号自校验 | 不做业务聚合 |
| 边缘网关 | 鉴权、路由、限流 | 不做字段裁剪（不知客户端诉求） |
| BFF | 按端裁剪字段、协议转换（移动端 Protobuf / Web JSON） | 不做缓存一致性（那是中台的事） |
| 内容中台读侧 | 批量聚合、缓存代理、失效处理 | 不做端相关的字段决策 |
| 各域数据源 | 只回答"content_id/author_id 是什么" | 不做跨域合并 |

**一次 Feed 请求的延迟账本（预算 200ms）：**

```
用户下拉刷新
  │
  ├─ ① 边缘网关：鉴权 + 路由                     ≈ 5ms（缓存命中）
  ├─ ② BFF：组装批量参数，请求内容中台             ≈ 2ms
  ├─ ③ 内容中台：批量聚合（核心预算）              ≈ 60ms
  │      · L4 批量取内容元数据（命中）             ≈ 8ms
  │      · 批量取统计（计数服务本地缓存）           ≈ 6ms
  │      · 批量取作者信息（账号域批量接口）         ≈ 10ms
  │      · 并行取互动状态 + 关系状态               ≈ 12ms（并行）
  │      · 缺 key 回源 DB（少量，命中率 99.5%+）   ≈ 25ms（兜底）
  ├─ ④ BFF 字段裁剪 + 组装响应                    ≈ 5ms
  ├─ ⑤ 传输（30 条卡片 ~120KB，含压缩）           ≈ 30ms
  ▼ 渲染
```

关键设计判断：
1. **扇出只发生在内容中台一层**，BFF 与各域之间是"1 对 1"，各域与内容中台之间是"1 对 N 但批量"——把扇出压缩在单个边界上，而不是在每一层都扇出。
2. **互动 / 关系两个并行请求拿到最慢的那个**，因为它们数据量小（布尔 + 状态），是为数不多值得并行的部分；其余全部走批量。
3. 兜底回源只发生在**缓存 miss**，命中率 99.5% 时回源量不到总请求的 0.5%，不会成为瓶颈。

**这张账本必须按 P50 读，不能按 P95 读——这是延迟预算里最常见的误用。** 上表各项相加是 102ms，但它不是 P95 的 102ms，而是"典型请求"的 102ms（P00 实测 Feed P50 = 130ms，含客户端与网络的其余开销）。

P95 无法用"各段 P95 相加"求得，原因有两个方向相反的效应：

```
效应 A（让 P95 小于各段 P95 之和）：各段的慢是独立事件，不会同时发生
   若 5 段各自 P95 = 20ms、P50 = 8ms，
   则"5 段同时落在自己的 P95"的概率 = 0.05^5 = 3×10⁻⁷ —— 几乎不可能
   直接相加得 100ms，是一个几乎不会出现的悲观值

效应 B（让 P95 大于朴素估计）：并行段取 max，尾部被放大
   互动 + 关系两路并行，整体延迟 = max(两者)
   max 的 P95 严格劣于单路 P95：P(max ≤ t) = P(a ≤ t) × P(b ≤ t)
   要让 max 的 P95 = 20ms，需要单路 P975 = 20ms

正确做法：对整条链路的实测分布直接取分位数，不做分段合成。
分段账本只用于「定预算」与「找瓶颈」，不用于「预测 P95」。
```

落到本篇的目标上：**端到端 P95 = 185ms（P00 实测口径），P50 = 130ms，预算 200ms**。后文所有"达成"数字都按这个口径。**任何写着"P95 = 各环节预算之和"的设计文档，都还没有理解分位数不可加。**

### 缓存命中率的目标推导：99.5% 不是拍脑袋

设计约束里写着"L4 命中率 > 99.5%"。这个数字不是行业惯例，它是**从 DB 的承载能力反推出来的**——先确定底层能扛多少，再倒算缓存必须挡掉多少。

```
第一步：读侧打到存储层的总请求量
  Feed 峰值 6.5 万 QPS × 30 条 = 195 万条/秒 元数据读
  （播放请求 64.8 万 QPS 走播放地址签发，只读 5 个字段的 play_guard 视图，
    同样命中同一份内容缓存，此处保守只算 Feed 侧）

第二步：MySQL 只读副本池能扛多少
  单实例 32c128G + 4TB NVMe（P00 成本模型口径）
  主键点查、命中 buffer pool：单实例约 3-4 万 QPS
  但读侧兜底不能跑满——它同时承载 miss 回源与运营后台查询，
  且 miss 是突发的（雪崩时瞬间涌入），必须留 3 倍突发余量
  → 单实例可用于兜底回源的份额 ≈ 1.2 万 QPS
  → 8 台只读副本池 ≈ 9,600 QPS 稳态兜底能力，取整 1 万 QPS

第三步：反解命中率下限
  195 万 × (1 - h) ≤ 1 万
  → 1 - h ≤ 0.513%
  → h ≥ 99.487%   ⇒  目标定为 99.5%
```

**这条推导决定了"99.5%"这个数字的性质：它不是一个"越高越好的努力目标"，而是一条容量红线——跌破它，DB 就是被打死，不是变慢。** 命中率的敏感度非常陡峭，因为它作用在 195 万这个大基数上：

| L4 命中率 | 回源 QPS | 所需只读副本（1.2 万/台） | 副本月成本 | 结论 |
|----------|---------|------------------------|-----------|------|
| 99.9% | 1,950 | 2 台 | ¥0.5 万 | 舒适，但 L4 需更大热集 |
| **99.5%** | **9,750** | **8 台** | **¥2 万** | **设计目标** |
| 99.0% | 19,500 | 17 台 | ¥4.3 万 | 副本翻倍，仍可运营 |
| 98.0% | 39,000 | 33 台 | ¥8.3 万 | 副本池比主库还大，架构变形 |
| 95.0% | 97,500 | 82 台 | ¥21 万 | 已不是"缓存 + 兜底"，是"用副本硬扛" |
| 90.0% | 195,000 | 163 台 | ¥41 万 | **不可行**：连接数与复制延迟先崩 |

**读法：命中率从 99.5% 掉到 95%，看起来只差 4.5 个百分点，但回源量涨 10 倍、机器涨 10 倍。** 这就是为什么读侧的一切设计（热集选择、TTL 抖动、错峰 TTL、singleflight、布隆过滤器）都在围着"命中率不许掉"转——它是**唯一一个几个百分点的波动就能改变整个架构形态的指标**。

同样重要的是反向的一条：**命中率不必追到 99.9%。** 从 99.5% 提到 99.9% 只省 6 台副本（¥1.5 万/月），代价是 L4 热集要从 1% 扩到 3%（多 320 GB × 3 副本 ≈ 多 ¥26 万/月）。**过度追求命中率是负收益——缓存成本的增长比副本成本的下降快得多。** 99.5% 恰好是这条 U 型成本曲线的底部。

### 跨域读扇出的治理：批量、预算与降级

**扇出的第一准则是：合并接口，而不是拆散字段。** 内容中台向各域暴露批量接口，任何域都不允许"循环单查"：

```
内容中台对外暴露的批量契约（Protobuf）：
  BatchGetContentView(content_ids[])  → 统一层内容（content + content_ext 扁平化）
  BatchGetContentStat(content_ids[])  → 计数服务快照
  BatchGetAuthorBrief(author_ids[])   → 昵称/头像/认证/粉丝数
  BatchGetInteractStatus(uid, content_ids[]) → 是否已赞/已收藏/已投币
  BatchGetRelationStatus(uid, author_ids[]) → 是否关注/拉黑
```

**扇出预算**（内容中台内部的硬约束）：

| 规则 | 数值 | 理由 |
|------|------|------|
| 单次 Feed 聚合的子 RPC 数 | ≤ 6 | 超出说明边界画错了 |
| 单个子 RPC 的等待预算 | ≤ 15ms | 5 路并发的最慢值被 200ms 总预算卡死 |
| 单个批量请求的 id 数 | ≤ 100 | 见下文推导 |
| 可降级的子请求 | 互动 / 关系 | 丢了用户只看到"灰色互动"，不阻塞渲染 |
| 不可降级的子请求 | 内容元数据 / 统计 / 作者 | 缺了 Feed 卡片不完整 |

#### 批量大小的上界：为什么是 100，而不是"越大越好"

既然批量能省 RPC，直觉是批量越大越好——一次拉 500 条比拉 100 条更省。这个直觉在**摊销**上成立，在**尾延迟**上不成立。

摊销侧，收益很快饱和。单次批量调用的耗时可以拆成固定开销与变量开销：

```
T(N) = 固定开销 + N × 单条开销
     = 1.2ms（RPC 往返 + 序列化 + 调度）+ N × 0.05ms（单条查找与拷贝）

每条摊销成本 = 1.2/N + 0.05 ms

  N=1    → 1.250 ms/条
  N=10   → 0.170 ms/条    （比 N=1 降 86%）
  N=30   → 0.090 ms/条    （再降 47%）
  N=100  → 0.062 ms/条    （再降 31%）
  N=500  → 0.052 ms/条    （再降 16% —— 边际收益已基本枯竭）
  N=∞    → 0.050 ms/条    （理论下界）
```

**N=100 已经拿到了摊销收益的 96%（从 1.25 降到 0.062，理论下界是 0.05）。** 继续加大 N，收益不到 20%，而代价是两项线性增长的坏处：

| N | 单请求字节（2 KB/条） | 触及的 Redis 分片数 | 分片层慢概率 p=0.01% 时的整体慢概率 |
|---|---------------------|-------------------|--------------------------------|
| 30 | 60 KB | 30 | 0.30% |
| **100** | **200 KB** | **100** | **1.00%** |
| 200 | 400 KB | 200 | 1.98% |
| 500 | 1 MB | 480（打满全集群） | 4.69% |

第三列是关键，而且它把挑战 1 的公式**又用了一次**：批量接口并没有消除尾延迟放大，它只是把放大从"跨域 RPC 层"下推到"存储分片层"——一次批量拉 N 条，要等 N 个分片都响应，整体延迟仍是 `max`。

**批量之所以仍然是对的，是因为下推之后 p 小了两个数量级：** 跨域 RPC 的单次慢概率 p ≈ 1%（要过网络、过网关、过业务逻辑、过 GC），而 Redis 分片内一次内存查找的 p ≈ 0.01%（只有网络与单线程排队）。同样的公式，同样的 N，结果差 100 倍。

**所以批量大小的上界由三条同时约束，取最紧的一条：**
1. 摊销边际收益枯竭 → N ≤ 100（再大没意义）
2. 单请求字节不触发带宽告警（512 KB）→ N ≤ 256
3. 分片层尾延迟放大不超过 1% → N ≤ 100

三条交出来就是 **N ≤ 100**。Feed 一次只要 30 条，天然在预算内；**约定这条上限是为了防住"批量接口被当成万能查询口"**（见陷阱 8 与对应异常场景）。

**降级策略不是"超时重试"，而是"超时替换"：** 互动状态超时 → 返回 `unknown`，前端渲染成灰色按钮（点击再单独查询）；内容元数据超时 → 不重试，直接从缓存读上一个版本。

**为什么"重试是最差的降级"值得单独量化：** 重试的危害不是多等一个超时周期，而是**它在下游最虚弱的时刻给下游加压，形成正反馈**。

```
互动域正常容量 12 万 QPS，当前负载 9.75 万 QPS（Feed 峰值 6.5 万 × 1.5 次调用）
  ↓ 互动域某分片 GC，P99 从 10ms 恶化到 800ms
  ↓ 15ms 超时触发，客户端重试 1 次
  ↓ 互动域收到的流量变成 9.75 万 × 2 = 19.5 万 QPS（已超容量 62%）
  ↓ 过载 → 全部请求变慢 → 全部超时 → 全部重试
  ↓ 流量稳定在 2 倍，而容量因过载下降到 8 万 QPS
  ↓ 【亚稳态失败】即使最初的 GC 早已结束，系统也回不到正常态——
     因为维持故障的动力已经从"GC"变成"重试流量"自身
```

**这就是重试必须被禁止在扇出路径上的原因：它把一次持续 200ms 的 GC 抖动，变成一次需要人工介入（限流、停服冷启）才能退出的持续故障。** 允许的替代品只有三种：超时替换（返回 unknown）、读上一个版本（stale-while-error）、请求对冲（hedged request，且必须配额度上限，见下文）。

> **唯一允许的"重试型"手段是请求对冲（hedged request）**：在 P95 时刻（而非超时时刻）提前发出第二个请求，取先到的。它与重试的区别是**有总量配额**——对冲请求不得超过总请求的 5%，超过即熔断。没有配额的对冲就是重试，同样会引发亚稳态失败。

**结果合并的"空槽"策略：** 批量接口可能部分命中、部分缺。缺失的槽位不回源补查（那又是一轮扇出），而是：统计缺 → 展示 0 并标记"统计加载中"由前端二次补齐；元数据缺 → 该卡片降级为"内容已下架"占位。**宁可显示占位，不可因补查拖慢整体。**

**空槽策略有一条容易被忽略的硬规则：空槽率必须上报，且有熔断阈值。** 空槽对用户是"缺一张卡片"，对系统是"静默降级"——它不产生错误日志、不触发失败率告警，可以长期存在而无人发现。规则：单次 Feed 的空槽率 > 10%（30 条里缺 3 条以上）时，宁可返回 27 条也不返回 30 条含占位的卡片；空槽率整体 > 2% 持续 5 分钟即告警。**没有告警的降级不是降级，是掩盖。**

### 多级缓存体系：五级分层与失效手段

读链路依赖五级缓存，每一级解决不同的读放大问题：

| 级别 | 载体 | 容量 | 目标命中率 | 失效手段 | 典型 TTL |
|------|------|------|-----------|---------|---------|
| L1 客户端 | 客户端本地（MMKV/SQLite） | 千条级 | 兜底渲染 | 服务端版本号自校验 | 会话级 |
| L2 边缘 | CDN 私有缓存（公开数据） | 按响应 | 低（Feed 高度个性化） | 主动清除（仅公开数据） | 60s |
| L3 进程内 | 内容中台本地缓存（Caffeine） | 8GB/实例 | >70% | 版本号 + 短 TTL | 60s |
| L4 分布式 | Redis Cluster | 160GB+ 热集 | >99.5%（对 L3 miss） | 事件主动失效 | 10min 抖动 |
| L5 存储 | MySQL 256 表 + 只读副本池 | 80 亿行 | 兜底 | — | — |

**为什么 L3 本地缓存能挡 70% 的读？** Feed 消费有强局部性——同一个用户短时间内反复翻 Feed、同一个热门列表被大量用户短时间内同时访问。这部分流量命中 L3 时连 Redis 的网络开销都省了，还能顺手扛住热点（见后文）。代价是一致性弱（60s TTL + 版本号），由失效分级来兜。

#### 五级缓存的容量与命中率推导

上表的每个数字都可以推出来，且推导过程会暴露一个**容易致命的隐含假设**。

**先定分布模型。** 内容读的偏斜可以用 Zipf 刻画：秩为 r 的内容被读到的概率 ∝ 1/r^α。取 α ≈ 1（调和分布）时，前 k 条内容占总读量的比例约为 `ln(k)/ln(N)`。用它校验已知事实：

```
N = 80 亿（内容元数据总量）
前 1%（8,000 万条）占读量 = ln(8×10⁷)/ln(8×10⁹) = 18.20/22.80 = 79.8%
                                                          ≈ 80%  ✓
```

**"1% 的内容占 80% 的播放"这条经验事实，恰好等价于 α ≈ 1 的 Zipf 分布**——这不是巧合，是长尾内容消费的普遍形态。有了模型就可以定容量：

**L3（进程内，8 GB/实例）：**

```
容量换算：8 GB ÷ 2 KB/条 = 400 万条
内容中台实例数：单实例承载约 800 QPS 的 Feed 聚合（6 路批量 + 30 条合并 + 投影）
              → 6.5 万 ÷ 800 ≈ 81 台，按 100 台部署

L3 命中率 = ln(4×10⁶)/ln(8×10⁹) = 15.20/22.80 = 66.7%
实测 70%（Zipf 之外还有会话局部性：同一用户 30 秒内翻两页，第二页
          的作者、合集、相关推荐大量复用第一页已缓存的对象）
```

**L4（分布式，160 GB 热集）——这里有一个必须讲清楚的坑。** 如果直接沿用上面的模型算 L4，会得到一个错误结论：

```
【错误推导】
L4 装前 8,000 万条（1%），覆盖 79.8% 的读
L3 已经吃掉前 400 万条对应的 66.7%
→ L4 对 L3-miss 的命中率 = (79.8% - 66.7%) / (100% - 66.7%) = 39.3%

39.3% ≪ 99.5%，差了一个数量级。哪里错了？
```

错在**用播放分布去设计 Feed 缓存**。两条链路的读分布完全不同：

| 维度 | 播放（VV）分布 | Feed 曝光分布 |
|------|--------------|--------------|
| 入口 | 推荐 + 搜索 + 分享链接 + 收藏 + 历史 + 深链 | **只有推荐** |
| 可触达范围 | 全部 80 亿条（三年前的老视频可以被搜到、被分享） | 推荐候选池内 |
| 有效 N | 80 亿 | **约 1 亿**（近 7 日新内容 9,100 万 + 存量精品约 2,000 万） |
| 长尾 | 真实存在且很长 | 被候选池物理截断 |

**推荐系统只会曝光候选池里的内容，这个池是有界的**——这就是 L4 命中率能到 99.5% 的结构性原因。重算：

```
【正确推导】
有效 N = 1 亿（Feed 曝光候选池）
L4 常驻集 = 一个 TTL 窗口内被触达过的 key ≈ 8,000 万
前 8,000 万占池内读量 = ln(8×10⁷)/ln(10⁸) = 18.20/18.42 = 98.8%
再加上按需填充（长尾 key 首读即入 L4，同一窗口内后续读全部命中）
→ 实测 99.5% ✓
```

**这个坑的普适教训：缓存必须按它自己服务的那条链路的读分布来设计。** 用播放分布设计 Feed 缓存会低估命中率、超配容量；反过来用 Feed 分布设计播放缓存会高估命中率、然后在上线后被长尾打穿。P05 的存储分层用的是播放分布（因为那里要决定 80 亿条各自放哪层），本篇用的是曝光分布——**同一个平台，两个正确但不同的分布，不能混用。**

**命中率的等价表述——重用因子，这是最好监控的形式：**

```
195 万读/秒 ÷ 9,750 miss/秒 = 200

即：每个 key 被拉进 L4 之后，平均要被读 200 次才过期。
```

**监控命中率不如监控重用因子。** 命中率是个百分比，99.5% 和 99.0% 看起来差不多；重用因子是个倍数，200 和 100 一眼就能看出差了一倍。运维上把"重用因子 < 120 告警"作为主指标，比"命中率 < 99% 告警"灵敏得多。

**L4 的 TTL 为什么是 10 分钟：**

TTL 直接决定常驻集大小（窗口内被触达的 key 数），也就直接决定内存成本：

| TTL | 常驻集 | 内存（×3 副本） | 月成本 | 重用因子 | 命中率 | 可省的只读副本 |
|-----|-------|---------------|-------|---------|--------|--------------|
| 2min | 3,000 万 | 180 GB | ¥14 万 | 40 | 97.5% | — |
| **10min** | **8,000 万** | **480 GB** | **¥13 万→¥26 万** | **200** | **99.5%** | **基准** |
| 30min | 1.2 亿 | 720 GB | ¥39 万 | 600 | 99.83% | 6 台（¥1.5 万） |
| 60min | 1.5 亿 | 900 GB | ¥49 万 | 1000 | 99.90% | 6 台（¥1.5 万） |

**从 10min 加到 30min，多花 ¥13 万/月的内存，只省 ¥1.5 万/月的副本——净亏 ¥11.5 万。** 加上更长的 TTL 意味着 Q 级变更的陈旧窗口更长（观感变差），10 分钟是成本与一致性的共同最优点。

**TTL 抖动 ±2min 能做到什么、做不到什么——这个必须算清楚，否则会误以为抖动就够了：**

```
雪崩场景：一批同批次发布的内容（占热集 30% ≈ 2,400 万 key）同时过期

无抖动：全部在同一秒过期
        → 瞬时 miss 2,400 万 QPS（DB 容量的 2,400 倍）→ 必死

±2min 抖动：过期时刻均匀摊到 240 秒
        → 峰值 miss = 2,400 万 ÷ 240 = 10 万 QPS
        → 仍是 DB 容量（1 万）的 10 倍 → 还是会死，只是死得慢一点

结论：抖动把"必死"变成"仍会死"。它是必要条件，不是充分条件。
```

**所以雪崩防护必须是三层叠加，抖动只是第一层：**

| 层 | 手段 | 把峰值 miss 压到 | 残余风险 |
|----|------|----------------|---------|
| 1 | TTL ±2min 抖动 | 10 万 QPS | 仍超 DB 容量 10 倍 |
| 2 | 错峰 TTL（写入侧：新发布内容 3 天内用 60s 短 TTL，之后切 10min） | 3 万 QPS | 打散了"同批次"这个根因，但同类内容仍会聚集 |
| 3 | miss 侧限流队列（≤ 1 万 QPS 进 DB，其余快速失败让客户端重试） | **1 万 QPS（硬保证）** | 短暂丢请求 |

**第 3 层是唯一能给出硬保证的，前两层都只是降低概率。** 这条排序很重要：很多团队做完抖动就以为解决了雪崩，实际只降了两个数量级中的一个半——**只有 miss 侧限流是"无论前面怎么错，DB 都不会死"的那道闸门。**

**L4 只放"热集"不放全量。** 80 亿行 × 2KB = 160TB 全量放 Redis 的成本是存储的 100 倍以上，不可能。热集判定：7 日内有播放 + 新发布内容（冷启动窗口）。热集约 1%（8000 万条）× 2KB ≈ 160GB，三副本 480GB，可控。冷数据直接读 L5。

**L2 边缘缓存只面向"公开、无登录态"的响应**（分享页、详情页的公开部分）。Feed 响应高度个性化（每个人不同），进 CDN 缓存命中率极低，徒增成本——这是 P01 否决 GraphQL 的同一个理由：**对一个 73% 成本在带宽的平台，缓存不可用是致命的。**

### 缓存一致性：三类变更、三套失效通道

这是本篇最核心的设计。**把"缓存一致性"拆成三个独立问题，而不是一个。**

#### 前置问题：缓存与数据库的写顺序，以及为什么"删缓存"永远不够

在讨论分级之前必须先解决一个更基础的问题。所有"改了就删缓存"的方案——无论删得多快、多可靠——都有一个共同的失效模式：**旧值可以在失效之后被重新写回缓存。**

四种写顺序，全部有竞态：

```
方案 A：先删缓存，再写库
  T0  写线程：DEL content:1001
  T1  读线程：GET content:1001 → miss
  T2  读线程：SELECT ... → 读到【旧值】（写事务还没提交）
  T3  写线程：UPDATE ... COMMIT
  T4  读线程：SET content:1001 = 【旧值】   ← 旧值写回，且失效已经发生过了
  结果：旧值驻留直到 TTL 过期（最长 10 分钟），期间任何失效事件都不会再来一次

方案 B：先写库，再删缓存（Cache-Aside 标准做法）
  T0  读线程：GET → miss
  T1  读线程：SELECT ... → 读到旧值
  T2  写线程：UPDATE ... COMMIT
  T3  写线程：DEL content:1001
  T4  读线程：SET content:1001 = 【旧值】   ← 同样的结局
  结果：窗口更窄（要求读的回填慢于整个写事务 + 删除），但非零

方案 C：延迟双删（写库 → 删缓存 → 等 N ms → 再删一次）
  依赖"N > 读回填的最长耗时"这个猜测。而回填耗时的上界不存在——
  一次 GC、一次网络重传、一次 DB 慢查询就能超过任何固定的 N。
  且延迟期间缓存里就是旧值，第二次删除本身也可能失败。
  它把一个确定性问题变成了一个概率问题，只是把概率调小。

方案 D：写时给 key 加分布式锁，读时检查锁
  正确，但读路径每次要多一次锁检查 —— 195 万 QPS × 一次 RTT，
  代价是把整条读链路的延迟预算吃掉，为了一个万分之一概率的问题。
```

**这个竞态的危险性不在概率高，而在"低到测不出、高到天天发生"。** 实算量级：

```
miss 量：9,750/秒 = 8.4 亿次/日
元数据写：500 万次/日，每次的危险窗口 ≈ 25 ms（一次 DB 回源的耗时）

对高频编辑的头部内容（约 10 万条，日均 20 次编辑）：
  单 key 处于危险窗口的时间占比 = 20 × 0.025s ÷ 86,400s = 5.8×10⁻⁶
  单 key 的 miss 次数 = 每 10 分钟 TTL 过期一次 = 144 次/日
  → 单 key 每日撞上竞态的概率 = 144 × 5.8×10⁻⁶ = 8.3×10⁻⁴
  → 10 万条 × 8.3×10⁻⁴ ≈ 每日 80 次脏缓存
```

**每天几十次，每次持续最长 10 分钟——压测里永远复现不出来，线上永远在发生。** 而且它比"短暂不一致"严重得多：**脏值是在失效事件之后写入的，所以没有任何后续事件会清理它**，只有 TTL 能救。落到业务上：一次下架（F 级）的脏缓存意味着违规内容多传播 10 分钟；一次改名（Q 级）意味着用户看到旧昵称 10 分钟，而运营已经在后台确认"改了"。

**本篇的解法：版本号 + 单调回填（CAS 语义）。** 缓存的每次写入都必须带版本号，且**只允许版本号单调前进**：

```
回填规则（读路径）：
  读 DB 时一并读出 content.version
  回填 L4 时执行：
      IF cached.version IS NULL OR incoming.version >= cached.version
      THEN SET
      ELSE 丢弃本次回填

失效规则（写路径）：
  版本号 bump 与失效是同一个原子动作的两面：
      1. 内容域在写事务内 version = version + 1
      2. 事务提交后发出携带 new_version 的失效事件
      3. 失效代理不仅 DEL，还写入一个"版本水位"标记：
         SET content:1001:ver = new_version  （TTL 略长于内容 key）

  于是方案 A/B 的 T4 步骤变成：
      读线程携带旧 version=7 回填，但水位标记显示 ver=8
      → 7 < 8，回填被拒绝 → 旧值无法进入缓存 ✓
```

**为什么这个方案成立而双删不成立：** 双删依赖"时间"（等足够久），版本号依赖"因果"（旧值永远小于新版本）。**时间的上界不存在，因果的顺序永远成立。** 代价只是每个 key 多存一个 8 字节的版本水位（8,000 万 × 8B = 640 MB，可忽略），以及回填从 `SET` 变成 `Lua 脚本里的比较后写入`（Redis 单分片内原子执行，无额外 RTT）。

**这也解释了版本号为什么是本篇的中枢——它承担三个不同的职责，而这三个职责恰好都需要"单调递增的因果标记"：**

| 职责 | 解决的问题 | 出现位置 |
|------|-----------|---------|
| 回填单调性 | Cache-Aside 竞态（旧值写回） | L4 回填的 CAS 判断 |
| 新鲜度判断 | L3/L4 的新旧数据跳变（陷阱 7） | `LocalCache.get(cid, min_version)` |
| 客户端自校验 | L1 兜底渲染时判断内容是否已变 | 客户端携带 version 请求，服务端只回变更项 |

**版本号必须由内容域单写生成**（雪花或 DB 序列），其他域只读不写——否则多写方并发 bump 会造成版本号倒退，而版本号倒退会让上面三个职责同时失效（见异常场景「版本号回退导致旧内容覆盖新内容」）。这是 P00「状态单写方」原则在版本维度上的直接应用。

#### 三套失效通道

```
变更类型         失效通道              时效目标            机制
─────────────────────────────────────────────────────────────────────
监管/版权强失效   强失效通道（F 级）    < 1s              事件 + L4 立即删 + 版本号 bump
                                                                + 播放接口最终校验
用户可见元数据     快失效通道（Q 级）    < 5s              事件 + 版本号 bump + L4 删除
                                                                + L3/L2 靠 60s 短 TTL 兜
统计类            弱一致通道（W 级）    60s 内            不主动失效，靠 200ms 聚合 + TTL
```

**强失效通道（F 级）——下架 / 封禁 / 可见范围变更：**

```
content.status 变更（下架/删除） → 内容域发出 content.takedown 事件
  → 失效代理：
      1. L4 立即删除该 content 的所有缓存 key
      2. 版本号 +1 并广播（客户端 / L3 据此判旧）
      3. 联动 CDN：清除播放地址（含所有档位所有边缘）★最容易漏
      4. 播放接口最终校验：返回地址前查一次状态（走本地缓存，<1ms）
```

F 级的**最终兜底不是缓存失效，而是播放接口的最终校验**——缓存的失效可以漏、事件可以迟到，但播放地址签发前必须确认状态。这直接复用了 P00 下架工作流的"主动探测"哲学：**没有最终校验的失效流程都是自欺欺人。** 这条规则同时服务 P00 场景⑤与场景 ②：即使缓存清理滞后，违规内容也无法被播放。

**快失效通道（Q 级）——作者改名、封面替换等：**

通过内容域统一发的 `content.change(content_id, version, change_type)` 事件驱动。L4 删除 + 版本号 bump；L3（进程内缓存）和 L2（边缘）**无法被主动清**（分布在成百上千个实例上），靠 60s 短 TTL 收敛。为什么 5s 的时效目标允许 60s 的 TTL？因为这类变更只影响观感不影响合规，60s 内大部分用户已经看到新值（翻页频率远高于 60s），P95 远好于目标。

**弱一致通道（W 级）——统计类：**

播放 / 点赞 / 评论数完全不做主动失效。计数服务每 200ms 预聚合热点内容写本地缓存（P01 计数服务设计），读侧取快照，TTL 自然过期。用户对"播放数差 30 秒"无感知，而**统计恰恰是变更最频繁的数据**（峰值 23 万 QPS 写），若对统计做主动失效，失效事件量会是全部其他变更的一万倍——纯属自焚。

**为什么"全链路实时失效"是错的（反模式）：**

直觉上"改了什么就删什么"最安全。但 F+Q 两类变更在热门内容上的频率不低（热门视频频繁编辑封面、标题），每次都要全网广播失效、每个节点都要重新回源。**实时失效把"写侧的每一次变化"放大成"读侧的一次全量重建"，写放大因子是节点数。** 分级后：F 级走实时（数量少、必须快），Q 级走版本号 + TTL（数量中、容忍慢），W 级完全不失效（数量巨大、无所谓）。

### BFF 字段裁剪与视图分离

**原则：一份模型（content 全字段），一份投影注册表（场景 → 字段白名单），零重复映射。** 每个消费视图在注册表里声明自己需要的字段，BFF 按注册表裁剪，而不是每个视图写一套 DTO 类。

| 消费视图 | 字段数 | 关键字段 | 载体 |
|---------|-------|---------|------|
| Feed 卡片 | 14 | title/cover/type/stat/时长/认证 | Protobuf |
| 详情页 | 40+ | 全字段 + 标签 + 合集 + 章节 | Protobuf |
| 分享卡片 | 6 | title/cover/作者/摘要 | 无 |
| 创作者后台 | 25 | 状态/审核/数据 | JSON |
| 播放前校验 | 5 | 状态/可见范围/档位 | Protobuf |
| 第三方嵌入 | 8 | title/cover/player_url | JSON |

**字段裁剪的字节账本：**

```
Feed 每次返回 30 条卡片：
  全字段方案：30 × 15KB = 450KB/请求
  裁剪方案：  30 × 4KB  = 120KB/请求
  每请求省：  330KB

按 QPS 折算（两个口径都列出来，因为它们相差 3.5 倍）：
                      均值 1.85 万 QPS      峰值 6.5 万 QPS
  全字段带宽            8.3 GB/s              29.3 GB/s
  裁剪后带宽            2.2 GB/s               7.8 GB/s
  节省带宽              6.1 GB/s              21.5 GB/s

月度账（带宽账单只能用均值算，峰值只用于容量规划）：
  全字段    8.3 GB/s × 2.592e6 s = 21.6 PB/月 → ¥108 万/月
  裁剪后    2.2 GB/s × 2.592e6 s =  5.8 PB/月 → ¥ 29 万/月
  ─────────────────────────────────────────────────
  月省                                          ¥ 79 万/月
```

**用峰值 QPS 乘满一个月去算账单是一个高频错误**（峰谷比 3.5 倍，会把账单算成 ¥278 万）。**容量看峰值，账单看均值**——两个数字服务于两个不同的决策，混用哪一个方向都是错的。

**投影注册表要防两个方向的腐化：** 一是字段**泛滥**（Feed 要 40 个字段，等于没裁剪）；二是字段**漂移**（模型加字段后忘了进注册表，新字段被静默丢弃）。机制：注册表字段清单由**单测强制校验**——模型新增字段时测试断言"该字段已归属某个视图"，无归属的新字段直接报错，倒逼明确意图。

**协议选择的约束（承接 P01）：** 移动端 Protobuf、Web JSON，由 BFF 转换。不在各域之间用裸 HTTP+JSON——跨域聚合的字节都经过 Protobuf 压缩，这一条在 Feed 这类高频链路上的收益（~40% 字节节省）直接进成本账本。

### 热点内容与缓存崩溃防护

**第一步：热点识别。** 内容中台按 content_id 统计读 QPS，进入热点管理的阈值是 5,000 QPS。

阈值的来源不是拍脑袋，而是从单分片容量倒推：单 Redis 分片的运维上限 5 万 QPS，一个分片上会落约 8,000 万 ÷ 480 ≈ 17 万个 key，其中绝大多数是长尾。**只要单 key 占到分片容量的 10%（5,000 QPS），它就已经在挤压同分片其他 key 的延迟**——此时干预还来得及；等到它自己打满 5 万 QPS，同分片的其他内容早就一起慢了。**热点治理的阈值应当由"它开始伤害邻居"的点决定，而不是"它自己撑不住"的点。**

识别算法的选择比阈值更容易做错。三个候选：

| 方案 | 内存 | 问题 |
|------|------|------|
| 全量 `HashMap<content_id, counter>` | 8,000 万 × 约 40B = 3.2 GB/进程 × 100 台 | 为了找 100 个热点，存了 8,000 万个恒为 1 的计数器 |
| 采样 1%，再全量计数 | 32 MB | 5,000 QPS 的 key 采样后是 50 QPS，与噪声难分；且**采样对长尾无损，对头部同样按比例缩小，信噪比并没有改善** |
| **Count-Min Sketch + 滑动窗口 Top-K** | **约 2 MB/进程** | 有过估计（只会高估不会低估），对热点识别恰好是安全方向 |

选 CMS。参数推导：

```
CMS 的过估计误差上界：ε × 总计数，置信度 1-δ
  宽度 w = ⌈e/ε⌉，深度 d = ⌈ln(1/δ)⌉

要求：对 5,000 QPS 的 key，误差不超过其 10%（即 500 QPS）
单进程承接的总读 QPS = 195 万 ÷ 100 台 = 1.95 万 QPS
  → ε = 500 / 19,500 = 2.56%   ... 看似够松

但真正的约束是【区分度】：需要把 5,000 QPS 的 key 与 500 QPS 的 key 分开
  单进程视角：50 QPS vs 5 QPS，1 秒窗口内计数 50 vs 5
  → 取 ε = 0.1%，δ = 0.1%
  → w = ⌈e/0.001⌉ = 2,719 → 取 4,096（对齐 2 的幂，位运算取模）
  → d = ⌈ln(1000)⌉ = 7  → 取 4（见下）
  → 内存 = 4,096 × 4 × 4B(uint32) = 65 KB/窗口
  → 滑动窗口取 10 个 1 秒的桶 = 650 KB，加上 Top-K 小顶堆 ≈ 2 MB ✓
```

**d 从 7 降到 4 是一个有意识的取舍**：d 决定的是"多个 key 哈希碰撞后都被高估"的概率，而热点识别里高估的后果只是**多拆了几个不该拆的 key**（浪费一点内存），远轻于漏判。**代价与收益不对称时，参数就该偏向便宜的那一侧。** 这与布隆过滤器的取舍方向恰好相反（见第四步）。

**热点判定还要过一道时间维度的门：连续 3 个 1 秒窗口都超阈值才升级。** 单窗口触发会把"某个 push 带来的 1 秒尖峰"误判为热点，而拆 key 的代价（10 倍写放大 + 预热延迟）不该为一次尖峰付出。

**第二步：热点拆 key。** 热点 key 不打单个 Redis 分片，而是打散成 N 个副本：

```
原始 key：  content:{id}
热点拆 key：content:{id}:r0 .. content:{id}:r9   （N=10）
读请求：   hash(uid) % 10 选定副本
写回：     10 个副本全写（写量小，热点内容写频率极低）
```

**N = 10 的推导——两侧夹逼：**

```
下界（必须够分散）：
  单 key 峰值 4.5 万 QPS（挑战 3 已算）
  单分片安全水位取上限的 60% = 3 万 QPS，但热点 key 还要与同分片的长尾共存，
  分给单个 key 的额度取 5,000 QPS（即识别阈值本身）
  → N ≥ 45,000 / 5,000 = 9

上界（写放大与内存）：
  写放大：每次内容更新要写 N 个副本。头部内容日均编辑 20 次，
    N=10 → 200 次写/日/key，微不足道；
    但【失效】也要 N 倍：F 级失效要删 10 个 key，且必须全成功——
    失效的原子性随 N 线性变差（10 个 DEL 里第 7 个失败，就有 10% 的读看到已下架内容）
  内存：2 KB × 10 × 10 万热点 = 2 GB，占 L4 总容量 160 GB 的 1.25%，可接受
  → N 不宜超过 16（超过后失效的部分失败概率超过 1%）

取 N = 10。且【副本数不必相同】：QPS 4.5 万的取 10，QPS 8,000 的取 2。
按 ⌈QPS / 5000⌉ 动态定档，避免为一个刚过线的 key 也拆 10 份。
```

**失效的 N 倍不原子性是拆 key 引入的新风险，必须单独处理**：F 级失效对拆 key 内容改为**先写"下架水位"标记（单 key，原子），再逐个删副本**。读路径检查水位标记优先于副本值——于是即使某个副本删除失败，水位标记也能拦住它。**拆 key 换来了吞吐，代价是把"一个 key 的原子操作"变成"N 个 key 的分布式操作"，这个代价必须由一个额外的单点原子标记来偿付。**

拆 key 的效果：单分片压力从 4.5 万 QPS 摊到 10 个分片各 4,500 QPS，且**任意一个副本失效只影响 10% 的请求**——击穿从"打垮 DB"退化为"轻微回源"。

**第三步：本地缓存扛热点。** 热点内容主动预热进 L3 本地缓存（8GB 容量专门留了热点区），热点读大部分命中 L3，连 Redis 都不碰。这是 L3 存在的另一个理由：**分布式缓存挡不住热点（单分片 CPU 有限），只有进程内缓存能。**

算一下 L3 对热点的实际效果，这是拆 key 之外更根本的一层：

```
10 万个热点内容 × 2 KB = 200 MB，100 台机器全量各存一份 —— 完全装得下 8GB 热点区
L3 对热点的命中率：热点内容 100% 常驻，TTL 60s 到期时后台主动刷新（不等 miss）
  → 热点读几乎不下沉到 L4
  → 单个头部 key 到达 L4 的 QPS = 100 台 × (1 次/60s 刷新) = 1.67 QPS

对比拆 key：把 4.5 万 QPS 摊成 10 份 × 4,500 QPS
      L3 常驻：把 4.5 万 QPS 降到 1.67 QPS —— 相差四个数量级
```

**所以真正扛住热点的是 L3 常驻，拆 key 只是 L3 未覆盖时的兜底。** 顺序不能颠倒：如果只做拆 key 不做 L3 常驻，L4 要承受 4.5 万 QPS 的持续压力；如果只做 L3 常驻不做拆 key，则新晋热点（刚爆的内容，还没进入常驻名单）会在 L3 预热完成前的几十秒里把 L4 单分片打满。**两者防的是不同时刻：L3 常驻防稳态，拆 key 防升温期。**

**第四步：防穿透（query 不存在的内容）。** 恶意遍历不存在的 content_id，缓存永远 miss。两道防线：

**布隆过滤器的参数推导：**

```
n = 8×10⁹ 个已存在的 content_id
目标误判率 FPR = 1%

最优 bits/key：m/n = -ln(p) / (ln2)² = -ln(0.01) / 0.4805 = 4.605 / 0.4805 = 9.58
  → 取 10 bits/key
最优哈希个数：k = (m/n) × ln2 = 10 × 0.693 = 6.93 → 取 7
实际 FPR：(1 - e^(-kn/m))^k = (1 - e^(-0.7))^7 = 0.5034^7 = 0.82%
内存：8×10⁹ × 10 bit = 10 GB
```

10 GB **不能每台机器各存一份**（100 台 = 1 TB 内存，成本超过它节省的一切）。它放在 L4 Redis 侧（`BF.EXISTS`，Redisson/RedisBloom），读路径的判断顺序是：L3 miss → 布隆判断 → L4 → L5。这意味着布隆过滤器省下的是**L5 的 DB 查询**，而不是 L4 的网络往返——**这也是它值得做的原因：DB 查询 25ms + 稀缺连接，Redis 判断 1ms + 廉价。**

**0.82% 的漏网率是可接受的，因为它后面还有第二道防线**：漏过去的 key 会在 L4 缓存一个 30 秒的空占位（`__NULL__` 哨兵值），所以同一个不存在的 key 最多每 30 秒穿到 DB 一次。两道防线的组合效果：

```
攻击者以 10 万 QPS 遍历随机 content_id：
  布隆拦掉 99.18% → 到达空值缓存层 820 QPS
  空值缓存拦掉重复 key。攻击者若用随机 id，则每个 key 只出现一次，空值缓存无效
  → 仍有 820 QPS 打到 DB  ← 单靠这两层挡不住随机遍历
  → 第三层必须是【按 uid/IP 的读限流】：单 uid 未命中次数 > 50/分钟即降级
```

**这是穿透防护最容易被漏掉的一环**：布隆和空值缓存都假设"重复访问同一个不存在的 key"，而真正的恶意遍历恰好不重复。**没有限流的穿透防护只挡住了误操作，挡不住攻击。**

**第五步：防雪崩。** L4 的 TTL 加随机抖动（基准 10min ± 2min），L3 保持独立 TTL（60s）作为第二层，miss 侧并发限流器（1 万 QPS 硬闸）作为第三层——三层的定量效果见前文「五级缓存的容量与命中率推导」的抖动分析。**只有第三层是硬保证。**

**第六步：防击穿（单热点 key 失效瞬间）。** 拆 key + L3 之后击穿概率已大降，剩下的缺口用 **singleflight（单飞）**：同一 key 同一瞬间只放一个回源请求，其余请求等这一个的结果。回源量从"一瞬间 N 次"降为"最多 1 次"。

**singleflight 有三个几乎必踩的实现陷阱：**

```
陷阱 A：用 Map<key, List<Waiter>> 实现 —— 检查与插入之间有竞态
  线程 1：get(key) → null → 准备创建 List
  线程 2：get(key) → null → 也准备创建 List      ← 两个 leader，单飞失效
  线程 1：put(key, list1)
  线程 2：put(key, list2)（覆盖）→ 线程 1 的等待者永远等不到唤醒
  修法：必须用 computeIfAbsent / putIfAbsent 返回值判断谁是 leader，
        且等待者容器要在【原子插入的同时】创建，而不是插入后再填

陷阱 B：leader 异常时不唤醒等待者 —— 等待者卡到超时
  修法：leader 的回源必须在 try/finally 里完成，
        finally 中无论成功失败都要 complete（失败则 completeExceptionally）

陷阱 C：单飞的作用域是【单进程】，不是全局
  100 台机器 × 每台 1 个 leader = 100 次并发回源，不是 1 次
  → 单飞把回源从 N 万降到 100，这已经够了（DB 能扛）
  → 想降到 1 次要引入分布式锁，多一次 RTT 且锁本身会成为新的单点
  → 【不要追求全局单飞】：100 次/秒的回源对 DB 是噪声级负载
```

陷阱 C 是判断力问题而非编码问题：**很多人在 singleflight 之上再加分布式锁，用一个新的分布式依赖去优化一个已经不成问题的数字。** 100 台机器同时回源一个 key，DB 的负载是 100 QPS——而 DB 的兜底容量是 1 万 QPS。

### 计数读取：展示快照与单调性

统计字段的展示值来自计数服务的异步快照，不是实时值。读路径约定：

- 内容中台聚合统计时调用计数服务的**本地缓存**（200ms 预聚合），绝不实时累加
- 展示层对同一 content 的计数取 `max(快照值, 本地已见最大值)`，保证**用户看到的数字只增不减**（计数回退是创作者投诉的高发点，P01 计数服务异常场景专门处理过）
- 快照与真实值的偏差上限 60s，落到 UI 上是"播放数 123 万"，用户无感知

这条约定也回答了挑战 2 的 W 级通道为什么不需要主动失效——**计数从源头就不追求实时，展示快照天然安全。**

### 读路径的降级矩阵

把"每个域故障时用户看到什么"事先定义清楚，而不是故障时现场决策：

| 故障域 | 降级策略 | 用户影响 |
|--------|---------|---------|
| 域 9 推荐 | 客户端 L1 本地 Feed 兜底渲染 | 看到上次会话内容，可立即起播 |
| 域 10 互动 | 互动状态返回 unknown，灰色按钮 | 点赞/收藏需点击后单独查 |
| 域 2 关系 | 关注状态 unknown | 同上 |
| 计数服务 | 展示最近一次快照 | 统计短暂陈旧 |
| 内容中台 L4 | 直连 L5 只读副本，但强制限流（≤ 1 万 QPS） | 延迟从 8ms 涨到 30ms，不塌 |
| 内容中台 L3+L4 全挂 | 所有读直连 L5，BFF 端削峰 50% | 延迟 50-100ms，可用性降低但可用 |
| 域 5 媒资 | 已签发播放地址走本地缓存兜底 | 新内容无法起播，存量可播 |

**降级矩阵的两条硬规则：**
1. **播放是最后底线**——域 9/10/2 全挂不影响已发布内容播放（P00 域依赖关系图的结论）
2. **直连 DB 必须限流**——DB 能扛 1 万 QPS 兜底，扛不了 195 万 QPS 回源。**缓存层故障时宁可丢弃部分请求（BFF 端削峰），也不能让 DB 被打死**——DB 死了整个平台都不可用，丢请求只是部分用户短暂失败。

### 数据库设计

读链路的表设计有一个反直觉的前提：**主数据（`content` / `content_stat` / `content_ext_*`）不属于本篇**，它们在 P00「统一内容模型」里定义。本篇要建的表全部是**为了让缓存正确工作而存在的元数据**——版本水位、失效流水、热点档案、投影注册表。

这个区分很重要，因为它决定了这些表的性质：**它们不在读路径的关键路径上。** 195 万 QPS 的读一次也不会碰到本节的任何一张表。它们服务于控制面（失效、预热、审计），QPS 在千级以下。**如果本节的某张表出现在了读路径上，说明设计错了。**

```sql
-- ============================================================
-- 表 1：内容版本水位（内容域单写，读链路只读）
-- 用途：Cache-Aside 回填的单调性判断 + L3 新鲜度判断 + 客户端自校验
-- ============================================================
CREATE TABLE content_version (
    content_id      BIGINT UNSIGNED NOT NULL          COMMENT '内容 ID，与 content.id 同源（P00 定义的雪花 ID）',
    version         BIGINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '内容版本号，单调递增。内容域在写事务内 +1，其他域只读。回填 CAS 与 L3 新鲜度判断的唯一依据',
    f_version       BIGINT UNSIGNED NOT NULL DEFAULT 1 COMMENT 'F 级（下架/封禁/可见范围）版本号。与 version 分离，使 F 级变更能独立触发强失效而不惊动 Q 级通道',
    visible_scope   TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '可见范围快照：0=全网 1=仅粉丝 2=仅自己 3=已下架 4=已封禁。冗余一份在此，供播放接口最终校验时单表查询，不必回内容主表',
    last_write_at   DATETIME(3)     NOT NULL           COMMENT '最近一次写入时间（毫秒精度）。用于排查"缓存里的值比这个时间更旧"的脏缓存',
    PRIMARY KEY (content_id),
    KEY idx_last_write (last_write_at)                 COMMENT '支撑"最近 N 分钟被修改的内容"扫描，用于失效补偿任务'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COMMENT='内容版本水位表。按 content_id 分 256 表，与 content 主表同分片规则同库，保证版本 +1 与内容写入在同一本地事务内';

-- ============================================================
-- 表 2：缓存失效流水（Outbox 模式，保证"写库"与"发失效事件"的原子性）
-- ============================================================
CREATE TABLE cache_invalidation_outbox (
    id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '自增主键，同时充当消费位点（消费者按 id 顺序推进，无需额外位点表）',
    content_id      BIGINT UNSIGNED NOT NULL           COMMENT '待失效的内容 ID',
    level           TINYINT UNSIGNED NOT NULL           COMMENT '失效级别：1=F（强，<1s）2=Q（快，<5s）3=W（弱，不主动失效，仅记录）',
    new_version     BIGINT UNSIGNED NOT NULL           COMMENT '变更后的版本号。失效代理写入 Redis 版本水位时用它，使并发回填能被 CAS 拒绝',
    changed_fields  VARCHAR(512)    NOT NULL DEFAULT '' COMMENT '变更字段名列表（逗号分隔）。用于判断是否需要失效 L2 边缘缓存——只有影响 Feed 卡片的 14 个字段变更才值得动 CDN',
    created_at      DATETIME(3)     NOT NULL           COMMENT '写入时间。与 consumed_at 之差就是失效延迟，是 F 级 SLA(<1s) 的直接度量',
    consumed_at     DATETIME(3)     NULL               COMMENT '消费完成时间。NULL 表示未消费；用于"失效积压"告警',
    retry_count     TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '失效重试次数。超过 5 次转入死信并告警——F 级失效失败必须有人知道',
    PRIMARY KEY (id),
    KEY idx_unconsumed (consumed_at, level, id)        COMMENT '消费者扫描未消费记录，按级别优先。F 级独立消费者组，不与 Q 级排队',
    KEY idx_content (content_id, created_at)           COMMENT '排查"某内容的失效历史"，故障复盘高频查询'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COMMENT='缓存失效 Outbox。与内容主表同库同事务写入，消费者独立进程轮询。这是"写库成功但事件丢失"的唯一防线';

-- ============================================================
-- 表 3：热点内容档案（热点识别的持久化侧，控制面）
-- ============================================================
CREATE TABLE hot_key_registry (
    content_id      BIGINT UNSIGNED NOT NULL           COMMENT '内容 ID',
    peak_qps        INT UNSIGNED    NOT NULL           COMMENT '最近观测窗口内的峰值读 QPS（CMS 估计值，只会高估）',
    replica_count   TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '当前拆 key 副本数 N。1 表示未拆；按 ⌈peak_qps/5000⌉ 定档，上限 16',
    l3_resident     TINYINT(1)      NOT NULL DEFAULT 0 COMMENT '是否已进入 L3 常驻名单。常驻的 key 由后台主动刷新，不等 TTL 过期',
    promoted_at     DATETIME(3)     NOT NULL           COMMENT '升级为热点的时间。用于观察"从爆量到防护生效"的时延——这段时间就是 L4 单分片的裸奔窗口',
    demote_after    DATETIME(3)     NOT NULL           COMMENT '计划降级时间。热点冷却后必须降级回收副本内存，否则热点名单只增不减',
    PRIMARY KEY (content_id),
    KEY idx_demote (demote_after)                      COMMENT '降级扫描任务的驱动索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COMMENT='热点档案。真实的热点判定在各进程的 Count-Min Sketch 里实时进行，本表只是【汇总后的决策结果】，供新启动的进程快速加载常驻名单';

-- ============================================================
-- 表 4：投影注册表（BFF 字段裁剪的元数据，同时是防字段漂移的单测数据源）
-- ============================================================
CREATE TABLE content_projection_field (
    view_code       VARCHAR(32)     NOT NULL           COMMENT '消费视图编码：feed_card / detail / share_card / creator_console / play_precheck / third_party_embed',
    field_name      VARCHAR(64)     NOT NULL           COMMENT '统一内容模型中的字段名，必须与 content 系列表或聚合字段一一对应',
    is_required     TINYINT(1)      NOT NULL DEFAULT 1 COMMENT '该字段缺失时是否阻断渲染。0 表示可降级为空（如互动状态 unknown）——降级矩阵的字段级依据',
    source_domain   TINYINT UNSIGNED NOT NULL          COMMENT '字段来源域编号（P00 域编号）。用于按域故障时自动推导哪些视图会受损',
    added_at        DATETIME(3)     NOT NULL           COMMENT '字段加入该视图的时间。审计"字段泛滥"趋势——单视图字段数的增长曲线是抽象腐化的先行指标',
    PRIMARY KEY (view_code, field_name),
    KEY idx_field (field_name)                         COMMENT '反查"某字段被哪些视图使用"，删字段前的影响面评估'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COMMENT='投影注册表。CI 阶段导出为静态资源随服务发布，运行时不查库；线上表仅供运营查看与单测校验';
```

**几个字段的设计意图值得单独说明：**

- **`version` 与 `f_version` 为什么要分开。** 如果只有一个版本号，那么一次改标题（Q 级）也会让 `version` 前进，从而使所有依赖版本号判断的客户端认为"内容变了"。而 F 级变更（下架）必须触发**所有层级**的立即失效，Q 级只需触发 L4。**合并版本号会强迫 Q 级变更付出 F 级的代价**——每天 500 万次元数据写全部走强失效通道，L2 边缘缓存会被刷穿。分开之后，F 级通道每天只有几千条流量。

- **`cache_invalidation_outbox.id` 兼作消费位点。** 常见做法是单独建一张 `consumer_offset` 表，但那样"消费一条"就变成了"更新两张表"，又需要事务。用自增 id 作为位点，消费者只需记住"我处理到哪个 id"，而这个位点本身可以存在 Redis 里丢了也无所谓（重复消费失效是幂等的——多删一次缓存不会错）。**幂等的操作不需要精确一次的位点。**

- **`changed_fields` 为什么必要。** L2 边缘缓存的刷新是要花钱的（CDN 刷新 API 有配额与费用），且刷新会短暂降低边缘命中率。只有当变更字段落在 Feed 卡片那 14 个字段里时才值得刷 L2；改了个"内部备注"字段却刷了全网 CDN，这是**成本第一约束下不可接受的浪费**。这个字段让"是否刷 L2"从人工判断变成了可自动裁决的规则。

- **`hot_key_registry.promoted_at` 与 `demote_after` 成对存在。** 只有升级没有降级，是热点治理最常见的腐化形式：三个月后热点名单里躺着 5,000 个早就凉了的内容，各占 10 份副本内存。降级必须有默认过期时间（本篇取 24 小时），续期靠再次触发阈值。**任何"加入名单"的机制都必须同时设计"离开名单"的机制**，否则名单本身会变成泄漏。

- **`content_projection_field.source_domain` 是降级矩阵的机器可读版本。** 前文的降级矩阵是人写的表格，容易与代码漂移。把字段的来源域记下来之后，"域 10 互动挂了，哪些视图的哪些字段会空"可以自动推导——**文档里的矩阵与数据库里的注册表应当是同一份事实的两种呈现，而不是两份需要人工同步的事实。**

**为什么不给这些表做缓存。** 全部四张表的合计 QPS 不到 2,000（失效消费者 + 后台任务 + 运营查询），且都在控制面。**给控制面加缓存是一种典型的过度设计**：它引入了新的一致性问题（热点档案的缓存过期了怎么办），换来的是本来就不存在的性能收益。

**分表策略上的一个不对称：** `content_version` 分 256 表（必须与 `content` 同分片，才能在同一本地事务里 +1），`cache_invalidation_outbox` 也必须分 256 表（同理），但 `hot_key_registry` 和 `content_projection_field` 单表即可（前者最多几万行，后者最多几百行）。**分表的理由永远是"必须与谁同事务"或"数据量必须拆"，不是"看起来该拆"。**

## 常见陷阱（深度分析）

### 陷阱 1：为每个字段单独建缓存

**后果：** title 一个缓存、cover 一个缓存、stat 一个缓存、作者信息一个缓存……一份内容的完整视图要查 5 个 key。一致性爆炸（5 个 key 各有各的 TTL 和失效时机）、原子性爆炸（下架要删 5 个 key，漏删一个就残留旧数据）、内存爆炸（同一条内容存 5 份，key 前缀还带字段名）。**一个 content 对应一个缓存 value（整条扁平化后的内容），变更按整条失效。**

**为什么这个错误如此常见：** 它是从"缓存计算结果"的直觉里长出来的。单独缓存一个字段看起来更精确——改了 title 就只失效 title，其他字段的缓存不受影响，命中率更高。**这个推理在单机时代是对的，在分布式缓存下是错的**，因为它忽略了往返次数的代价：

```
5 个 key 的方案，在 Feed 场景下的真实代价：
  30 条内容 × 5 个 key = 150 个 key
  即使用 MGET 批量（Redis Cluster 下 MGET 会按 slot 拆分）：
    150 个 key 分布在约 130 个不同的 slot → 拆成约 130 个子请求
    → 前文的尾延迟公式再次生效：p=0.01%, N=130 → 1.3% 的 Feed 变慢
  1 个 key 的方案：30 个 key → 30 个 slot → 0.30%

命中率的账：
  假设 5 个字段中任一变更的概率相等，单字段变更率 = 整条变更率 / 5
  分字段缓存的"有效命中率"= 各字段命中率的乘积（要 5 个都命中才能渲染）
  99.5%^5 = 97.5%   ← 比单 key 的 99.5% 更差
```

**分字段缓存把"命中"从一次伯努利试验变成了五次的合取，命中率必然下降。** 这是它最反直觉的地方：为了提高命中率而拆分，结果降低了命中率。

**解决方案：** 缓存粒度 = 数据变更单位。content 的字段一起变（一次 UPDATE 改多个列）、一起失效（一个事件）、一个 key 承载。统计单独一个 key（走 W 级通道），作者信息单独一个 key（属于账号域）。

**判据：一个 key 的失效必须对应一次有业务意义的变更，而不是一个字段的变更。** 反过来说，**允许拆 key 的唯一正当理由是"变更频率相差一个数量级以上"**——统计字段每秒变、元数据每天变，把它们放一个 key 意味着每秒失效元数据，这才是真正需要拆的场合。本篇的 `content` / `content_stat` 两 key 之分正是按这条判据划的，而不是按"字段属于哪个模块"。

### 陷阱 2：全链路统一实时失效

**后果：** 热门视频每改一次封面，全网广播失效 + 所有实例回源重建。统计字段（峰值 23 万 QPS 变更）若也走实时失效，失效事件量是其他变更的一万倍，缓存系统直接退化为"每次都回源"，命中率掉到 20%。**实时的代价是写放大因子等于缓存节点数。**

**把写放大算清楚：**

```
一次"实时失效"要触达的节点数：
  L4 Redis：1 个分片（拆 key 的热点内容是 N 个）
  L3 本地缓存：100 台机器，每台都要收到失效广播
  L2 边缘：约 2,000 个边缘节点（刷新 API 调用）
  → 单次实时失效的写放大 ≈ 2,100 次操作

若统计字段走实时失效：
  23 万次变更/秒 × 2,100 = 4.83 亿次失效操作/秒
  这个量级本身就超过了整个 L4 集群的处理能力（480 分片 × 5 万 = 2,400 万 QPS）
  → 失效流量会把缓存集群打死，而缓存集群死了读路径就全部落到 DB
  → 【为了让数据更新更快，导致了完全不可用】
```

**这就是"实时性"这个诉求最危险的地方：它听起来是一个可以逐步优化的性能指标，实际上它是一个会突然翻转成不可用的容量问题。** 23 万 QPS 的变更走实时失效不是"慢一点"，是"崩掉"。

**解决方案：** 失效分级（本篇核心设计）。F 级实时、Q 级版本号 + TTL、W 级不失效。三级的流量落差要有量级差别才有意义：

| 级别 | 日事件量 | 写放大 | 日失效操作 |
|------|---------|-------|-----------|
| F 级 | 约 5,000（下架/封禁） | 2,100 | 1,050 万 |
| Q 级 | 500 万（元数据变更） | 1（只删 L4，L3/L2 靠短 TTL） | 500 万 |
| W 级 | 200 亿（统计） | 0 | 0 |

**注意 Q 级的写放大是 1 而不是 101**——它只删 L4，不广播 L3。这是分级设计里最容易被削弱的一环：一旦有人为了"让改名更快生效"给 Q 级加上 L3 广播，Q 级的日失效操作就从 500 万变成 5 亿，代价上升 100 倍，换来的只是"改名生效从 60 秒变成 1 秒"。**要拒绝这个改动，必须先把上面这张表算出来给人看。**

**判据：如果一个变更让缓存命中率下降超过 1%，说明它不该走实时失效通道。** 更实用的等价判据是：**变更 QPS × 写放大 > 缓存集群容量的 5%，就必须降级通道。**

### 陷阱 3：把"下架"做成最终一致

**后果：** 缓存 TTL 10 分钟，下架后违规内容继续在 Feed 和详情页可见长达 10 分钟。监管检查或版权诉讼中，这不是"技术瑕疵"而是"还在传播"的证据。

**把 10 分钟换算成实际传播量，才能理解为什么这条不能妥协：**

```
一条已经进入推荐池的违规内容，下架前的曝光速率约 5,000 次/秒（中部热度）
  10 分钟 = 600 秒 → 300 万次曝光
  按 3% 的点播转化 → 9 万次实际播放

若是头部内容（曝光 5 万次/秒）：
  10 分钟 → 3,000 万次曝光、90 万次播放
```

**90 万次违规播放不是一个"技术债"，它是一个需要向监管解释的数字。** 而且这个数字有一个尴尬的性质：**平台自己的数据系统会精确地把它记录下来**——曝光日志、播放日志、CDN 账单都在，无法声称"我们不知道传播了多少"。

**更隐蔽的第二重风险：** 即使做了 F 级强失效，如果只删缓存而不做播放接口最终校验，仍然会漏。因为**播放地址是提前签发的**——用户在下架前 30 秒打开了详情页，播放 URL 已经发到客户端，此时删掉所有缓存也拦不住这次播放（CDN 上有内容，签名还有效）。

**解决方案：** 三层叠加，缺一不可：

```
第 1 层  F 级强失效通道：<1s 内删掉 L4 + 广播 L3 + 刷新 L2
         → 阻止【新的】详情页/Feed 看到它
第 2 层  播放接口最终校验：每次签发播放地址前查 content_version.visible_scope
         → 阻止【已看到详情页但还没起播】的用户
         → 这一步必须查库或查专用的强一致 key，不能查普通缓存（否则又回到 TTL 问题）
第 3 层  CDN 侧 URL 失效 + 密钥轮转：对已签发的地址做主动失效
         → 阻止【已拿到播放地址】的用户
         → 代价最高（要刷 CDN），只对 F 级中的"封禁"子类做
```

**第 2 层是性价比最高的一层**：它把强一致的代价局限在"播放请求"这一个接口上，而不是让整条读链路都强一致。播放接口的 QPS 是 64.8 万，比 Feed 曝光的 195 万低 3 倍，且它本来就要查媒资域（有一次网络往返的预算）。

**判据：任何状态变更，如果延迟 10 分钟能带来生存风险，就必须走 F 级。** 而 F 级本身也要分层——**"删缓存"只覆盖未来的读，覆盖不了已发出的凭证。凡是签发过凭证的链路，都需要一次最终校验。**

### 陷阱 4：缓存穿透无防护

**后果：** 恶意遍历不存在的 content_id，缓存永远 miss，DB 被低频高量打穿。攻击者只需一个脚本，就能用极低的流量成本让内容库的只读副本 CPU 打满——**穿透是成本最低、收益最高的攻击方式。**

**攻击成本的不对称性是这个陷阱的核心：**

```
攻击方成本：
  单机构造 1 万 QPS 的 HTTP 请求，带宽约 1 万 × 200B = 2 MB/s
  一台 ¥50/月的 VPS 即可
防守方成本：
  1 万 QPS 全部穿透到 DB，每次 25ms、占用一个连接
  → 需要 1 万 × 0.025 = 250 个并发连接
  → 单个只读副本的连接池上限约 500，两台副本被打满
  → 而只读副本池共 8 台，攻击者用 4 万 QPS 就能打满全部
  → 打满之后，正常的 9,750 QPS miss 回源也一起失败 → 缓存过期即雪崩

放大倍数 = 攻击方 ¥50/月 : 防守方全站读链路
```

**这也解释了为什么穿透防护不能只做在 DB 前面**（比如靠 DB 连接池限流）：连接池打满时正常流量也被拒了，攻击已经成功。**防护必须在攻击流量与正常流量还能被区分的地方进行，也就是在缓存代理层。**

**解决方案：** 三道防线，且必须理解每道防线各自挡住的是什么：

| 防线 | 挡住的攻击形态 | 挡不住的 |
|------|-------------|---------|
| 布隆过滤器（10 GB，FPR 0.82%） | 99.18% 的不存在 id | 漏网的 0.82%；以及**存在但用户无权看**的 id |
| 空值缓存（`__NULL__`，30s） | 重复请求同一个不存在 id | 随机不重复的遍历 |
| **按 uid/IP 的 miss 限流** | 随机遍历（单 uid miss > 50/分钟即降级） | 分布式的、每个 IP 都很轻的攻击 |

前两道是**幂等性防护**（假设攻击者重复请求），第三道是**行为防护**（假设攻击者流量集中）。三道都被绕过的攻击形态是"大量 IP 各自低频地请求随机不存在 id"——这已经需要僵尸网络，攻击成本上升了三四个数量级，**防护的目标达成了：把攻击成本从 ¥50/月提到需要僵尸网络。**

注意布隆过滤器必须放在**缓存代理层**（在进 Redis 之前拦截），而不是放 DB 前面；且**它只能判断"曾经存在过"，不能判断"现在可见"**——已删除的内容仍在布隆里（布隆不支持删除）。所以布隆过滤器和可见性校验是两件不同的事，不能互相替代。**布隆过滤器的语义是"这个 id 从未被分配过"，仅此而已。**

### 陷阱 5：热点 key 单副本

**后果：** 爆款内容的读集中打在一个 Redis 分片。单分片的 CPU 上限（约 5 万 QPS）被一条内容打满，分片 P99 飙升，进而拖垮同一分片上的所有其他内容；热点 key 一过期，回源风暴直接击穿 DB。

**"拖垮邻居"是这个陷阱最容易被低估的部分。** 单分片上约有 17 万个 key，热点 key 打满 CPU 之后：

```
分片 CPU 100% → 所有请求排队 → 该分片 P99 从 1ms 涨到 200ms
  ↓
17 万个 key 里的其他内容也慢了 200ms
  ↓
这些内容分布在各种 Feed 里 —— 一个 Feed 有 30 条内容，
  只要有 1 条落在这个分片上，整个 Feed 就慢（并行取 max）
  ↓
落在该分片的概率 = 1 - (1 - 1/480)^30 = 6.05%
  ↓
【一条爆款内容，让 6% 的 Feed 请求变慢 200ms】
```

**一个 key 的问题变成了 6% 请求的问题**，这个放大路径完全隐藏在"Redis 是共享资源"这个事实里。排查时的表象是"Feed P99 涨了"，而根因是"某条视频火了"——两者之间没有任何直观关联，如果没有分片级的 QPS 监控，这个故障可以查一整天。

**解决方案：** 热点拆 key（按 ⌈QPS/5000⌉ 定档，上限 16）+ L3 常驻预热 + singleflight。三者防的时刻不同（见前文），不能只做一个。

**监控上必须补两个指标，否则防护是盲的：**
- **分片级 QPS 的 max / avg 比值**：健康时接近 1.5，出现热点时会冲到 10 以上。这个比值比"单 key QPS Top-N"更早报警，因为它不依赖热点识别本身是否正确
- **从"QPS 越线"到"防护生效"的时延**（`hot_key_registry.promoted_at` 减去越线时刻）：这段窗口就是 L4 单分片的裸奔时间，本篇的目标是 < 5 秒（3 秒判定 + 2 秒预热）

**判据：热点 key 的单分片 CPU 占用超过 60% 时必须拆。** 用 CPU 而不是带宽做判据，是挑战 3 里那条推导的直接结论——2 KB 的 value 在 5 万 QPS 下只占 0.8 Gbps，看带宽永远发现不了问题。

### 陷阱 6：不做字段裁剪，全量返回

**后果：** 每次 Feed 请求多传 330KB 无用字节，月成本 ¥79 万（均值口径，见挑战 4 的完整推导）；且客户端解析成本上升、弱网下延迟劣化。**注意这笔钱只占全平台带宽的 0.55%——所以它不是字段裁剪的主要理由，弱网延迟与热点分片容量才是。**

**弱网下的延迟劣化比成本更值得关注，因为它影响的是留存：**

```
4G 弱网实测下行 1.5 Mbps（地铁、电梯、演唱会场馆）：
  裁剪方案   120 KB → 120 × 8 / 1500 = 0.64 秒
  全量方案   450 KB → 450 × 8 / 1500 = 2.40 秒
  差值 1.76 秒 —— 全部落在【首屏出现之前】

再叠加 TCP 慢启动：
  初始拥塞窗口 10 MSS ≈ 14 KB，每 RTT 翻倍
  120 KB 需要约 4 个 RTT（14→28→56→112→…）
  450 KB 需要约 6 个 RTT
  弱网 RTT 150ms → 多 2 个 RTT = 额外 300ms
```

**慢启动这一项是纯粹的结构性损失**：它与带宽无关，只与字节数跨过了多少次窗口翻倍有关。所以字节裁剪在弱网下的收益是超线性的——**省 3.75 倍字节，换来的不只是 3.75 倍的传输时间，还有两个额外的 RTT。**

**解决方案：** 投影注册表 + 单测强制校验 + 字节成本纳入月度账单监控（BFF 统计各视图的字节/请求）。

**防腐化的机制比方案本身更重要**，因为字段泛滥是一个单向棘轮——每次都只多加一个字段，每次都"就这一个没关系"：

```
CI 阶段的两条断言：
  1. 模型新增字段必须归属至少一个视图（否则报错）
     → 防【漂移】：新字段被静默丢弃，前端拿不到数据却查不出原因
  2. 单视图字段数不得超过基线 + 20%（超过需在 PR 里显式提高基线）
     → 防【泛滥】：让"加第 15 个字段"变成一个需要解释的动作，而不是默认允许

运行时的一条监控：
  各视图的 P50 响应字节数，按周环比。增长 > 5% 触发人工复核
  → 字段数没变但字节数涨了，通常意味着某个字段的内容变长了（如 tag 列表膨胀）
```

第三条尤其容易被忽略：**字段数是可控的，字段的内容长度不是。** 一个 `tags` 字段从 3 个标签涨到 30 个标签，字段数没变，字节数涨了 10 倍。

### 陷阱 7：本地缓存与分布式缓存 TTL 打架

**后果：** L3 TTL 60s、L4 TTL 10min，且 L4 失效后 L3 仍有旧值。表现为**新旧数据来回跳**——同一用户 30 秒内两次翻 Feed，前一次命中 L3 旧值，后一次命中 L4 新值，内容版本不一致，用户困惑，严重时引发"内容回退"类投诉。

**"来回跳"比"一直旧"更难排查，也更伤用户信任。** 因为它不满足单调性：

```
用户视角的时间线（100 台机器，负载均衡随机路由）：
  T0   请求落到机器 A → A 的 L3 有旧值（version=7）→ 看到旧标题
  T1   请求落到机器 B → B 的 L3 刚过期 → 查 L4 → 新值（version=8）→ 看到新标题
  T2   请求落到机器 A → A 的 L3 还没过期 → 又看到旧标题     ← 回退了

一直旧：用户会认为"还没生效，等等看"
来回跳：用户会认为"这个平台的数据是坏的"
```

而且**排查者复现不出来**：他自己刷新几次可能一直落在同一台机器上，看到的是稳定的旧值或稳定的新值。**只有 1/100 的概率恰好观察到跳变**，于是工单被标记为"无法复现"关闭。

**解决方案：** 版本号方案统一判断。每个 content 缓存带 `content_version`，L3/L4 的值都带版本号；失效事件 bump 版本号，L3 读到版本低于本地记录时丢弃。**本地缓存判断新鲜度靠版本号，不靠 TTL 绝对值。**

具体协议（这是版本号的第二个职责，与回填 CAS 是同一个机制的两种用法）：

```
L3 的读取签名从 get(cid) 变为 get(cid, min_version)：
  min_version 来自哪里？—— 来自【同一批次里其他来源已见的最大版本】
  Feed 聚合 30 条内容时：
    1. 先批量查 L4 的版本水位（一次 MGET，只取 8 字节的 version，不取 value）
    2. 用这批水位作为 min_version 去查 L3
    3. L3 中版本低于水位的条目视为 miss，回源 L4
  代价：多一次 MGET（30 个 key × 8B = 240B，约 1ms）
  收益：L3 命中的数据保证不比 L4 旧
```

**这个"先查版本再查值"的模式看起来是把一次读变成了两次读，实际上它是把"不一致"换成了"多 1ms"。** 在 200ms 的预算里，1ms 换掉一类无法复现的用户投诉，是明确划算的。

注意它**不能**用"让 L3 的 TTL 短于 L4"来替代——那只能缩短跳变窗口，不能消除跳变；也不能用"失效时广播 L3"替代（那是 F 级的做法，Q 级承受不起 100 倍写放大，见陷阱 2）。

### 陷阱 8：批量接口的"头部放大"

**后果：** 批量接口做出来后被当成"什么都能查"的万能口：Feed 请求塞 200 个 content_id、要 40 个字段，单请求载荷 1MB。批量接口的收益（减少 RPC 数）被单请求体量的膨胀抵消，网络往返没省多少，却占满带宽。**批量的正确姿势是"小批量、少字段、可并行"。**

**批量接口会腐化，是因为它的调用方与代价承担方不是同一个团队。** 调用方看到的是"一次调用就拿到全部数据，代码更简单"；代价（分片扇出、GC 压力、带宽）由被调用方承担。**这种代价外部化的接口，一定会被用到它的极限。**

腐化的典型轨迹，以及每一步的合理化理由：

```
v1  ≤ 30 个 id，14 个字段            "Feed 卡片需要"
v2  ≤ 100 个 id                      "预加载下一页，减少一次 RPC"
v3  加 5 个字段                      "详情页也想复用这个接口，就多几个字段"
v4  ≤ 200 个 id                      "运营后台要导出，一次多拿点"
v5  字段白名单改成"传什么给什么"      "每个场景需求不同，服务端不该管"
    ← 到这一步，接口已经退化为"远程 SELECT *"，
      服务端完全失去了对自己负载的控制权
```

**v5 是不可逆的**：一旦允许调用方自由指定字段，就无法知道哪些字段可以下线、哪些索引可以删、单请求的字节上界是多少。**接口的约束一旦放开就收不回来，因为收回意味着破坏已有调用方。**

**解决方案：** 三层约束，且必须由服务端强制而非文档约定：

```
1. id 数量硬上限 100（超过直接拒绝，返回 INVALID_ARGUMENT，不做截断）
   → 【不能截断】：静默截断会让调用方拿到不完整数据却以为成功，
     比报错危险得多
2. 字段白名单由【场景码】决定，而非调用方传参
   → 调用方传 scene=feed_card，服务端查投影注册表决定返回哪 14 个字段
   → 调用方无法要求额外字段，想要就得改注册表（走评审）
3. 单请求字节数与 id 数同时限流，并按调用方（scene + app_id）分别统计
   → 暴露腐化：某个 scene 的平均 id 数从 30 涨到 90，会在周报里显形
```

**判据：批量接口的单请求字节应小于等于"串行 N 次单查"的字节。** 更根本的判据是**接口的负载上界必须由服务端唯一决定**——凡是调用方可以通过参数把服务端负载放大 10 倍的接口，都迟早会被放大 10 倍。

### 陷阱 9：Cache-Aside 只删缓存，不做回填单调性校验

**后果：** 这是前文「前置问题」推导的那个竞态，单独列为陷阱是因为它**在所有教科书版本的 Cache-Aside 里都存在，却几乎不会被提及**。表现为：每天几十条内容的缓存里躺着已经被失效过的旧值，持续最长 10 分钟。

**它之所以能长期潜伏，是因为它同时具备三个特性：**

| 特性 | 后果 |
|------|------|
| 概率低（约 8×10⁻⁴ / key / 日） | 压测、灰度、单测全部复现不出 |
| 绝对量不低（约 80 次/日） | 客服工单里天天有，但每次只有一个用户报 |
| 自愈（TTL 到期即恢复） | 排查者去看的时候数据已经正常了 |

**"用户报了但我们查的时候是好的"——这个组合让它被归类为"用户看错了"。** 而真正的信号藏在时间戳里：如果记录了缓存写入时刻，就会发现脏值的写入时刻**晚于**失效事件的时刻，这是逻辑上不可能的（除非有回填竞态）。

**解决方案：** 回填时做版本号 CAS（Lua 脚本内原子比较），见前文。这里补充**如何证明它被修好了**——因为一个每天只发生 80 次的问题，修好之后你无法通过"没再发生"来确认：

```
埋点：每次回填被 CAS 拒绝时打一条日志（含 cid、incoming_version、water_mark）
预期：这个计数应当每天出现几十次，且与前文推导的量级一致

如果计数是 0 → 说明 CAS 没生效（水位标记没写、或比较逻辑写反）
如果计数是几万 → 说明版本号在倒退（见异常场景「版本号回退」）
如果计数是几十 → 与推导吻合，防护在工作 ✓
```

**这是本篇少数几个"必须靠埋点计数才能确认修复"的问题。** 修复一个概率性缺陷的正确验收方式不是"观察它不再发生"，而是**观察防护机制被触发的频率符合预期**——防护从不触发和防护不存在，在监控上是同一个样子。

### 陷阱 10：singleflight 实现里的"双 leader"

**后果：** 用 `Map<key, List<Waiter>>` 手写单飞，检查与插入之间存在竞态，产生两个 leader。表现为：**单飞看起来生效了（大部分并发被合并），但热点 key 失效瞬间仍偶发回源风暴**——因为并发度越高，双 leader 的概率越大，而这恰好就是最需要单飞的时刻。

**竞态的展开（三个不同的失败模式，都来自同一个根因）：**

```
模式 A：双 leader（合并失败）
  T0  线程 1：map.get(k) → null
  T1  线程 2：map.get(k) → null          ← 两者都认为自己是 leader
  T2  线程 1：map.put(k, list1)
  T3  线程 2：map.put(k, list2)           ← 覆盖 list1
  结果：两次回源；且 list1 里的等待者永远等不到唤醒（对象已不可达）

模式 B：唤醒丢失
  T0  线程 1（leader）：回源中
  T1  线程 2：map.get(k) → list1 → list1.add(waiter2)
  T2  线程 1：回源完成 → list = map.remove(k) → 唤醒 list 中所有等待者
      若 T1 的 add 发生在 remove 之后 → waiter2 加进了一个已被移除的 list
  结果：waiter2 等到超时

模式 C：NPE / KeyError
  线程 2 拿到 list 引用后，线程 1 完成并 remove
  线程 2 再执行 map.get(k).add(...) → NPE
  （Python 版本表现为 self._inflight[cid].append 抛 KeyError）
```

**三个模式的根因是同一个：把"判断是否为 leader"和"注册等待者"做成了两个独立的非原子步骤。**

**解决方案：** 用 `computeIfAbsent`（Java）/ `setdefault`（Python）把两步合一，并让容器本身携带完成状态——即用 `Future`/`Event` 而不是 `List`：

```
正确骨架（语言无关）：
  fut, is_leader = map.compute_if_absent(k, () -> new Future())
      ← 原子操作。返回值同时告诉调用方"容器"和"我是不是创建者"
  if is_leader:
      try:      fut.set_result(load_from_source(k))
      except e: fut.set_exception(e)        ← 必须！否则等待者卡到超时
      finally:  map.remove(k, fut)          ← 带值比较的 remove，避免删掉后来者的 Future
  return fut.get(timeout=...)               ← leader 和 follower 走同一条返回路径
```

**四个不能省的细节：**
1. **`is_leader` 必须由原子操作的返回值给出**，不能事后用 `map.get(k) == myFuture` 判断
2. **异常路径必须 `set_exception`**，否则一次回源失败会让所有等待者卡满超时时间——**这会把"一次 DB 慢查询"放大成"一批请求全部超时"**，比不做单飞更糟
3. **`remove` 必须带值比较**（`remove(k, fut)` 而非 `remove(k)`），否则会误删下一轮的 Future，导致下一轮出现模式 A
4. **等待要有超时**，且超时后**不重试**——单飞的等待者超时说明回源本身有问题，重试只会加剧

**判据：单飞的正确性无法通过功能测试验证，必须通过并发压测 + 回源计数验证。** 具体做法：让 1,000 个线程同时请求同一个刚失效的 key，断言回源计数恰好为 1。功能测试（串行调用两次，第二次命中缓存）对以上三个模式全部无感。

## 异常场景完整演练

### 场景 1：互动域故障导致 Feed 扇出延迟暴涨

**场景描述：** 晚间高峰，互动域（域 10）的批量接口 P99 从 10ms 恶化到 800ms。Feed 聚合的 6 个子 RPC 里，`BatchGetInteractStatus` 是最慢的。若聚合逻辑"等最慢"，Feed 整体 P95 从 185ms 涨到 900ms，直接击穿 200ms 预算。

**故障演进的时间线（关键是理解它为什么会自我强化）：**

```
T+0s     互动域某分片 GC 停顿 400ms，P99 从 10ms → 800ms
T+2s     Feed 侧 15ms 超时开始大量触发
         此时若配置了重试：互动域收到 9.75 万 × 2 = 19.5 万 QPS
T+5s     互动域容量 12 万 QPS 被超出 62% → 排队 → 全部请求变慢
         → 更多超时 → 更多重试
T+15s    互动域进入过载态：因为线程全在处理注定超时的请求，
         有效吞吐从 12 万降到 8 万 QPS
T+30s    【亚稳态】最初的 GC 早已结束，但流量仍稳定在 2 倍，
         系统无法自行恢复
T+?      只能靠人工介入（关重试 / 限流 / 重启）
```

**根因分析——三层，只有第三层是真根因：**

| 层次 | 表象 | 是否根因 |
|------|------|---------|
| 表层 | 互动域 P99 高 | 否。GC 停顿是常态，任何 JVM 服务每天都有 |
| 中层 | Feed 聚合等最慢子请求 | 否。这只是让故障可见 |
| **深层** | **重试没有配额；且互动状态被当成必需字段** | **是** |

**真根因是"必需性判断错误"：** 互动状态（是否点赞、是否收藏）**不是渲染 Feed 的必需数据**——灰色按钮完全可以接受。把它当成必需字段，等价于把整个 Feed 的可用性与互动域的可用性做了串联。**串联的可用性是乘法：99.9% × 99.9% × 99.9% × … 六个域串联就是 99.4%，即每月 4.3 小时不可用。**

**错误做法：** 对互动域请求做超时重试——每个 Feed 请求多等 1-2 个超时周期，且重试流量继续打向已故障的互动域，**把互动域的单域故障放大成全平台 Feed 超时**。

**正确做法：**

```
1. 互动状态子请求设置硬超时 15ms
2. 超时后不重试，返回 unknown → BFF 渲染灰色互动按钮
3. 前端对灰按钮做"点击再单独查询"的降级
4. 聚合逻辑对 6 个子请求做"最慢容忍"：互动/关系两类标记为可降级，
   其超时不计入整体预算
5. 互动域恢复后，通过开关灰度恢复实时回填
```

**检测代码——关键是区分"下游慢"与"我们在放大下游的慢"：**

```python
class FanoutHealthMonitor:
    """扇出健康度监控。核心指标不是下游延迟，而是【降级率】与【重试放大比】。

    下游延迟高是外部事件；重试放大是我们自己的行为。
    只有后者是我们能控制、也必须监控的。
    """

    def __init__(self, degradable_domains: set[str]):
        self._degradable = degradable_domains
        self._sent = defaultdict(int)        # 我们发出的请求数（含重试）
        self._logical = defaultdict(int)     # 逻辑请求数（不含重试）
        self._degraded = defaultdict(int)    # 降级次数
        self._timeout = defaultdict(int)

    def record(self, domain: str, *, retries: int, degraded: bool, timed_out: bool):
        self._logical[domain] += 1
        self._sent[domain] += 1 + retries
        if degraded:
            self._degraded[domain] += 1
        if timed_out:
            self._timeout[domain] += 1

    def amplification(self, domain: str) -> float:
        """重试放大比。健康值 = 1.0。> 1.5 意味着我们正在把故障推向亚稳态。"""
        n = self._logical[domain]
        return self._sent[domain] / n if n else 1.0

    def check(self) -> list[str]:
        alerts = []
        for d in set(self._logical):
            amp = self.amplification(d)
            deg_rate = self._degraded[d] / max(self._logical[d], 1)
            to_rate = self._timeout[d] / max(self._logical[d], 1)

            # 规则 1：放大比是硬红线。对已在超时的下游做重试，等于主动制造亚稳态
            if amp > 1.5 and to_rate > 0.05:
                alerts.append(
                    f"[P0] {d} 重试放大比 {amp:.2f} 且超时率 {to_rate:.1%}"
                    f" —— 立即关闭该域重试，否则将进入亚稳态失败"
                )

            # 规则 2：可降级域的降级率越线 —— 用户有感但不致命，P2
            if d in self._degradable and deg_rate > 0.01:
                alerts.append(f"[P2] {d} 降级率 {deg_rate:.1%}（阈值 1%）")

            # 规则 3：不可降级域出现降级 —— 说明降级矩阵与代码不一致，P1
            if d not in self._degradable and deg_rate > 0:
                alerts.append(
                    f"[P1] {d} 不在可降级清单却发生了 {self._degraded[d]} 次降级"
                    f" —— 降级矩阵与实现漂移，或有人加了未评审的降级分支"
                )

            # 规则 4：降级率恒为 0 且持续数日 —— 降级路径可能已经坏了
            #        （空槽告警：没有告警的降级不是降级，是掩盖）
            if d in self._degradable and self._logical[d] > 1_000_000 and deg_rate == 0:
                alerts.append(f"[P3] {d} 百万请求零降级 —— 降级分支疑似不可达，需演练验证")
        return alerts
```

**规则 4 是这套监控里最容易被删掉、也最有价值的一条。** 降级路径是"平时不跑、故障时必须对"的代码，它腐化了没人知道。**唯一能发现它腐化的方式，是在它长期不被触发时主动报警，并用混沌演练强制触发一次。**

**处置代码——自动关闭重试并进入降级模式：**

```python
class DegradableCaller:
    """可降级下游的调用封装。

    设计要点：
      - 重试配额是【全局】的，不是每请求的。这是与普通重试库最大的区别
      - 熔断的判据是"超时率"而非"错误率"：超时意味着下游还在处理我们的请求
        （消耗它的资源），错误意味着它快速拒绝了（不消耗）。前者才需要熔断
      - 降级返回值必须是【显式的 unknown】，不能是空值或默认值
    """
    RETRY_QUOTA_RATIO = 0.05   # 重试量不得超过正常量的 5%

    def __init__(self, domain: str, fallback, timeout_ms: int = 15):
        self._domain, self._fallback, self._timeout = domain, fallback, timeout_ms
        self._quota = TokenBucket(rate_ratio=self.RETRY_QUOTA_RATIO)
        self._breaker = TimeoutRatioBreaker(threshold=0.10, window_s=10)

    def call(self, request, monitor: FanoutHealthMonitor):
        if self._breaker.is_open():
            # 熔断期间连一次都不发 —— 让下游有机会恢复
            monitor.record(self._domain, retries=0, degraded=True, timed_out=False)
            return self._fallback(request)

        retries = 0
        try:
            return self._invoke(request)
        except TimeoutError:
            self._breaker.on_timeout()
            # 关键：重试要先申请全局配额。没有配额的对冲就是重试
            if self._quota.try_acquire():
                retries = 1
                try:
                    return self._invoke(request)
                except TimeoutError:
                    pass
            monitor.record(self._domain, retries=retries, degraded=True, timed_out=True)
            return self._fallback(request)
        finally:
            if retries == 0:
                monitor.record(self._domain, retries=0, degraded=False, timed_out=False)

    def _invoke(self, request):
        return rpc_call(self._domain, request, timeout_ms=self._timeout)
```

**结果：** Feed 整体 P95 保持 185ms，用户只看到互动状态短暂变为灰色，点击仍可单独查询。**互动域故障被隔离在"互动状态这一个字段"里，而不是蔓延到整个 Feed。**

**这个场景留下的通用结论：** 扇出治理的可用性收益不来自"更快"，而来自**把串联改成并联**。六个域串联是 99.4%，六个域中四个可降级则是 `99.9% × 99.9% = 99.8%`（只有两个必需域串联）——每月不可用时间从 4.3 小时降到 1.4 小时，而这个收益完全来自一次"哪些字段是必需的"的分类判断，不涉及任何性能优化。

### 场景 2：缓存雪崩——批量 key 同时过期

**场景描述：** 一批热门短视频（同批次发布、同 TTL 起点）的 L4 key 在同一时刻过期，且 L3 本地缓存此刻也命中率低（这批内容刚被大范围转发，此前不在任何实例的本地缓存中）。6.5 万 QPS 的 Feed 中 30% 的请求同时 miss，回源流量瞬间到 58 万 QPS——只读副本池 8 台机器的 CPU 被打满，P99 从 10ms 涨到 4 秒。

**为什么"同批过期"会自然发生——三个独立的成因，都不需要任何人犯错：**

```
成因 1：批量导入 / 批量回填
  运营一次导入 1 万条内容，或缓存预热脚本按顺序回填
  → 全部 key 的写入时刻集中在几秒内 → TTL 起点相同 → 10 分钟后同时过期

成因 2：热点内容的同步生命周期
  一次热点事件（如赛事）产生的内容，被同一批用户在同一时段访问
  → 首次 miss 的时刻天然聚集 → 回填时刻聚集 → 过期时刻聚集

成因 3：上一次雪崩的余波（最隐蔽）
  雪崩发生 → 大量 key 同时 miss → 同时回填 → TTL 起点再次对齐
  → 10 分钟后再次同时过期 → 【雪崩会自我复制，周期等于 TTL】
```

**成因 3 意味着雪崩不是一次性事件，而是一个会自持振荡的系统。** 排查时的典型现象是"每 10 分钟一个尖峰"，且尖峰幅度缓慢衰减（因为抖动在逐步打散对齐）——**如果看到延迟毛刺的周期恰好等于某个 TTL，几乎可以确定是这个机制。**

**根因分析：**

| 层次 | 表象 | 是否根因 |
|------|------|---------|
| 表层 | DB CPU 打满 | 否 |
| 中层 | 命中率骤降到 70% | 否，这是现象 |
| 中层 | TTL 未抖动 | 部分。抖动只降低概率，不设上界 |
| **深层** | **miss 侧没有硬性并发上限，DB 暴露在"命中率 × 总流量"这个不可控的乘积下** | **是** |

**这是本篇反复强调的那一点：抖动、错峰、预热都是概率手段；只有 miss 侧限流是硬保证。** 前两者把雪崩概率从 100% 降到 3%，但 3% 的概率乘上一天 8.6 万秒，仍然意味着每天都会发生。

**错误做法：** 把 TTL 调短或调长——调短是雪崩常态化，调长是让统计类数据永不过期。

**正确做法：**

```
1. 检测：按 (缓存层, key 前缀) 分组的命中率监控，命中率跌破 95% 触发告警
2. 应急：开启"降级保护"开关——缓存 miss 时不再直连 DB，
   而是走 L5 只读副本的限流队列（≤ 1 万 QPS），其余请求短暂失败返回重试
3. 恢复：DB 侧把冷数据预加载进 L4（回填脚本按热度降序），命中率回升后关开关
4. 预防：TTL 加随机抖动（10min ± 2min）+ 新发布内容使用"错峰 TTL"
   （发布后 3 天用 60s 短 TTL，之后切到 10min），避免同类内容同批过期
```

**检测代码——检测的关键是抓"过期时刻的分布"，而不是抓"命中率下降"（后者已经晚了）：**

```python
class ExpiryClusteringDetector:
    """TTL 对齐检测器。在雪崩【发生之前】发现过期时刻聚集。

    命中率监控是事后指标：它跌破 95% 时 DB 已经在承压了。
    真正的先行指标是"未来某一秒内将要过期的 key 数量"。
    """
    BUCKET_S = 1
    HORIZON_S = 900                       # 看未来 15 分钟

    def __init__(self, db_fallback_qps: int = 10_000, avg_read_qps: int = 1_950_000):
        self._buckets = defaultdict(int)  # 相对秒 → 将在该秒过期的 key 数
        self._db_cap = db_fallback_qps
        self._avg_qps = avg_read_qps

    def on_backfill(self, cid: int, ttl_s: int, now_s: int):
        """每次回填时登记它的过期时刻。开销：一次自增。"""
        self._buckets[(now_s + ttl_s) // self.BUCKET_S] += 1

    def forecast(self, now_s: int) -> list[dict]:
        """预测未来每一秒的 miss 洪峰，与 DB 兜底容量比较。"""
        risks = []
        for offset in range(0, self.HORIZON_S, self.BUCKET_S):
            b = (now_s + offset) // self.BUCKET_S
            expiring = self._buckets.get(b, 0)
            if not expiring:
                continue
            # 这些 key 过期后，多久会被重新请求？按其平均读频率估算
            # 保守假设：热点 key 在过期后 1 秒内必被请求
            projected_miss_qps = expiring
            if projected_miss_qps > self._db_cap * 0.5:
                risks.append({
                    "in_seconds": offset,
                    "expiring_keys": expiring,
                    "projected_miss_qps": projected_miss_qps,
                    "db_capacity_pct": projected_miss_qps / self._db_cap,
                    # 处置建议：给这批 key 现在就打散，别等它过期
                    "action": "pre_scatter" if offset > 60 else "pre_warm",
                })
        return risks

    def scatter(self, now_s: int, redis) -> int:
        """把即将聚集过期的 key 主动打散：给它们重设一个随机化的 TTL。

        这是【提前】干预 —— 在 key 还有效时改 TTL 是零成本的（EXPIRE 命令），
        等它过期了再补救就只能靠限流扛。
        """
        scattered = 0
        for risk in self.forecast(now_s):
            if risk["action"] != "pre_scatter":
                continue
            b = (now_s + risk["in_seconds"]) // self.BUCKET_S
            for cid in self._sample_keys_in_bucket(b):
                # 重设 TTL 到 [600, 1200] 秒的均匀分布，彻底打散对齐
                redis.expire(f"content:{cid}", 600 + _stable_jitter(cid, 600))
                scattered += 1
        return scattered
```

**`_stable_jitter(cid, span)` 必须是 cid 的确定性函数（如 `hash(cid) % span`），不能用随机数。** 原因：100 台机器可能同时回填同一个 key，用随机数会让各机器给出不同的 TTL，导致 L4 里同一个 key 的过期时刻取决于"哪台机器最后写的"，无法预测也无法登记到上面的桶里。**确定性抖动让"过期时刻"从一个随机变量变成一个可计算的量，这才使上面的 forecast 成为可能。**

**处置代码——miss 侧硬闸，这是唯一的硬保证：**

```python
class MissGate:
    """回源闸门。缓存 miss 之后、访问 DB 之前的最后一道硬性上限。

    三条设计原则：
      1. 上限是【绝对值】（1 万 QPS），不是比例。比例会随流量增长而失效
      2. 超限时【快速失败】，不排队。排队会让请求堆积到超时，
         既没减轻 DB 压力（请求已经发出去了），又拖垮了调用方线程
      3. 拒绝时优先保住【热门内容】：按内容热度分级配额，
         保证头部内容始终能回源（它们的 miss 影响面最大）
    """
    def __init__(self, hard_cap_qps: int = 10_000):
        # 分级配额：头部内容拿 60%，中部 30%，长尾 10%
        self._buckets = {
            "hot":  TokenBucket(hard_cap_qps * 0.6),
            "warm": TokenBucket(hard_cap_qps * 0.3),
            "cold": TokenBucket(hard_cap_qps * 0.1),
        }
        self._rejected = defaultdict(int)

    def acquire(self, cid: int, tier: str) -> bool:
        if self._buckets[tier].try_acquire():
            return True
        # 降级借用：长尾被拒时不借；头部被拒时可以借长尾的额度
        if tier == "hot" and self._buckets["cold"].try_acquire():
            return True
        self._rejected[tier] += 1
        return False

    def load(self, cid: int, tier: str, loader, stale_value=None):
        if not self.acquire(cid, tier):
            # 拒绝路径的三种兜底，按优先级
            if stale_value is not None:
                # 1. 有过期的旧值 → 返回旧值并标记 stale
                #    【宁可给旧数据，也不要给错误页】—— 对内容平台，
                #    10 分钟前的播放数完全可以接受
                return stale_value, "stale"
            return None, "rejected"     # 2. 无旧值 → 让上层降级渲染
        return loader(cid), "fresh"
```

**"返回过期旧值"这条兜底是雪崩处置里性价比最高的一招，但它要求缓存在过期后不立即删除**——即 L4 的 value 带一个逻辑过期时间，物理 TTL 设为逻辑 TTL 的 2 倍。逻辑过期后进入"可用但需刷新"状态，闸门放行时刷新，闸门拒绝时直接返回旧值。**代价是内存占用增加约 15%（多存一份即将淘汰的数据），收益是雪崩期间用户完全无感——从"部分请求失败"变成"部分数据陈旧"。**

**根因反思：** 同批内容同 TTL 的根源是"发布时统一设置过期时间"，而不是"同一时刻过期"。**雪崩的预防在写入侧（错峰 TTL + 确定性抖动），检测在过期时刻的分布（而非命中率），兜底在 miss 侧的硬闸 + 逻辑过期。三者防的是同一个问题的三个阶段，缺任何一个都会在某种流量形态下失效。**

### 场景 3：热点视频击穿缓存

**场景描述：** 一条明星视频 2 小时内播放冲到 4.5 万 QPS。单个 Redis 分片的 CPU 上限约 5 万 QPS，该 key 打满整片；恰逢该 key 过期，singleflight 未生效前有 200 个并发回源请求同时打向 DB。

**升温曲线决定了防护必须多快生效——这是本场景与"稳态热点"最大的区别：**

```
一条内容从发布到打满单分片的真实曲线（明星事件类）：
  T+0min    发布，QPS 约 10（作者粉丝）
  T+3min    进入推荐小流量池，QPS 约 500
  T+8min    小流量池 CTR 超阈值，升级中流量池，QPS 约 8,000   ← 已越过 5,000 阈值
  T+12min   进入热搜/大流量池，QPS 约 3.5 万
  T+15min   峰值 4.5 万 QPS
  → 从越线（8,000）到打满（4.5 万）只有【7 分钟】

而防护链路的耗时：
  CMS 识别（连续 3 个 1 秒窗口）        3 秒
  上报 + 决策 + 写 hot_key_registry     1 秒
  100 台机器拉取名单（1 秒轮询）        1 秒
  拆 key 写入 10 副本 + L3 预热         1 秒
  → 合计约 6 秒 ≪ 7 分钟  ✓ 有充足余量
```

**余量充足这个结论很重要，它说明这里不需要"预测性"的热点识别。** 有人会提出用推荐系统的流量池升级事件来提前预热（内容进入大流量池时主动拆 key）——这在 7 分钟的升温曲线下是过度设计。**但如果升温曲线是 7 秒（例如站外爆款空降、或推送引流），6 秒的防护链路就只剩 1 秒余量，此时联动推荐侧的预判才有必要。** 判断依据是升温速度与防护速度的比值，不是"能不能预测"。

**根因分析：**

| 层次 | 表象 | 是否根因 |
|------|------|---------|
| 表层 | Redis 分片 CPU 100% | 否 |
| 中层 | 单 key QPS 4.5 万 | 否，这是业务事实，不可避免 |
| 中层 | 未拆 key | 部分。拆 key 只把 4.5 万摊成 10×4,500 |
| **深层** | **读流量没有在"离用户最近的一层"被吸收；4.5 万 QPS 全部穿透到了共享的 L4** | **是** |

**真正的解法方向是 L3 常驻（把 4.5 万降到 1.67 QPS），拆 key 只是升温期的兜底。** 这个判断的依据在挑战 3 里已经推出：单分片先见顶的是 CPU 而非带宽，而 CPU 只能靠减少请求数来省——加内存、加带宽、加分片都不解决问题，**只有"请求根本不到达 Redis"才解决问题。**

**错误做法：** 无脑延长热点 key 的 TTL——热点内容一旦下架（明星事件反转），F 级失效仍然会清掉，但 TTL 太长会让"已修复的旧数据"长时间滞留。更隐蔽的错误是**给热点 key 加大 Redis 内存或单独部署一个"热点 Redis 集群"**：内存不是瓶颈，把 4.5 万 QPS 从一个分片挪到另一个分片上仍然是 4.5 万 QPS。

**正确做法：**

```
1. 检测：单 key 读 QPS > 5000（CMS 估计），连续 3 个 1 秒窗口确认
2. 拆 key：content:{id} → content:{id}:r0..r9（N=⌈QPS/5000⌉，上限 16）
3. 预热 L3：热点内容主动写进各实例本地缓存热点区（8GB 预留）+ 后台主动刷新
   （不等 TTL 过期），单个头部 key 到达 L4 的 QPS 降到 1.67
4. singleflight：同一副本 key 同一瞬间只允许 1 个回源，其余等待同一个 Future
5. F 级失效改走"下架水位标记 + 逐个删副本"，解决拆 key 的失效非原子性
6. 热点退出：读 QPS 回落后自动合并回单 key（demote_after 驱动），回收副本空间
```

**检测代码——CMS + 滑动窗口 Top-K：**

```python
class HotKeyDetector:
    """基于 Count-Min Sketch 的热点识别。

    为什么不用全量 HashMap：8,000 万 key × 40B × 100 台 = 320 GB，
    为了找出 100 个热点而付出的代价。CMS 用 2 MB 做同一件事。

    为什么 CMS 的"只高估不低估"特性在这里是安全的：
      高估 → 多拆了不该拆的 key → 浪费一点内存（可接受）
      低估 → 漏判热点 → 分片被打满（不可接受）
    代价不对称时，参数就该偏向便宜的那一侧。
    """
    WIDTH = 4096            # ε = e/4096 ≈ 0.066%
    DEPTH = 4               # 见正文：d 从 7 降到 4 是有意识的取舍
    WINDOW_BUCKETS = 10     # 10 个 1 秒桶的滑动窗口
    THRESHOLD_QPS = 5000    # 全局阈值
    CONFIRM_WINDOWS = 3     # 连续 3 个窗口确认，过滤瞬时尖峰

    def __init__(self, node_count: int = 100):
        self._node_count = node_count
        # 本进程只看到全局流量的 1/node_count，阈值同比例缩放
        self._local_threshold = self.THRESHOLD_QPS / node_count
        self._buckets = [
            [[0] * self.WIDTH for _ in range(self.DEPTH)]
            for _ in range(self.WINDOW_BUCKETS)
        ]
        self._cur = 0
        self._candidates: dict[int, int] = {}   # cid → 连续越线次数

    def _hashes(self, cid: int):
        # DEPTH 个独立哈希。用一个 64 位哈希切分，避免多次哈希计算的开销
        h = _mix64(cid)
        for i in range(self.DEPTH):
            yield (h >> (i * 13)) & (self.WIDTH - 1)

    def record(self, cid: int):
        """读路径上调用。开销：DEPTH 次数组自增 = 4 次内存写，纳秒级。"""
        table = self._buckets[self._cur]
        for i, idx in enumerate(self._hashes(cid)):
            table[i][idx] += 1

    def estimate(self, cid: int) -> int:
        """窗口内的估计计数 = 所有桶累加后取各行最小值（CMS 的标准查询）。"""
        return min(
            sum(self._buckets[b][i][idx] for b in range(self.WINDOW_BUCKETS))
            for i, idx in enumerate(self._hashes(cid))
        )

    def tick(self, observed_cids: Iterable[int]) -> list[tuple[int, int]]:
        """每秒调用一次：滚动窗口、评估候选、返回确认的热点。

        observed_cids 是本秒内实际出现过的 cid 采样集合（几千个），
        用于限定 estimate 的评估范围 —— CMS 不能枚举 key，必须外部提供候选集。
        这是 CMS 的固有限制，也是它省内存的代价。
        """
        promoted = []
        for cid in observed_cids:
            local_qps = self.estimate(cid) / self.WINDOW_BUCKETS
            if local_qps >= self._local_threshold:
                self._candidates[cid] = self._candidates.get(cid, 0) + 1
                if self._candidates[cid] == self.CONFIRM_WINDOWS:
                    global_qps = int(local_qps * self._node_count)
                    promoted.append((cid, global_qps))
            else:
                self._candidates.pop(cid, None)   # 连续性中断即重置

        # 滚动：清空最旧的桶，前移指针
        self._cur = (self._cur + 1) % self.WINDOW_BUCKETS
        nxt = self._buckets[self._cur]
        for row in nxt:
            for j in range(self.WIDTH):
                row[j] = 0
        return promoted
```

**注意 `tick` 需要外部提供 `observed_cids`——这是 CMS 最容易被忽略的限制：它能估计任意 key 的频率，但无法列出"频率最高的 key"。** 实践中的解法是维护一个几千项的采样集合（每 100 次读采样 1 次 cid 放进 set），CMS 负责在这个候选集上给出准确的频率估计。**采样只影响候选集的完整性（一个 5,000 QPS 的 key 在 1 秒内被采样到的概率是 `1-(1-0.01)^5000 ≈ 100%`），不影响频率估计的准确性——这个分工是 CMS 方案能成立的关键。**

**处置代码——拆 key 的读写与失效：**

```python
class HotKeyManager:
    """热点 key 的副本管理。

    最容易出错的地方不是读写路由，是【失效的原子性】：
    拆成 10 个 key 之后，"删除"从一个原子操作变成 10 个独立操作。
    解法是引入一个单点的"下架水位"标记，用一次原子写覆盖 N 次删除的不确定性。
    """
    def __init__(self, redis, registry: dict[int, int]):
        self._redis = redis
        self._replicas = registry          # cid → N（1 表示未拆）

    def read_key(self, cid: int, uid: int) -> str:
        n = self._replicas.get(cid, 1)
        if n == 1:
            return f"content:{cid}"
        return f"content:{cid}:r{_mix64(uid) % n}"

    def write_all(self, cid: int, payload: bytes, version: int, ttl_s: int):
        """回填/更新时写全部副本。带版本 CAS，与非热点路径同一套语义。"""
        n = self._replicas.get(cid, 1)
        keys = [f"content:{cid}"] if n == 1 else [f"content:{cid}:r{i}" for i in range(n)]
        # 单个 Lua 脚本内完成全部副本的 CAS 写入。
        # 副本 key 必须带同一个 hash tag（见下）才能保证它们在同一 slot，
        # 否则 Redis Cluster 不允许跨 slot 的多 key 脚本
        self._redis.eval(_CAS_WRITE_MULTI, keys, [payload, version, ttl_s])

    def invalidate_f_level(self, cid: int, new_f_version: int) -> bool:
        """F 级失效。顺序至关重要：先写水位，再删副本。

        若顺序颠倒（先删副本再写水位），则在两步之间有一个窗口：
        副本已删、水位未写 → 并发读会 miss 后回填【旧值】，且不会被拦
        """
        # 第 1 步：原子写下架水位。这一步成功即意味着失效【逻辑上已完成】
        ok = self._redis.set(f"content:{cid}:fver", new_f_version, ex=1800)
        if not ok:
            return False        # 水位写失败 → 整个失效失败 → 必须重试/告警

        # 第 2 步：尽力删除各副本。允许部分失败 —— 水位已经能拦住它们
        n = self._replicas.get(cid, 1)
        keys = [f"content:{cid}"] if n == 1 else [f"content:{cid}:r{i}" for i in range(n)]
        failed = [k for k in keys if not self._safe_del(k)]
        if failed:
            # 只是延长了这些副本的无效数据驻留（但读路径会因水位而丢弃它们），
            # 记录为 P2 而非 P0
            log.warning("F 级失效副本残留 cid=%s keys=%s（水位已生效，读路径安全）", cid, failed)
        return True

    def demote(self, cid: int):
        """热点降级：合并回单 key，回收副本内存。

        降级的顺序同样重要：先写单 key，再删副本，最后改路由表。
        反过来会让路由表指向还不存在的单 key，造成一段时间的全量 miss。
        """
        payload = self._redis.get(f"content:{cid}:r0")
        if payload:
            self._redis.set(f"content:{cid}", payload, ex=600 + _stable_jitter(cid, 600))
        n = self._replicas.pop(cid, 1)
        for i in range(n):
            self._safe_del(f"content:{cid}:r{i}")
```

**副本 key 必须使用 hash tag 才能落在同一 slot——`content:{1001}:r0`，花括号内的 `1001` 是 Redis Cluster 的 hash tag。这带来一个矛盾：hash tag 让 10 个副本落在同一 slot，也就是同一分片，于是拆 key 完全失效了。** 正确做法是**放弃多 key 原子脚本，让副本 key 不带 hash tag（`content:1001:r0`，各自哈希到不同 slot），写入时逐个 CAS**：

```
放弃的：10 个副本写入的原子性
换来的：10 个副本分布在 10 个不同分片（这是拆 key 的全部意义）
补偿：单点的下架水位标记（content:{1001}:fver 单 key，天然原子）
      + 每个副本各自的版本号 CAS（保证不会写回旧值）
最终语义：副本之间可能短暂版本不一致（某个副本还是 v7，其他已是 v8），
         但【任何副本都不会返回比水位更旧的数据】
```

**这是一个必须被明确记录的设计取舍**：拆 key 与多副本原子写入在 Redis Cluster 下不可兼得，本篇选择放弃原子性、用水位标记补偿。**如果实现时因为"想要原子性"而加了 hash tag，拆 key 会静默失效——所有副本仍在同一分片上，监控看到的分片 QPS 一点没降，而代码看起来完全正确。**

**结果：** L4 单个头部 key 的 QPS 从 4.5 万降到 1.67（L3 常驻），升温期由拆 key 承接（10 × 4,500），击穿回源量从 200 并发降到每台 1 次共 100 次（singleflight 的进程内作用域），DB 无感。

**热点治理的核心不是"缓存更大"，而是"读流量在离用户最近的一层被吸收"。** 而这句话的可操作版本是：**每一层缓存的价值等于它拦下的 QPS × 下一层单位 QPS 的成本。** L3 拦下 4.5 万 QPS 中的 99.996%，用的是 200 MB 内存 × 100 台；L4 拦下剩余的部分，用的是 480 个分片。前者的单位成本低两个数量级——**这就是为什么进程内缓存在超大规模下不是"可选优化"而是"必需层级"。**

### 场景 4：内容下架后缓存仍可见——违规传播

**场景描述：** 某内容被判定违规，后台执行下架。F 级失效删了 L4，但：① 某实例的 L3 本地缓存 60s 内仍返回旧值；② CDN 边缘缓存的播放地址未清；③ 客户端 L1 缓存的 Feed 仍含该内容。表现为**下架后 1-2 分钟内，部分用户仍能刷到并播放**。

**"删了 Redis 就完成了下架"这个误判，源于一个更深的建模错误：把缓存当成一棵树，实际上它是一片森林。**

```
误以为的结构（树，删根即可）：
              L5 DB
                ↓
              L4 Redis          ← 删这里
             ↙   ↓   ↘
           L3   L3   L3         ← 以为会跟着失效

真实结构（森林，各自独立持有副本）：
    L5 DB     L4 Redis     L3×100     L2 边缘×2000     L1 客户端×2亿
      │          │            │             │                │
      └──────────┴────────────┴─────────────┴────────────────┘
         五个【平级的】数据持有者，各有各的过期规则，
         其中 L1 有 2 亿个副本，且完全不受服务端控制
```

**L1 是这个森林里最不可控的一层：2 亿个客户端，各自缓存了 Feed 列表，服务端既不知道谁缓存了什么，也无法主动推送失效。** 任何"逐层清理"的方案在 L1 面前都会失败——**所以下架的正确性不能建立在"清理所有副本"上，必须建立在"最终校验"上。**

**根因分析：**

| 层次 | 表象 | 是否根因 |
|------|------|---------|
| 表层 | 下架后仍能刷到 | 否 |
| 中层 | L3/L2/L1 未清理 | 否。L1 在物理上不可清理 |
| 中层 | F 级失效通道覆盖不全 | 部分 |
| **深层** | **把"可见"与"可播"当成同一个语义；下架的执行点在"数据副本"而不在"访问凭证"** | **是** |

**关键的语义分离：**

```
「可见」= 内容出现在 Feed / 详情页 / 搜索结果里
  → 由分布在 5 层的元数据副本决定 → 无法保证强一致 → 只能尽力而为

「可播」= 客户端拿到了有效的播放地址并能取到媒体数据
  → 由【播放地址签发】这一个动作决定 → 单点 → 可以强一致

结论：下架的硬保证必须落在「可播」上，「可见」只做尽力而为。
      用户可能短暂看到卡片，但点进去必须播不了。
```

**这个分离带来一个反直觉的验收标准：** 下架完成的判据**不是**"Feed 里搜不到了"，而是**"播放接口对该内容返回拒绝"**。前者依赖 5 层缓存的收敛（不可保证），后者是一次数据库查询（可保证）。**把验收标准放在可保证的那一侧，是这个设计能成立的全部原因。**

**错误做法：** 认为"删了 Redis 就完成了下架"。同样错误的是**在播放接口的最终校验里查缓存**——那等于把强一致的校验又变成了最终一致，绕了一圈回到原地。

**正确做法：**

```
1. 版本号 bump（f_version）+ 广播：所有实例的 L3 读到旧 f_version 即丢弃
2. 联动 CDN 清除播放地址：所有档位、所有边缘（P00 下架工作流第 4 步）
3. 播放接口最终校验：签发播放地址前查 content_version.visible_scope
   —— 必须查库或强一致 key，【不能查普通缓存】
4. 已签发地址的处置：对"封禁"子类做 CDN 密钥轮转，使存量 URL 立即失效
5. 主动探测：从多个地区尝试播放，确认真的播不了才算下架完成
```

**检测代码——下架完成度的主动验证：**

```python
class TakedownVerifier:
    """下架完成度探测。

    核心设计：验收标准是【可播性】，不是【可见性】。
    对可见性只做观测与上报（因为它无法保证），对可播性做硬性断言。
    """
    PROBE_REGIONS = ["cn-east", "cn-north", "cn-south", "cn-southwest", "overseas-sg"]

    def verify(self, cid: int) -> dict:
        result = {"cid": cid, "playable": [], "visible": [], "verdict": None}

        # 断言 1（硬）：所有地区的播放接口都必须拒绝签发
        for region in self.PROBE_REGIONS:
            grant = probe_playback_grant(cid, region=region)
            if grant.granted:
                result["playable"].append(region)

        # 断言 2（硬）：已签发的存量 URL 必须失效
        #   这一条最容易漏。删了缓存、拒了新签发，但 5 分钟前签发的
        #   URL 仍然有效 —— 而热门内容 5 分钟内可能签发了几十万个 URL
        stale_urls = recent_signed_urls(cid, within_s=600)
        still_live = [u for u in stale_urls[:50] if probe_media_fetch(u).ok]

        # 观测（软）：可见性只上报，不作为拒绝依据
        for region in self.PROBE_REGIONS:
            if probe_feed_contains(cid, region=region):
                result["visible"].append(region)

        if result["playable"]:
            result["verdict"] = f"FAILED_HARD：{result['playable']} 仍可签发播放地址"
        elif still_live:
            result["verdict"] = f"FAILED_HARD：{len(still_live)} 个存量 URL 仍可取数据"
        elif result["visible"]:
            # 可见但不可播 —— 这是【预期状态】，不是故障
            result["verdict"] = "OK_WITH_RESIDUAL_VISIBILITY：可见性将在 60s 内收敛"
        else:
            result["verdict"] = "OK"
        return result
```

**`OK_WITH_RESIDUAL_VISIBILITY` 这个状态必须存在，且必须是"通过"。** 如果把它判为失败，下架流程会在每次执行时都卡在"等 L1/L2 收敛"上——而 L1 永远不会完全收敛（有的客户端可能一周不启动）。**把不可达成的条件写进验收标准，会让整个流程变成永久失败，进而被人为绕过——这比标准宽松危险得多。**

**处置代码——最终校验的正确实现：**

```python
class PlaybackGuard:
    """播放地址签发前的最终校验。整条下架链路的硬保证就在这里。

    三个不可妥协的设计约束：
      1. 【不查普通缓存】—— 查了就退化成最终一致
      2. 【失败时拒绝】—— 校验查不到结果时必须拒绝签发（fail-closed），
         不能因为"DB 抖动"就放行
      3. 【必须能扛 64.8 万 QPS】—— 这是本方案唯一的技术难点
    """
    def __init__(self, redis, db):
        self._redis, self._db = redis, db

    def check(self, cid: int) -> tuple[bool, str]:
        # 强一致 key：只存 visible_scope + f_version，8 字节。
        # 它与普通内容缓存的区别在于【写入方与失效方式】：
        #   普通缓存：读路径回填，TTL 过期
        #   本 key：  由 F 级失效通道【主动写入】，永不过期（无 TTL）
        # 无 TTL 意味着它不会因过期而回退到"查不到"，
        # 从而不需要在读路径上回源 —— 这是它能扛 64.8 万 QPS 的原因
        raw = self._redis.get(f"content:{cid}:guard")

        if raw is None:
            # 冷启动或 Redis 故障。fail-closed：查库，查不到就拒绝
            row = self._db.query_visible_scope(cid)      # 走独立的小连接池
            if row is None:
                return False, "guard_unavailable"        # 拒绝，而非放行
            self._redis.set(f"content:{cid}:guard", row.pack())   # 无 TTL
            raw = row.pack()

        scope, f_version = unpack_guard(raw)
        if scope in (SCOPE_TAKEN_DOWN, SCOPE_BANNED):
            return False, f"scope={scope}"
        return True, "ok"
```

**"无 TTL"是这个 guard key 设计里最关键、也最违反直觉的一点。** 常规缓存都要有 TTL 兜底（防止失效丢失导致永久脏数据），但 guard key 恰恰不能有：**有 TTL 就会过期，过期就要回源，64.8 万 QPS 的回源会打死 DB，于是不得不放行 —— 一个"为了防止脏数据"的 TTL，最终导致了违规内容被放行。** 代价是必须用别的机制保证 guard key 不会长期错误：

```
补偿机制（三条，缺一不可）：
  1. 全量对账：每 10 分钟扫 content_version 表中 f_version 变更过的行，
     比对 guard key，不一致则修正 —— 覆盖"失效事件丢失"
  2. 容量：8,000 万 × 16B ≈ 1.3 GB，独立 Redis 集群（与内容缓存物理隔离），
     不设淘汰策略（noeviction）—— 覆盖"被 LRU 淘汰导致回源"
  3. 内存告警：使用率 > 70% 即扩容。guard 集群 OOM 等价于全站不可播
```

**第 2 条的 `noeviction` 是另一个反直觉决定**：通常 Redis 都配 `allkeys-lru`，避免 OOM 导致写入失败。但 guard 集群宁可写入失败（触发告警，人工介入）也不能淘汰 key——**淘汰是静默的、按访问频率的，被淘汰的恰好是冷门内容的 guard，而冷门违规内容正是最需要拦截的（它们不在任何人的 L3 里，唯一的防线就是 guard）。**

**结果：** 播放被最终校验物理阻断，`可见` 与 `可播` 两个语义彻底分离。

**判据：任何"已下架内容仍可访问"的漏洞，最终都必须由"播放接口的最终校验"兜底，而不是指望缓存时效。** 更一般的表述是：**在一个有 N 层独立缓存的系统里，强一致的保证只能建立在"所有请求都必经的那个单点"上。** 找到那个单点（本篇是播放地址签发），把校验放在那里，其余各层全部按最终一致设计——这比试图让 N 层都强一致，既便宜也可靠。

## 性能与成本分析

**读链路的扇出治理前后对比：**

| 指标 | 朴素实现 | 治理后 | 说明 |
|------|---------|--------|------|
| 每 Feed 请求子 RPC | 150 | ≤ 6 | 批量接口合并 |
| 峰值子 RPC/秒 | 975 万 | ~39 万 | 扇出压缩 25 倍 |
| 元数据 DB 读（峰值） | 195 万 QPS | ~9750 QPS | L4 命中率 99.5% |
| 单请求字节 | 450KB | 120KB | 字段裁剪 |
| Feed P50 / P95 | >400ms（易超时） | 130ms / 185ms | 批量 + 并行 + 降级 |
| 对单个下游域的稳定性要求 | P9997 < 100ms | P99 < 100ms | 扇出从 150 降到 6 的真实收益 |

**关键结论：扇出治理让"任意域抖动"不再必然传导成全链路超时，缓存让 DB 从"扛 195 万 QPS"降为"扛 9750 QPS"——差三个数量级。** 而表格最后一行是最容易被忽略、实际最重要的一行：**扇出治理的产出不是"省了 144 个 RPC"，是把对每个下游域的 SLA 要求从不可能（P9997）降到了可能（P99）。**

**字节账本（与成本原则一致：带宽是命根子）：**

```
Feed 字段裁剪：   均值省 330KB/请求 → 月省 ¥79 万（占全平台带宽 0.55%）
批量 Protobuf：   跨域字节省 ~40% → 月省 ¥20 万+
缓存回源节省：    DB 读从 195 万 QPS 降到 9750 QPS
                 只读副本从 1,625 台降到 8 台（按 1,200 QPS/台）
                 → 月省硬件 ¥2,426 万（1,625 × ¥1.5 万 vs 8 × ¥1.5 万）
缓存资源成本：    L4 热集 160GB × 3 副本 ≈ ¥13 万/月；L3 为进程内存复用，零边际
```

**这四行里，只有第三行是数量级级别的收益，而它恰恰是最不像"优化"的一行。** 字段裁剪和 Protobuf 是主动做的优化，看得见、写得进周报；缓存替代掉的 1,617 台 DB 只读副本是**从未被采购过的机器**，没有任何账单记录它。**基础设施最大的收益通常以"没有发生的支出"形式存在，因此永远不出现在成本报表里，也永远不会被算进任何人的绩效。**

**顺带修正一处口径：** 若按"40 台降到 8 台"来算这笔账（¥12 万/月），会把缓存的价值低估 200 倍——而 200 倍恰好就是命中率 99.5% 对应的容量放大倍数。**这类错误的特征是：分子（QPS 降 200 倍）和分母（机器降 5 倍）用了不同的换算率**，两个数字单独看都不离谱，放在一句话里才露出矛盾。

**读链路缓存的总投入产出：** 缓存资源月成本约 ¥15 万，换来回源流量 99.5% 的削减 + 延迟 3 倍改善 + 单域故障不再拖垮全局。**缓存是读侧唯一"投入小、回报跨数量级"的基础设施。**

**命中率的成本最优点——为什么不追求更高：**

前文推导过命中率的下界（99.487%，由 DB 兜底容量倒推）。上界则由成本曲线给出：

| L4 命中率 | 所需缓存内存 | 缓存月成本 | 只读副本 | 副本月成本 | **合计** |
|----------|------------|-----------|---------|-----------|---------|
| 90% | 8 GB | ¥0.7 万 | 163 台 | ¥245 万 | ¥246 万（DB 侧不可行） |
| 98% | 40 GB | ¥3.3 万 | 33 台 | ¥50 万 | ¥53 万 |
| 99.0% | 80 GB | ¥6.5 万 | 17 台 | ¥26 万 | ¥32 万 |
| **99.5%** | **160 GB** | **¥13 万** | **8 台** | **¥12 万** | **¥25 万** ← 最优 |
| 99.9% | 480 GB | ¥39 万 | 2 台 | ¥3 万 | ¥42 万 |
| 99.99% | 约 2 TB | ¥163 万 | 1 台 | ¥1.5 万 | ¥165 万 |

**这条 U 形曲线的底部很宽（99.0%–99.5% 之间总成本差 ¥7 万，占月度总成本 ¥1.17 亿的 0.06%），所以真正的决策依据不是成本，而是 DB 侧的安全边界。** 99.0% 意味着 DB 承担 1.95 万 QPS——超过了 1 万 QPS 的兜底容量，一旦 L4 抖动就没有余量。**选 99.5% 是选"成本接近最优、且 DB 有 2 倍余量"的那个点，而不是选成本最低点。**

反过来说，**99.9% 是净负的**：多花 ¥26 万缓存，只省 ¥9 万副本。这个方向的直觉陷阱很强——"命中率越高越好"听起来无可辩驳，但 Zipf 分布下命中率的边际提升需要指数级的内存（从 99.5% 到 99.9%，覆盖的 key 数从 8,000 万涨到 2.4 亿，因为要吃进分布的长尾）。**命中率不是一个越大越好的指标，它是一个有最优值的成本参数。**

**各层缓存的单位效益（这是分层的量化依据）：**

```
每层拦下的 QPS ÷ 该层月成本 = 单位成本拦流量

L1 客户端：  拦 ~20%（约 39 万 QPS），成本 ¥0        → ∞（但不可控，不能依赖）
L2 边缘：    拦 ~30%（约 58 万 QPS），成本已含在 CDN 账单 → 边际近零
L3 进程内：  拦 70%（剩余流量的 70%，约 136 万 QPS），成本 ¥0（复用内存）
             → 单位效益最高的一层
L4 Redis：   拦 98.8%（剩余 58.5 万中的绝大部分），成本 ¥13 万/月
             → 1.05 万 QPS/万元
L5 DB：      承接最后 9,750 QPS，成本 ¥12 万/月
             → 0.08 万 QPS/万元（比 L4 低 13 倍）
```

**L3 的单位效益最高且边际成本为零，这就是"必须有进程内缓存"的量化理由。** 而 L4 与 L5 的 13 倍效益差，正是"缓存命中率每提高一点都在省钱"的来源——直到内存的指数增长追上这个 13 倍差距为止（即上表的 99.5% 拐点）。

**延迟预算达成情况：**

| 环节 | 预算 | P50 达成 | P95 达成 |
|------|------|---------|---------|
| Feed 端到端 | 200ms (P95) | 130ms | 185ms |
| 单条内容缓存命中聚合 | — | 4ms | 8ms |
| 下架失效时效（可见） | < 1s | 200ms | 800ms |
| 下架生效时效（可播） | 立即 | — | 强一致，无窗口 |
| 元数据变更时效 | < 5s（L4）/ 60s（L3） | 300ms / 30s | 1s / 60s |

**注意"可见"与"可播"两行的预算性质完全不同**：前者是一个尽力而为的时延目标（因为它依赖 5 层缓存的收敛），后者是一个强一致保证（因为它只依赖一次 guard 查询）。**把它们放在同一张表里但用不同的口径表述，是为了防止后来者把"下架 800ms 生效"误读为"违规内容会传播 800ms"——实际上违规内容在下架的那一刻就已经播不了了。**

## 延伸思考

以下问题本篇给出了明确判断的，直接写在正文里（版本号 vs 时间戳见「前置问题」，热点 N 的定档见「热点内容与缓存崩溃防护」）。留在这里的是本篇**没有**给出答案、且答案会随场景变化的：

- **客户端 L1 缓存与内容权益冲突**——离线下载缓存的内容如何受 DRM 约束？L1 的"兜底渲染"和"盗版风险"怎么平衡？注意本篇的 guard 机制对 L1 完全无效（2 亿个副本、无法推送失效），而离线下载让这个问题从"短暂陈旧"变成"永久持有"。
- **字段裁剪的粒度**——本篇按"视图"裁剪（14 字段 vs 40 字段）。更进一步可以按"设备/网络/会员"动态裁剪（弱网只发关键字段）。动态裁剪的收益边际在哪？代价是投影注册表的组合数从 6 涨到 6×N，以及缓存 key 是否要按投影分裂（分裂则命中率下降，不分裂则每次都要现场裁剪）。
- **读链路的一致性最终能做到多强？** 本篇接受 60s 统计偏差。如果未来有"实时榜单"这类强实时读诉求，W 级通道要升级成什么？直接的困难是 23 万 QPS 的变更量——任何"主动失效"方案在这个量级下都会先打死缓存集群（见陷阱 2）。
- **guard 集群本身的可用性怎么保证？** 它是全站可播性的唯一单点，配了 noeviction、无 TTL、fail-closed。这意味着 **guard 集群不可用 = 全站不可播**。要不要给它做多活？多活之后 F 级失效的"写入成功"该以几个副本为准？这是本篇留下的最大未决问题。
- **L3 常驻名单的一致性**——100 台机器各自维护常驻区，名单从 `hot_key_registry` 拉取。若某台机器拉取失败（网络抖动），它的常驻区就与其他机器不同，热点内容在这台机器上会持续回源 L4。这个"局部不一致"要不要治理，还是接受它（1/100 的流量多打一次 L4）？

## 内容读链路 BFF 与缓存代理完整实现

读侧两个最难的部分代码化：**缓存代理**（L3/L4 + 版本号 + 失效分级 + 三兄弟防护）与 **BFF 字段裁剪**（投影注册表）。扇出聚合是编排逻辑，此处用接口契约表达。

```python
from __future__ import annotations

import hashlib
import math
import threading
import time
from collections import OrderedDict, defaultdict
from concurrent.futures import Future
from dataclasses import dataclass, field
from enum import Enum
from typing import Callable, Iterable, Optional


def _mix64(n: int) -> int:
    """确定性 64 位混淆哈希。

    刻意不用 random 与 hash()：
      - random 会让同一 cid 在不同机器上算出不同的 TTL/副本，
        使过期时刻不可预测（ExpiryClusteringDetector 就失效了）
      - Python 的内置 hash() 对 int 是恒等函数，且字符串哈希带进程随机盐，
        跨进程不一致
    """
    n = (n ^ (n >> 33)) * 0xFF51AFD7ED558CCD & 0xFFFFFFFFFFFFFFFF
    n = (n ^ (n >> 33)) * 0xC4CEB9FE1A85EC53 & 0xFFFFFFFFFFFFFFFF
    return n ^ (n >> 33)


class InvalidationLevel(Enum):
    FORCE = 'force'       # F 级：下架/封禁，需实时 + 播放接口最终校验
    QUICK = 'quick'       # Q 级：用户可见元数据，版本号 + 短 TTL 收敛
    WEAK = 'weak'         # W 级：统计类，完全不主动失效


@dataclass
class Content:
    content_id: int
    version: int = 0          # 版本号：内容域每次元数据变更 +1
    data: dict = field(default_factory=dict)   # 扁平化后的统一层内容


class ContentVersionStore:
    """版本号来源。真实实现里由内容域维护，这里用单机模拟。
    版本号用于：L3/L4 判断新鲜度、客户端 L1 自校验。
    """
    def __init__(self):
        self._versions: dict[int, int] = {}

    def bump(self, content_id: int) -> int:
        self._versions[content_id] = self._versions.get(content_id, 0) + 1
        return self._versions[content_id]

    def get(self, content_id: int) -> int:
        return self._versions.get(content_id, 0)


class LocalCache:
    """L3 进程内缓存。只放热数据 + 短 TTL，新鲜度靠版本号判断。

    淘汰策略用 OrderedDict 实现 O(1) LRU，而不是"扫一遍找过期的、还满就随机删"。
    随机驱逐在 Zipf 分布下是灾难性的：被驱逐的大概率是【头部内容】
    （因为头部内容只占 key 数的 0.05%，但它们的驱逐会导致 99% 的 miss）。
    L3 的全部价值来自"头部常驻"，随机驱逐恰好破坏这一点。
    """
    def __init__(self, max_entries: int = 4_000_000, ttl_sec: int = 60,
                 resident_capacity: int = 200_000):
        self._max = max_entries
        self._ttl = ttl_sec
        # OrderedDict 的插入顺序即 LRU 顺序，move_to_end/popitem 均为 O(1)
        self._store: "OrderedDict[int, tuple[float, Content]]" = OrderedDict()
        # 常驻区与 LRU 区物理分离：热点内容不参与 LRU 竞争，
        # 否则一次冷数据扫描（如爬虫顺序遍历）就能把头部内容全部挤出去
        self._resident: dict[int, tuple[float, Content]] = {}
        self._resident_cap = resident_capacity
        self._lock = threading.Lock()

    def get(self, cid: int, min_version: int) -> Optional[Content]:
        with self._lock:
            item = self._resident.get(cid)
            in_resident = item is not None
            if item is None:
                item = self._store.get(cid)
                if item is None:
                    return None
                self._store.move_to_end(cid)      # 命中即刷新 LRU 位置
        at, content = item
        # 常驻区不按 TTL 过期 —— 它由后台主动刷新（见 refresh_resident），
        # 若也按 TTL 过期，头部内容每 60s 就要回源一次，L3 的意义大打折扣
        if not in_resident and time.monotonic() - at > self._ttl:
            with self._lock:
                self._store.pop(cid, None)
            return None
        if content.version < min_version:
            return None          # 版本落后，视作 miss（避免新旧数据跳变）
        return content

    def put(self, content: Content) -> None:
        with self._lock:
            if content.content_id in self._resident:
                self._resident[content.content_id] = (time.monotonic(), content)
                return
            self._store[content.content_id] = (time.monotonic(), content)
            self._store.move_to_end(content.content_id)
            while len(self._store) > self._max:
                self._store.popitem(last=False)   # O(1) 淘汰最久未用

    def pin_resident(self, content: Content) -> bool:
        """把热点内容钉进常驻区。由 HotKeyDetector 的判定结果驱动。"""
        with self._lock:
            if len(self._resident) >= self._resident_cap \
                    and content.content_id not in self._resident:
                return False                      # 常驻区满，拒绝而非挤掉别人
            self._resident[content.content_id] = (time.monotonic(), content)
            self._store.pop(content.content_id, None)
            return True

    def unpin_resident(self, cid: int) -> None:
        with self._lock:
            item = self._resident.pop(cid, None)
        if item is not None:
            self.put(item[1])                     # 降级回 LRU 区，而非直接丢弃

    def clear_content(self, cid: int) -> None:
        with self._lock:
            self._store.pop(cid, None)
            self._resident.pop(cid, None)         # F 级失效必须同时清常驻区

    def stats(self) -> dict:
        with self._lock:
            return {"lru_size": len(self._store), "resident_size": len(self._resident)}


class DistributedCache:
    """L4 分布式缓存。key 粒度 = 单条内容；支持热点拆副本。
    真实实现为 Redis Cluster，此处用 dict 模拟。

    三个与教科书 Cache-Aside 不同的关键点：
      1. put 带版本 CAS —— 拒绝写回比水位更旧的值（Cache-Aside 竞态的解法）
      2. 逻辑过期 + 物理 TTL 分离 —— 逻辑过期后仍可返回 stale 值，
         由 MissGate 决定是刷新还是直接用旧值（雪崩时的救命兜底）
      3. 热点副本【不带 hash tag】—— 副本必须落在不同 slot 才有意义，
         代价是放弃多副本写入的原子性，由 fver 水位标记补偿
    """
    def __init__(self, logical_ttl_sec: int = 600, physical_multiplier: float = 2.0,
                 hot_replicas: int = 10):
        self._logical_ttl = logical_ttl_sec
        self._physical_ttl = logical_ttl_sec * physical_multiplier
        self._hot_replicas = hot_replicas
        self._store: dict[str, tuple[float, Content]] = {}
        self._water: dict[int, int] = {}          # cid → 版本水位（回填 CAS 的依据）
        self._fver: dict[int, int] = {}           # cid → F 级水位（下架标记，无 TTL）
        self._hot: dict[int, int] = {}            # cid → 副本数 N
        self._lock = threading.Lock()

    def _keys(self, cid: int) -> list[str]:
        n = self._hot.get(cid, 1)
        if n == 1:
            return [f"content:{cid}"]
        # 注意：不加 {} hash tag。加了会让 N 个副本落在同一 slot、
        # 也就是同一分片上，拆 key 静默失效（监控看到分片 QPS 一点没降）
        return [f"content:{cid}:r{i}" for i in range(n)]

    def _ttl_for(self, cid: int) -> float:
        """确定性抖动：同一 cid 在任何机器上算出的 TTL 都相同。

        用随机数会让"过期时刻"取决于最后写入的是哪台机器，
        从而无法被 ExpiryClusteringDetector 登记与预测。
        """
        return self._logical_ttl * 0.8 + (_mix64(cid) % int(self._logical_ttl * 0.4))

    def get(self, cid: int, uid: int) -> tuple[Optional[Content], str]:
        """返回 (内容, 状态)。状态为 fresh / stale / miss。

        返回 stale 而不是 None，是把"是否使用旧值"的决策权交给上层（MissGate）：
        正常时刷新，雪崩时直接用旧值。缓存层不该自己做这个业务决策。
        """
        keys = self._keys(cid)
        key = keys[_mix64(uid) % len(keys)]
        with self._lock:
            item = self._store.get(key)
            if item is None:
                return None, "miss"
            at, content = item
            age = time.monotonic() - at
            if age > self._physical_ttl:
                self._store.pop(key, None)
                return None, "miss"
        return content, ("stale" if age > self._ttl_for(cid) else "fresh")

    def put(self, content: Content) -> bool:
        """带版本 CAS 的回填。返回 False 表示本次回填被拒绝（携带的是旧值）。

        这是 Cache-Aside 写顺序竞态的解法：读线程回填时携带的版本
        若低于失效通道写入的水位，则丢弃。
        """
        cid = content.content_id
        with self._lock:
            water = self._water.get(cid)
            if water is not None and content.version < water:
                return False                 # 旧值写回，拒绝 —— 必须打点计数
            self._water[cid] = max(water or 0, content.version)
            now = time.monotonic()
            for key in self._keys(cid):
                self._store[key] = (now, content)
        return True

    def invalidate(self, cid: int, new_version: int,
                   f_level: bool = False) -> bool:
        """失效。顺序至关重要：先写水位，再删副本。

        颠倒顺序会留下一个窗口：副本已删、水位未写 →
        并发读 miss 后回填旧值，且因为水位还没写而不会被 CAS 拦住。
        """
        with self._lock:
            # 第 1 步：抬高水位（原子）。这一步成功即意味着失效逻辑上已完成
            self._water[cid] = max(self._water.get(cid, 0), new_version)
            if f_level:
                self._fver[cid] = new_version    # 下架水位，永不过期
            # 第 2 步：尽力删除各副本。部分失败可接受 —— 水位已能拦住它们
            for key in self._keys(cid):
                self._store.pop(key, None)
        return True

    def is_taken_down(self, cid: int) -> bool:
        return cid in self._fver

    def mark_hot(self, cid: int, peak_qps: int) -> int:
        """按 ⌈QPS/5000⌉ 定档，上限 16。不是所有热点都拆成 10 份。"""
        n = min(16, max(1, -(-peak_qps // 5000)))
        with self._lock:
            self._hot[cid] = n
        return n

    def is_hot(self, cid: int) -> bool:
        return cid in self._hot

    def unmark_hot(self, cid: int) -> None:
        with self._lock:
            self._hot.pop(cid, None)


class BloomFilter:
    """穿透防护：从未被分配过的 content_id 直接短路。

    参数按目标误判率反解，而不是"给个大概的容量"：
      m/n = -ln(p) / (ln2)²    位/元素
      k   = (m/n) × ln2        哈希个数
    n=8e9, p=1% → m/n=9.58（取 10）, k=6.93（取 7）, 实际 FPR 0.82%, 内存 10 GB

    语义边界（极易误用）：
      - 它只回答"这个 id 是否【曾经】存在"，不回答"现在是否可见"
      - 布隆过滤器【不支持删除】，已下架内容仍在其中 —— 所以它
        不能替代可见性校验，两者是不同的机制
      - 10 GB 无法每台机器各存一份（100 台 = 1 TB），必须放 L4 侧
        （RedisBloom）。因此它省下的是【DB 查询】，不是网络往返
    """
    def __init__(self, expected_items: int = 8_000_000_000,
                 target_fpr: float = 0.01):
        bits_per_item = -math.log(target_fpr) / (math.log(2) ** 2)
        self._m = int(expected_items * bits_per_item)
        self._k = max(1, round(bits_per_item * math.log(2)))
        self._bits = bytearray((self._m + 7) // 8)

    @property
    def actual_fpr(self) -> float:
        """实际误判率。用于启动时断言参数没被人手改坏。"""
        ratio = self._m / 8_000_000_000
        return (1 - math.exp(-self._k / ratio)) ** self._k

    def add(self, cid: int) -> None:
        for h in self._hashes(cid):
            self._bits[h // 8] |= 1 << (h % 8)

    def maybe_contains(self, cid: int) -> bool:
        return all(self._bits[h // 8] & (1 << (h % 8)) for h in self._hashes(cid))

    def _hashes(self, cid: int):
        # Kirsch-Mitzenmacher：用两个独立哈希线性组合出 k 个，
        # 避免调用 k 次 blake2b（读路径上 7 次密码学哈希是不可接受的开销）
        h1 = _mix64(cid)
        h2 = _mix64(cid ^ 0x9E3779B97F4A7C15) | 1
        for i in range(self._k):
            yield (h1 + i * h2) % self._m


class CacheProxy:
    """缓存代理：L3 + L4 + 布隆 + 空值兜底 + 单飞 + 失效分级。"""

    NEGATIVE_TTL_SEC = 30

    def __init__(self, versions: ContentVersionStore,
                 bloom: BloomFilter, loader: Callable[[int], Content],
                 gate: Optional["MissGate"] = None):
        self._local = LocalCache()
        self._dist = DistributedCache()
        self._versions = versions
        self._bloom = bloom
        self._load = loader
        self._gate = gate or MissGate()
        # 单飞容器用 Future 而不是 list：Future 自带"完成/异常"状态，
        # 且 leader 与 follower 走同一条返回路径（见陷阱 10）
        self._inflight: dict[int, "Future[Optional[Content]]"] = {}
        # 空值兜底：cid → 记录时刻。真的要有存储，不能只写注释
        self._negative: "OrderedDict[int, float]" = OrderedDict()
        self._lock = threading.Lock()
        self._metrics = defaultdict(int)

    def get(self, cid: int, uid: int) -> Optional[Content]:
        """读路径：空值兜底 → L3 → L4 → (布隆 → 闸门 → 单飞回源)。"""
        # 空值兜底放在最前面：它的目的是省掉后续【所有】层级的开销
        if self._is_negative(cid):
            self._metrics["negative_hit"] += 1
            return None

        min_version = self._versions.get(cid)

        hit = self._local.get(cid, min_version)
        if hit is not None:
            self._metrics["l3_hit"] += 1
            return hit

        content, state = self._dist.get(cid, uid)
        if content is not None and content.version >= min_version:
            if state == "fresh":
                self._metrics["l4_hit"] += 1
                self._local.put(content)
                return content
            # 逻辑过期：交给闸门决定"刷新"还是"直接用旧值"
            if not self._gate.acquire(cid, self._tier(cid)):
                self._metrics["stale_served"] += 1
                return content            # 雪崩保护：宁可给旧数据也不给错误
            self._metrics["l4_stale_refresh"] += 1
            return self._load_single_flight(cid, min_version)

        # 到这里是真 miss（或 L4 版本落后）
        if not self._bloom.maybe_contains(cid):
            self._metrics["bloom_reject"] += 1
            self._mark_negative(cid)      # 记录空值，防同一 key 反复穿
            return None

        # 布隆放行但可能是那 0.82% 的误判 —— 仍然要过闸门
        if not self._gate.acquire(cid, self._tier(cid)):
            self._metrics["gate_reject"] += 1
            return None                   # 让上层降级渲染，不打 DB
        return self._load_single_flight(cid, min_version)

    # ── 空值兜底 ──────────────────────────────────────────────
    def _is_negative(self, cid: int) -> bool:
        with self._lock:
            at = self._negative.get(cid)
            if at is None:
                return False
            if time.monotonic() - at > self.NEGATIVE_TTL_SEC:
                self._negative.pop(cid, None)
                return False
            return True

    def _mark_negative(self, cid: int) -> None:
        """空值兜底必须有容量上限。

        没有上限时，一次随机 id 遍历攻击会把攻击者构造的几千万个
        不存在的 id 全部塞进来 —— 防穿透的机制自己变成了内存耗尽攻击的入口。
        """
        with self._lock:
            self._negative[cid] = time.monotonic()
            self._negative.move_to_end(cid)
            while len(self._negative) > 100_000:
                self._negative.popitem(last=False)

    # ── 单飞（见陷阱 10 的三个失败模式）────────────────────────
    def _load_single_flight(self, cid: int, min_version: int) -> Optional[Content]:
        with self._lock:
            fut = self._inflight.get(cid)
            is_leader = fut is None
            if is_leader:
                fut = Future()
                self._inflight[cid] = fut     # 判断与注册在同一把锁内，无双 leader

        if not is_leader:
            self._metrics["singleflight_merged"] += 1
            # follower 也要有超时。超时后【不重试】——
            # 等待者超时说明回源本身有问题，重试只会加剧
            return fut.result(timeout=0.5)

        try:
            content = self._load(cid)
            if content is None:
                self._mark_negative(cid)      # DB 也查不到 → 记空值
            else:
                if not self._dist.put(content):
                    # CAS 拒绝：说明回填期间发生了失效，我们拿的是旧值。
                    # 必须打点 —— 这个计数是陷阱 9 的唯一验收手段
                    self._metrics["cas_rejected"] += 1
                else:
                    self._local.put(content)
            fut.set_result(content)
            return content
        except BaseException as exc:
            # 必须传播异常，否则所有 follower 卡满 0.5s 超时
            fut.set_exception(exc)
            raise
        finally:
            with self._lock:
                # 带值比较的删除：避免误删下一轮的 Future
                if self._inflight.get(cid) is fut:
                    self._inflight.pop(cid, None)

    def _tier(self, cid: int) -> str:
        return "hot" if self._dist.is_hot(cid) else "warm"

    # ── 失效分级 ──────────────────────────────────────────────
    def on_change(self, cid: int, level: InvalidationLevel) -> None:
        version = self._versions.bump(cid)
        if level is InvalidationLevel.FORCE:
            # 顺序：先抬水位（含 F 级），再清本地，最后联动 guard
            self._dist.invalidate(cid, version, f_level=True)
            self._local.clear_content(cid)
            self._negative.pop(cid, None)     # 内容重新上架时要能立刻被读到
            self._notify_playback_guard(cid, version)
        elif level is InvalidationLevel.QUICK:
            # Q 级只动 L4，L3/L2 靠版本号 + 短 TTL 收敛。
            # 【不广播 L3】—— 广播会让写放大从 1 变成 101（见陷阱 2）
            self._dist.invalidate(cid, version)
            self._negative.pop(cid, None)
        # WEAK：不主动失效，靠 200ms 聚合 + TTL

    def _notify_playback_guard(self, cid: int, version: int) -> None:
        """F 级联动：写入无 TTL 的 guard key（P00 下架工作流）。

        guard 集群与内容缓存物理隔离、配 noeviction —— 宁可写入失败告警，
        也不能让冷门违规内容的 guard 被 LRU 静默淘汰。
        """
        guard_redis.set(f"content:{cid}:guard", pack_guard(cid, version))  # 无 TTL

    def hit_rates(self) -> dict:
        """命中率与重用因子。重用因子比命中率百分比更敏感（见正文）。"""
        m = self._metrics
        total = m["l3_hit"] + m["l4_hit"] + m["l4_stale_refresh"] \
            + m["gate_reject"] + m["bloom_reject"] + m["negative_hit"]
        loads = max(m["l4_stale_refresh"], 1)
        return {
            "l3_rate": m["l3_hit"] / max(total, 1),
            "l4_rate": m["l4_hit"] / max(total, 1),
            "reuse_factor": total / loads,      # 目标 200；跌到 100 即命中率腰斩
            "cas_rejected": m["cas_rejected"],  # 期望每日几十次；0 说明 CAS 没生效
            "stale_served": m["stale_served"],
        }

# ── 扇出聚合的契约（真实实现为跨域批量 RPC）────────────────────
class FeedAggregator:
    """Feed 聚合：BFF 拿到 30 个 content_id 后，一次编排完成
    BatchGetContentView / BatchGetContentStat / BatchGetAuthorBrief /
    BatchGetInteractStatus / BatchGetRelationStatus 五路批量调用。
    本处用接口契约表达——实现细节在各域，不在本篇。"""
    def build_feed(self, uid: int, content_ids: list[int]) -> list[dict]:
        contents = self._batch_get_content(content_ids)        # 内容中台
        stats = self._batch_get_stat(content_ids)              # 计数服务
        authors = self._batch_get_author({c.author_id for c in contents})
        interact = self._batch_get_interact(uid, content_ids)  # 可降级
        relations = self._batch_get_relation(uid, authors)     # 可降级
        # 合并 + 投影 FEED_CARD ...
        return [
            self._merge(c, stats, authors, interact, relations)
            for c in contents
        ]
```

**关键设计：**
1. `CacheProxy.get` 的读顺序（L3 → L4 → 布隆 → 单飞）保证**每一层 miss 都在上一层被拦截**，DB 只承受单飞后的兜底流量
2. 版本号同时服务 L3/L4 与客户端 L1——新鲜度判断**与 TTL 绝对值解耦**，消除"新旧数据来回跳"
3. `on_change` 按失效分级分流：F 级全清 + 播放守卫联动，Q 级清 L4 靠版本号收敛，W 级什么都不做
4. 投影注册表是**唯一**的字段真相来源，BFF 各视图零重复映射

## 异常场景补充

### 场景：批量接口被滥用为"万能口"

```
触发：某下游把 BatchGetContentView 当通用查询口，单请求塞 500 个 id、
      靠"要全字段"绕过投影注册表 → 单请求载荷 2.5MB，带宽与 DB 双飙
检测：
  1. 批量接口的 p99 请求字节监控，超过 512KB 告警
  2. 字段白名单外字段的访问计数——有请求在拉"未注册字段"
  3. 单请求 id 数量分位数，P99 超过 100 告警
处理：
  1. 该调用方降级到独立限流，防止拖垮正常 Feed 流量
  2. 约定收紧：批量上限 100 id、字段由服务端按场景强制约束
  3. 推动调用方改用专用投影视图
预防：批量契约按"场景"建视图而非按"库表"建接口 + 字节/字段超限即告警
```

**这个场景的关键不是"有人滥用"，而是"万能口必然被滥用"。**

```
一个接受 N 个 id + 字段列表的接口，在能力上【严格覆盖】任何专用接口
→ 对调用方，用它永远比对接一个新视图省事
→ "推动调用方改用专用投影视图"是一个组织行动，会输给便利性

统计上：万能口上线 6 个月后，调用方数量与专用视图数量的比值只会上升
```

**所以处理步骤 3（推动改造）会失败，且失败不是执行力问题。** 有效的做法是让万能口在滥用场景下**协议上不可表达**：

```
错误的契约：BatchGetContentView(ids[], fields[])
           → "要全字段"是一个合法请求，服务端只能靠校验去拦

正确的契约：BatchGetContentView(ids[], scene)
           → 字段集由 scene 在投影注册表里决定，调用方无法指定
           → 想要新字段必须注册新 scene（有评审、有归属、有配额）
           → "要全字段"这个请求【写不出来】
```

**把治理从"检查"变成"不可表达"，是所有契约设计里最省力的一步。** 校验要持续运维、会被绕过、会有例外；协议里没有那个参数则一劳永逸。

**第二个必须量化的点：500 个 id 的批量请求几乎必然是慢的。**

```
承接前文的尾延迟放大：P(整批慢) = 1 − (1 − p)^N
单项慢的概率 p = 0.1%

N = 50  → 1 − 0.999^50  = 4.9%
N = 500 → 1 − 0.999^500 = 39.4%

→ 批量上限从 100 收紧到 50 不只是省字节，
  它把这个调用方自己的 P99 从"经常慢"降到"偶尔慢"
```

**这一点在和调用方谈收紧上限时特别有用：收紧对他们有利，不是纯粹的限制。** 一个只讲"你占用太多资源"的协商会遇到抵抗，一个能算出"你的 P99 会从 400ms 降到 90ms"的协商不会。

**第三个点：按 QPS 限流对这个场景完全无效。**

```
500-id 请求 和 1-id 请求，在 QPS 限流器眼里【一模一样】
调用方把 500 个请求合成 1 个，QPS 降了 500 倍，资源消耗一分没少

→ 限流的计量单位必须是【加权成本】：id 数 × 字段数（或估算字节数）
→ 令牌桶扣减 max(1, ids × fields / K)，而不是恒扣 1
```

**"合并请求以绕过限流"是所有按请求数计量的限流器的通用绕过方式，而且调用方通常不是故意的**——他们只是在做批量优化。**限流的计量单位与被保护的资源必须一致**：保护 CPU 就按 CPU 计量，保护带宽就按字节计量，按请求数计量只保护了"请求数"这个没人关心的量。

### 场景：版本号回退导致旧内容覆盖新内容

```
触发：内容域批量修改时把 version 写错（多实例并发 bump 未合并），
      个别 content 的版本号倒退 → L3 用"旧版本号+新数据"覆盖本地
      → 用户看到内容状态回退（已下架内容又被展示）
检测：
  1. 版本号单调性校验：同一 content 出现版本下降即告警
  2. L4 命中内容的 version 与本地记录比对，差异告警
  3. 用户反馈"内容回退"类问题的聚类埋点
处理：
  1. 回滚错误变更，重新 bump 版本号
  2. 受影响 content 走 F 级强失效，全链清除后重建
  3. 版本号生成收敛到内容域单写（状态单写方原则的版本维度）
预防：version 由内容域唯一生成（雪花/DB 序列），其他域只读不写
```

**这是前置问题（写序与版本 CAS）的运行时对偶，而且方向反了一次：CAS 从保护变成了伤害。**

```
CAS 的设计目的：拒绝【旧版本的数据】覆盖【新版本的缓存】
CAS 的前提假设：版本号单调递增

版本号回退之后：
  真实的新数据带着一个【小】版本号到来
  → CAS 判定它是陈旧数据 → 静默丢弃
  → 缓存里永远是那个"版本号更大"的旧数据

→ 保护机制变成了污染的固化机制，且【丢弃是静默的】
```

**处理步骤 1 和 2 的顺序不能颠倒，而且颠倒之后的失败表现极具误导性。**

```
错误顺序：先 F 级强失效清全链 → 再修版本号
  清除后重建时，读到的还是那个错误的低版本
  → 重建的数据再次被 CAS 拒绝（或写入后立刻被下一次同步覆盖）
  → 现象是"清了缓存也没用"
  → 排查方向被引向"失效通道是不是漏了某一级"

正确顺序：先修版本号（让它重新单调且高于污染值）→ 再强失效
```

**"清了缓存也没用"是一句会把排查带偏很久的现象描述**，因为它指向失效通道，而根因在版本号。**判据很简单但需要有人想到：把污染 key 的 value 连同它的 version 一起打出来，看 version 是不是比数据源的还大。**

**预防措施里"雪花/DB 序列"这个二选一不是随意的，两者有一处不兼容。**

| 方案 | 单调 | 连续 | 风险 |
|------|------|------|------|
| `UPDATE ... SET version = version + 1` | ✓ | ✓ | 单行热点，高频修改的内容会锁竞争 |
| `SELECT version` → `+1` → `UPDATE` | ✗ | ✓ | **多实例并发就是本场景的成因** |
| 雪花 / 时间戳序列 | ✓ | **✗** | 任何 `expected == current + 1` 的假设全线失效 |

**第三行的坑最深：雪花 ID 单调但不连续。** 如果代码里任何地方写了 `if incoming.version != cached.version + 1: 判为乱序`，换成雪花之后这个判断会对**每一次**更新都成立，等于全量拒绝。**版本号的语义只能是"可比较"，不能是"可预测下一个"**——一旦有代码依赖了连续性，版本号方案就被锁死了，换不掉。

**这也解释了为什么必须"单写"而不只是"小心地多写"：** 多写方要保证全局单调，就必须协调；协调的代价（分布式锁或中心序列）和直接单写一样，但复杂度更高、失效模式更多。**多写方 + 单调性要求 = 用更复杂的方式实现单写。**

### 场景：L3 本地缓存命中率骤降引发连锁回源

```
触发：某次发布把 Feed 的 content 批量回源参数改错（预热脚本失效），
      本地缓存命中率从 70% 掉到 15% → Redis 读 QPS 涨到 2.8 倍，
      接近热集分片带宽上限，P99 开始劣化
检测：
  1. 按实例分组的 L3 命中率监控，跌破 50% 告警
  2. Redis 集群按分片的读 QPS 监控，超过带宽 60% 告警
  3. 回源脚本的任务成功率监控
处理：
  1. 修复预热脚本，按热度降序重新预热
  2. 热点拆 key 触发门槛临时下调（更早拆），分散 Redis 读压力
  3. 观察命中率回升后恢复门槛
预防：L3 预热/回源参数变更走灰度 + 命中率作为回源脚本的验收指标
```

**先把放大倍数算准——命中率是乘性放大器，而且放大的是它的补数。**

```
命中率 70% → 穿透到 L4 的比例 = 30%
命中率 15% → 穿透到 L4 的比例 = 85%

Redis 读 QPS 倍数 = 85% / 30% = 2.83 倍

注意被放大的量是【1 − 命中率】，不是命中率本身。
命中率下降 55 个百分点（相对下降 79%），穿透量涨 183%
```

**这个"看补数"的习惯决定了告警阈值该定在哪，而检测里的"跌破 50%"定错了：**

```
命中率 70% → 50%：穿透 30% → 50%，Redis 压力 +67%
              等到这时告警，容量已经吃掉一大半

正确做法：阈值直接定在【穿透率】上，穿透率相对上升 30% 即告警
        → 对应命中率 61%，比 50% 早得多

推广：所有"命中率 / 成功率 / 可用性"类指标，
     告警阈值都应该定在它们的补数上 ——
     因为下游承受的是补数，不是本身
```

**（这与 P06 里 CDN 边缘命中率的告警阈值是同一条原理，两处独立出现说明它是通用的：正向指标的小幅下降对应补数的大幅上升，用正向指标定阈值会系统性地把告警定晚。）**

**第二个点：L3 是每实例独立的，所以"命中率"是一个分布，不是一个值。**

```
1000 个实例，均值命中率 68% —— 看起来只掉了 2 个点
实际分布：
  950 个实例 = 71%（正常）
  50 个实例  = 15%（预热脚本在这批机器上失效了）

均值 = (950×0.71 + 50×0.15) / 1000 = 68.2%  ← 完全看不出来

而那 50 个实例贡献的穿透量 = 50 × 85% = 42.5 单位
     950 个正常实例贡献 = 950 × 29% = 275 单位
→ 5% 的实例贡献了 13% 的 Redis 压力，且集中在它们各自访问的分片上
```

**监控必须看 P5 分位（最差的那一批），不能只看均值。** 更准确地说：**任何"每实例独立"的资源，其聚合指标的均值都会掩盖局部崩塌**，而局部崩塌恰恰是热点分片压力的主要来源——因为失效的实例往往是同一批（同一次发布、同一个可用区），它们的访问模式相似，压力会集中而不是分散。

**第三个点：处理步骤 2（提前拆热点 key）只在一种瓶颈下有效，选错了会加剧问题。**

| 真实瓶颈 | 拆 key 的效果 |
|---------|-------------|
| 单分片带宽打满 | **有效** —— 把一个 key 的流量摊到多个分片 |
| 集群总带宽打满 | **无效** —— 总量不变，只是换了分布 |
| 连接数 / CPU 打满 | **有害** —— key 数变多，单次批量读要访问更多分片，往返和连接数上升 |
| L3 命中率崩塌（本场景） | **可能有害** —— 拆 key 会让本地缓存的 key 基数膨胀，进一步压低 L3 命中率 |

**最后一行是本场景特有的反馈回路：拆 key 是为了缓解 Redis，但它让 L3 更难命中，从而制造更多 Redis 请求。** 在命中率已经崩塌的状态下叠加拆 key，有把"一次性故障"变成"自持续故障"的风险。**处理动作的选择必须先确认瓶颈在哪一层**——而这个场景的瓶颈明确在 L3，正确的动作只有步骤 1（修预热），步骤 2 应当被移出预案，或明确标注"仅当确认瓶颈为单分片带宽时使用"。

### 场景：计数器与内容统计的展示偏差引发创作者投诉

```
触发：计数服务某节点重启，WAL 重放前读到了旧快照，
      播放数展示从 523 万回退到 500 万 → 创作者截图投诉"数据造假"
检测：
  1. 计数单调性校验：同一 content 展示值下降即告警（P01 已定义）
  2. 展示层与快照源比对，差值超阈值告警
  3. 创作者侧"计数回退"类反馈的聚类监控
处理：
  1. 展示层取 max(当前值, 历史最大值) 兜底展示（读侧最后一公里）
  2. 等计数服务重放补齐后恢复真实值
  3. 创作者投诉工单附展示逻辑说明（快照 + 单调性保证）
预防：展示层单调性兜底 + 计数服务重启强制重放补齐 + 读写分离不跨层
```

**先说清这个场景为什么值得单独立案：偏差的幅度很小，反应却是"数据造假"级别的。**

```
523 万 → 500 万，误差 4.4%

对照：一个长期偏高 5% 的播放数，从来没有人投诉
     一次下降 4.4% 的播放数，立刻上升为信任事件

→ 创作者对【方向】的敏感度远高于对【精度】的敏感度
→ 计数系统在展示场景下的设计目标应当是【单调性优先于准确性】
```

**这个优先级是反直觉的**——工程上的本能是"先做对，再做稳"。但计数的消费者不是对账系统，而是人，而人从一个数字的**下降**里读出的是"之前的数字是假的"，而不是"现在的数字更准了"。**单调性在这里不是精度的妥协，它本身就是正确性的一部分。**

**但处理步骤 1 的 `max` 兜底有一个必须配套的逃生口，否则它会制造下一个问题。**

```
max(当前值, 历史最大值) 意味着：计数【永远不能下降】

而合法的下降是真实存在的：
  · 刷量治理清理了 100 万虚假播放
  · 误统计回收（同一用户重复计数的修复）
  · 内容部分删除（合集里下架了几集）

治理团队清理完虚假播放 → 展示值不变
  → 治理成果不可见
  → 而且对外沟通更糟："你们说清理了，为什么数字没变？"
```

**所以 `max` 兜底不能是终点，它把"计数会错"换成了"计数不可修正"——这是换掉问题，不是解决问题。**

**正确的结构是把两个语义拆成两个字段：**

```
true_count   真实值，可增可减，由计数服务维护，对内使用
display_count 展示值 = max over epoch(true_count)，对外使用
epoch        纪元号，由【显式的合法下降操作】递增

展示逻辑：
  · 同一 epoch 内：display = max(见过的 true_count)  → 单调，抗抖动
  · epoch 递增时：display 重置为当前 true_count      → 允许合法下降

epoch 递增是一个【需要审批的显式动作】，不是自动行为：
  → 刷量治理提单，附清理量与原因，走审批
  → 审批通过后 bump epoch，展示值可以下降
  → 且创作者侧同步收到一条说明（"因清理异常流量，播放数已修正"）
```

**关键在于"合法下降"必须是一个有人签字的动作，而不是一个技术条件。** 因为技术上无法区分"WAL 没重放完"和"刷量被清理了"——两者都表现为 `true_count` 变小。**区分它们的信息不在系统里，在人的意图里，所以必须由一个显式操作把这个意图带进系统。**

**这条模式可以推广：任何"单调性兜底"都需要一个配套的显式重置通道。** 只做兜底不做重置，系统会在第一次需要合法下降时被自己的保护机制卡住，而那时兜底逻辑已经跑了几个月、被所有人当成理所当然，改动的代价远高于一开始就做对。**判据：给任何 `max` 兜底提一个问题——"如果这个值真的应该变小，怎么办？"** 答不出来就是缺了一半。
