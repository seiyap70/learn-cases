# P11: 统一内容平台的商业化与创作者收益

## 业务场景

承接 P00 的域 11（商业化）与域 12（创作者服务）。商业化是全平台的**收入引擎**——平台每月技术成本 ¥1.17 亿（单位 DAU ¥0.59），必须被收入模型覆盖并盈利。同时商业化也是最容易"杀鸡取卵"的部分：广告挤占内容、激励被刷、分成算错，每一项都能在短期赚钱的同时摧毁长期价值。

**已知数据：**
- DAU 2 亿，人均日播放 80 次，人均日使用时长 120 分钟
- 四条收入线：广告、会员、带货、虚拟礼物/激励
- 信息流广告是收入主力（占比约 65%），广告负载上限受"体验护栏"约束
- 带货链路：归因窗口 7 天、退货窗口 15 天、佣金率挂载时快照
- 结算链路：预估 → 待结算 → 可提现 三种余额，月度账期
- 商业化团队 100 人（域 11）+ 创作者服务团队（域 12）
- 与 C16（跨境多币种结算）、C31（商户结算对账）方法论相通，本篇不重写结算细节

**为什么商业化是"最容易赚快钱、也最容易毁灭平台"的域？**

四条收入线的失败模式各不相同，但都有一个共同点：**错误在发生时几乎不可见，在结账时才爆雷。**

- 广告竞价慢 100ms，用户感觉"Feed 卡了一下"，但收入当天少几十万
- 分成提前结算，退货风暴来了多付的钱追不回，直接是现金损失
- 佣金率实时读，对账永远对不平，结算系统变成无底洞
- 激励无防作弊，刷量工作室一天刷走一个月的创作者激励预算

更根本的是**商业化与推荐（域 9）的目标冲突**：推荐要长期留存（让用户明天还来），商业化要短期 ARPU（今天多卖广告）。两者在同一条 Feed 上抢位置。

**核心矛盾**：**商业化要在"今天的收入"和"明天的留存"之间找平衡，且所有涉及钱的操作必须绝对正确——错误不可见，但代价致命。** 本篇解决的是"四条收入线各自怎么搭、怎么互相约束、怎么保证资金链路不出错"。

## 核心挑战

### 挑战 1：商业化与留存的冲突——广告每多一条，都是拿明天换今天

信息流广告是收入主力，但它和推荐抢 Feed 位置。广告塞得越多，短期 ARPU 越高，长期留存越差——用户在广告疲劳后卸载。

难点在于**这是一个延迟出现的负反馈**：今天多塞 10% 广告，明天下载量不会马上掉，但三个月后 DAU 和时长会持续走低。**商业化的 KPIs（填充率、eCPM）和推荐的 KPIs（时长、留存）互相伤害，需要一个跨域机制把它们绑在一起。**

### 挑战 2：RTB 是延迟敏感系统——竞价必须在用户无感的时间内完成

信息流广告的竞价链路是：曝光请求 → 定向 → 召回 → 精排 → 拍卖 → 返回，需要在 **50ms 内**完成（叠加在 Feed 请求预算内）。而 Feed 本身只有 130ms 的域 9 预算——广告竞价是这 130ms 里最贵的一段。

难点：竞价要快，但定向、CTR 预估、拍卖都依赖数据；**广告库存、定向人群、竞价策略每时每刻都在变**，缓存命中和实时计算要平衡。且竞价延迟是收入直接损失（超时的广告位空置 = 填充率下降 = eCPM 收入下降）。

### 挑战 3：资金安全——分成、结算、退款、幂等，任何错误都是现金损失

这是全平台**唯一不允许"最终一致"的地方**。资金链路的每一步：

- 订单成交 → 归因 → 佣金计算 → 平台服务费 → 创作者分成 → 税务 → 提现
- 每个环节都可能出错：重复扣款、漏结算、对账不平、退款退回错误账户

难点：**资金错误在发生时不可见，在月结对账时才爆雷**。而结算系统又是平台里最复杂的状态机（跨 15 天退货窗口、跨 7 天归因窗口、跨月度账期、跨多币种）。

### 挑战 4：激励与反作弊——刷量工作室在与你的风控赛跑

创作者激励（流量分成 + 创作补贴）是创作者生态的发动机，但它直接奖励"播放量"——而播放量是**最容易伪造的数字**：

- 机器号矩阵批量刷播放、刷关注
- 低质内容循环播放（自己刷自己的内容）
- 挂机、众包刷量（真实账号但非真实意愿）

难点：**激励的反作弊不是"事后追回"，而是"事前控价"**——激励单价要动态下调以吸收刷量水分，否则真实创作者的激励被刷量工作室稀释。

### 挑战 5：合规是硬约束——广告标识、税务、广告法

商业化要过三道合规关：**广告标识**（信息流广告必须显式标注"广告"，否则违反《广告法》）、**广告内容审查**（极限词、虚假宣传）、**税务**（创作者分成代扣个税、发票）。

难点：**合规是"不做就出大事"的部分**——漏标一个广告标识被举报，罚款是收入的数倍。合规必须内嵌在链路上，而不是事后人工检查。

## 设计约束

- 广告负载上限：每 N 条自然内容最多 1 条广告（guardrail，与推荐联动）
- RTB 竞价端到端延迟 < 50ms，超时广告位空置不阻塞 Feed
- 分成必须在退货窗口（15 天）后结算，佣金率挂载时快照
- 资金类数据必须强一致（MySQL 事务），禁止"最终一致"用于金额
- 所有金额操作幂等（重复请求不重复扣/不重复结）
- 广告必须显式标识，广告内容必须过广告法审查
- 激励单价动态调控，刷量不可获利
- 带货内容独立内容池，商业化负载 ≤ 20%

## 设计解析

### 商业化全景：四条收入线的账本

先看清收入结构（这是商业化的"成本模型"，与 P00 的带宽成本模型对称）：

| 收入线 | 月收入估算 | 占收入 | 收入模型 | 平台成本 |
|--------|-----------|--------|---------|---------|
| 信息流广告 | ¥12 亿 | 65% | 人均日 10 次曝光 × eCPM ¥20 | 竞价算力、归因 |
| 会员订阅 | ¥2.5 亿 | 14% | 付费率 5% × 月费 ¥25 | 权益系统、支付通道 |
| 电商带货 | ¥3 亿 | 16% | 月 GMV ¥100 亿 × 平台服务费 3% | 挂载/归因/结算 |
| 虚拟礼物/激励 | ¥1 亿 | 5% | 打赏流水抽成 5% + 创作者激励 | 礼物系统、风控 |
| **合计** | **¥18.5 亿** | 100% | 人均月 ARPU ¥9.25 | ¥1.17 亿/月 |

**两条结构性结论：**
1. **广告是绝对主力（65%）**——广告的体验护栏直接决定平台生死，保护用户体验 = 保护最大的收入来源
2. **人均月 ARPU ¥9.25 覆盖技术成本 ¥0.59/DAU 绰绰有余**——平台的技术成本已优化到很低，商业化的问题不是"亏不亏"，而是"能不能持续"（用户体验、创作者生态、资金安全）

### 信息流广告与 RTB 竞价

**竞价链路（50ms 预算）：**

```
曝光请求（Feed 广告位，slot 已由混排预留）
  │
  ├─ ① 定向（10ms）     用户人群/兴趣/上下文 → 广告候选池
  │     · 人群包、兴趣标签、LBS 定向
  │     · 索引：定向条件 → 广告集合（内存索引，毫秒级）
  ├─ ② 召回（15ms）     从候选池召回 Top 500 广告
  ├─ ③ 精排（20ms）     CTR 预估 × bid → eCPM = CTR × bid
  │     · 排序模型打分，取 Top 5
  ├─ ④ 拍卖（5ms）      第二价格拍卖，胜出者付次高价
  │     · 频控过滤：该用户今日广告曝光是否超限
  └─ ⑤ 返回广告（→客户端渲染）
```

**竞价架构的关键判断：**

1. **定向和召回能吃缓存（广告索引是只读的，分钟级更新）**——人群包、广告上下架都走增量索引，竞价请求只做内存查询，不打数据库
2. **CTR 预估必须实时**——精排模型按上下文（内容、时间、位置）实时打分，这是 50ms 里最贵但不可省略的部分
3. **拍卖是第二价格**（胜者付次高价），防止广告主恶意抬价，也鼓励真实出价
4. **超时策略是"空置"而非"等待"**——竞价 50ms 超时直接返回空，广告位留白，Feed 不阻塞。**广告延迟的代价是空置（少赚），而不是阻塞（整体超时，更亏）**

**库存管理与频控：** 广告库存是可售曝光量，受两个约束：广告负载上限（每 N 条内容 1 条广告）+ 人均频控（单人每日广告曝光上限）。库存预估 = 自然曝光量 × 负载上限 ×（1 - 频控削减）。**库存是商业化的供给面，预估不准会导致超卖（竞价失败）或滞销（填充率低）。**

### 广告与自然内容的混排治理

**混排规则：** 广告 slot 由推荐（域 9）在混排时预留固定位置，广告服务只负责"这个 slot 放什么广告"，不决定"这个位置有没有广告"。**广告的数量与位置由推荐决定，广告的内容由商业化决定**——两个域的职责边界清晰。

**体验护栏（商业化与推荐的跨域契约）：**

```
护栏 1：广告负载上限——每 8 条自然内容最多 1 条广告
护栏 2：连续广告惩罚——不允许连续 2 条广告
护栏 3：广告疲劳频控——单人每日广告曝光 ≤ 20 次
护栏 4：长期留存护栏——广告位曝光量 vs 次日留存率联动监控，
        若广告曝光增加而留存下降，自动降低广告负载上限
```

**关键设计：护栏 4 是商业化的"刹车"。** 它把"广告挤占自然内容伤害留存"这个延迟负反馈，变成"可监控、可自动收敛"的机制——**广告负载不是拍脑袋定死的，是和留存指标动态联动、自动收紧的。** 这就是"今天多卖广告"和"明天用户还来"的统一机制。

### 会员订阅体系

**权益分层：**

| 权益 | 说明 | 对架构的影响 |
|------|------|------------|
| 去广告 | 订阅期间无广告 | 广告系统按用户会员状态过滤 |
| 高清 + 4K | 解锁最高档位 | 播放签发联动（P06 已定义） |
| 离线缓存下载 | 本地缓存 + DRM | 与 P06 离线下载结合 |
| 独家内容/专栏 | 付费内容免费 | 内容鉴权 |

**订阅状态管理：** 订阅是**时间线状态**（连续包月，从 X 日到 Y 日有效），不是简单布尔。权益判断必须按"当前时间是否在有效期内"。关键约束：

- **续费幂等**：重复的续费请求不重复扣款
- **生效与失效**：到期自动失效，权益判断以订阅快照为准
- **防薅羊毛**：首月特价限一次（同一支付身份只能享受一次），防止反复注册薅首月价
- **与播放联动**：会员状态影响档位选择（非会员最高 720P，档位 2 下更低），联动逻辑在域 7 播放签发执行，商业化只给"权限结论"

### 电商带货链路

承接 P00 场景⑥ 的完整带货闭环，本篇聚焦链路里最容易出错的三个设计点：

**1. 佣金率快照（挂载时定格）：**

```
商品挂载时：content_id × item_id → 佣金率快照（如 5%）
结算时：    用挂载时的快照，绝不实时读商品当前佣金率
```

为什么必须快照：商家中途调低佣金率（从 5% 调到 1%）时，若实时读，历史已成交订单的分成金额全部变化，对账永远对不平。**快照让"挂载那一刻的商业约定"在结算时不变形。**

**2. 归因窗口固定（点击后 7 天）：**

```
用户点击商品卡 → 记录归因（content_id, uid, ts）
成交时：      订单时间 ≤ 点击时间 + 7 天 → 归因给该内容
```

归因窗口必须**在埋点时固定**（click 记录里带截止时间），不能"下单时再算窗口"——否则跨日、跨时区、跨系统的订单归因判断不一致。

**3. 退货窗口（15 天）后结算：**

```
成交 → 确认收货 → 进入退货窗口（15 天）→ 窗口过 → 可结算
```

退货窗口是"结算资格的闸门"——窗口没过，即使成交了也不能结算。**这个闸门在资金链路里由状态机强制，不允许跳过。**

### 收益中心与结算引擎

**三种余额（承接 P00）：**

| 余额 | 含义 | 可提现 |
|------|------|--------|
| 预估收益 | 已成交未过退货窗口 | 否 |
| 待结算收益 | 已过退货窗口，未到账期 | 否 |
| 可提现余额 | 已出账 | 是 |

**结算引擎的四个铁律：**

1. **资金类数据强一致**：收益流水、余额、提现全部走 MySQL 事务，禁止"最终一致"（这是全平台唯一例外）
2. **金额幂等**：每次结算/扣款带唯一幂等键（order_id × 事件序号），重复事件不重复执行
3. **状态机强制**：预估 → 待结算 → 可提现 的跃迁由状态机控制，跳过 = 拒绝并告警
4. **对账是内置流程**：订单流（外部）vs 收益流（内部）每日对账，差异自动告警，不等到月结

**结算引擎事件流：**

```
订单成交事件 ──► 归因匹配（7天窗口）──► 佣金计算（佣金率快照）
    ──► 平台服务费扣除 ──► 入"预估收益"
确认收货 ──► 开始 15 天退货窗口
窗口过 ──► 预估 → 待结算
账期（每月 X 日）──► 出账 ──► 待结算 → 可提现 ──► 税务代扣 → 提现
```

### 创作者激励与反作弊

**激励结构：** 流量分成（播放 × 单价 × 质量因子）+ 创作补贴（活动激励）。质量因子防止纯刷量：完播率、互动率、粉丝结构加权。

**反作弊的核心不是"抓"，而是"让刷量无利可图"：**

```
激励单价动态调控（每周更新）：
  有效播放总量（经反作弊过滤）↑ → 单价 ↓（预算池固定，分摊的人多了单价就降）
  刷量工作室加入 → 有效播放虚增 → 单价下降 → 真实创作者的激励被稀释 → 社区压力
  → 刷量越多，单价越低，刷量的收益递减 → 刷量工作室自动退出
```

**反作弊三层防线：**
1. **前置过滤**：机器号特征（设备指纹、行为序列、IP 聚集）在计数服务入口过滤
2. **中置质量因子**：播放按完播/互动/粉丝质量加权，纯刷的播放质量因子趋近于 0
3. **后置单价调控**：预算池固定 + 有效播放动态分母 → 刷量越多单价越低

**关键设计：激励预算池固定（如每月 ¥2,000 万），不随播放量膨胀。** 这让"单价调控"成为硬约束——**刷量工作室抢的不是平台的钱，是真实创作者的池子，这会激起创作者生态的自净压力。**

### 商业化合规

| 合规项 | 要求 | 落地 |
|--------|------|------|
| 广告标识 | 信息流广告必须显式标注"广告" | 混排时广告位强制带标识字段 |
| 广告法审查 | 极限词、虚假宣传、医疗/金融类广告资质 | 广告入库前广告法审查（域 6 联动） |
| 税务 | 创作者分成代扣个税 | 结算引擎扣税后出账，税务报表 |
| 跨境合规 | 跨境带货/多币种结算 | 承接 C16（汇率锁定、合规牌照） |
| 未成年人保护 | 直播打赏限额、未成年人模式 | 礼物系统按实名状态限流 |

**合规必须内嵌在链路上，不是事后检查：** 广告标识是混排输出的必填字段，缺标识的广告直接不产出；广告法审查是广告入库的前置条件，未过审的广告不进索引。

## 常见陷阱（深度分析）

### 陷阱 1：广告无限挤占自然内容

**后果：** 短期 ARPU 飙升，长期留存崩溃。广告从 1/8 加到 1/3，当月广告收入 +80%，但三个月后 DAU 跌 15%、人均时长跌 20%，广告曝光总量反而下降——**收入结构性的自我毁灭。**

**解决方案：** 体验护栏（负载上限 + 疲劳频控 + 留存联动刹车）。**判据：广告负载的任何调整，必须同时观察"广告收入"和"次日留存"，留存恶化自动收紧。**

### 陷阱 2：竞价延迟失控

**后果：** 竞价 50ms 超时，广告位空置率上升，填充率下降，eCPM 收入损失。更糟的是如果"超时等待"处理成"Feed 等广告返回"，整个 Feed 跟着慢。

**解决方案：** 竞价超时返回空置，Feed 不阻塞。定向/召回走缓存，CTR 预估是唯一实时部分。**判据：竞价链路的任何环节延迟翻倍，广告收入损失可量化；而 Feed 延迟绝不能因广告而劣化。**

### 陷阱 3：分成立即结算

**后果：** 一条爆款带货视频当日成交 500 万，若立即分成，15 天内退货 18% 导致平台向创作者多付 ¥90 万且难以追回——**这是真金白银的现金损失。**

**解决方案：** 收益中心三余额状态机，退货窗口不过闸门不打开。**判据：任何"成交即结算"的诉求，都要先回答"退货怎么办"。**

### 陷阱 4：金额操作无幂等

**后果：** 网络重试导致重复扣款（用户投诉退款）、重复结算（多付钱）、重复入账（对账不平）。**资金系统里，重试是常态不是异常，每个重试都可能重复执行。**

**解决方案：** 所有金额操作带幂等键（order_id × 事件序号），重复事件直接忽略。**判据：任何金额接口，同一请求重复 100 次与执行 1 次的结果必须一致。**

### 陷阱 5：佣金率实时读

**后果：** 商家中途调低佣金率，历史已成交订单的分成金额全部变化，对账永远对不平，结算系统变成一个改不完的毛线团。

**解决方案：** 佣金率挂载时快照，结算用快照。**判据：一笔订单的收益，无论商家中途改多少次佣金率，计算结果必须不变。**

### 陷阱 6：归因窗口随意

**后果：** 归因窗口在"成交时"才计算，跨日、跨系统、跨时区的订单归因判断不一致，创作者对账时发现"该归给我的订单没归给我"，信任崩塌。

**解决方案：** 归因窗口在点击埋点时固定（click 记录带截止时间），成交时只比对时间戳。**判据：归因逻辑是幂等的——同一订单重算 100 次归因结果必须一致。**

### 陷阱 7：激励无防作弊

**后果：** 刷量工作室用机器号矩阵刷播放，激励预算被刷走，真实创作者的激励被稀释，创作者生态萎缩。**最坏的是：不防作弊的激励 = 变相奖励刷量，劣币驱逐良币。**

**解决方案：** 前置过滤 + 质量因子 + 预算池固定/单价动态调控。**判据：刷量工作室的投入产出比应趋近于 1（不赚不亏），自然退出。**

### 陷阱 8：广告无标识

**后果：** 信息流广告未标注"广告"，被举报后按《广告法》处罚——**漏标一个广告的罚款可能是广告收入的数倍。** 合规不是小事，是生存问题。

**解决方案：** 广告标识是混排输出的必填字段，缺标识不产出。**判据：任何渲染出来的广告，必须自带"广告"标识，且标识由系统强制，不由广告主决定。**

## 异常场景完整演练

### 场景 1：广告系统故障——Feed 空置与降级

**场景描述：** 晚间高峰，广告精排集群故障，竞价成功率从 99% 跌到 20%。若 Feed 等广告返回，整体延迟翻倍；若直接空置，广告收入损失。

**错误做法：** 让 Feed 等广告返回（"少赚不如稳"）——Feed 延迟从 130ms 涨到 400ms，整体体验崩溃，用户流失的损失远超广告空置。

**正确做法：**

```
1. 竞价 50ms 硬超时，超时即返回空置，Feed 不阻塞（架构已内置）
2. 广告 slot 空置 → 用"自然内容填充"（推荐系统补一条）或留白
3. 广告系统降级为"预取模式"：用 10 分钟前的竞价结果缓存直接返回（无实时 CTR）
   → 填充率从 20% 恢复到 70%（CTR 略旧但可接受）
4. 精排集群恢复后灰度放量回实时竞价
```

**结果：** Feed 延迟保持 130ms，广告收入损失被压到最小。**关键设计：广告永远不能阻塞 Feed——广告是收入的增量，Feed 是留存的基础，优先级不可倒置。**

### 场景 2：分成对账不平

**场景描述：** 月结时发现某创作者的分成金额与订单流对不上：平台算 ¥120 万，外部电商对账单是 ¥118 万，差 ¥2 万。不查清不能出账，但账期在即。

**错误做法：** 按平台侧 ¥120 万先出账（"差 2 万回头再说"）——一旦出账，金额就固化到提现记录，回头再改就是资金事故。

**正确做法：**

```
1. 对账差异自动告警（每日对账，非等到月结才爆）
2. 按订单逐条比对：找出差异订单集合
3. 归因核对：某笔订单归因窗口内但内容已删除 → 归因记录不完整
4. 修复归因记录（补 content_id），重算该订单收益
5. 差异消除后出账，保留对账审计日志
```

**根因反思：** 对账必须在**每日**做（而不是月结），让差异在发生时即可定位，而不是积累一个月变成一团乱麻。**判据：任何资金差异，从发生到被定位的时间应 < 24 小时。**

### 场景 3：虚拟货币充值重复扣款

**场景描述：** 用户充值时网络抖动，客户端重试了 3 次，支付通道返回了 3 次扣款成功，但到账只有 1 次。用户投诉"扣了 3 次只到 1 次"。

**错误做法：** 认为是"重试导致"就不处理——**资金系统里，重试必然发生，幂等是前提不是可选项。**

**正确做法：**

```
1. 充值请求带幂等键（订单号），重复请求直接返回首次结果
2. 支付通道回调按幂等键去重，重复回调不重复入账
3. 用户投诉通道：核查幂等键，发现重复扣款 → 原路退款
4. 复盘：为什么重试链路没有幂等兜底（充值接口幂等率 100% 是硬指标）
```

**结果：** 重复扣款被幂等机制挡住（第 2 步），退款流程作为兜底（第 3 步）。**判据：充值/扣款接口的幂等率必须 100%，不允许任何"重试导致重复"的例外。**

### 场景 4：激励被刷量工作室侵蚀

**场景描述：** 某创作者激励活动上线，一周后有效播放量暴涨 300%，但真实创作者反映"分成变少了"。核查发现：300% 增量里 80% 来自刷量工作室（机器号矩阵批量播放 + 挂机）。

**错误做法：** 直接封禁所有异常播放（误伤真实用户）+ 单价不变（刷量利润丰厚，换了马甲继续来）。

**正确做法：**

```
1. 检测：有效播放量异常增长 + 播放来源聚集（同 IP/同设备指纹/同行为序列）
2. 前置过滤：机器号特征批量识别，入口过滤，计入无效播放
3. 质量因子：纯刷播放的完播/互动质量因子趋近于 0 → 计入分母但不计入激励
4. 单价调控：有效播放分母变大 → 单价下降 → 刷量收益递减
5. 复盘：活动设计是否给了刷量可乘之机（如"播放即得"类规则太粗）
```

**结果：** 刷量播放被过滤 + 单价被稀释，刷量工作室投入产出比趋近于 1，自然退出。**关键设计：激励系统不追求"完全禁刷"（成本无限），追求"刷了不划算"（收益有限）。**

## 分成结算引擎完整实现

资金链路是商业化里**唯一不允许"最终一致"**的部分，本篇给出它的核心实现：事件驱动的收益中心，含退货窗口闸门、三种余额状态机、金额幂等、对账。

```python
from __future__ import annotations

import threading
import time
from dataclasses import dataclass, field
from enum import Enum
from typing import Optional


class RevenueStatus(Enum):
    ESTIMATED = 'estimated'      # 预估收益：已成交未过退货窗口
    PENDING = 'pending'          # 待结算：已过退货窗口，未到账期
    AVAILABLE = 'available'      # 可提现：已出账
    CANCELLED = 'cancelled'      # 已取消（退货/风控）


@dataclass
class RevenueRecord:
    record_id: str
    creator_id: int
    content_id: int
    order_id: str                # 幂等键的基础
    event_seq: int               # 幂等键：order_id × event_seq
    status: RevenueStatus
    commission_rate: float       # 佣金率快照（挂载时定格）
    gmv: float                   # 成交额
    service_fee: float           # 平台服务费
    creator_income: float        # 创作者应得 = (gmv - service_fee) * rate
    refund_window_end_ts: int    # 退货窗口截止
    billing_cycle: str           # 归属账期
    created_ts: int
    updated_ts: int


class RevenueLedger:
    """收益账本：资金类数据的唯一事实来源（强一致，禁止最终一致）。
    实际存储为 MySQL 事务表，此处用内存 dict 模拟。"""

    def __init__(self):
        self._records: dict[str, RevenueRecord] = {}
        self._lock = threading.Lock()

    def get(self, record_id: str) -> Optional[RevenueRecord]:
        return self._records.get(record_id)

    def put(self, rec: RevenueRecord) -> None:
        self._records[rec.record_id] = rec


class RevenueStateMachine:
    """收益状态机：预估 → 待结算 → 可提现。
    跃迁由状态机强制，非法跃迁拒绝并告警（资金安全）。"""

    _ALLOWED = {
        RevenueStatus.ESTIMATED: {RevenueStatus.PENDING, RevenueStatus.CANCELLED},
        RevenueStatus.PENDING: {RevenueStatus.AVAILABLE, RevenueStatus.CANCELLED},
        RevenueStatus.AVAILABLE: set(),
        RevenueStatus.CANCELLED: set(),
    }

    def transition(self, rec: RevenueRecord, to: RevenueStatus) -> RevenueRecord:
        if to not in self._ALLOWED[rec.status]:
            raise ValueError(
                f"非法状态跃迁: {rec.status.value} -> {to.value} for {rec.record_id}")
        rec.status = to
        rec.updated_ts = int(time.time())
        return rec


class CommissionCalculator:
    """佣金计算：挂载时快照的佣金率，绝不实时读商品当前佣金率。"""

    def calculate(self, gmv: float, commission_rate: float,
                  service_fee_rate: float = 0.10) -> tuple[float, float]:
        service_fee = gmv * service_fee_rate
        creator_income = (gmv - service_fee) * commission_rate
        return service_fee, creator_income


class SettlementEngine:
    """分成结算引擎：事件驱动，幂等，退货窗口闸门，账期出账。"""

    def __init__(self, ledger: RevenueLedger,
                 sm: RevenueStateMachine,
                 calculator: CommissionCalculator,
                 refund_window_sec: int = 15 * 86400,
                 billing_day: int = 1):
        self.ledger = ledger
        self.sm = sm
        self.calc = calculator
        self.refund_window = refund_window_sec
        self.billing_day = billing_day
        self._processed: set[str] = set()   # 幂等键集合

    def on_order_settled(self, order_id: str, creator_id: int, content_id: int,
                         gmv: float, commission_rate: float,
                         ts: int) -> RevenueRecord:
        """订单确认收货事件 → 入预估收益（未过退货窗口）。"""
        event_seq = 0
        record_id = self._record_id(order_id, event_seq)
        if record_id in self._processed:      # 幂等：重复事件直接返回
            return self.ledger.get(record_id)

        service_fee, income = self.calc.calculate(gmv, commission_rate)
        rec = RevenueRecord(
            record_id=record_id, creator_id=creator_id, content_id=content_id,
            order_id=order_id, event_seq=event_seq,
            status=RevenueStatus.ESTIMATED, commission_rate=commission_rate,
            gmv=gmv, service_fee=service_fee, creator_income=income,
            refund_window_end_ts=ts + self.refund_window,
            billing_cycle=self._billing_cycle(ts), created_ts=ts, updated_ts=ts)
        self.ledger.put(rec)
        self._processed.add(record_id)
        return rec

    def on_refund(self, record_id: str, event_seq: int) -> None:
        """退货事件 → 取消收益。"""
        key = f"{record_id}|{event_seq}"
        if key in self._processed:
            return
        rec = self.ledger.get(record_id)
        if rec is not None:
            self.sm.transition(rec, RevenueStatus.CANCELLED)
        self._processed.add(key)

    def on_refund_window_passed(self, record_id: str, now: int) -> RevenueRecord:
        """退货窗口过 → 预估 → 待结算。闸门由状态机强制。"""
        rec = self.ledger.get(record_id)
        if rec is None or rec.refund_window_end_ts > now:
            return rec
        if rec.status is not RevenueStatus.ESTIMATED:
            return rec
        return self.sm.transition(rec, RevenueStatus.PENDING)

    def run_billing(self, cycle: str) -> list[RevenueRecord]:
        """账期出账：该账期内所有待结算 → 可提现（进提现队列）。"""
        available = []
        for rec in self.ledger._records.values():
            if rec.billing_cycle == cycle and rec.status is RevenueStatus.PENDING:
                self.sm.transition(rec, RevenueStatus.AVAILABLE)
                available.append(rec)
        return available

    def _record_id(self, order_id: str, event_seq: int) -> str:
        return f"{order_id}:{event_seq}"

    def _billing_cycle(self, ts: int) -> str:
        import datetime
        d = datetime.datetime.fromtimestamp(ts)
        # 账期 = 成交所在月；月末成交的订单结算到下月账期
        return d.strftime('%Y-%m')


class CreatorBalance:
    """创作者余额视图：三种余额的聚合（预估 / 待结算 / 可提现）。"""

    def __init__(self, ledger: RevenueLedger):
        self.ledger = ledger

    def snapshot(self, creator_id: int) -> dict[str, float]:
        estimated = pending = available = 0.0
        for rec in self.ledger._records.values():
            if rec.creator_id != creator_id:
                continue
            if rec.status is RevenueStatus.ESTIMATED:
                estimated += rec.creator_income
            elif rec.status is RevenueStatus.PENDING:
                pending += rec.creator_income
            elif rec.status is RevenueStatus.AVAILABLE:
                available += rec.creator_income
        return {
            'estimated': round(estimated, 2),
            'pending': round(pending, 2),
            'available': round(available, 2),
        }
```

**关键设计：**
1. **幂等是资金系统的地基**——每个事件带 `(order_id, event_seq)` 幂等键，重复事件直接返回首结果（`on_order_settled` 的 `_processed` 集合 + 状态机双重防重）
2. **退货窗口是状态机的闸门**——`on_refund_window_passed` 检查 `refund_window_end_ts`，未过窗口拒绝跃迁；`on_refund` 直接取消，保证"成交 ≠ 可结算"
3. **佣金率快照**——`CommissionCalculator` 只吃挂载时的 `commission_rate`，与商品当前佣金率解耦，保证历史订单收益不随商品改价变化
4. **对账可审计**——`RevenueLedger` 是收益的唯一事实来源，订单流（外部）与收益流（内部）每日比对差异即告警

## 异常场景补充

### 场景：广告竞价预算超支导致广告主投诉

```
触发：竞价策略误将某广告主的日预算上限改大 → 单日消耗 ¥80 万（预算 ¥30 万）
      → 广告主投诉"消耗异常"，平台需要赔付
检测：
  1. 单广告主日消耗 vs 预算的监控，超 90% 预警、超 100% 告警
  2. 预算配置变更的审计日志 + 变更影响预演
  3. 消耗异常的归因（哪条内容、哪个 slot、哪个策略版本）
处理：
  1. 立即暂停该广告主投放，防止继续超支
  2. 补偿协议：超支部分按"预估损失"赔付或返还预算
  3. 复盘：为什么预算配置变更没有触发二次确认
预防：预算上限变更强制二人复核 + 消耗实时监控 + 超支自动熔断投放
```

### 场景：归因数据丢失导致创作者分成偏低

```
触发：某内容埋点采样率误调，点击归因记录丢失 30%
      → 该内容创作者当月分成偏低，对账时发现差异
检测：
  1. 归因记录完整性校验：点击事件 vs 归因落库率，低于 95% 告警
  2. 创作者对账差异（订单流 vs 收益流）聚类
  3. 埋点链路的数据质量监控
处理：
  1. 用兜底归因（近邻时间窗口的点击事件）补齐丢失归因
  2. 重算受影响创作者的收益，补发差额
  3. 修复采样率配置，回放补采数据
预防：归因链路数据质量监控 + 落库率验收 + 创作者对账差异自动告警
```

### 场景：会员续费失败导致权益抖动

```
触发：支付通道故障，一批续费请求失败 → 会员被判定到期
      → 权益消失（高清锁定），用户投诉"我续费了怎么没会员"
检测：
  1. 续费成功率监控，跌破 95% 告警
  2. 权益判定的"会员状态"与支付状态一致性校验
  3. 用户侧"会员失效"类投诉聚类
处理：
  1. 续费失败重试队列，支付通道恢复后自动重试
  2. 权益判定加"宽限期"：支付中状态的用户保留权益 24h
  3. 已扣款未生效的：核查幂等键，确认扣款则立即补发会员
预防：续费重试机制 + 支付中宽限期 + 扣款与权益的幂等对账
```

### 场景：激励活动被"真实账号众包"刷量

```
触发：激励活动上线后，出现"真人众包刷量"（真实账号但非真实意愿，接单平台派发）
      → 行为特征与机器号不同（真实网络、真实设备），前置过滤失效
检测：
  1. 有效播放的"行为合理性"分析：播放时长分布、滑动速度、退出模式
  2. 异常聚集：同一时段、同一内容、播放节奏高度一致
  3. 转化异常：高播放但互动/关注转化显著偏低（刷量的"只看不互动"）
处理：
  1. 质量因子下调：这类播放的完播/互动加权趋近于 0
  2. 单价调控：有效播放分母变大，单价下降
  3. 活动规则收紧：改"有效播放 + 有效互动"双条件
预防：激励按"行为质量"而非"播放量"计 + 单价动态调控吸收水分 + 活动规则防"纯播放可薅"
```
