# P00: 统一内容平台的业务全景与域划分

## 业务场景

某综合内容平台（类似 B站/小红书/抖音的并集），同时承载图文笔记、短视频、长视频、直播四种内容形态，服务 2 亿 DAU。平台的本质是一台"内容流转机器"——创作者生产的内容经过**处理、治理、分发**三道关口触达消费者，任一关口的效率或成本失控，整台机器就会停摆。

**已知数据：**
- DAU：2 亿（纯图文用户 15%、纯视频用户 60%、混合 25%）
- 人均日播放：80 次；人均日使用时长：120 分钟
- 日播放量（VV）：160 亿
- 日新增内容：图文 800 万条、短视频 500 万条、长视频 5 万条、直播 40 万场
- 内容总库存：图文 60 亿条、视频 20 亿条
- 播放请求峰值：64.8 万 QPS；Feed 请求峰值：6.5 万 QPS
- 峰值出口带宽：26.7 Tbps；日出流量：96 PB
- 存储：原始年增量 569 PB（含转码副本）；经生命周期治理后稳态存量 534 PB
- 日转码素材量：3 亿秒
- 创作者规模：月活创作者 3000 万，其中职业创作者约 80 万

**为什么统一平台比两条独立业务线更难？**

直觉上"图文 + 视频"只是把两个系统并排放。实际上四种形态在**九个维度上全然不同**，但用户视角必须是**一个统一的信息流**：

| 维度 | 图文 | 短视频 | 长视频 | 直播 |
|------|------|--------|--------|------|
| 单条体积 | 200 KB | 8 MB | 1.5 GB | 流式无限 |
| 生产到可见 | < 3 秒 | 30 秒 - 2 分钟 | 20 分钟 - 2 小时 | 实时 |
| 审核时机 | 先审后发 | 先发后审 + 秒级回捞 | 先审后发 | 边播边审 |
| 单次消费时长 | 20 秒 | 32 秒 | 25 分钟 | 45 分钟 |
| 存储成本占比 | 0.3% | 22% | 77% | 录制后转点播 |
| 带宽成本占比 | 0.1% | 38% | 55% | 6.9% |
| 热度衰减 | 慢（长尾数月） | 极快（48 小时衰减 90%） | 慢（年度长尾） | 即时归零 |
| 商业化形态 | 信息流广告 + 带货 | 信息流广告 + 带货 | 贴片 + 会员 | 打赏 + 带货 |
| 一致性要求 | 最终一致 | 最终一致 | 最终一致 | **强实时** |

如果四种形态各建一套中台，会产生四套账号、四套关系链、四套审核、四套推荐、四套商业化——成本翻四倍还是次要的，**致命的是用户兴趣画像被割裂在四个系统里**：用户在长视频区追科技纪录片，在短视频区刷美食，两份画像互不知情，推荐效果显著劣于统一画像。反过来，如果强行用一套模型抹平差异，长视频的 1.5 GB 会拖垮为 200 KB 图文设计的链路。

**核心矛盾**：**上层体验必须统一（一个信息流、一份画像、一套互动），底层链路必须差异（体积差 7500 倍、时效差 4 个数量级）**。统一在哪一层、差异从哪一层开始下沉，是本平台的第一设计命题。

## 核心挑战

### 挑战 1：四种形态的统一抽象——统一到哪一层

"内容"这个概念在四种形态下的共性只有：有作者、有标题、有发布时间、有可见范围、能被点赞评论。差异部分（媒体文件、时长、码率、分辨率、推流地址、切片列表）占了字段总量的 70%。

如果统一表塞进所有字段，会得到一张 120 列、70% 为 NULL 的巨表——图文记录白背 80 个视频字段，长视频记录白背图文的排版字段。如果彻底分表，则每加一种形态就要改所有下游（推荐、搜索、审核、商业化、数据），扇出成本失控。抽象的边界画错一次，代价是全平台重构。

### 挑战 2：域边界切分与端到端 SLA 预算分配

一条长视频从创作者点"发布"到用户能播放，总预算 30 分钟（P95），要穿过 6 个域：上传 → 媒资入库 → 转码 → 审核 → 索引构建 → CDN 预热。这 30 分钟怎么切？

难点在于**各环节的耗时分布形态完全不同**：上传耗时取决于创作者网络（长尾极重，P99 是 P50 的 20 倍）；转码耗时正比于时长与分辨率（可预测）；审核耗时是双峰分布（机审秒级 vs 人审分钟级）。用平均值做预算分配必然导致 P95 击穿。而如果每个域都按自己的 P99 留余量，六个 P99 串联起来预算会膨胀到 3 小时。

### 挑战 3：成本是第一约束——带宽与存储合计占 93%

实算：日出流量 96 PB，按 ¥0.05/GB 计，**CDN 月成本 ¥1.44 亿**（占 73%）。稳态存量 534 PB，分层优化后**存储月成本 ¥1,258 万**（占 20%）。两者合计 93.3%，其余全部加起来不到 7%。

这颠覆了通常的架构直觉。多数系统的第一约束是延迟或并发，而亿级 DAU 内容平台的第一约束是**成本**——具体说是**字节数**：传输的字节数（带宽）与留存的字节数（存储）。这意味着任何能降低单位播放字节数的手段（更高效的编码、更准的码率、P2P 分担、更精确的预加载），其收益都以千万元/月计；而任何增加冗余传输或冗余留存的设计（激进预加载、无脑高清、重复回源、预转全档位），代价同样以千万元/月计。

单位 DAU 月成本必须压到 ¥1.0 以下，否则广告 + 会员 + 带货的收入模型无法覆盖。当前朴素方案下这个数字是 ¥1.58。

### 挑战 4：审核时效与分发时效的结构性冲突

监管要求违规内容漏检率 < 0.05%，这倾向于"先审后发"。推荐系统要求新内容尽快进入冷启动流量池——短视频的黄金分发窗口只有发布后 2 小时，等 5 分钟人审等于放弃这条内容的大部分潜力。

两个要求在**同一条链路上直接对撞**。更麻烦的是它们的失败代价不对称：漏检一条政治违规内容可能导致全平台下架整改（代价：数亿元 + 生存风险）；延迟分发一条内容的代价是创作者体验下降（代价：可量化但小）。不对称代价意味着不能简单折中。

### 挑战 5：热点事件的全域压力传导

一场突发热点（明星事件、社会新闻、体育赛事），压力不是均匀上升，而是**沿着域依赖链逐级放大并错峰到达**：

投稿量先涨（创作者涌入，2 倍）→ 转码队列积压（2 倍且持续）→ 审核量涨（2 倍，且新型违规增多导致机审置信度下降，人审比例从 20% 涨到 45%，人审绝对量涨 4.5 倍）→ 播放量涨（5 倍）→ 带宽涨（5 倍，成本单日多支出 ¥3000 万）→ 评论弹幕涨（8 倍）。

各域的峰值不在同一时刻，扩容不能一起做；且带宽的成本弹性远大于计算，需要在"体验"和"当日多花几千万"之间实时决策。

## 设计约束

- 发布到可见（P95）：图文 < 3 秒、短视频 < 2 分钟、长视频 < 30 分钟、直播 < 5 秒
- 播放首帧（P95）< 800ms，卡顿率 < 1%，播放成功率 > 99.5%
- 违规内容漏检率 < 0.05%（监管红线，不可协商），误杀率 < 1%
- 单位 DAU 月成本 < ¥1.0（商业模型底线）
- 任一非播放域故障不得导致播放不可用——**播放是最后底线**
- 内容 ID 与外链一经发布永久有效，不可回收、不可变更语义

## 设计解析

### 分层抽象：统一在"内容"，差异下沉到"媒体"

回答挑战 1 的关键洞察：**"内容"和"媒体"是两个不同的概念，混淆它们是所有内容平台架构腐化的起点。**

- **内容（Content）**：一个可被发现、可被消费、可被互动、可被治理、可被变现的**业务对象**。它有作者、标题、标签、状态、可见范围、统计数据。图文和长视频在这一层**完全同构**。
- **媒体（Media）**：内容的**物理载体**。它有格式、体积、编码、清晰度档位、存储位置、播放地址。图文的载体是若干张图片，长视频的载体是一组 ABR 切片，直播的载体是一条持续的流。这一层**完全异构**。

于是抽象边界清晰了：

```
┌──────────────────────────────────────────────────────────┐
│  统一层（所有形态同构，一套代码一套表）                    │
│                                                          │
│  内容主体  content(content_id, author_id, type, title,   │
│            status, visibility, publish_time, ...)        │
│  内容统计  content_stat(play, like, comment, share, ...)  │
│  内容标签  content_tag / content_embedding                │
│  内容治理  content_audit / content_copyright              │
│  内容互动  comment / like / favorite                      │
│  内容变现  content_monetize                               │
├──────────────────────────────────────────────────────────┤
│  形态适配层（多态，按 type 分派）                          │
│                                                          │
│  content_ext_article  (排版JSON、字数、图片列表)           │
│  content_ext_video    (时长、原始码率、ABR档位、封面)      │
│  content_ext_live     (房间ID、推流码、开播时间、状态)     │
├──────────────────────────────────────────────────────────┤
│  媒体层（完全异构，独立演进，不被上层感知）                 │
│                                                          │
│  media_asset(asset_id, type, storage, codec, bitrate...)  │
│  media_variant(转码产物档位)                              │
│  media_playback(播放地址、DRM、签名策略)                   │
└──────────────────────────────────────────────────────────┘
```

**核心原则：上层只认 content_id，永远不碰媒体细节；媒体层的任何变化（新增 AV1 档位、切换 CDN、启用 DRM）对上层完全透明。**

这条边界带来的直接收益：推荐、搜索、审核、商业化、数据五个下游只依赖统一层的 content 表。新增一种内容形态（比如未来的 3D/VR 内容），只需加一张 `content_ext_xxx` 和一套媒体处理链路，五个下游**零改动**。

**反过来验证边界是否画对**——问三个问题：
1. 推荐系统需要知道视频的码率吗？不需要（它只需要时长、清晰度等级这类**业务语义**）→ 码率属于媒体层，正确。
2. 审核系统需要知道视频存在哪个 bucket 吗？不需要（它只需要一个可读取的临时地址）→ 存储位置属于媒体层，正确。
3. 商业化需要知道内容类型吗？需要（贴片广告只能挂长视频）→ type 属于统一层，正确。

### 域划分与边界契约

功能清单只是"有什么"，域划分要回答"谁负责、谁不负责"。每个域的契约包含四项：**职责、输入、输出、明确不做**。第四项最重要——**"明确不做"是防止域膨胀的唯一有效手段**。

**域 3：内容生产与投稿**

- **职责**：接收创作者的内容提交，落地为一个处于 `draft` 或 `pending` 状态的 content 记录 + 一份 media_asset
- **输入**：客户端上传的文件分片、编辑器提交的结构化内容、发布参数（可见范围、话题、定时）
- **输出**：`ContentSubmitted` 事件（含 content_id、asset_id、type、author_id）
- **明确不做**：
  - 不做转码——只负责把原片安全落到对象存储，转码由域 4 消费事件触发
  - 不做审核——不判断内容是否合规，只标记 `pending`
  - 不做索引——不写搜索引擎、不写推荐内容池
  - 不等待下游——提交成功即返回，绝不同步等转码或审核

**域 4：媒体处理**

- **职责**：把一份原始 media_asset 转换为一组可播放的 media_variant
- **输入**：`ContentSubmitted` 事件、原片对象存储地址
- **输出**：`MediaReady` 事件（含 variant 列表、时长、封面、指纹）
- **明确不做**：
  - 不决定内容能否发布——只报告"媒体就绪"，发布决策在编排层（跨域的内容中台组件，不属于十四域之一）
  - 不管 CDN 分发——产物写回对象存储即完成，预热由域 7 负责
  - 不存储长期媒资——落盘与生命周期归域 5

**域 6：内容理解与治理**

- **职责**：判定内容能否公开、打上理解标签、检测版权
- **输入**：`MediaReady` 事件（视频需要转码后的低码率代理片做分析，比分析原片省 90% 算力）
- **输出**：`AuditPassed` / `AuditRejected` / `AuditNeedManual` 事件，以及 `ContentUnderstood`（标签 + Embedding）
- **明确不做**：
  - 不直接改 content 状态——发出事件，由编排层改状态（避免多写方竞争）
  - 不做流量调控——判定"能不能发"，不判定"发多少量"

**域 9：推荐与搜索**

- **职责**：决定"什么内容给什么人看多少量"
- **输入**：`AuditPassed` + `ContentUnderstood` 事件（**两者都到齐才能进池**）
- **输出**：Feed 结果、搜索结果、曝光日志
- **明确不做**：
  - 不判断内容合规——只信任域 6 的结论
  - 不管播放——只返回 content_id 列表，播放地址由域 7 换取

**域 7：分发与播放**

- **职责**：把 content_id 换成一个当下最优的可播放地址，并保障播放质量
- **输入**：content_id + 用户上下文（网络、地域、设备、会员等级）
- **输出**：签名后的播放地址、清晰度档位列表、QoE 上报
- **明确不做**：
  - 不做内容鉴权的业务判断——只执行域 1/域 11 给出的权限结论（是否会员、是否付费）
  - 不缓存业务数据——只缓存媒体分片

**跨域的三条铁律**：

1. **状态单写方**：`content.status` 只有编排层能写。任何域想改状态，发事件。违反此律的后果见"陷阱 5"。
2. **事件即契约**：域间只通过事件通信，不允许跨域直连数据库。事件 schema 变更需向后兼容。
3. **下游不可反向依赖**：域 9（推荐）不能反向调用域 4（转码）要求补一个档位。需要则走域 7 的 JIT 通道。

**关键设计：依赖是单向的，域 6 是唯一的发布闸门，域 7 是唯一不可故障的域。**

这张图揭示了两个非对称性：

- **域 6 是全局串行点**：所有内容都必须过审核。它既是合规保障，也是全平台最大的延迟来源和单点风险。因此域 6 内部必须做分级（机审快通道 vs 人审慢通道），且必须有"审核系统故障时的降级策略"——不能是"全部卡住"，也不能是"全部放行"。
- **域 7 是可用性底线**：即使域 3/4/6/9 全部挂掉，已发布内容的播放**必须**还能工作。这要求域 7 对上游的依赖全部是**弱依赖 + 本地兜底**（播放地址可从本地缓存/CDN 边缘配置生成，不必实时问域 5）。

| 商业化 | 域 11 | 100 人 | ARPU、广告填充率 | 算法（广告挤占自然流量） |
| 数据 | 域 13 | 60 人 | 数据时效、口径一致性 | — |
| 基础架构 | 域 14 | 70 人 | 可用性、单位 DAU 成本 | 所有业务域 |

**四组结构性冲突及其治理机制**：

| 冲突 | 表现 | 不能靠"沟通"解决，要靠机制 |
|------|------|--------------------------|
| 媒体技术 vs 分发技术 | 前者想提画质（VMAF），后者想降码率（省带宽） | 设**联合 KPI**：单位 VMAF 分的带宽成本。双方共同优化一个数 |
| 内容治理 vs 创作平台 | 审核越严，创作者投稿体验越差 | 设**误杀率**为治理团队的硬 KPI，与漏检率同权重 |
| 内容治理 vs 算法 | 治理要"先审后发"，算法要"抢冷启动窗口" | 见下文"分级审核 + 灰度曝光"设计，用**受限流量池**同时满足 |
| 商业化 vs 算法 | 广告位挤占自然内容曝光 | 设**广告负载上限**（每 N 条内容最多 1 条广告）+ 长期留存作为商业化的 guardrail 指标 |

**核心原则：跨团队的结构性冲突必须用联合 KPI 或硬约束来治理，指望双方"多沟通"必然失败。**

### 统一内容模型的核心表设计

**为什么 `media_variant` 要有 `play_count_7d`？** 这是回答挑战 3（成本）的关键设计。569 PB 年增存储里，绝大部分是"生成了但几乎没人播"的档位——一条长尾视频转了 6 档，实际 95% 的播放集中在 720P 一档。有了这个字段，就能做副本回收：7 日播放为 0 且创建超过 30 天的非兜底档位直接删除，需要时用 JIT 重新生成。实算这一项可省 298 PB/年。

### 内容状态机

四种形态共享同一个状态机骨架，差异体现在**允许的跃迁子集**上。这是"统一 + 差异"在状态维度的落地。

```
                    ┌──────────┐
                    │  draft   │ 草稿（仅作者可见）
                    └────┬─────┘
                         │ 提交发布
                         ▼
                    ┌──────────┐
              ┌─────│processing│ 处理中（转码/理解）
              │     └────┬─────┘
       转码失败│          │ MediaReady
              │          ▼
              │     ┌──────────┐
              │     │ auditing │ 待审/审核中
              │     └────┬─────┘
              │     ┌────┴────┬──────────┐
              │     │         │          │
              │  通过│    驳回│     需人审│
              │     ▼         ▼          ▼
              │ ┌────────┐ ┌──────┐ ┌──────────┐
              │ │published│ │rejected│ │manual_q │
              │ └───┬────┘ └──────┘ └────┬─────┘
              │     │                     │ 人审结论
              │     │  ┌──────────────────┘
              │     ▼  ▼
              │ ┌─────────┐    ┌─────────┐
              └▶│ failed  │    │ offline │ 下架（可恢复）
                └─────────┘    └────┬────┘
                                    ▼
                               ┌─────────┐
                               │ deleted │ 删除（终态）
                               └─────────┘

各形态允许的跃迁差异：
  图文    : draft → auditing → published        （跳过 processing，无转码）
  短视频  : draft → processing → published        （先发后审：转码完直接发，审核并行）
                            ↘ auditing（异步）→ offline（回捞）
  长视频  : draft → processing → auditing → published  （先审后发，全串行）
  直播    : draft → living → ended → processing → published（录制转点播）
```

**关键设计：短视频的 `processing → published` 跃迁不经过 `auditing`，审核并行进行并保留"回捞"通路——这是挑战 4 的答案的一半。**

### 端到端场景串讲

域划分和表设计都是静态视图。真正检验架构是否成立，要看**一条请求穿过多个域时预算怎么分、失败怎么退**。以下六个场景覆盖了平台的全部关键路径。

#### 场景 ①：创作者投稿一条 4K 长视频，直到用户可播放

这是平台最长的链路，也是 SLA 预算分配最难的一条。总预算 30 分钟（P95），一条 60 分钟 4K 原片（约 12 GB）。

```
创作者客户端                                        总预算 30min (P95)
    │
    │ ① 分片上传（10MB/片，1200 片，6 并发）
    │    ┌─────────────────────────────────────┐
    ├───▶│ 域3 投稿服务 → 对象存储直传          │  预算 8min  实测P50 4min
    │    │  · 客户端算 SHA256 → 秒传命中则跳过  │           实测P95 7.5min
    │    │  · 分片并发 + 断点续传               │           ← 长尾主因：创作者上行带宽
    │    └─────────────────────────────────────┘
    │    ▼ 合并分片 → media_asset 落库 → 发 ContentSubmitted
    │    ┌─────────────────────────────────────┐
    │    │ 域4 转码调度                          │  预算 14min 实测P50 9min
    │    │  · 优先级入队（长视频=P2，短视频=P1） │           实测P95 13min
    │    │  · 先出「代理片」(360P,极速档)  40s   │  ← 关键：代理片先出，
    │    │  · 并行出 6 档 ABR（GPU 集群）        │     审核与索引不等全档位
    │    │  · 封面抽帧 + 雪碧图 + ASR 字幕       │
    │    └─────────────────────────────────────┘
    │    ▼ 代理片就绪即发 MediaProxyReady（不等全档）
    │    ┌─────────────────────────────────────┐
    │    │ 域6 审核与理解（消费代理片，省90%算力）│  预算 6min  实测P50 45s
    │    │  · 机审：抽帧 + ASR + OCR 多模态      │           实测P95 5min
    │    │  · 置信度≥95% → 直接通过（占 78%）    │           ← 长尾主因：人审排队
    │    │  · 置信度<95% → 人审队列（占 22%）    │
    │    │  · 并行：打标签 + Embedding + 指纹    │
    │    └─────────────────────────────────────┘
    │    ▼ AuditPassed + ContentUnderstood 双事件到齐
    │    ┌─────────────────────────────────────┐
    │    │ 编排层：status → published            │  预算 30s   实测P50 2s
    │    └─────────────────────────────────────┘
    │    ▼ ContentPublished
    │    ┌──────────────────┬──────────────────┐
    │    │ 域9 索引构建      │ 域7 CDN 预热      │  预算 90s   实测P50 20s
    │    │ · 写搜索倒排      │ · 仅预热 720P     │
    │    │ · 进冷启动内容池  │ · 仅预热首 3 分片 │
    │    │ · 写作者粉丝 Feed │   （不预热全片！） │
    │    └──────────────────┴──────────────────┘
    │
    ▼ 用户可搜到、可播放
```

**SLA 预算分配表**：

| 阶段 | 预算 | 实测 P50 | 实测 P95 | 长尾主因 | 预算依据 |
|------|------|---------|---------|---------|---------|
| 分片上传 | 8 min | 4 min | 7.5 min | 创作者上行带宽（长尾极重） | 12GB / 平均上行 40Mbps ≈ 40min → 靠 6 并发压到 7min |
| 转码 | 14 min | 9 min | 13 min | 4K HEVC 单档耗时 | 60min 素材 × 0.15x 实时（GPU）× 6 档 / 4 并发 |
| 审核与理解 | 6 min | 45 s | 5 min | 人审排队（22% 走人审） | 机审 40s + 人审队列 P95 4min |
| 状态跃迁 | 30 s | 2 s | 8 s | — | 事件传播 + DB 写 |
| 索引 + 预热 | 90 s | 20 s | 60 s | 搜索索引刷新周期 | ES near-realtime 1s + 池写入 |
| **合计** | **30 min** | **14 min** | **26 min** | — | 留 4min 余量 |

**为什么串联 6 个环节的 P95 之和（7.5+13+5+0.13+1 = 26.6min）没有膨胀到 3 小时？** 因为**长尾不相关**：上传慢的原因（创作者网络差）和审核慢的原因（内容敏感需人审）是独立事件，同时发生的概率是 5%×22% ≈ 1%。串联 P95 ≈ 各环节 P95 之和只在**完全正相关**时成立；独立时实际接近 √(Σ方差)，远小于和。这是预算分配可以"各环节按 P95 留"而总量不爆的数学依据。

**两个决定性的架构技巧**：

1. **代理片优先（Proxy-First）**：转码不是"全部完成才通知下游"，而是先用 40 秒出一个 360P 极速档作为"代理片"，审核和内容理解消费代理片而非原片。收益：审核算力降 90%（分析 360P vs 4K），且审核可以和高档位转码**并行**，把 14+6=20min 的串行压成 max(14, 0.7+6)=14min。
2. **预热只预热"首 3 分片 + 单一档位"**：全片预热 12GB × 6 档 = 72GB 推到边缘，而 95% 的观众只会看前 3 分钟且只用 720P。实算：全预热的 CDN 回源成本是选择性预热的 24 倍，而首帧收益完全相同。

#### 场景 ②：用户冷启动打开 App 到首帧画面

这是最高频的链路（日 2 亿次冷启动），预算 800ms（P95）。它的难点不是单点性能，而是**串行依赖太多**。

```
用户点击图标
  │
  ├─ ⓪ 并行预热（App 启动即触发，不等 Feed）
  │    · DNS 预解析 + QUIC 预连接 CDN
  │    · 读上次退出时缓存的 Feed（本地兜底，可立即渲染）
  │
  ├─ ① 鉴权 + 拉 Feed                                  预算 200ms
  │    网关 → 域1 鉴权(缓存命中 3ms) → 域9 推荐服务
  │      域9 内部：召回 30ms + 粗排 15ms + 精排 40ms
  │           + 重排/混排 10ms + 商业化插入 15ms
  │      并行读：域10 互动状态(是否点赞过) 8ms
  │
  ├─ ② 换取播放地址                                    预算 80ms
  │    域7 播放服务：content_id → variant 选档 → 签名
  │      · 选档依据：网络类型 + 会员等级 + 设备解码能力
  │      · CDN 选择：质量分 × 成本权重
  │
  ├─ ③ 建连 + 首片下载                                 预算 400ms
  │    · QUIC 0-RTT（复用 ⓪ 的连接）  → 省 1 个 RTT
  │    · 首片请求（GOP 对齐的 2s 分片，约 250KB）
  │    · 边缘命中 → 30ms；未命中回源 → +120ms
  │
  ├─ ④ 解码 + 渲染首帧                                 预算 120ms
  │    · 硬解初始化 60ms（可与 ③ 并行预初始化）
  │
  ▼ 首帧可见
```

**首帧延迟预算账本**：

```
用户冷启动到首帧（预算 800ms P95）：
  ┌──────────────────────────────────────────────────────┐
  │ App 启动 → 鉴权完成            ≈  40ms              │
  │ Feed 请求 → 推荐返回            ≈ 130ms              │ ← 域9 内部见下
  │ 换取播放地址（域7）              ≈  35ms              │
  │ QUIC 建连（0-RTT 复用）          ≈  15ms              │ ← 冷连接则 +90ms
  │ 首片下载（250KB，边缘命中）      ≈ 180ms              │ ← 未命中 +120ms
  │ 硬解初始化（与下载并行）          ≈   0ms（已重叠）     │
  │ 解码 + 渲染首帧                  ≈  85ms              │
  ├──────────────────────────────────────────────────────┤
  │ 合计（理想路径）                 ≈ 485ms              │
  │ 合计（边缘未命中 + 冷连接）      ≈ 695ms              │
  └──────────────────────────────────────────────────────┘

  域9 推荐服务内部（130ms）：
  ┌──────────────────────────────────────────────────────┐
  │ 多路召回（6 路并行，取最慢）      ≈  30ms              │
  │ 粗排（轻量模型，1000→200）        ≈  15ms              │
  │ 精排（DNN，200→30）               ≈  40ms              │
  │ 重排 + 多形态混排                 ≈  10ms              │
  │ 商业化广告插入                    ≈  15ms              │
  │ 结果组装 + 互动状态回填（并行）    ≈  20ms              │
  ├──────────────────────────────────────────────────────┤
  │ 合计                             ≈ 130ms              │
  └──────────────────────────────────────────────────────┘
```

**关键设计：⓪ 阶段的本地 Feed 兜底让"首帧"与"Feed 是否返回"解耦——即使域 9 完全不可用，用户仍能看到上次的内容并立即起播。**

这条兜底是"域 7 不可故障"原则的具体实现：播放能力不依赖推荐能力。代价是极端情况下内容陈旧，但**能播放的陈旧内容远好于转圈的空白页**。

#### 场景 ③：一场千万人同时在线的直播

难点在于**扇出规模**与**强实时约束**同时存在，且录制后要无缝转为点播。

```
主播端                     ┌──────────────────────────────┐
```

**千万在线的分发容量测算**：

| 项 | 计算 | 结果 |
|---|------|------|
| 同时在线 | 1000 万 | — |
| 档位分布 | 1080P 30% / 720P 45% / 480P 25% | — |
| 加权平均码率 | 0.3×4Mbps + 0.45×2.5Mbps + 0.25×1.2Mbps | 2.6 Mbps |
| 峰值带宽 | 1000 万 × 2.6 Mbps | **26 Tbps** |
| 单场 3 小时流量 | 26 Tbps × 3h / 8 | 35 PB |
| 单场 CDN 成本 | 35 PB × ¥0.05/GB | **¥175 万** |
| 弹幕峰值 | 按 3% 观众/分钟发言 | 5000 条/秒 |
| 礼物峰值 | 高峰期集中打赏 | 8000 笔/秒 |

**一场头部直播的带宽就等于平台日常带宽的全部**（26 Tbps vs 平台峰值 26.7 Tbps）。这解释了为什么直播必须有独立的容量池和独立的成本审批——一场超预期的头部直播能把当月带宽预算打穿。

**关键设计：礼物走独立强一致通道，绝不与弹幕共用聚合管道。** 弹幕丢一条无所谓（用户不会察觉 200ms 窗口里少了一条），礼物丢一条是资金事故（用户付了钱没显示 → 投诉 + 退款 + 品牌损失）。

#### 场景 ④：突发热点事件的全域压力传导

热点的可怕之处是压力**逐级放大 + 错峰到达 + 成本弹性不一致**。以一场持续 6 小时的突发社会热点为例：

```
时间轴      域3投稿   域4转码   域6审核    域9推荐   域7带宽   域10互动   当刻主要风险
────────┼────────┼────────┼─────────┼────────┼────────┼────────┼──────────────
T+0      1.0x     1.0x     1.0x      1.0x     1.0x     1.0x     —
T+10min  2.2x     1.3x     1.2x      1.4x     1.3x     1.8x     投稿峰值先到
T+30min  2.5x     2.4x     2.0x      2.6x     2.4x     3.5x     转码队列开始积压
T+1h     2.1x     2.8x     3.2x      3.8x     3.6x     6.0x     ★人审积压（机审置信度↓）
T+2h     1.8x     2.2x     4.5x      4.6x     4.8x     8.0x     ★★带宽成本失控
T+4h     1.4x     1.5x     3.0x      5.0x     5.0x     7.0x     ★★播放峰值 + 评论峰值
T+6h     1.1x     1.1x     1.8x      3.2x     3.4x     4.0x     缓慢回落
T+24h    1.0x     1.0x     1.1x      1.3x     1.4x     1.5x     长尾
```

**放大链条的机制**：

| 环节 | 放大倍数 | 放大机制 |
|------|---------|---------|
| 投稿 → 转码 | 1.1x | 基本线性（投稿即转码） |
| 转码 → 审核 | 1.6x | **非线性**：热点内容含新型违规变体，机审置信度从 92% 降到 78% → 人审比例从 22% 飙到 45%，人审绝对量放大 2x |
| 审核 → 推荐 | 1.2x | 内容池膨胀 + 用户主动搜索激增 |
| 推荐 → 带宽 | 1.05x | 基本线性 |
| 播放 → 互动 | 1.7x | **非线性**：热点内容的评论率是日常的 2.5 倍（用户有表达欲） |

**成本弹性的不一致是最难处理的**：

| 资源 | 扩容速度 | 成本弹性 | 应对策略 |
|------|---------|---------|---------|
| 转码算力 | 5 分钟（K8s 弹性） | 线性，可控 | 直接扩，同时降级：热点内容只转 3 档不转 6 档 |
| 人审产能 | 30-60 分钟（叫人） | 阶梯，刚性 | 提前储备 + 阈值临时收紧 + 优先级队列 |
| 带宽 | 秒级（CDN 自动） | **线性但基数巨大** | ★需要实时成本决策，见下 |
| 互动写入 | 3 分钟 | 线性，便宜 | 直接扩 |

带宽是唯一需要**实时商业决策**的资源：5x 带宽意味着当日多花 `96PB × 4 × ¥0.05/GB ≈ ¥1920 万`。这不是技术团队能单独决定的。因此架构上必须提供**分档降级开关**，让运营/管理层在 3 个档位间实时选择：

```
带宽成本熔断三档（由值班总监一键切换）：
  档位0 正常     : 全档位可选，默认 1080P，预加载 3 片
  档位1 温和降级 : 默认档位降至 720P，预加载 2 片，关闭 4K
                   → 省 32% 带宽，用户几乎无感（实测 QoE 降 0.4%）
  档位2 强力降级 : 默认 480P，预加载 1 片，非会员禁 1080P+，P2P 强制开启
                   → 省 58% 带宽，用户可感知（QoE 降 4.2%，投诉率 +0.8%）
```

**关键设计：成本熔断必须是"一键、分档、可量化影响"的运营开关，而不是工程师临时改配置。**

#### 场景 ⑤：一条侵权视频的处置闭环

这个场景检验的是"删除"的完整性——内容平台最容易出漏洞的地方。

```
① 发现（三条独立入口）
   ├─ 主动：投稿时指纹比对命中版权库          → 拦在发布前（最优，占 71%）
   ├─ 巡检：离线指纹全量扫描（每日）           → 发布后 1 天内（占 22%）
   └─ 被动：版权方投诉 / 用户举报              → 发布后不定（占 7%）
                    │
                    ▼
② 判定（域6）
   ├─ 指纹相似度 ≥ 90% 且时长重叠 ≥ 30s  → 高置信侵权，自动处置
   ├─ 相似度 60-90%                      → 人审（可能是合理引用/二创授权）
   └─ 有授权白名单记录                   → 放行
                    │
                    ▼
③ 处置（必须是原子的全链路清理，任一环节遗漏即为事故）
   ┌──────────────────────────────────────────────────────┐
   │ 1. content.status → offline           (编排层)        │
   │ 2. 搜索索引删除                        (域9)           │
   │ 3. 推荐内容池移除 + 已下发 Feed 打标    (域9)           │
   │ 4. CDN 全网缓存清除（含所有档位所有边缘）(域7) ★最易漏  │
   │ 5. 播放地址签名密钥轮换（作废已发地址）  (域7) ★最易漏  │
   │ 6. 离线下载的本地副本远程失效（DRM 吊销）(域7) ★最易漏  │
   │ 7. 站外分享链接失效                     (域7)           │
   │ 8. 创作者收益冻结（该内容产生的分成）    (域11)          │
   │ 9. 创作者违规记录 + 信用分扣减           (域12)          │
   │ 10. 版权方通知 + 处置回执                (域6)           │
   └──────────────────────────────────────────────────────┘
                    │
                    ▼
④ 申诉（域12）→ 人审复核 → 恢复或维持
                    │
                    ▼
⑤ 归档：处置记录留存 3 年（合规要求）
```

**为什么第 4/5/6 步最容易漏？** 因为它们不在"业务数据库"里——CDN 边缘缓存、已签发的播放地址、用户设备上的离线文件都是**分布在系统外部的副本**。只改数据库状态会造成"数据库里已下架，但用户仍能播放"，这在版权诉讼中是直接的败诉证据。

对应的设计要求：**下架必须是一个有状态、可重试、可验证的工作流，而不是一次同步调用**。

```sql
-- 内容下架任务表：把"下架"建模为可追踪的多步工作流
CREATE TABLE content_takedown_task (
    task_id          BIGINT PRIMARY KEY,
    content_id       BIGINT NOT NULL,
    reason_type      TINYINT NOT NULL COMMENT '1-侵权,2-违规,3-作者删除,4-监管要求',
    reason_detail    VARCHAR(512) NOT NULL DEFAULT '',
    -- 十个步骤各自的状态，任一未完成则任务未完成
    step_status      JSON NOT NULL COMMENT '{"db":2,"search":2,"pool":1,"cdn":0,...} 0-待执行,1-执行中,2-成功,3-失败',
    retry_count      SMALLINT NOT NULL DEFAULT 0,
    verified_at      DATETIME DEFAULT NULL COMMENT '全链路验证通过时间（探测确认不可播）',
    sla_deadline     DATETIME NOT NULL COMMENT '监管要求的处置截止时间',
    created_at       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY uk_content_reason (content_id, reason_type),
    INDEX idx_unfinished (verified_at, sla_deadline),
    INDEX idx_deadline (sla_deadline)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='内容下架工作流任务表';
```

`verified_at` 字段是这张表的灵魂——它不是"我们执行了下架动作"，而是"**我们主动探测确认了内容真的播不了**"。没有这一步的下架流程都是自欺欺人。

#### 场景 ⑥：一条内容的商业化闭环

```
创作者发布带货短视频
  │
  ├─ ① 商品挂载（域11）
  │    · 选品广场选货 or 自有店铺商品
  │    · 商品资质校验（域6 联动：三无产品/违禁品拦截）
  │    · 生成 content_id ↔ item_id 关联 + 佣金率快照
  │
  ├─ ② 分发（域9）
  │    · 带货内容进入独立内容池（避免过度商业化污染主池）
  │    · 商业化负载约束：连续 N 条内容中带货内容 ≤ 20%
  │
  ├─ ③ 曝光与点击（域7 + 域11）
  │    · 播放埋点 → 商品卡曝光埋点 → 点击埋点
  │    · 归因窗口：点击后 7 天内成交归因给该内容
  │
  ├─ ④ 成交（外部电商域）
  │    · 订单创建 → 支付 → 发货 → 确认收货
  │    · 退货窗口 15 天（★分成必须等过这个窗口）
  │
  ├─ ⑤ 分成计算（域11）
  │    · 确认收货 + 过退货期 → 佣金可结算
  │    · 用 ③ 的归因结果 × ①的佣金率快照
  │    · 平台服务费扣除 → 创作者应得
  │
  └─ ⑥ 结算与提现（域11 + 域12）
       · 月度账期出账 → 创作者对账 → 提现 → 税务代扣
```

**这条链路上最反直觉的约束：分成不能在成交时立即结算，必须等退货窗口（15 天）过去。** 一条爆款带货视频当日成交 500 万，若立即分成，15 天内退货 18% 会导致平台向创作者多付 ¥90 万且难以追回。因此收益中心必须区分三种余额：

| 余额类型 | 含义 | 可提现 |
|---------|------|-------|
| 预估收益 | 已成交未过退货期 | 否 |
| 待结算收益 | 已过退货期，未到账期 | 否 |
| 可提现余额 | 已出账 | 是 |

**关键设计：佣金率必须在挂载时"快照"，不能实时读商品当前佣金率。** 否则商家中途调低佣金率会导致历史分成金额变化，对账永远对不平。

**峰均比 3.5x 的来源**：内容平台的流量高峰集中在 20:00-23:00（占全日 32%）与 12:00-13:00（占 11%）。峰均比决定了所有无状态服务必须按峰值的 1.3 倍备容（留 30% 缓冲），意味着**日均只用得上 37% 的容量**——这是内容平台计算成本高的结构性原因，也是混部/弹性/Serverless 化收益巨大的原因。

### 成本模型：为什么带宽是第一约束

这是整篇蓝图最重要的一张表。

| 成本项 | 朴素方案月成本 | 占比 | 优化后月成本 | 优化手段 |
|--------|--------------|------|------------|---------|
| **CDN 带宽** | **¥23,040 万** | **73.0%** | **¥9,220 万** | 见下文四项 |
| **存储** | **¥6,409 万** | **20.3%** | **¥1,258 万** | 冷热分层 + EC + 副本回收 |
| 转码算力 | ¥1,120 万 | 3.5% | ¥310 万 | GPU/VPU 硬编 + JIT |
| 推荐/搜索算力 | ¥620 万 | 2.0% | ¥480 万 | 模型蒸馏 + 混部 |
| 审核算力 | ¥190 万 | 0.6% | ¥95 万 | 代理片分析 |
| 其余（DB/缓存/MQ/大数据） | ¥180 万 | 0.6% | ¥165 万 | — |
| **合计** | **¥31,559 万** | 100% | **¥11,528 万** | **降 63%** |
| **单位 DAU 月成本** | **¥1.58** | — | **¥0.58** | 达标（< ¥1.0） |

> **存储基数说明**：按运营第 3 年的**稳态存量 534 PB** 计算，而非年增量——长视频原片与图文永久保留（137 + 22 PB）、短视频原片仅留 90 天（17 PB）、转码副本经 JIT 与回收后滚动约 53 PB、直播转点播 15 PB、其余素材 290 PB。朴素方案指全量标准存储三副本 ¥0.12/GB/月。

**带宽（73.0%）与存储（20.3%）合计占 93.3%——两者共同主导一切，其余四项加起来不到 7%。** 这个结论有三个直接推论：

**推论 1：任何架构决策都要先问"它对带宽和存储的影响是多少"。**
一个能把播放延迟从 500ms 优化到 400ms 的方案，如果代价是多预加载一个分片（带宽 +15%），那它是**负收益**的——+15% 带宽 = 每月多花 ¥3,456 万，而 100ms 首帧改善带来的时长提升远不值这个钱。

**推论 2：编码效率是最高杠杆的技术投入。**
带宽 ∝ 码率，且转码副本体积同样 ∝ 码率——**降码率同时省带宽和存储，是唯一的双赢杠杆**。任何降低同画质下码率的技术，收益直接乘以 ¥2.3 亿/月：

| 手段 | 码率降幅 | 月节省（带宽） | 代价 |
|------|---------|-------------|------|
| H.264 → H.265 | 35% | ¥8,064 万 | 转码算力 ×3，老设备兼容性 |
| H.265 → AV1（头部内容） | 额外 25% | ¥2,880 万 | 转码算力 ×10，需硬解支持 |
| 窄带高清（预处理+感知编码） | 20% | ¥4,608 万 | 转码算力 ×1.8，需自研 |
| 场景自适应码率（CAE） | 12% | ¥2,765 万 | 需内容复杂度分析 |
| P2P/PCDN 分担 | 22%（等效） | ¥5,069 万 | 端侧上行占用，弱网体验风险 |
| 精准预加载（少预加载 1 片） | 8% | ¥1,843 万 | 起播成功率 -0.3% |

**推论 3：存储优化是仅次于带宽的第二杠杆，值得实质投入。**
存储从 ¥6,409 万优化到 ¥1,258 万，**省 ¥5,151 万/月，相当于带宽优化收益（¥13,820 万）的 37%**。按"物理容量 × 介质单价"逐步拆解（介质单价：NVMe ¥0.040、HDD ¥0.020、归档 HDD ¥0.012，均为每 GB **物理**容量月单价）：

| 步骤 | 各层冗余与介质 | 物理容量 | 月成本 | 本步节省 |
|------|--------------|---------|-------|---------|
| 基线 | 全 NVMe + 3 副本 | 1,602 PB | ¥6,409 万 | — |
| ① 冷热分层（介质降级，仍 3 副本） | Hot NVMe / Warm HDD / Cold 归档 HDD | 1,602 PB | ¥2,211 万 | **¥4,197 万** |
| ② 冷层改 EC(16,4) | 冷层冗余 3.0x → 1.25x | 807 PB | ¥1,258 万 | **¥953 万** |
| **合计** | | | **¥1,258 万** | **¥5,151 万（降 80%）** |

最终三层分布：

| 层 | 逻辑容量 | 冗余 | 物理容量 | 介质 | 月成本 |
|----|---------|------|---------|------|-------|
| Hot (3%) | 16.0 PB | 3.00x | 48.1 PB | NVMe | ¥192 万 |
| Warm (12%) | 64.1 PB | 3.00x | 192.2 PB | HDD | ¥384 万 |
| Cold (85%) | 453.9 PB | 1.25x | 567.4 PB | 归档 HDD | ¥681 万 |

**注意介质分层（¥4,197 万）的收益是 EC（¥953 万）的 4.4 倍。** 直觉上 EC 把冗余从 3.0x 压到 1.25x 听起来收益巨大，但它只作用于冷层的**冗余系数**；而介质分层作用于 85% 数据的**单价**（NVMe ¥0.040 → 归档 HDD ¥0.012，降 70%）。**先做分层，再做 EC**——顺序反了会让人误判 EC 的价值。

另有一项独立于上表的收益：**转码副本回收 + JIT** 把副本逻辑量从 350 PB 压到 53 PB，这部分已计入转码域的账（省 ¥699 万/月），不重复计入此处。

**这与"存储只占 2.6% 所以不重要"的常见直觉相反。** 之所以容易低估，是因为人们习惯用**年增量**（569 PB）而非**稳态存量**（534 PB）估算，且容易忘记三副本冗余把**物理**占用放大 3 倍——1,602 PB 物理容量才是真正的付费对象。存储成本必须按"稳态逻辑存量 × 冗余系数 × 介质单价"算。

```
成本结构的视觉化（优化前 ¥31,559 万/月）：

  CDN 带宽    ████████████████████████████████████ 73.0%
  存储        ██████████ 20.3%
  转码算力    ██ 3.5%
  推荐算力    █ 2.0%
  审核算力    ▏0.6%
  其余        ▏0.6%
```

**核心原则：内容平台的架构优化优先级 = 成本占比排序。带宽（73%）> 存储（20%）> 转码（3.5%）> 其余，前两项合计 93%，工程资源应当按此比例投放。**

### 分级审核与灰度曝光：化解审核与分发的冲突

回到挑战 4。审核要"先审后发"（合规），分发要"抢冷启动窗口"（时效），两者在同一条链路上对撞，且失败代价不对称（漏检可能致命，延迟只是体验差）。

**错误的解法是折中**——比如"审核限时 30 秒，超时放行"。这把两个目标都做坏了：30 秒对人审不够（人审 P95 是 4 分钟），超时放行等于在漏检率上开了个后门。

**正确的解法是把"曝光量"变成连续变量，而不是"发/不发"的二元开关。**

传统模型只有两态，所以必须二选一：

```
传统二元模型：
   审核中 ──▶ 零曝光（时效损失）
   审核通过 ─▶ 全量曝光（合规安全）
```

引入受限流量池后，曝光量与审核置信度挂钩，两个目标同时满足：

```
分级曝光模型（曝光量 = f(审核置信度, 内容风险等级)）：

  机审完成(40s)
      │
      ├─ 置信度 ≥ 98% 且 低风险类目 ──▶ 【全量池】立即全量曝光
      │                                    占比 61%，零时效损失
      │
      ├─ 置信度 95-98% ─────────────▶ 【灰度池】限量 5000 次曝光
      │                                 占比 17%，边曝光边观察
      │                                 · 并行送人审
      │                                 · 用户举报率 > 阈值 → 立即撤回
      │                                 · 人审通过 → 升入全量池
      │
      ├─ 置信度 80-95% ─────────────▶ 【冷启池】限量 500 次曝光
      │                                 占比 15%，仅推给高信任用户
      │                                 （历史举报准确率高的用户）
      │                                 · 本质：用用户当"人审前置过滤器"
      │
      ├─ 置信度 < 80% ──────────────▶ 【零曝光】纯人审，通过后进灰度池
      │                                 占比 6%
      │
      └─ 高风险类目（政治/未成年） ────▶ 【零曝光】强制人审，不走灰度
                                        占比 1%，无论置信度多高
```

**为什么这个设计同时满足两个目标？**

- **时效**：61% 的内容零延迟全量曝光，17% 的内容 40 秒后即有 5000 次曝光（足以完成冷启动的初步数据收集）。加权平均"有效曝光延迟"从纯先审后发的 4 分钟降到 38 秒。
- **合规**：违规内容的**最大传播量被硬约束**。一条漏检的违规内容在灰度池最多曝光 5000 次，在冷启池最多 500 次——而不是先发后审模式下可能的百万次。漏检的**期望危害**从"不可控"变成"可计算且可接受"。

**风险敞口的量化**：

| 池 | 曝光上限 | 内容占比 | 漏检率 | 期望违规曝光量/天 |
|----|---------|---------|--------|-----------------|
| 全量池 | 无限 | 61% | 0.008% | 需靠机审精度保障 |
| 灰度池 | 5,000 | 17% | 0.9% | 1300万×17%×0.9%×5000 ≈ 受 5000 硬顶约束 |
| 冷启池 | 500 | 15% | 3.2% | 受 500 硬顶约束 |
| 零曝光 | 0 | 7% | — | 0 |

**关键设计：把"要不要发"改成"发多少"，用曝光量上限把不确定性的危害变成有界的。**

这个思路可以推广：**任何"安全 vs 效率"的二元冲突，都应该先检查能否引入一个连续的中间量把它变成可调节的谱系。** 二元决策必然要牺牲一方；连续谱系可以让双方都拿到大部分收益。

配套的表设计：

```sql
-- 内容流量池表：曝光量的硬约束在这里落地
CREATE TABLE content_traffic_pool (
    content_id       BIGINT PRIMARY KEY,
    pool_type        TINYINT NOT NULL COMMENT '0-零曝光,1-冷启池,2-灰度池,3-全量池',
    exposure_limit   INT NOT NULL DEFAULT 0 COMMENT '曝光上限，0=无限',
    exposure_used    INT NOT NULL DEFAULT 0 COMMENT '已消耗曝光（原子递增）',
    audit_confidence DECIMAL(5,4) NOT NULL DEFAULT 0 COMMENT '机审置信度',
    risk_category    TINYINT NOT NULL DEFAULT 0 COMMENT '风险类目：越高越敏感',
    report_count     INT NOT NULL DEFAULT 0 COMMENT '灰度期间举报数',
    report_rate      DECIMAL(6,5) NOT NULL DEFAULT 0 COMMENT '举报率（撤回依据）',
    promoted_at      DATETIME DEFAULT NULL COMMENT '升池时间',
    withdrawn_at     DATETIME DEFAULT NULL COMMENT '撤回时间',
    updated_at       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    INDEX idx_pool_used (pool_type, exposure_used),
    INDEX idx_report (report_rate DESC),
    INDEX idx_pending_promote (pool_type, promoted_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='内容流量池与曝光配额表';
```

曝光配额的扣减必须是原子的，否则灰度池的 5000 次上限会在高并发下被击穿：

```python
class TrafficPoolGuard:
    """流量池曝光配额守卫——保证灰度内容的曝光量硬上限不被击穿"""

    # 各池的曝光上限
    POOL_LIMITS = {
        0: 0,          # 零曝光
        1: 500,        # 冷启池
        2: 5000,       # 灰度池
        3: -1,         # 全量池，无限
    }
    REPORT_RATE_WITHDRAW = 0.002   # 举报率超 0.2% 立即撤回
    MIN_SAMPLE_FOR_WITHDRAW = 200  # 少于 200 次曝光不做撤回判断（样本不足）

    def __init__(self, redis_client, mysql_client, config):
        self.redis = redis_client
        self.mysql = mysql_client
        self.batch_flush_size = config.get('batch_flush_size', 50)

    def try_acquire(self, content_id, pool_type, count=1):
        """
        尝试为一次曝光申请配额。返回 True 表示允许曝光。
        全量池直接放行，不走 Redis（避免给 61% 的内容加无谓开销）。
        """
        # 1. 全量池无限制，快速路径直接放行
        limit = self.POOL_LIMITS.get(pool_type, 0)
        if limit == -1:
            return True
        if limit == 0:
            return False

        # 2. 受限池走 Redis 原子递增 + 上限判断
        key = f"pool:quota:{content_id}"
        used = self.redis.incrby(key, count)
        if used == count:
            # 首次创建，设置 TTL（灰度期 24 小时后自动失效）
            self.redis.expire(key, 86400)

        if used > limit:
            # 超限：回滚本次递增，并触发升池/降池决策
            self.redis.decrby(key, count)
            self._on_quota_exhausted(content_id, pool_type)
            return False

        return True

    def record_report(self, content_id):
        """记录一次举报，达到阈值立即撤回（不等人审）"""
        # 1. 举报计数
        report_key = f"pool:report:{content_id}"
        reports = self.redis.incr(report_key)
        self.redis.expire(report_key, 86400)

        # 2. 取当前曝光量算举报率
        used = int(self.redis.get(f"pool:quota:{content_id}") or 0)
        if used < self.MIN_SAMPLE_FOR_WITHDRAW:
            return  # 样本不足，不做判断（避免前几个用户的误举报导致误撤）

        # 3. 举报率超阈值 → 立即撤回并转人审
        if reports / used > self.REPORT_RATE_WITHDRAW:
            self._withdraw(content_id, reason=f"举报率{reports/used:.4f}超阈值")

    def _on_quota_exhausted(self, content_id, pool_type):
        """配额耗尽：说明内容跑完了灰度期，等人审结论决定升池还是驳回"""
        # 配额耗尽本身不是坏事——它意味着内容成功完成了灰度观察
        # 此时把内容挂到"待升池"队列，人审通过后升入全量池
        self.redis.zadd("pool:pending_promote", {str(content_id): pool_type})

    def _withdraw(self, content_id, reason):
        """撤回：立即停止曝光 + 转人审高优队列"""
        # 1. 配额清零，后续 try_acquire 全部拒绝
        self.redis.set(f"pool:quota:{content_id}", 10 ** 9)
        # 2. 落库留痕
        self.mysql.execute(
            "UPDATE content_traffic_pool SET pool_type=0, withdrawn_at=NOW() "
            "WHERE content_id=%s", (content_id,))
        # 3. 插入人审最高优队列（灰度撤回的内容风险更高，优先处理）
        self.redis.zadd("audit:manual:urgent", {str(content_id): 0})
```

## 常见陷阱（深度分析）

### 陷阱 1：图文与视频各建一套中台

**后果：** 四套账号体系、四套关系链、四套审核、四套推荐、四套商业化。工程成本翻 4 倍是次要的，致命的是**用户兴趣画像被割裂**——用户在长视频区追科技纪录片、在短视频区刷美食，两份画像互不知情。实测这种割裂导致推荐 CTR 相对统一画像低 18%，人均时长低 23%。更隐蔽的代价是**互动数据无法互通**：用户关注的创作者在另一个形态下发内容，用户收不到通知。

**解决方案：** 按"内容 / 媒体"两层切分而非按形态切分。统一层（content、content_stat、标签、Embedding、互动、治理、商业化）所有形态共用一套；形态差异下沉到 `content_ext_*` 与 `media_*`。判据：**下游域（推荐/搜索/商业化/数据）应当只依赖统一层，对形态无感知。** 如果推荐系统里出现了 `if content_type == VIDEO` 的业务分支，说明抽象边界画错了。

### 陷阱 2：把审核放进发布的同步链路

**后果：** 创作者点"发布"后界面转圈等待。机审 40 秒还能忍，一旦落入人审队列（22% 的概率）就要等 4 分钟，超时率极高。更糟的是审核系统抖动会直接表现为"发布失败"，创作者会重复提交——实测审核延迟从 40s 涨到 90s 时，重复提交率从 0.3% 飙到 11%，反过来把审核队列压力再放大一倍，形成正反馈崩溃。

**具体数据：** 某次审核集群故障，同步链路设计下发布成功率从 99.6% 跌到 41%，且故障恢复后队列积压 280 万条，需 6 小时消化。

**解决方案：** 发布链路只做三件事——落库、落对象存储、发事件，然后**立即返回成功**。审核、转码、索引全部异步。创作者看到的是"已提交，处理中"，配合明确的进度反馈（"正在转码 60%"→"正在审核"→"已发布"）。审核系统故障时，内容停留在 `auditing` 状态，用户体验是"处理慢"而不是"发布失败"，且故障恢复后自动继续，无需重新提交。

### 陷阱 3：预转码全部档位

**后果：** 一条视频转 6 档 ABR，但内容消费的长尾极端不均——实测 1% 的内容占 80% 的播放，而 90% 的内容 7 日播放量 < 100 次。给这 90% 的长尾内容转全 6 档，等于**为几乎不会发生的播放预付了转码算力和存储成本**。

**具体数据：** 全档位预转码年产生 350 PB 转码副本，其中 298 PB（85%）的档位 7 日播放为 0。浪费的存储成本 ¥699 万/月，浪费的转码算力成本 ¥680 万/月。

**解决方案：** 分层转码策略——
- **预转码**：只出 2 档（720P 主力档 + 360P 兜底档），覆盖 88% 的实际播放
- **JIT 按需转码**：其余档位（1080P/2K/4K/AV1）在首次被请求时实时生成，生成期间用邻近档位兜底（用户拉 1080P 时先给 720P，30 秒后切到 1080P）
- **热度晋升**：7 日播放 > 1 万的内容自动补齐全档位 + AV1 编码（这批内容占播放量的 80%，值得精细编码）

实算：转码算力从 ¥1,120 万/月降到 ¥310 万/月，存储副本从 350 PB/年降到 53 PB/年。

### 陷阱 4：绑定单一 CDN 厂商

**后果：** 三重风险同时暴露。**成本风险**：失去议价能力，续约时单价涨 20% 只能接受，年多支出 ¥5.5 亿。**可用性风险**：单一厂商区域故障直接导致该区域播放不可用——CDN 厂商的区域级故障年均发生 2-4 次，每次 20-90 分钟。**质量风险**：没有厂商能在所有地区都最优，绑定单一厂商等于在其弱势地区永久承受劣质体验。

**解决方案：** 至少 3 家商业 CDN + 自建边缘节点覆盖头部区域，按"质量分 × 成本权重"实时调度。关键是**调度权必须在自己手里**（自建 DNS/HTTPDNS + 客户端多地址下发），而不是靠 CNAME 交给某一家。同时保留**分钟级全量切换能力**并每月演练——没演练过的切换能力在真实故障时必然失效。

### 陷阱 5：允许多个域直接写 content.status

**后果：** 转码域写 `processing→published`，审核域写 `auditing→rejected`，运营后台写 `published→offline`，创作者删除写 `→deleted`。四个写方并发时状态机跃迁乱序：审核驳回后转码完成又把状态改回 `published`，一条违规内容就这样上线了。

**真实案例：** 某平台曾因转码回调与审核驳回竞争，导致 1.2 万条已驳回内容被转码回调重新置为已发布，其中含 37 条严重违规内容，公开曝光 4 小时。

**解决方案：** **状态单写方原则**——`content.status` 只有编排层（Orchestrator）能写，其他域一律发事件。编排层内部对同一 content_id 串行处理（按 content_id 哈希到固定分区，单分区单线程消费），并做状态跃迁合法性校验：`auditing→published` 合法，`rejected→published` 非法直接丢弃并告警。配合 `content_state_log` 的 `uk_event` 唯一键做幂等，重复事件不会重复跃迁。

### 陷阱 6：域边界按技术分层切，而不是按业务能力切

**后果：** 切出"接入层团队""服务层团队""数据层团队"这种横向切分。任何一个业务需求（比如"给长视频加章节功能"）都要三个团队协作，沟通成本极高，且没有任何团队对"章节功能好不好用"负最终责任。实测这种切分下需求平均交付周期是纵向切分的 2.8 倍。

**解决方案：** 按业务能力纵向切域（本文的十四域），每个域自己拥有从接口到存储的完整栈。横向的只保留真正与业务无关的**平台基础域**（网关、Mesh、可观测性、CI/CD）。判据：**一个典型业务需求应该能在单个域内完成 80% 的工作量。** 如果大多数需求都要跨 3 个以上域，说明域边界切错了。

### 陷阱 7：把"下架"实现成一次同步调用

**后果：** 数据库状态改成 `offline` 就认为下架完成，但 CDN 边缘缓存仍有副本、已签发的播放地址仍然有效、用户设备上的离线文件仍能播放。表现为"后台显示已下架，但用户还能看"。在版权诉讼或监管检查中这是直接的败诉/处罚证据。

**解决方案：** 把下架建模为**有状态、可重试、可验证的工作流**（见场景 ⑤ 的 `content_takedown_task`）。十个清理步骤各自记录状态，任一失败自动重试。最关键的是最后的 `verified_at`——用**主动探测**（从多个地区的探测节点实际尝试播放）确认真的播不了，才算下架完成。没有主动验证的下架流程都是自欺欺人。

### 场景 1：转码集群故障导致投稿链路全面积压

**场景描述：** GPU 转码集群所在可用区网络分区，320 张 A10 卡失联，占总转码算力的 45%。此时正值晚间投稿高峰（每秒 480 条投稿）。剩余算力只能处理 55% 的流量，队列以每秒 216 条的速度积压。15 分钟后积压 19 万条，创作者端表现为"处理中"状态长时间不变，客服工单量激增。若不干预，2 小时后积压将达 155 万条，且高峰过后需 9 小时才能消化。

**根因分析：** 转码是投稿链路上唯一的重资源串行环节，且其算力无法秒级弹性（GPU 实例创建 + 镜像拉取 + 模型加载需 5-8 分钟）。队列积压的危险在于它是**正反馈**：创作者看到长时间无进展会重复提交（实测重复率随等待时长指数上升），进一步加剧积压。

**检测机制：**

```python
class TranscodeQueueMonitor:
    """转码队列健康度监控——积压的早期识别与分级响应"""

    # 积压分级阈值（按预计消化时长而非绝对条数，更贴近业务感受）
    DRAIN_TIME_WARNING = 300      # 预计 5 分钟消化完 → 告警
    DRAIN_TIME_CRITICAL = 1800    # 预计 30 分钟 → 触发降级
    DRAIN_TIME_EMERGENCY = 7200   # 预计 2 小时 → 触发熔断

    def __init__(self, redis_client, k8s_client, config):
        self.redis = redis_client
        self.k8s = k8s_client
        self.alert = config['alert_service']

    def check(self):
        """每 15 秒执行一次，返回当前应采取的动作等级"""
        # 1. 采集队列深度与实际消费速率
        backlog = self.redis.zcard("transcode:queue:pending")
        throughput = self._get_throughput_per_sec()   # 近 60s 滑动窗口

        if throughput <= 0:
            self.alert.fire("transcode_throughput_zero", severity="P0")
            return "EMERGENCY"

        # 2. 关键指标是"预计消化时长"，不是绝对积压数
        #    5 万条积压在 500/s 吞吐下只需 100 秒，不算事故
        #    5 万条积压在 50/s 吞吐下需 1000 秒，是事故
        drain_time = backlog / throughput

        # 3. 分级响应
        if drain_time > self.DRAIN_TIME_EMERGENCY:
            return "EMERGENCY"
        elif drain_time > self.DRAIN_TIME_CRITICAL:
            return "CRITICAL"
        elif drain_time > self.DRAIN_TIME_WARNING:
            return "WARNING"
        return "OK"

    def _get_throughput_per_sec(self):
        """近 60 秒实际完成的转码任务数 / 60"""
        now_bucket = self.redis.get("transcode:completed:minute") or 0
        return int(now_bucket) / 60.0
```

**解决方案：**

```python
class TranscodeDegradeController:
    """转码降级控制器——算力不足时的分级降级，保证链路不崩"""

    def __init__(self, redis_client, k8s_client, config):
        self.redis = redis_client
        self.k8s = k8s_client
        self.config = config

    def apply(self, level):
        """按告警等级施加降级策略"""
        if level == "WARNING":
            self._level1_reduce_ladder()
        elif level == "CRITICAL":
            self._level2_priority_only()
        elif level == "EMERGENCY":
            self._level3_proxy_only()

    def _level1_reduce_ladder(self):
        """一级降级：ABR 档位从 6 档砍到 3 档，算力立降 50%"""
        # 只出 360P/720P/1080P，2K/4K/AV1 全部推迟到 JIT
        self.redis.set("transcode:config:ladder", "360,720,1080")
        # 效果：单条视频转码耗时降 50%，吞吐翻倍
        # 代价：高清档位首播时需 JIT 生成，首帧 +2s（仅影响 4% 请求）

    def _level2_priority_only(self):
        """二级降级：只转高优内容，长尾内容延后"""
        self.redis.set("transcode:config:ladder", "360,720")
        # 按创作者等级 + 预估播放量分优先级
        # 头部创作者(占投稿 3%，占播放 52%) → 正常转
        # 长尾创作者 → 进低优队列，高峰过后再处理
        self.redis.set("transcode:config:min_priority", "2")
        # 同时扩容：GPU 不够时降级用 CPU 集群兜底（慢但有容量）
        self.k8s.scale("transcode-cpu-worker", replicas=800)

    def _level3_proxy_only(self):
        """三级熔断：只出代理片，保证审核链路不断"""
        # 关键取舍：此时放弃"可播放"，但保住"可审核"
        # 代理片(360P极速档)单条只需 8 秒，吞吐提升 12 倍
        # 内容进入 auditing 状态，审核完成后标记为"待补转码"
        self.redis.set("transcode:config:ladder", "proxy_only")
        self.redis.set("transcode:config:defer_full", "1")

        # 同时对创作者端做明确的期望管理——这是防止重复提交的关键
        self.redis.set("ingest:notice",
                       "当前投稿量较大，视频处理预计延迟 30 分钟，"
                       "已提交内容无需重复操作")

    def recover(self):
        """恢复：分阶段回放积压，避免恢复瞬间打爆下游"""
        # 1. 先恢复正常档位配置
        self.redis.delete("transcode:config:ladder")
        self.redis.delete("transcode:config:min_priority")

        # 2. 积压任务限速回放（关键！全速回放会打爆审核与索引）
        #    按下游审核能力的 70% 限速
        audit_capacity = int(self.redis.get("audit:capacity_per_sec") or 200)
        self.redis.set("transcode:replay:rate_limit", int(audit_capacity * 0.7))

        # 3. 补转码：把降级期间只出了代理片的内容重新入队（低优）
        self.redis.zunionstore(
            "transcode:queue:low",
            ["transcode:queue:low", "transcode:deferred:full"])
```

**降级效果对比：**

| 降级档位 | 算力需求 | 吞吐倍数 | 可播放性 | 可审核性 | 用户可感知影响 |
|---------|---------|---------|---------|---------|--------------|
| 正常（6 档） | 100% | 1.0x | 全档位 | 是 | 无 |
| 一级（3 档） | 50% | 2.0x | 主力档位 | 是 | 4% 请求首帧 +2s |
| 二级（2 档 + 优先级） | 28% | 3.6x | 主力档位 | 是 | 长尾内容延迟 30min |
| 三级（仅代理片） | 8% | 12.0x | **暂不可播** | **是** | 内容延迟发布 |

**关键设计：三级熔断放弃"可播放"但保住"可审核"——因为审核是合规底线，可播放只是体验。降级的优先级排序必须按"违反后的代价"而非"用户感知强度"。**

### 场景 2：审核系统故障时的两难降级

**场景描述：** 机审模型服务因一次模型版本发布引入的内存泄漏，在运行 40 分钟后 OOM 崩溃，且自动重启后 40 分钟再次崩溃，形成崩溃循环。此时投稿以每秒 480 条持续到来，无法完成机审判定。

**根因分析：** 审核是发布链路上的**合规闸门**，它的故障构成一个真正的两难：全部卡住会导致所有创作者无法发布（业务停摆）；全部放行会导致违规内容无审核上线（监管风险，可能致命）。这不是技术问题，而是需要预先明确的**业务决策**。

**解决方案：** 预先定义"审核不可用"时的分类降级矩阵，按内容风险分层处理，而不是全局一刀切。

```python
class AuditFailureDegradeStrategy:
    """审核系统不可用时的分类降级——按风险分层，而非全局一刀切"""

    # 高风险类目：审核不可用时一律卡住，绝不放行
    HIGH_RISK_CATEGORIES = {
        'politics', 'minor_related', 'gambling', 'drug', 'weapon'
    }
    # 创作者信任分阈值：高于此值的历史清白创作者可走信任放行
    TRUST_SCORE_THRESHOLD = 850
    # 信任放行的曝光上限（即使放行也限流，把风险敞口做成有界的）
    TRUST_EXPOSURE_LIMIT = 2000

    def __init__(self, redis_client, mysql_client, config):
        self.redis = redis_client
        self.mysql = mysql_client

    def decide(self, content):
        """
        审核系统不可用时，决定单条内容的处置。
        返回 (动作, 曝光上限, 原因)
        """
        # 1. 高风险类目一律卡住——这条不可协商
        if content['category'] in self.HIGH_RISK_CATEGORIES:
            return ('HOLD', 0, '高风险类目，审核不可用时强制卡住')

        # 2. 有历史违规的创作者一律卡住
        trust = self._get_creator_trust(content['author_id'])
        if trust['violation_count_90d'] > 0:
            return ('HOLD', 0, f"作者近90天有{trust['violation_count_90d']}次违规")

        # 3. 高信任创作者：限量放行（信任但验证）
        #    依据：信任分 >850 的创作者历史违规率 0.003%，
        #    远低于机审漏检率 0.008%——放行他们比机审更安全
        if trust['score'] >= self.TRUST_SCORE_THRESHOLD:
            return ('RELEASE_LIMITED', self.TRUST_EXPOSURE_LIMIT,
                    f"信任分{trust['score']}，限量放行")

        # 4. 其余内容：卡住等审核恢复
        return ('HOLD', 0, '普通创作者，等审核恢复')

    def _get_creator_trust(self, author_id):
        """读创作者信任画像（审核域故障时此数据仍可用——独立存储）"""
        cached = self.redis.hgetall(f"creator:trust:{author_id}")
        if cached:
            return {
                'score': int(cached.get(b'score', 0)),
                'violation_count_90d': int(cached.get(b'violations', 0)),
            }
        # 缓存未命中时保守处理：视为低信任
        return {'score': 0, 'violation_count_90d': 0}

    def estimate_impact(self):
        """量化降级影响，供值班决策——必须能回答'放行了多少风险'"""
        stats = self.mysql.query("""
            SELECT
                COUNT(*) AS total,
                SUM(CASE WHEN action='HOLD' THEN 1 ELSE 0 END) AS held,
                SUM(CASE WHEN action='RELEASE_LIMITED' THEN 1 ELSE 0 END) AS released
            FROM audit_degrade_log
            WHERE created_at > DATE_SUB(NOW(), INTERVAL 1 HOUR)
        """)
        # 期望违规曝光量 = 放行数 × 高信任创作者违规率 × 曝光上限
        expected_violation_exposure = (
            stats['released'] * 0.00003 * self.TRUST_EXPOSURE_LIMIT)
        return {
            'held_count': stats['held'],
            'released_count': stats['released'],
            'expected_violation_exposure': expected_violation_exposure,
        }
```

**降级决策的影响量化（每小时 172 万条投稿）：**

| 处置 | 占比 | 条数 | 风险敞口 | 业务影响 |
|------|------|------|---------|---------|
| 高风险类目卡住 | 1% | 1.7 万 | 0 | 该类创作者无法发布 |
| 有违规史卡住 | 6% | 10.3 万 | 0 | 影响可接受 |
| 高信任限量放行 | 34% | 58.5 万 | 期望违规曝光 3.5 万次 | 无感知 |
| 普通创作者卡住 | 59% | 101.5 万 | 0 | 延迟发布 |

**关键设计：降级不是"全放"或"全卡"，而是用创作者信任分做风险分层——把 34% 的低风险内容放行以维持业务，同时把风险敞口压缩到可计算的 3.5 万次曝光。**

### 场景 3：带宽成本单日超预算 3 倍

**场景描述：** 一场未预期的头部直播（明星突然开播）叠加一条爆款视频，单日出口流量从 96 PB 涨到 290 PB。按 ¥0.05/GB 计，单日 CDN 成本从 ¥480 万涨到 ¥1,450 万，超出月度预算的 30%。若持续 3 天，当月带宽预算将完全耗尽。

**根因分析：** 带宽是唯一"技术上无上限、财务上有上限"的资源。CDN 会自动承接所有流量而不会拒绝——**技术系统不会告诉你钱花超了**。没有成本熔断机制的平台，会在财务上被动接受任意金额的账单。

**检测机制：**

```python
class BandwidthCostGuard:
    """带宽成本实时守卫——把财务约束变成技术约束"""

    def __init__(self, redis_client, config):
        self.redis = redis_client
        self.monthly_budget = config['monthly_bandwidth_budget']  # 元
        self.unit_price = config['cdn_unit_price_per_gb']         # 元/GB
        self.alert = config['alert_service']

    def check_and_act(self):
        """每分钟执行：预测本月总支出，超预算则分档降级"""
        # 1. 本月已消耗
        spent = self._month_to_date_cost()
        # 2. 按近 1 小时速率外推本月剩余天数
        current_rate_per_day = self._current_daily_rate()
        days_left = self._days_left_in_month()
        projected = spent + current_rate_per_day * days_left

        ratio = projected / self.monthly_budget

        # 3. 分档响应——关键是给出可量化的影响，让决策者能判断
        if ratio > 1.30:
            self._set_degrade_level(2, projected, ratio)
            self.alert.fire("bandwidth_budget_critical", severity="P0",
                            detail=f"预测超支{(ratio - 1) * 100:.0f}%")
        elif ratio > 1.10:
            self._set_degrade_level(1, projected, ratio)
            self.alert.fire("bandwidth_budget_warning", severity="P1")
        elif ratio < 0.95:
            self._set_degrade_level(0, projected, ratio)

    def _set_degrade_level(self, level, projected, ratio):
        """设置全局降级档位——播放服务读此配置决定默认清晰度与预加载策略"""
        current = int(self.redis.get("bandwidth:degrade_level") or 0)
        if current == level:
            return
        # 降级需要人工确认（影响用户体验），升级（恢复）可自动
        if level > current:
            self.redis.setex("bandwidth:degrade_pending", 3600, level)
            # 推送到值班群，等一键确认
        else:
            self.redis.set("bandwidth:degrade_level", level)

    def _month_to_date_cost(self):
        traffic_gb = float(self.redis.get("bandwidth:mtd_traffic_gb") or 0)
        return traffic_gb * self.unit_price

    def _current_daily_rate(self):
        """近 1 小时流量 × 24，作为日速率估计"""
        hourly_gb = float(self.redis.get("bandwidth:last_hour_gb") or 0)
        return hourly_gb * 24 * self.unit_price
```

**解决方案：** 三档降级开关（见场景 ④），配合以下三条硬约束：

| 约束 | 实现 | 效果 |
|------|------|------|
| 单场直播带宽上限 | 超过阈值自动降默认档位，且需审批才能放开 | 防止单场直播打穿预算 |
| 单条内容带宽上限 | 爆款内容超过 X PB/日后强制开启 P2P + 降默认档 | 长尾成本可控 |
| 非会员清晰度上限 | 预算紧张时非会员最高 720P | 省 24% 带宽，且推动会员转化 |

**关键设计：财务约束必须以技术形式落地为可执行的开关，否则它只是一个事后才发现被违反的数字。**

## 延伸思考

- **如果内容形态从 4 种扩展到 8 种**（增加播客、图集、互动视频、VR），本文的两层抽象还成立吗？`content_ext_*` 表的数量增长会不会让编排层变成一个巨大的 switch？
- **如果平台要出海**，域划分需要怎么调整？内容治理的规则差异（各国监管口径不同）应该作为域内配置还是拆成独立的区域化域？
- **带宽成本占 73%**，如果自建 CDN 能把单价从 ¥0.05/GB 降到 ¥0.018/GB，需要多大的资本开支和多长的回本周期？临界点在哪个流量规模？
- **分级曝光模型**把"发/不发"变成"发多少"。这个"把二元决策变成连续谱系"的思路还能用在平台的哪些地方？（提示：账号封禁、创作者处罚、推荐降权）
- **十四域 742 人**的组织，域间的结构性冲突用联合 KPI 治理。如果公司规模只有 80 人，域划分应该怎么合并？哪些域可以先不独立？

## 内容发布编排器完整实现

编排层是全平台的状态单写方，也是"统一 + 差异"落地的关键组件。它消费各域事件，做状态跃迁决策，并按形态分派不同的发布策略。

```python
from enum import IntEnum


class ContentStatus(IntEnum):
    DRAFT = 0
    PROCESSING = 1
    AUDITING = 2
    PUBLISHED = 3
    REJECTED = 4
    OFFLINE = 5
    DELETED = 6
    FAILED = 7


class ContentType(IntEnum):
    ARTICLE = 1
    SHORT_VIDEO = 2
    LONG_VIDEO = 3
    LIVE = 4
    AUDIO = 5


# 合法跃迁白名单：任何不在此表中的跃迁一律拒绝并告警
LEGAL_TRANSITIONS = {
    ContentStatus.DRAFT:      {ContentStatus.PROCESSING, ContentStatus.AUDITING,
                               ContentStatus.DELETED},
    ContentStatus.PROCESSING: {ContentStatus.AUDITING, ContentStatus.PUBLISHED,
                               ContentStatus.FAILED},
    ContentStatus.AUDITING:   {ContentStatus.PUBLISHED, ContentStatus.REJECTED},
    ContentStatus.PUBLISHED:  {ContentStatus.OFFLINE, ContentStatus.DELETED},
    ContentStatus.REJECTED:   {ContentStatus.AUDITING, ContentStatus.DELETED},
    ContentStatus.OFFLINE:    {ContentStatus.PUBLISHED, ContentStatus.DELETED},
    ContentStatus.FAILED:     {ContentStatus.PROCESSING, ContentStatus.DELETED},
    ContentStatus.DELETED:    set(),   # 终态
}

# 各形态的发布策略：决定是否需要转码、审核时机、是否走灰度
PUBLISH_POLICY = {
    ContentType.ARTICLE:     {'need_transcode': False, 'audit_before_publish': True,
                              'allow_gray': True},
    ContentType.SHORT_VIDEO: {'need_transcode': True,  'audit_before_publish': False,
                              'allow_gray': True},
    ContentType.LONG_VIDEO:  {'need_transcode': True,  'audit_before_publish': True,
                              'allow_gray': False},
    ContentType.LIVE:        {'need_transcode': True,  'audit_before_publish': False,
                              'allow_gray': False},
    ContentType.AUDIO:       {'need_transcode': True,  'audit_before_publish': True,
                              'allow_gray': True},
}


class ContentOrchestrator:
    """内容发布编排器——全平台 content.status 的唯一写方

    部署方式：按 content_id 哈希分区消费，单分区单线程，保证同一内容串行处理。
    这是避免多写方竞争（陷阱 5）的结构性保障，不依赖分布式锁。
    """

    def __init__(self, mysql_client, redis_client, event_bus, config):
        self.mysql = mysql_client
        self.redis = redis_client
        self.bus = event_bus
        self.traffic_pool = config['traffic_pool_guard']
        self.alert = config['alert_service']

    # ── 事件入口 ──

    def on_content_submitted(self, event):
        """域3 投稿完成 → 决定进转码还是直接进审核"""
        content = self._load(event['content_id'])
        policy = PUBLISH_POLICY[ContentType(content['content_type'])]

        if policy['need_transcode']:
            # 视频/音频：先转码
            self._transition(content, ContentStatus.PROCESSING,
                             source='ingest', event_id=event['event_id'])
            self.bus.publish('transcode.request', {
                'content_id': content['content_id'],
                'asset_id': event['asset_id'],
                'priority': self._calc_priority(content),
                # 关键：要求先出代理片，让审核可以尽早开始
                'proxy_first': True,
            })
        else:
            # 图文：无转码，直接送审
            self._transition(content, ContentStatus.AUDITING,
                             source='ingest', event_id=event['event_id'])
            self._request_audit(content, media_ref=None)

    def on_media_proxy_ready(self, event):
        """域4 代理片就绪 → 立即启动审核（不等全档位转码完成）

        这是把 14min 转码 + 6min 审核的串行压成并行的关键钩子。
        """
        content = self._load(event['content_id'])
        if content['status'] != ContentStatus.PROCESSING:
            return  # 状态已变（可能已被删除），忽略

        # 注意：此处不做状态跃迁——内容仍在 PROCESSING（转码未完）
        # 审核作为并行分支启动，其结果暂存，等 MediaReady 到达后合并判断
        self._request_audit(content, media_ref=event['proxy_url'])

    def on_media_ready(self, event):
        """域4 全档位转码完成 → 检查审核结论是否已到齐"""
        content = self._load(event['content_id'])
        policy = PUBLISH_POLICY[ContentType(content['content_type'])]

        # 1. 落库转码产物信息
        self._save_variants(content['content_id'], event['variants'])

        # 2. 短视频策略：转码完成即可发布，审核并行（先发后审）
        if not policy['audit_before_publish']:
            self._try_publish(content, event_id=event['event_id'])
            return

        # 3. 长视频策略：必须等审核通过（先审后发）
        audit = self._get_audit_result(content['content_id'])
        if audit is None:
            # 审核还没出结论，跃迁到 AUDITING 等待
            self._transition(content, ContentStatus.AUDITING,
                             source='transcode', event_id=event['event_id'])
        else:
            self._apply_audit_result(content, audit, event['event_id'])

    def on_audit_completed(self, event):
        """域6 审核出结论 → 决定发布/驳回/进灰度"""
        content = self._load(event['content_id'])
        self._save_audit_result(event)

        # 转码尚未完成时，先暂存审核结论，等 MediaReady 再合并判断
        if content['status'] == ContentStatus.PROCESSING:
            return

        self._apply_audit_result(content, event, event['event_id'])

    # ── 内部决策 ──

    def _apply_audit_result(self, content, audit, event_id):
        """把审核结论翻译成状态跃迁 + 流量池分配"""
        if audit['verdict'] == 'REJECTED':
            self._transition(content, ContentStatus.REJECTED,
                             source='audit', event_id=event_id,
                             reason=audit.get('reason', ''))
            self.bus.publish('content.rejected', {
                'content_id': content['content_id'],
                'reason': audit.get('reason', ''),
            })
            return

        if audit['verdict'] == 'NEED_MANUAL':
            # 需人审：内容留在 AUDITING，但按置信度分配受限曝光
            policy = PUBLISH_POLICY[ContentType(content['content_type'])]
            if policy['allow_gray']:
                self._assign_traffic_pool(content, audit['confidence'])
                self._try_publish(content, event_id=event_id)
            # 不允许灰度的形态（长视频/直播）继续等人审
            return

        # 通过：分配流量池并发布
        self._assign_traffic_pool(content, audit['confidence'])
        self._try_publish(content, event_id=event_id)

    def _assign_traffic_pool(self, content, confidence):
        """按审核置信度与风险类目分配曝光配额（分级曝光模型的落地）"""
        risk = self._get_risk_category(content['category_id'])

        if risk >= 4:                      # 高风险类目：强制零曝光等人审
            pool_type, limit = 0, 0
        elif confidence >= 0.98:
            pool_type, limit = 3, 0        # 全量池，无上限
        elif confidence >= 0.95:
            pool_type, limit = 2, 5000     # 灰度池
        elif confidence >= 0.80:
            pool_type, limit = 1, 500      # 冷启池
        else:
            pool_type, limit = 0, 0        # 零曝光

        self.mysql.execute("""
            INSERT INTO content_traffic_pool
                (content_id, pool_type, exposure_limit, audit_confidence, risk_category)
            VALUES (%s, %s, %s, %s, %s)
            ON DUPLICATE KEY UPDATE
                pool_type=VALUES(pool_type),
                exposure_limit=VALUES(exposure_limit),
                audit_confidence=VALUES(audit_confidence)
        """, (content['content_id'], pool_type, limit, confidence, risk))

    def _try_publish(self, content, event_id):
        """发布：处理定时发布，并触发下游索引与预热"""
        # 定时发布：未到时间则挂到延迟队列
        if content['publish_time'] and content['publish_time'] > self._now():
            self.redis.zadd("content:scheduled",
                            {str(content['content_id']):
                             content['publish_time'].timestamp()})
            return

        if not self._transition(content, ContentStatus.PUBLISHED,
                                source='orchestrator', event_id=event_id):
            return

        # 触发下游（全部异步，发布不等待它们）
        self.bus.publish('content.published', {
            'content_id': content['content_id'],
            'author_id': content['author_id'],
            'content_type': content['content_type'],
            'category_id': content['category_id'],
        })

    def _transition(self, content, to_status, source, event_id, reason=''):
        """状态跃迁：合法性校验 + 幂等 + 留痕。返回是否实际发生跃迁"""
        from_status = ContentStatus(content['status'])

        # 1. 合法性校验——拒绝非法跃迁（如 REJECTED → PUBLISHED）
        if to_status not in LEGAL_TRANSITIONS.get(from_status, set()):
            self.alert.fire("illegal_state_transition", severity="P1", detail={
                'content_id': content['content_id'],
                'from': from_status.name, 'to': to_status.name, 'source': source,
            })
            return False

        # 2. 幂等写日志：唯一键冲突说明此事件已处理过
        try:
            cost_ms = self._calc_stay_duration(content)
            self.mysql.execute("""
                INSERT INTO content_state_log
                    (content_id, from_status, to_status, trigger_source,
                     trigger_event_id, reason, cost_ms)
                VALUES (%s, %s, %s, %s, %s, %s, %s)
            """, (content['content_id'], int(from_status), int(to_status),
                  source, event_id, reason, cost_ms))
        except Exception as e:
            if 'Duplicate entry' in str(e):
                return False    # 事件重投，已处理，静默跳过
            raise

        # 3. 更新主表（带 from_status 条件，防并发覆盖）
        affected = self.mysql.execute("""
            UPDATE content SET status=%s, updated_at=NOW()
            WHERE content_id=%s AND status=%s
        """, (int(to_status), content['content_id'], int(from_status)))

        return affected > 0

    def _calc_priority(self, content):
        """转码优先级：头部创作者与短内容优先（短内容转得快，先放行提升整体吞吐）"""
        author_level = self._get_author_level(content['author_id'])
        if author_level >= 5:
            return 1                                   # 头部创作者最高优
        if content['content_type'] == ContentType.SHORT_VIDEO:
            return 2
        return 3
```

## 异常场景补充

### 场景：编排器消费分区倾斜导致部分内容卡住

```
触发：某个 content_id 哈希分区上有一条巨型长视频（8 小时 4K）的转码事件
      → 该分区单线程处理时被长事务阻塞 → 同分区其他内容全部排队
检测：
  1. 各分区消费延迟的方差监控：max(lag) / avg(lag) > 5 告警
  2. content 表 status=PROCESSING 且 updated_at 超 40 分钟未变的条数
  3. content_state_log 的 cost_ms P99 按分区分组，识别异常分区
处理：
  1. 编排器内部把"重操作"（写多张表、调外部服务）移出主消费线程，
     主线程只做状态跃迁与事件转发
  2. 单条消息处理超 2 秒即打点告警，超 10 秒强制超时并重投
  3. 临时扩分区数（Kafka 分区只能增不能减，需提前规划冗余）
预防：主消费线程只做轻量状态机操作 + 单消息处理超时熔断 + 分区数预留 3 倍冗余
```

### 场景：定时发布的内容到点未发布

```
触发：定时发布依赖 Redis ZSET 延迟队列 → Redis 主从切换丢失未持久化的 ZADD
      → 内容永久停留在待发布状态，创作者以为已发布
检测：
  1. 对账任务每 5 分钟扫 content 表：publish_time < NOW() 且 status != PUBLISHED
  2. Redis ZSET 成员数与 DB 中待发布内容数的差值监控
  3. 创作者侧"预约发布"列表与实际发布状态的一致性巡检
处理：
  1. 立即用对账结果补发（幂等，重复发布无副作用）
  2. 定时发布改为"DB 为准 + Redis 为加速"：DB 存 publish_time 作为
     唯一事实来源，Redis ZSET 只是性能优化，丢了可从 DB 重建
  3. 重建 ZSET：扫未来 24 小时内待发布内容重新 ZADD
预防：DB 为事实来源 + Redis 仅作加速 + 5 分钟对账补偿 + 到点未发主动告警
```

### 场景：内容删除后推荐仍在下发

```
触发：用户删除内容 → content.status=DELETED，但推荐内容池是内存索引
      → 已构建的召回结果仍含该 content_id → 用户点击后 404
检测：
  1. 播放接口 404 率突增（正常 < 0.02%）
  2. 曝光日志中出现 status != PUBLISHED 的 content_id
  3. 内容池与 DB 的定期一致性抽样比对
处理：
  1. 删除事件走高优通道广播到所有推荐实例，同步剔除内存索引
  2. 播放接口做最终校验：返回地址前查一次状态（走本地缓存，成本 <1ms）
  3. 客户端收到 404/410 时静默跳过该条并上报，不展示错误页
预防：删除事件高优广播 + 播放前状态终检 + 客户端静默跳过 + 定期一致性巡检
```

### 场景：状态机死锁——内容永久停留在 PROCESSING

```
触发：转码任务在 worker OOM 时被杀死，未发出成功或失败事件
      → 编排器收不到任何事件 → 内容永久停在 PROCESSING
检测：
  1. status=PROCESSING 且 updated_at 超过该形态转码预算 2 倍的内容数
  2. 转码任务表中 status=running 且心跳超时的任务
  3. 投稿数与最终发布数的日终对账差额
处理：
  1. 编排器内置超时扫描：PROCESSING 超时 → 查转码任务真实状态
  2. 转码任务确认失败 → 跃迁 FAILED 并自动重试（最多 3 次）
  3. 重试仍失败 → 通知创作者并提供"重新处理"入口
预防：每个状态设最大停留时长 + 超时主动查下游真实状态 + 日终投稿发布对账
```
